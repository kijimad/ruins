# 施設の横展開基盤。施設同一性を一本化し half-wired を fail-closed で弾く

## 背景

方向性は収束済み。型付き都市は残す。建物は施設の型と loot テーブルで raw.toml 中心に足す。内装の深さは浅く凍結し、幾何を作り込む段へは新規投資しない。これから建物データを横展開で増やすにあたり、その前に基盤を整える。

現状、建物1種の同一性が複数箇所に分散し、追加時の同期が手作業で、しかも失敗が silent になる。

- **施設 enum が3系統に分裂**。`interior.FacilityKind`(`internal/mapplanner/interior/facility.go:12`)、`overworld.facilityType`(`internal/overworld/urban.go:75`)、`oapi.FacilityKind`(`oas/typespec/types.tsp:89` → `internal/oapi/models.gen.go:189`)。文字列で暗黙一致する契約だけで型的に無関係。境界で素キャストする(`internal/overworld/interior_furnish.go:25`)。
- **exhaustive linter が強制するのは1箇所だけ**。`facilityPlanner` の switch(`internal/mapplanner/interior/furnish.go:150`)は default 無しで網羅を強制するが、残りは map なので漏れても通る。
- **未登録が silent**。施設を足して `zoneCatalog`(`internal/overworld/urban.go:124`)に入れ忘れると抽選対象に入らず街に一切出ない。`facilityEnemyTables` 未割り当ては既定 `ruins_area` へ黙って落ちる(`internal/overworld/urban.go:89`)。どちらもコンパイル・テストとも緑のまま。
- **施設キーの綴り typo が無検出**。`internal/raw/validate.go` は content や enemyTable の参照実在は見るが、施設キーが enum メンバーかは照合しない。
- **half-wired 被覆を見るゲートが無い**。「facilityContents はあるが facilityRooms が無い」「glyph が無い」を横断検出するテストが無い。

このまま建物を十数種データで足すと、緑なのに出ない・敵がおかしい建物が紛れ、どれが壊れているか分からなくなる。横展開の前提として、(A)同一性の一本化と(B)half-wired の fail-closed 化を先に入れる。

## 要件

- 施設の型は1つ。`interior` と `overworld` が同じ型を共有し、境界の素キャストを無くす。
- half-wired を fail-closed で弾く。全施設 × 全テーブルの被覆を検証し、片側漏れをロード時かテストで即エラーにする。
- 追加時の触点を減らし、残った触点は「漏れたら赤」にする。silent を無くす。
- 幾何は Go に残す。間取り関数・矩形演算・相対配置はデータ化しない。データ化するのは「どの施設に何をどれだけ」の宣言のみ。
- 決定的純関数・serde 安全性・既存の生成結果を壊さない。純粋なリファクタで golden は不変を原則とする。
- 新規ディレクトリを作らない。レジストリは既存パッケージへ置く。

## 設計

パッケージ依存は `overworld` → `interior` の一方向。幾何と施設型は `interior`、地区・記号・抽選は `overworld` 側にある。この向きを保ったまま、型を下位へ一本化し、配置データのレジストリを上位へ集める。

### 1. FacilityKind を一本化する

`overworld.facilityType` を廃し、下位の `interior.FacilityKind` に統一する。`overworld` は既に `interior` を import しているので循環しない。全定数を1箇所に集め、被覆検証の起点となる `AllFacilityKinds` を公開する。

```go
// interior パッケージ。施設型の唯一の定義。
type FacilityKind string

const (
	FacHouse   FacilityKind = "house"
	FacStore   FacilityKind = "store"
	FacAntique FacilityKind = "antique"
	FacClinic  FacilityKind = "clinic"
	FacLab     FacilityKind = "lab"
	FacOffice  FacilityKind = "office"
	FacDepot   FacilityKind = "depot"
)

// AllFacilityKinds は被覆検証の分母。新施設はここに1つ足すのが起点になる。
var AllFacilityKinds = []FacilityKind{
	FacHouse, FacStore, FacAntique, FacClinic, FacLab, FacOffice, FacDepot,
}
```

`oapi.FacilityKind`(tsp 由来の生成物)は raw.toml の閉集合制約として残すが、値集合が `AllFacilityKinds` と一致することをテストで固定する。生成物なので手では揃えず、ズレたらテストが赤にする。

### 2. overworld に施設レジストリを置く

`zoneCatalog`・`facilityGlyphs`・`facilityOrder` に分散した配置側の宣言を、施設ごとの1エントリへ集める。地区・記号は overworld 固有の概念なのでレジストリは overworld に置く。間取り関数と `isShop` は interior 幾何なので interior に残し、被覆ゲートで型経由の整合を保つ。

```go
// overworld パッケージ。配置側の施設宣言の単一出典。
type facilityDef struct {
	kind  interior.FacilityKind
	glyph string             // 概略地図の記号
	order int                // 凡例の表示順
	zones []facilityZoneRoll // 出現する地区と抽選重み・規模 gate
}

// facilityZoneRoll は1施設が1地区に出るときの重みと規模 gate。
type facilityZoneRoll struct {
	zone    zone
	weight  int
	minSpan consts.Chunk
}

// facilityRegistry は施設ごとの配置宣言。新施設はここへ1エントリ足す。
// zoneCatalog はこの登録から導出する。glyph/order も同様。
var facilityRegistry = []facilityDef{
	{kind: interior.FacHouse, glyph: "H", order: 0, zones: []facilityZoneRoll{
		{zoneResidential, 65, 2}, {zoneIndustrial, 10, 2},
	}},
	// ... 他施設
}
```

`zoneCatalog` は `facilityRegistry` から地区別に畳んで導出する派生にする。単一出典は登録テーブル、地区別 map は読み取り時に組む。導出可能な状態を二重に持たない方針に沿う。

### 3. 完全性ゲート

追加時の silent を fail-closed に変える。

- **被覆行列テスト**。`interior.AllFacilityKinds` の各施設が、`facilityRegistry`・`facilityContents`・`facilityRooms`・`facilityEnemyTables`・glyph のすべてに存在することを検証する。既存の `internal/overworld/urban_enemy_test.go:44` が enemyTable だけを手書きリストで見ている前例を、分母を `AllFacilityKinds` にして全テーブルへ広げる。
- **3系統一致テスト**。`AllFacilityKinds` と `oapi.FacilityKind` の値集合が一致することを固定する。
- **施設キー検証**。`internal/raw/validate.go` の `validateInteriorContentReferences`(`:183`)と同型で、raw.toml の facilityContents/Rooms/EnemyTables の施設キーが `AllFacilityKinds` に属することをロード時に照合し、typo をロード時 error にする。
- **間取りの網羅**は既存の exhaustive switch(`facilityPlanner`)が引き続き強制する。テンプレを持たない施設は明示的に BSP フォールバックの case に入れる。

## 採用しなかった方法

- **全パッケージ横断の単一テーブル**。間取り関数(`interior`)と地区(`overworld`)を1つの struct にまとめる案。幾何を上位へ出すか地区を下位へ落とす必要があり、`overworld` → `interior` の依存方向を壊す。型の一本化と被覆ゲートで大半の同期ハザードは消えるので、依存を歪めてまで1テーブルに寄せない。
- **zoneCatalog だけ TOML 化**。配置重みを raw.toml へ出す案。施設追加で Go を触らなくなるが、間取り・isShop など他の Go 触点は残り、型の3系統分裂も解けない。まず型一本化とゲートを入れ、データ化はその後の別スライスで判断する。
- **テストだけ足して構造は据え置き**。層I の被覆ゲートだけ入れて3系統分裂は残す案。silent は消えるが触点の多さは残る。今回は横展開の前提として触点削減まで一気にやる判断。

## コメント

これは believability の作り込みや内装の深さには手を付けない、純粋な同一性と検証の基盤整備。golden は不変を原則とし、変わるなら理由を添える。この基盤が入った後は、建物追加は「定数1 + レジストリ1エントリ + raw.toml のデータ + 必要なら間取り case」に収束し、どれか漏れれば被覆ゲートが赤にする。横展開で silent-broken な建物が紛れ込むのを構造で防ぐのが狙い。
