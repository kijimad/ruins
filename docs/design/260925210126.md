# 施設を raw.toml のデータ行へ。キーで引き、幾何コードだけ Go に残す

## 背景

方向性は収束済み。型付き都市は残す。建物は施設の型と loot テーブルで raw.toml 中心に足す。内装の深さは浅く凍結し、幾何を作り込む段へは新規投資しない。これから建物データを横展開で増やすにあたり、その前に基盤を整える。

現状、建物1種の同一性が複数箇所に分散し、追加時の同期が手作業で、しかも失敗が silent になる。

- **施設 enum が3系統に分裂**。`interior.FacilityKind`(`internal/mapplanner/interior/facility.go:12`)、`overworld.facilityType`(`internal/overworld/urban.go:75`)、`oapi.FacilityKind`(`oas/typespec/types.tsp:89` → `internal/oapi/models.gen.go:189`)。文字列で暗黙一致する契約だけで型的に無関係。
- **exhaustive linter が強制するのは1箇所だけ**。`facilityPlanner` の switch(`internal/mapplanner/interior/furnish.go:150`)以外は map なので漏れても通る。
- **未登録が silent**。`zoneCatalog`(`internal/overworld/urban.go:124`)に入れ忘れると街に一切出ない。`facilityEnemyTables` 未割り当ては既定へ黙って落ちる(`internal/overworld/urban.go:89`)。どちらもコンパイル・テストとも緑。
- **施設キーの typo が無検出**。`internal/raw/validate.go` は content や enemyTable の参照実在は見るが、施設キーが enum メンバーかは照合しない。
- **half-wired 被覆を見るゲートが無い**。

横展開の理想は「建物を1つ足す = raw.toml に1行足す」。そのために施設の同一性を raw.toml の1テーブルへ集約し、Go にはデータ化できない幾何の実装だけをキー付きで残す。

## 要件

- **施設は raw.toml のデータ行**。施設集合の単一出典を raw.toml にし、既存テンプレを使う建物の追加は原則 TOML 1行で済ませる。
- **Go に残すのは幾何の実装だけ**。間取り関数を名前付きで登録し、raw.toml の施設行がその名前を指す。データ化できない関数だけが Go に残る。
- **施設 enum を廃す**。`interior.FacilityKind`・`overworld.facilityType`・`oapi.FacilityKind` の3系統を無くし、施設を string id のデータ行に一本化する。Go 側は施設 id で分岐せず、行が持つ属性で分岐する。
- **half-wired を fail-closed で弾く**。施設行の planner キーが実装に無ければロード時 error。content/rooms/enemyTable の施設キーが施設行に無ければ error。
- **暗黙のフォールバックを置かない**。planner は必須。BSP を使う施設も明示的に `planner = "bsp"` と書く。未設定・未知キーは既定へ落とさずロード時 error にする。
- 決定的純関数・serde 安全性・既存の生成結果を壊さない。純粋なリファクタで golden は不変を原則とする。
- 新規ディレクトリを作らない。幾何の実装は既存の `interior` に置く。

## 設計

施設の宣言データは raw.toml へ集約し、tsp でスキーマを与える。Go に残すのは間取り関数の登録表だけ。両者は planner キーで結ぶ。

### 1. 施設を tsp スキーマ + raw.toml データにする

```tsp
// oas/typespec。施設1種の宣言。id で content/rooms/enemyTable と紐づく。
model Facility {
  id: EntityID;        // 施設キー。他テーブルの facility 参照と一致する
  glyph: string;       // 概略地図の記号
  order: int32;        // 凡例の表示順
  isShop: boolean;     // 看板・シャッター・自販機を出す店系か
  planner: PlannerKey; // 間取りテンプレの選択キー。Go の実装を指す
  zones: FacilityZone[];
}

model FacilityZone {
  zone: Zone;
  weight: int32;
  minSpan: Chunk; // 市街地の一辺がこの値以上のときだけ抽選対象になる規模 gate
}

enum PlannerKey { house, store, clinic, bsp } // bsp は汎用分割フォールバック
enum Zone { downtown, residential, industrial }
```

```toml
# assets/metadata/entities/raw/raw.toml
[[facilities]]
id = "house"
glyph = "H"
order = 0
isShop = false
planner = "house"
[[facilities.zones]]
zone = "residential"
weight = 65
minSpan = 2
[[facilities.zones]]
zone = "industrial"
weight = 10
minSpan = 2
```

### 2. Go に残すのは planner 登録表だけ

間取り関数はデータ化できない幾何なので Go に残す。施設行の `planner` キーがこの表を引く。BSP 汎用分割も暗黙の既定でなく、明示的な planner キーの1つにする。表に無いキーはフォールバックせず error。

```go
// interior パッケージ。データ化できない幾何関数だけがここに残る。BSP も1つの planner。
var planners = map[string]func(Rect, uint64) []PlannedRoom{
	"house":  PlanHouseAny,
	"store":  PlanStore,
	"clinic": PlanClinic,
	"bsp":    planBSP, // 汎用分割も明示 planner。暗黙フォールバックは置かない
}

// PlannerByKey は planner キーから間取り関数を返す。未登録キーは ok=false。
// 呼び出し側は false を既定へ落とさず error にする。
func PlannerByKey(key string) (fn func(Rect, uint64) []PlannedRoom, ok bool) {
	fn, ok = planners[key]
	return fn, ok
}
```

`planBSP` は既存の BSP 分割 `SubdivideBuilding` を planner と同じ signature で包む薄いラッパー。これで「テンプレ無し」を nil で表さず、office/depot は raw.toml で `planner = "bsp"` を明示する。新しいレイアウトが要るときだけ Go 関数を書いて `planners` に1行足す。内装深さを凍結する方針では稀。骨董品店が店を、研究施設が診療所を共有する使い回しは、raw.toml で同じ planner キーを指すだけになる。

### 3. 廃止して raw から導出するもの

施設の宣言はすべて raw.toml の施設行から導出する。Go の並行定義を消す。

- `interior.FacilityKind` / `overworld.facilityType` / `oapi.FacilityKind` enum を廃止。施設は string id のデータ行。
- `zoneCatalog`(`urban.go:124`) は施設行の zones を地区別に畳んで導出する。
- `facilityGlyphs` / `facilityOrder`(`schematic.go`) は施設行の glyph / order から導出する。
- `facilityPlanner` の switch(`furnish.go:150`) は `PlannerByKey` の引きへ置換する。
- `isShop`(`facade.go:58`) は施設行の isShop を引く。
- `reportFacilities`(`balance/loot.go:26`) は施設行の列挙から導出する。

施設 id で分岐していた箇所は、施設行の属性を引く形へ変える。Go は施設集合を列挙せず、raw から読む。

### 4. 完全性ゲート

silent をロード時 fail-closed へ変える。大半は raw の参照検証に集約できる。

- **planner 解決**。施設行の `planner` が `planners` に無ければロード時 error。暗黙フォールバックは無く、BSP を使う施設も `planner = "bsp"` を明示する。`internal/raw/validate.go` に追加。加えて `PlannerKey` enum の全メンバーが `planners` に実装を持つことをテストで固定し、キー追加漏れを赤にする。
- **施設キー参照整合**。`facilityContents`・`facilityRooms`・`facilityEnemyTables` の facility キーが施設行の id に実在することを `validateInteriorContentReferences`(`validate.go:183`)と同型で照合し、typo をロード時 error にする。
- **enum 閉集合**。`zone`・`planner` は tsp enum なので `ValidateRaws` の VisitJSON(`validate.go:29`)が閉集合違反を弾く。
- **被覆テスト**。施設行の各 id が facilityContents と facilityRooms を持つことをテストで検証する。enemyTable は既定フォールバックを許容するので必須にはしない。

## 採用しなかった方法

- **Go の施設レジストリ(前案)**。overworld に `facilityRegistry []facilityDef` を Go で置く案。型分裂は解けるが、施設追加でなお Go を触り、単一出典が Go に残る。「TOML にまとめ、Go は対応コードだけ」の方が横展開が軽く、単一出典が raw.toml に定まる。
- **施設 enum を残す**。`FacilityKind` を型として維持し被覆テストだけ足す案。コンパイル時の型安全は得るが、施設追加が TOML 1行に閉じない。施設は data 行にし、幾何の planner キーだけを閉集合に保つ。
- **content/rooms/enemyTable を施設行へ入れ子にする**。1施設の全定義を `[[facilities]]` の下へ畳む案。1行完結は魅力だが、既存の3テーブルの大規模移設が要り差分が膨らむ。今回は施設行を背骨にして id で参照し、参照整合を fail-closed にするに留める。入れ子化は将来の別スライス。

## コメント

これは believability や内装の深さには手を付けない、施設の単一出典化と検証の基盤整備。golden は不変を原則とし、変わるなら理由を添える。この基盤の後は、既存テンプレを使う建物追加は raw.toml の `[[facilities]]` 1行 + content/rooms のデータで完結し、planner キーや参照が欠ければロード時に赤くなる。Go を触るのは新しい間取り関数が要るときだけに閉じる。
