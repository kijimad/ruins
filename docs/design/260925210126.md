# 地物のデータ化の総合設計。宣言を raw.toml へ、幾何コードだけ Go に残す

## 背景

方向性は収束済み。型付き都市は残す。建物や地物は raw.toml 中心のデータで足す。内装の深さは浅く凍結する。これから地物データを横展開で増やすにあたり、その前に基盤を整える。

overworld を調べると、施設だけでなく地物全般が同じアンチパターンを持つ。**宣言的データ、重み表・出現率・記号色・prop 名を Go 定数で持ち、表示写像が別ファイルに分裂し、種類を1つ足すと多数の箇所を手で同期し、しかも未登録が silent になる**。

- **施設**: `interior.FacilityKind`(`facility.go:12`)・`overworld.facilityType`(`urban.go:75`)・`oapi.FacilityKind`(`types.tsp:89`)の3系統分裂。`zoneCatalog`(`urban.go:124`)未登録で街に出ない silent。`facilityEnemyTables` 未割り当ては黙って既定へ。exhaustive linter は default 無しの enum switch を網羅検査するので `facilityPlanner`(`furnish.go:150`)や `scatterCatalogFor`(`scatter.go:117`)は新定数の case 漏れを止める。ただし `facilityPlanner` は末尾 return で raw 由来の未知文字列を実行時に BSP へ吸収する二面がある。守られないのは map/var で持つ表、`zoneCatalog`・`facilityGlyphs`・`roadsideCatalog` などで、これらは漏れても通る。
- **ランドマーク**: 種別 const(`landmark.go:23`)・出現率(`landmark.go:33`)・placeType 写像(`landmark.go:47`)・描画 switch(`landmark.go:82`)・表示写像(`schematic.go:57`)の5箇所分裂。施設と瓜二つ。
- **散布 scatter**: `roadsideCatalog`/`wildCatalog`(`scatter.go:90-115`)は `zoneCatalog` と完全同型の重み表を Go var で持つ。`scatterEarthTiles`(`scatter.go:85`)・`outdoorLootGroupFor`(`loot_scatter.go:35`)も Go 写像。
- **地物の表示**: `placeGlyphs`/`placeOrder`(`schematic.go:71-85`)は `facilityGlyphs`/`facilityOrder` と同型の記号色凡例表。
- **配置密度**: `Placement{Spacing,Separation}` が settlement/urban/landmark/dungeon_entrance の4ファイルに散在(`settlement.go:46` ほか)。
- **散在マジックナンバー**: 市街地の街路幅・setback・湧き数(`urban.go:24-27,299`)、散布/loot 密度(`scatter.go:57`, `loot_scatter.go:24`)、集落抽選率(`settlement.go:66`)など。

いずれも「重み表 + Go 定数 + 別ファイルの表示写像」で、追加時の多触点・調整のたび Go 再ビルド・silent 漏れが共通する。横展開の前に**1つの型を確立し、全地物へ広げる**。

## 要件

- **宣言は raw.toml のキー付きデータ行**。地物種の追加は原則 TOML の1行で済ませ、単一出典を raw.toml に定める。
- **Go に残すのは幾何関数だけ**。間取り・描画などの関数を小さな enum キーで登録し、データ行がキーで指す。データ化できない関数だけが Go に残る。
- **fail-closed**。キーの閉集合違反は schema で、実装欠けや参照 typo・被覆漏れはロード時か被覆テストで、必ず赤にする。暗黙フォールバックを置かない。
- 決定的純関数・serde 安全性・既存の生成結果を壊さない。純リファクタで golden は不変を原則とする。
- 幾何・座標・決定性ロジックは Go に残す。データ化するのは「何を・どれだけ・どの記号で」であって「どこにどう置くか」ではない。
- 新規ディレクトリを作らない。

## 設計

### 共通の型

全地物カテゴリを次の3層で統一する。

- **宣言**: raw.toml のデータ行。id で他テーブルと紐づく。重み・出現率・記号色・prop 名・密度などの「何を・どれだけ」。
- **実装**: Go の関数を `map[oapi.XxxKey]fn` で登録し、データ行の key で引く。間取り・描画などデータ化できない幾何だけ。
- **検証**: key の閉集合は tsp enum を schema の VisitJSON が弾く。実装欠けと参照整合はロード時 `validate.go` と被覆テストで守る。

以下、施設を reference case として詳細化し、他カテゴリへ同じ型を当てる。

### 1. 施設（reference case）

```tsp
// oas/typespec。施設1種の宣言。id で content/rooms と紐づく。
model Facility {
  id: EntityID;
  glyph: string;
  order: int32;
  isShop: boolean;
  planner: PlannerKey;  // 間取りテンプレの選択キー。Go の planners のキーと一致する
  enemyTable: EntityID; // 敵テーブル id。汎用が欲しければ "ruins_area" を明示する
  zones: FacilityZone[];
}

model FacilityZone { zone: Zone; weight: int32; minSpan: Chunk; }

enum PlannerKey { house, store, clinic, bsp } // Go の planners と1対1。被覆テストで固定
enum Zone { downtown, residential, industrial }
```

```toml
[[facilities]]
id = "house"
glyph = "H"
order = 0
isShop = false
planner = "house"
enemyTable = "urban_house"
[[facilities.zones]]
zone = "residential"
weight = 65
minSpan = 2
```

間取り関数はデータ化できない幾何なので Go に残す。Go の `planners` map を `oapi.PlannerKey` でキーする。BSP 汎用分割も暗黙既定でなく明示 planner の1つにする。

```go
// interior パッケージ。データ化できない幾何関数だけがここに残る。BSP も1つの planner。
// minW/minH は幾何なのでデータでなくここに置く。footprint がこれ未満なら planners["bsp"] へ明示的に落とす。
type plannerDef struct {
	fn         func(Rect, uint64) []PlannedRoom
	minW, minH consts.Tile
}

var planners = map[oapi.PlannerKey]plannerDef{
	oapi.PlannerKeyHouse:  {PlanHouseAny, 12, 9},
	oapi.PlannerKeyStore:  {PlanStore, 12, 9},
	oapi.PlannerKeyClinic: {PlanClinic, 12, 9},
	oapi.PlannerKeyBsp:    {planBSP, 0, 0},
}
```

`planner` を tsp enum にすることで、raw の planner 値の閉集合違反は zone と同じく schema の VisitJSON が自動で弾き、map キーも生成型でコンパイル時に妥当性が効く。新 planner の追加だけ tsp enum + genall + Go 実装が要る。既存 planner を使い回す施設追加は raw.toml 1行で tsp も Go も触らない。footprint が `minW/minH` 未満なら暗黙 nil でなく `planners[oapi.PlannerKeyBsp]` を明示的に引く。この最小サイズ縮退は生成時の幾何判断で、planner キーの解決失敗とは別物。

**廃止して raw から導出するもの**:
- `interior.FacilityKind` / `overworld.facilityType` / `oapi.FacilityKind` enum を廃止。施設は string id のデータ行。
- `overworld.zone`(`urban.go:113`) を廃し `oapi.Zone` に一本化。往復変換しない。
- `zoneCatalog`(`urban.go:124`) は施設行の zones を地区別に畳んで導出。
- `facilityGlyphs`/`facilityOrder`(`schematic.go`) は施設行から導出。
- `facilityPlanner` switch(`furnish.go:150`) は `planners` + `PlannerByKey` へ。
- `isShop`(`facade.go:58`) は施設行から引く。
- `facilityEnemyTables` テーブルと `urbanEnemyTableFor` の silent フォールバック(`urban.go:89`) を廃し、施設行の必須 `enemyTable` を引く。
- `reportFacilities`(`balance/loot.go:26`) は施設行の列挙から導出。

### 2. ランドマーク

施設と同じ型を当て、5箇所分裂を1データ行へ畳む。

```tsp
model Landmark {
  id: EntityID;
  weight: int32;     // 出現率。累積閾値でなく重みで持つ
  glyph: string;
  color: ColorRaw;
  order: int32;
  drawer: DrawerKey; // 描画関数の選択キー
  props: PropSpot[]; // 露天・内装の prop 名と相対座標
}
model PropSpot { name: EntityID; dx: int32; dy: int32; }
enum DrawerKey { hut, open } // hut=小屋の外壁+床+扉、open=露天配置のみ
```

Go に残すのは描画関数 `drawers map[oapi.DrawerKey]func`。`drawHut`(`landmark.go:106`)の外周壁・床・扉の描画は幾何なので残す。廃止: 種別 const(`landmark.go:23`)・`landmarkKindAt` 率(`landmark.go:33`)・`landmarkPlaceType`(`landmark.go:47`)・place switch(`landmark.go:82`)・`placeGlyphs` のランドマーク分(`schematic.go`)。小屋寸法 hw/hh は幾何なので drawer 側に持たせるか PropSpot と別に検討する。

### 3. 散布 scatter

`roadsideCatalog`/`wildCatalog` は `zoneCatalog` と完全同型なので、そのままデータ行にする。

```tsp
model ScatterZone {
  id: EntityID;      // roadside / wild
  grassDensity: float32;
  propDensity: float32;
  props: ScatterEntry[]; // 重み付き prop。satellites 相対座標を含む
}
```

`scatterEarthTiles`(`scatter.go:85`)・`outdoorLootGroupFor`(`loot_scatter.go:35`)の zone→group 写像もデータ化。ここは silent 漏れでなく触点問題で、砂地タイルや loot 対応を増やすたび Go を触る点を消すのが目的。silent と触点はどちらもこのアンチパターンの側面だが性質が違う。Go に残すのは散布の位相・経路幾何(`scatter.go:294-389`)と密度場。散布可能タイル集合はデータ、置く位置の計算は Go。

### 4. 地物の表示・配置・マジックナンバー

- **表示写像**: `placeGlyphs`/`placeOrder`(`schematic.go:71-85`) を地物ごとの記号・色・order のデータ行へ。施設・ランドマークの glyph/order と同じ枠に寄せる。
- **配置密度**: 4ファイルに散在する `Placement{Spacing,Separation}` を地物ごとのデータへ集約。`Placement.At`/`WinnerOf` の当選判定(`feature.go:26-44`)は決定性幾何なので Go 残し。
- **マジックナンバー**: 市街地の街路幅・setback・湧き数、散布/loot 密度、集落抽選率、ランドマーク出現率などの調整値を、地物データか consts leaf へ集約する。
- **地物の登録順・salt**: `features()`(`feature.go:64`)の評価順と salt(`feature.go:74`)は再訪一致=決定性を決めるので Go 残し。ただし追加は「末尾のみ」で触点1箇所に閉じており、silent でない。`chunkTypeAt`(`schematic.go:146`)の優先順との二重定義は解消を検討する。

### 5. Go に残すもの

データ化せず Go に残すのは幾何と決定性ロジック。`ChunkSeed2D` の splitmix64 定数(`chunkgen.go:27`)、road の L 字分解(`road_geometry.go:27`)、`zoneOf`/`planUrbanLot` の空間判定と描画(`urban.go:151-289`)、seed ビット位置(`urban.go:36-41,146`)、`Placement.At/WinnerOf`(`feature.go:26`)、散布の位相/経路幾何、`drawHut` 等の描画。これらは触ると再訪一致が壊れるか純粋な幾何。

### 完全性ゲート

- **key 閉集合**。`planner`・`zone`・`drawer` などの tsp enum は `ValidateRaws` の VisitJSON(`validate.go:29`)が違反を弾く。
- **実装照合**。データ行の key が Go の `planners`/`drawers` に実在することをロード時 error にする。enum に足して Go 登録を忘れる漏れを塞ぐ。
- **参照整合**。facilityContents/rooms・enemyTable・item group などの id 参照が実在することを `validateInteriorContentReferences`(`validate.go:183`)と同型で照合。
- **地区の基本施設**。各 `zone` に minSpan≤2 の施設が最低1つあることを検証。無いと `zoneCatalog` 導出後に候補が空になり `rollFacilityInZone`(`urban.go:178`)の `IntN(0)` で panic する。従来 Go 定数が保証していた不変条件を検証で守る。
- **被覆テスト**。各データ行が必要な従属テーブルを持つことを検証。

## 採用しなかった方法

- **Go の施設レジストリ**。overworld に Go の登録表を置く案。型分裂は解けるが単一出典が Go に残り、追加でなお Go を触る。TOML へ寄せる方が横展開が軽い。
- **施設だけに限定**。施設のみデータ化し他は据え置く案。同型パターンが5系統あり、施設で確立した型をそのまま広げられるので、総合設計として1本にまとめ段階実装する。ただし1PR には収めず、カテゴリごとに分割する。
- **content/rooms も施設行へ入れ子**。enemyTable は単一 id なので施設行へ畳むが、content/rooms は大きな入れ子で既存テーブルの大規模移設になる。id 参照に留め、入れ子化は将来の別スライス。
- **key を文字列にする**。planner/drawer を素の string にすると genall は減るが、schema の閉集合検証とコンパイル時の型安全を失う。新 key 追加は稀なので、tsp enum + oapi 生成型キーの型安全を採る。

## コメント

これは believability や内装の深さには手を付けない、地物宣言の単一出典化と検証の基盤整備。golden は不変を原則とし、変わるなら理由を添える。この基盤の後は、地物追加は raw.toml のデータ行で完結し、key や参照が欠ければロード時に赤くなる。Go を触るのは新しい幾何関数が要るときだけに閉じる。

`oapi.FacilityKind` の廃止は参照が広い破壊的変更なので、実装の最初に参照を洗ってから着手する。実装はカテゴリ単位で段階的に進める。施設を reference にして型と検証パターンを1つ通し、共通ヘルパーを実物から抽出してから、ランドマーク・散布・表示/配置へ薄く展開する。
