# メニュー画面を宣言的 MenuScreen コンポーネントへ統一する

## 背景

doc 84 でメニューをタブ化し、`newTabScreenUI` でモーダルの外枠を共通化した。しかし共通化できたのは
「見た目の枠」と「カーソル核ロジック `hooks.UseTabMenu`」だけで、両者を繋ぐ配線は各 state に手書きのまま
残った。結果、以下2つの痛みが生じている。

1. 使いにくい。同じキーが画面ごとに違う挙動をする。
2. 一貫性を保てない。同じ処理が各 state にコピーされ、追加や修正のたびに食い違う。

1つのメニュー画面は実際には次の掛け算で成り立つ。

**データ模型 × 入力 × 選択・ページング状態 × 描画 × サブ窓/詳細窓 × アクション実行**

このうち共通化済みは「枠の描画」と「カーソル核」のみ。残りのグルーが各 state に散り、`character_state.go`
は765行、`craft_menu.go` は616行に膨らんだ。

### 現状の不統一（コード調査で確定した事実）

振る舞いの分岐。これが「使いにくい」の正体で、共通関数では治せない。

| 症状 | 実態 |
|---|---|
| ←→ の意味が画面で違う | タブ切替 / ページ送り / 無効 の3通り |
| 上下の連射が画面で違う | メイン一覧はリピート有、サブ窓はリピート無 |
| キー説明が出たり出なかったり | フッター有 / help 行自作 / 無し が混在 |
| `[ ]` メンバー切替が発見不能 | character だけ `Update` 内で生キー直読み、案内なし |
| 1画面の件数が違う | 18 と 20 が混在 |
| 入力の入口が2系統 | インターフェース `HandleInput` 組と生 ebiten 直読み組に分裂 |

重複コード。共通関数化で消せる。

- アクションウィンドウ生成 5コピー
- ウィンドウ用カーソル reducer 6コピー
- 詳細モーダル生成 2コピー
- 「候補＋閉じる」型 5コピー
- 選択→ウィンドウ遷移の境界チェック 5コピー
- 所持金行 完全一致2コピー
- itemCounts ループ→`UseTabMenu` 全 state
- ページインジケータの空文字埋め 3コピー
- 3x3グリッドの空セル骨組み shop/craft/storage

二重抽象。`styled.NewTable*` 手組み系と、settings のみが使う `tabmenu.View` 系が併存し、後者の増分更新
API `UpdateFocus` は死蔵している。`UseRef`/`UseTimer` もメニューでは未使用。

## 要件

- 全メニューでキー操作の意味を統一する。ユーザーがどの画面でも同じキーで同じ操作ができる。
- キー案内を全画面で常設し、操作を発見可能にする。
- メニュー画面のループを単一のコンポーネントが所有し、各 state は宣言だけを書く。振る舞いの分岐が
  再発しない構造にする。
- 既存の hooks と styled 資産を活かす。丸ごと再描画方式は当面維持する。
- golden テストで各画面の見た目を守りながら、1メニューずつ段階移行する。

## 設計

### 正準キーマップ

`menuscreen` コンポーネントが唯一の入力入口となり、全メニュー共通のキーマップを持つ。生 ebiten 直読みと
`HandleWindowInput` のリピート差を撤廃する。

| キー | 動作 |
|---|---|
| ↑ ↓ | カーソル移動。リピート有で統一 |
| ← → | タブ切替に固定 |
| Enter | 決定 |
| x | 詳細表示 |
| Esc | 戻る / 閉じる |
| `[` `]` | 対象切替。member 切替など対象がある画面のみ |

ページングはカーソル位置から自動導出する。`UseTabMenu` は `ItemsPerPage` からページを導出できるため、
カーソルが端を越えたら自動でページを繰る。これにより ←→ をページ送りに使う必要が消え、意味の3分裂が
構造的に根絶される。

### コンポーネントのデータ定義

各 state は `Spec` を宣言し、ドメイン処理だけをコールバックで渡す。

```go
// Spec はメニュー画面の宣言。menuscreen コンポーネントがこれを解釈してループを回す
type Spec struct {
    Header  string
    Tabs    []Tab
    // OnSelect は決定時に呼ばれる。アクション submenu か画面遷移を返す
    OnSelect func(ctx Context) Result
    // OnDetail は x 押下時の詳細窓を返す。nil なら詳細なし
    OnDetail func(ctx Context) *widget.Window
    // Subjects は [ ] で切り替える対象。空なら対象切替なし
    Subjects []Subject
}

// Tab は1つのタブの中身
type Tab struct {
    Label   string
    Columns []Column
    // Rows は表示行を返す。選択位置は menuscreen が管理する
    Rows    func() []Row
    PerPage int // 0 なら既定値
}

// Column は列の定義
type Column struct {
    Header string
    Width  int
    Align  styled.TextAlign
}

// Row は1行の値。列数と一致させる
type Row struct {
    Cells []string
}

// Context は現在のカーソル状態をコールバックへ渡す
type Context struct {
    World     w.World
    TabIndex  int
    ItemIndex int
    Subject   int
}

// Result は決定時の結果。submenu アクションか遷移のいずれか
type Result struct {
    Actions    []Action           // 空でなければアクション submenu を開く
    Transition es.Transition[w.World]
}

// Action は submenu の1項目
type Action struct {
    Label string
    Run   func(w.World) error
}
```

コンポーネントが一元的に持つもの。

- 正準キーマップと単一入力入口
- カーソル・タブ・ページ・対象切替の状態管理。`UseTabMenu` を内部で駆動する
- サブ窓 submenu の生成。5コピーを吸収する
- 詳細窓の配置。`getCenterWinRect` でログ回避する
- ページインジケータ・カーソル reducer・itemCounts ループの定型
- フッターのキー案内を capability から自動生成する。詳細の有無・対象切替の有無で表示を変える
- `itemsPerPage` の既定を1定数に集約する

### 段階移行

各段階で `make check` を通し、golden を更新する。1メニューずつ移す。

1. 正準キーマップと入力契約の統一を先行する。振る舞いの分裂を先に治す。単独で出荷できる。
2. `internal/widgets/menuscreen` を新設し、最も複雑な item_action と character を移行して API を検証する。
3. shop / craft / storage / tavern / squad を移行する。3x3グリッド骨組みと重複を吸収する。
4. main / settings を枠へ回収する。`tabmenu.View` 系の二重抽象を撤去する。

## 採用しなかった方法

### 共有ヘルパ抽出のみ

重複9ブロックを関数化する案。安くリスクも低いが、本丸である振る舞いの不統一を治せない。単一の所有者が
いないため、また食い違う。重複は消えても使いにくさは残る。

### ebitenui 標準 List へ全面移行

カーソル・スクロール・フォーカスを ebitenui に委譲し、丸ごと再描画をやめる案。真の複雑さの根まで消せるが、
hooks + rebuild というこのリポジトリの土台思想ごと置換になり blast radius が大きすぎる。golden も全変更。
今の痛みに対して過剰。

### 独自 immediate-mode GUI

ebitenui と styled を捨て自作する案。コストが極大で、現在の資産をすべて捨てることになる。正当化できない。

## コメント

- 案1を段階導入する。既存資産を活かしつつ、使いにくさ（振る舞いの分裂）と保守性（重複）の両方を治せる。
- 段階1のキーマップ統一が最も高価値で低リスク。単独で出荷して効果を確認してから後続へ進む。
