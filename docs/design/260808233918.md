# 酒場を廃し雇用を商人の在庫売買へ統合する

## 背景

隊員の雇用は専用画面である酒場で行っていた。売買とは別導線・別NPC・別ステートで、同じ「対価を払って手に入れる」操作が二重に存在していた。`260628122716.md` の隊マネジメント設計では雇用を酒場に置いたが、売買と統合すれば導線が1本になり、商人だけで補給が完結する。

あわせて店の品揃えを商人ごとの在庫として持たせ、買うと減り、売ると店頭に並ぶ手応えを作る。従来の店は固定リストの無限在庫で、買っても売っても品揃えが変わらなかった。

## 要件

- 隊員候補を他の商品と同列に並べ、購入で雇用する。専用の酒場画面は持たない
- 店の在庫は商人ごとに持ち、買うと減り、売ると店頭に並ぶ
- 在庫は商人生成時に決める
- 新コンポーネントを足さず、既存の収納機構を再利用する
- 買われなかった在庫が商人の消滅で孤児化しない

## 設計

### 在庫は商人所有の LocationInStorage で持つ

商品も隊員候補も、商人を所有者とする `LocationInStorage` を持つ実体で表す。既存の収納システムをそのまま使い、新コンポーネントは足さない。

```go
// item:    既存のアイテム実体。Name/RawID/Value/Weight を持つ
// 隊員候補: GridElement を持たない member 実体。フィールドに出ないので描画も戦闘もAIも対象にならない inert 状態
world.Components.LocationInStorage.Add(stock, &gc.LocationInStorage{Owner: merchant})
```

判別は `query.IsRecruit`、すなわち `Abilities` を持つかで行う。アイテムは `Abilities` を持たず、候補は持つ。収納にはアイテムと候補しか入らない前提で、収納内の実体に対して呼ぶ。

### 生成と売買

- 在庫は商人生成時に決める。`SpawnNeutralNPC` が name=="merchant" のとき `PopulateMerchantStock` を呼び、`SpawnStorageItem` でアイテムを、`SpawnStorageRecruit` で候補を積む。集落でも街マップのマッププランナ経由でも同じ経路を通る
- 買う = `MoveToBackpack(item, player)` で商人→プレイヤーへ実体を移す。在庫が実体ごと減る。通貨を消費する
- 売る = `MoveToStorage(item, merchant)` でプレイヤー→商人へ移す。売った品が店頭に並ぶ。通貨を得る
- 雇う = 候補実体を活性化する。先に `SpawnSquadMember` で隊員を生成し、成功してから候補実体を消す。生成が失敗しても候補を在庫に残し、代金だけ返って候補も消える不整合を避ける

価格は `query.StockBaseValue`、すなわちアイテムは Value、候補は能力値、いずれも個数を掛けた値、に一本化する。表示と課金がこの1点を通り、乖離しない。

### 商人エンティティの受け渡し

店は商人の在庫を売買するため、開くときに商人の実体が要る。対話で得た相手を店まで運ぶ。

```
インタラクション target → TalkParams.Target → ShowDialog.SpeakerEntity
  → NewMerchantDialogState(name, merchant) → NewShopMenuState(merchant) → ShopMenuState.merchant
```

### クリーンアップ

隊員候補もアイテムも商人の在庫実体として持つため、買われなかった在庫が孤児化しないようにする。

- 帯シフトの座標カリング `RemoveEntitiesInXRange` で、消える所有者の `LocationInStorage` 在庫も一緒に消す。在庫は GridElement を持たず座標カリングでは拾われないため、所有者を消すときに道連れにしないと死んだ所有者を指す孤児になり、serde で保存され蓄積する
- 隊員候補は GridElement を持たないのでフィールドに現れず、戦闘・AI・描画の対象にならない。inert 状態はフィールド不在で自然に満たす

### member/NPC の体重

member と NPC に自身の体重 `Weight` を持たせる。値は能力値の体格から算出し、基準体重に Vitality と Strength を足す。頑健な個体ほど重く、売買価格と同じく体格を反映する。人身売買の店でも候補に重量が並ぶ。

```go
// components/ability.go。体重の算出点を1箇所に固定する
func (a Abilities) BodyWeight() consts.Milligram {
	physiqueKg := a.Vitality.Base + a.Strength.Base
	return consts.Milligram((bodyWeightBaseKg + physiqueKg) * consts.MilligramPerKg)
}
```

`NewMemberSpec`・`SpawnSquadMember`・`SpawnStorageRecruit` の全経路で付与する。

### 酒場の削除

雇用が店へ移ったので酒場を丸ごと削除する。酒場画面・酒場の主人 NPC・会話イベント、および酒場だけが使っていた `ActionWindow` ウィジェットと `newCurrencyRow` を除去する。街レイアウトの NPC 文字は削除でなく地形文字へ置換し、タイルの桁をずらさない。

## 採用しなかった方法

| 案 | 不採用理由 |
|----|----------|
| 在庫用の新コンポーネント `ShopInventory` を足す | `LocationInStorage` で同じことができ、serde も既存機構に乗る。新設計を足すと保存や除外の手当てが増える |
| 隊員候補を state 内の構造体スライスで持つ | 候補が実体でないとクリーンアップや serde が別扱いになる。実体にすれば在庫と同じ機構で消せる |
| 雇用時に候補実体をそのまま squad 化する in-place 手術 | `SquadAI` や `CommandTable` 等の付与を手作業で揃える必要があり脆い。生成済みの `SpawnSquadMember` を再利用し、候補は消す方が確実 |
| 体重を raw に定義する | 候補はランダム生成で raw を持たない。能力値からの算出なら全経路で同じ式を1箇所に置ける |
| 酒場を残し雇用を二重導線にする | 同じ「対価で手に入れる」操作が別画面に分かれ導線が冗長。商人に集約する |

## コメント

`260628122716.md` は隊マネジメントの全体設計であり、雇用を酒場に置いた当時の設計を記録した発行済みドキュメントとしてそのまま残す。本ドキュメントは雇用導線を店へ移した以降の設計を正典とする。
