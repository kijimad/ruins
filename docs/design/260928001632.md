# コード監査: worldgen・戦闘AI・継続アクティビティ・UI資源 2026-09-28

## 背景

自律コード監査エージェントによる定期監査。golangci-lint は forcetypeassert・errcheck・nilerr・nilnil・exhaustive・makezero 等を有効化しており機械的な誤りは既に潰されているため、lint が拾えない意味論的な誤りだけを狙って internal 配下を横断的に読んだ。oapi・editor-ui は対象外。

`internal/activity`・`internal/aiinput`・`internal/systems`、`internal/mapplanner`・`internal/maptemplate`・`internal/mapspawner`・`internal/dungeon`・`internal/geometry`・`internal/overworld`、`internal/components`・`internal/world`・`internal/resources`・`internal/save`・`internal/worldstream`、`internal/balance`・`internal/formula`・`internal/skill`・`internal/raw`、`internal/states`・`internal/widgets`・`internal/menuloop`・`internal/input`・`internal/inputmapper`・`internal/keybind`・`internal/screeneffect`・`internal/render3d` の5系統に分けて読み、各候補をコードとテストを読んで自己検証した。`balance`・`formula`・`skill`・`raw` および `components`・`world`・`resources`・`save`・`worldstream` の大半は高確度の指摘なしと判断した。以下は検証を通過した5件。

このドキュメントは提案であり、採否・優先度は人がレビューで判断する。修正は本 PR に含めない。

## 問題

### 1. `HostileNPCPlanner.planWithRandomPosition` が重み合計0のテーブルで無限ループする

- 該当: `internal/mapplanner/hostile_npc_planner.go:141-148`
- 症状: 部屋が無いマップ（フォールバック経路）で、危険度フィルタ後に残った敵テーブルの `Weight` 合計が0になると、マップ生成スレッドが無限ループしてハングする。
- 根拠: `selectSpawnEntry`（`internal/raw/weighted.go:21-22` の `SelectByWeightFunc`）は `totalWeight == 0` のとき乱数を引かずに毎回決定的にゼロ値 `SpawnEntry{}` を返す。呼び出し元は `entries` が空でないことしかチェックしておらず（`hostile_npc_planner.go:54`）、重み合計0のケースを排除できていない。`planWithRandomPosition`（141行目）は `entry.Name == ""` を `continue` するだけで `placed` もフェイルカウンタも増やさず、ループを抜ける手段が無い。
- 比較: 同じファイルの兄弟関数 `planWithRoomCluster`（部屋がある経路）は同じ分岐で `failCount++; continue` とし `failCount <= maxHostileNPCFailCount` で必ず抜ける。`internal/mapplanner/item_planner.go` の `ItemPlanner.PlanMeta` も同様に `failCount` でガードしている。`planWithRandomPosition` だけこのガードが漏れている。
- 発火条件: 現行の登録済み敵テーブル（forest/cave/ruins_area）が正常な限り通常は発火しないが、raw データの設定次第で容易に再現しうる非対称な実装。
- 修正方針案: `planWithRoomCluster` と同様に `failCount` を導入し `maxHostileNPCFailCount` で打ち切る。

### 2. Chasing 状態の見失い判定が「追跡開始からの経過ターン」を見ており「見失ってからの経過ターン」になっていない

- 該当: `internal/aiinput/planner_solo.go:126-134`（`updateFromChasing`）
- 症状: 敵が長時間プレイヤーを追跡し続けた後、視界が一瞬だけ途切れると即座に追跡を諦めて Driving へ戻ってしまう。
- 根拠: `elapsedTurns := currentTurn - solo.StartSubStateTurn`（`planner_solo.go:82`）で、`StartSubStateTurn` は `transitionToChasing` で Chasing に入った瞬間にしか更新されない。兄弟関数 `updateFromFleeing`（136-143行目）はプレイヤーが見えている間毎ターン `solo.StartSubStateTurn = currentTurn` とリセットし、`elapsedTurns` を「最後に見えてからの経過」として使っているのに対し、`updateFromChasing` にはこのリセットが無い。`TestUpdateState_ChasingPlayerVisible_ContinuesChase`（`internal/aiinput/state_machine_test.go:46-62`）が「Chasing 中に見えていても `StartSubStateTurn` は変化しない」ことを明示的に固定しているため、これは実装の書き忘れでなく現状の仕様として固定されてしまっている。
- 発火シナリオ: 敵が Chasing に入ってから8ターン継続してプレイヤーを視認し続けたとする。プレイヤーが柱の陰に1ターンだけ隠れて `canSeePlayer=false` になると、`elapsedTurns`（8）は既に3以上なので即座に `transitionToDriving` する。実際には1ターンしか見失っていないのに、3ターン以上見失った場合と同じ扱いになる。追跡が長引くほど脆くなる非対称な挙動。
- 修正方針案: Fleeing と同様に、Chasing でも視認できたターンに `StartSubStateTurn` をリセットするか、「最後に見えたターン」を別フィールドで持ち `elapsedTurns` と分離する。

### 3. `ReloadBehavior.DoTurn` が継続アクティビティの契約に反し弾薬保有を毎ターン再検証していない

- 該当: `internal/activity/reload.go:88-137`（`DoTurn`）
- 症状: 装填の進行中に弾薬が別の手段で失われても、進捗が完了閾値に達するまで中断が起きず、無駄なターンを消費したあとでようやく「弾切れ」で中断する。
- 根拠: `DoTurn` は周囲の安全（`query.IsAreaSafe`）は毎ターン検査するが、弾薬在庫は `comp.Progress.Current >= comp.Progress.Max`（完了）に達したときにしか `query.FindAmmoInInventory` を呼んでいない（106-113行目）。継続アクティビティの契約は「DoTurn の冒頭で毎ターン、対象の生存・周囲の安全・必要資源の保有を検査する」であり、同じ契約に従う `DisassembleBehavior.DoTurn`（`internal/activity/disassemble.go:120-136`）は工具の保有を毎ターン検査して無くなった瞬間に `Cancel` している。`ReloadBehavior` だけこの毎ターン検査が完了判定の中に埋もれている。
- 発火シナリオ: プレイヤーが装填を開始した後、同じ弾薬を消費する別の経路（例えばクラフトの材料消費や取引）で弾薬が尽きても、`DoTurn` は工数を積み続け、進捗が完了ラインに達して初めて弾切れに気づき中断する。他の継続アクティビティなら次のターンで即座に中断するところを、数ターン無駄にしたうえで結局失敗する。
- 修正方針案: `DoTurn` の冒頭で `query.FindAmmoInInventory` を毎ターン検査し、無ければ即座に `Cancel` する。

### 4. `messagelog.Widget.Draw` が毎フレーム `ebiten.Image` を生成し破棄しない

- 該当: `internal/widgets/messagelog/widget.go:67-69`
- 症状: ダンジョン探索中は常時描画される HUD のメッセージログが、毎フレーム新規の GPU 裏画像を確保し続け、`Dispose()` を一度も呼ばない。
- 根拠: `Draw` は `offscreen := ebiten.NewImage(width, height)` を呼び出すたび新規生成して `buildTree` の描画に使い、`cv.DrawImage` に貼ったあと解放しない。呼び出し経路は `hud.MessageArea.Draw`（`internal/widgets/hud/message_area.go:111`）→ `systems.HUDRenderingSystem.Run`（`internal/systems/hud_rendering.go:94`）で、ダンジョン探索中は毎フレーム無条件に呼ばれる。Go の GC 任せの解放は ebiten の GPU 側リソース解放を保証しないため、プレイ時間が伸びるほど GPU メモリ・ハンドルが積み上がる典型的なリーク。
- 比較: `internal/screeneffect/filter.go` の `Pipeline.ensureScratch` はサイズが変わらない限り中間バッファを使い回すキャッシュ方式を採っており、本来はこちらに倣うべき箇所。
- 修正方針案: `width`/`height` が前回と一致する間は既存の `offscreen` を使い回し、サイズが変わったときだけ確保し直す。state 破棄時に `Dispose` する経路も用意する。

### 5. `CraftMenuState.DoAction` の `ActionOpenDebugMenu` 分岐が到達不能

- 該当: `internal/states/craft_menu.go:70-71`
- 症状: クラフトメニューからデバッグメニューを開く分岐がコード上に存在するが、これを発火できるキー束縛が無く、常に死んでいる。
- 根拠: `CraftMenuState.KeyBindings()`（63-65行目）は `detailOpenBindings`（x キーのみ）しか返さない。`ActionOpenDebugMenu` を発火するキー束縛は `internal/states/dungeon_input.go` の `dungeonDebugBindings`（Slash キー、デバッグ設定時のみ合成）にしか存在せず、クラフト画面には配線されていない。`DoAction` に `case inputmapper.ActionOpenDebugMenu` があるのはこの2ファイルのみで、`detailOpenBindings` を使う他の画面（shop/storage/character/equip/feed_fuel/cube_module の各 State）には同種の case 自体が無い。
- 発火条件: プレイヤー操作では到達しない。機能追加時にキー配線を忘れたか、他画面からのコピー時の残骸と見られる。実害は無いが、意図と実装がずれた死んだ分岐であり、将来別の分岐を足す際の混乱源になる。
- 修正方針案: デバッグ設定時に有効なキー束縛をクラフト画面にも配線するか、意図的に不要ならこの case を削除する。
