# コード監査: ステージ共存下の座標検索が退避中ステージを混ぜる 2026-10-26

## 背景

自律コード監査エージェントによる定期監査タスク。golangci-lint は forcetypeassert・errcheck・nilerr/nilnil・exhaustive・makezero 等が有効で機械的な問題は既に捕捉しているため、今回は internal 配下を対象に lint が捕まえられない意味論的な誤りを横断的に読み込んだ。

最近の worldgen の地物データ化リファクタ、`260925210126.md` の実装、を中心に精読したが、`claude-review` による既存レビューが手厚く、新規に報告できる確度の高い問題は見つからなかった。代わりに `.claude/skills/ruins-review` が明記する既知の危険パターン「ステージ跨ぎクエリは生の `ecs.NewFilterN` でなく `query.ActiveFilter` を使う」に沿って `internal/` 全体を horizontal に洗ったところ、同じ根本原因を持つ2件を見つけた。いずれも Ark の生フィルタで座標検索を行い、退避中ステージ、Phase 7 共存方式で `Suspended` が付いたまま world に残るステージ、のエンティティを除外していない。

過去の監査doc、`260711000833.md` から `260921001438.md` までは事前に通読し、既出の問題は対象から除外した。`260914001354.md` が既に `query.ActiveFilter` 系の重要性に触れているが、具体的な2箇所の漏れそのものは未報告だったため今回報告する。

## 共通の背景: Phase 7 共存方式

`internal/world/query/active.go` のコメントが明記する設計: 「共存方式では全ステージのエンティティが同一 world にいる。ステージ跨ぎのシステムが退避中ステージのエンティティを巻き込むと、描画・視界・AI・座標索引が混ざる」。`internal/world/stage/stage.go` の `SwapTo` は、訪問済みステージへ戻るときも新規ステージへ進むときも、現在のステージを `suspend` するだけで world からは消さない。`suspend` は `Suspended` マーカーを付けるだけで、`GridElement`・`Material`・`LocationOnField` など他のコンポーネントはそのまま残る。

ダンジョン各階は `mapspawner.Spawn`、`SpawnAt(world, metaPlan, 0, 0)` の薄いラッパー、で生成され、オフセットは常に `(0,0)` から始まる。つまり**どの階も同じローカル座標レンジ `[0, TileWidth) x [0, TileHeight)` を使う**。退避中の階と現在の階が同一 world に同居する以上、同じ `(x, y)` に別ステージのエンティティが存在することは設計上普通に起こる。

この危険を踏まえて `query.GetEntitiesAt`、`internal/world/query/query.go:85`、は `query.ActiveFilter1` を使い、コメントで「座標が重なる退避中ステージのエンティティを座標検索に混ぜない」と明記している。しかし同種の座標検索が別の2箇所で生の `ecs.NewFilterN` を使っており、この保護が掛かっていない。

## 検出した問題

### 1. 着火が別ステージの可燃物を誤って消費・削除する

**file:line**: `internal/activity/execute_interaction.go:155-168`（`fieldFuelOnTile`、`executeIgnite` から呼ばれる）、`internal/world/lifecycle/fire.go:14-22`（`AddFuel`）

```go
// internal/activity/execute_interaction.go
func fieldFuelOnTile(world w.World, coord consts.Coord[consts.Tile]) []ecs.Entity {
	var fuels []ecs.Entity
	q := ecs.NewFilter3[gc.Material, gc.LocationOnField, gc.GridElement](world.ECS).Query()
	for q.Next() {
		e := q.Entity()
		if !query.IsCombustible(world, e) {
			continue
		}
		if world.Components.GridElement.Get(e).Coord == coord {
			fuels = append(fuels, e)
		}
	}
	return fuels
}
```

**症状**: プレイヤーが足元の隣接タイルで着火すると、見えている現ステージの可燃物だけでなく、退避中の別ステージ、別のダンジョン階や退避中のオーバーワールド、に存在する可燃物のうち同じローカル座標 `(x, y)` にあるものまで一括して `AddFuel` に渡り、そのまま `world.ECS.RemoveEntity(fuel)` で永久に消える。プレイヤーには見えない・触れていないはずの階の家具や拾得物が、無関係な着火操作で静かに消滅する。

**根拠・失敗シナリオ**:
1. ダンジョン階1へ入ると `SwapTo` が生成し、`mapspawner.Spawn` が `(0,0)` 起点で家具・ドロップ品を配置する。家具、木製の棚・椅子など、は `Material: WOOD` 相当を持ち `internal/world/query/fuel.go` の `materialHeatPerKg` 表により燃焼熱量が正になる、`WOOD`・`PAPER`・`CLOTH`・`LEATHER`・`PLANT`・`FOOD`・`BONE` が対象。
2. 階段で階2へ進むと `SwapTo` が階1を `suspend` するが、`Purge` はしない。階1の家具は `Suspended` を持つだけで `GridElement`・`Material`・`LocationOnField` を保持したまま world に残る。
3. 階2も `(0,0)` 起点で生成されるため、階1と同じ座標レンジを使う。階2のどこかの可燃物の座標と、階1に残っている可燃物の座標が一致するのは、どちらも手続き生成で部屋・通路に家具を敷くため、低確率ではない。
4. プレイヤーが階2で着火すると `fieldFuelOnTile` は座標一致だけで全ステージを走査するため、階1の家具がヒットし `AddFuel` → `RemoveEntity` で削除される。階1へ戻ると、見た目には何も起きていないはずの場所から家具が消えている。

同じ関数内の `query.GetEntitiesAt`、`射撃の射線判定 checkLineOfSight` 等が使う、は `ActiveFilter1` で同じ危険を避けており、この関数だけが保護を欠く。

**なぜ lint で捕まらないか**: `ecs.NewFilter3[...]` は型として正しく、forcetypeassert・errcheck 等の対象にならない。`query.ActiveFilter3` という同形の代替があることと、Phase 7 共存方式でステージが同一 world に同居するという設計知識を持たないと、何が欠けているか分からない。

**反証の検討**: 「ダンジョン階ごとに座標が一意になるよう生成時にオフセットが振られているのでは」と疑い `mapspawner.Spawn`/`SpawnAt` を確認したが、`Spawn` は `SpawnAt(world, metaPlan, 0, 0)` の固定呼び出しで、オフセットが入るのは overworld のチャンク配置、`offsetY` は現状常に0とコメントにある、だけ。ダンジョン階同士は常に `(0,0)` 起点で重なる。また「`Suspended` が付くと `Material`/`LocationOnField` ごと除去されるのでは」と疑い `suspend` 関数を確認したが、`Suspended` マーカーを `Add` するだけで他コンポーネントに触れない。両反証とも成立せず、問題は実在する。

**修正方針案**: `ecs.NewFilter3[gc.Material, gc.LocationOnField, gc.GridElement](world.ECS)` を `query.ActiveFilter3[gc.Material, gc.LocationOnField, gc.GridElement](world)` に替える。

### 2. キューブ設備の装着可否判定が別ステージの prop/item を誤って障害物にする

**file:line**: `internal/world/lifecycle/facility.go:16-46`（`FacilityCellFree`）

```go
// 空間索引は prop・アイテムを持たないので LocationOnField を走査する
q := ecs.NewFilter1[gc.LocationOnField](world.ECS).Query()
defer q.Close()
for q.Next() {
	e := q.Entity()
	if e == cube || !world.Components.GridElement.Has(e) {
		continue
	}
	if world.Components.GridElement.Get(e).Coord != coord {
		continue
	}
	if world.Components.Prop.Has(e) || world.Components.Item.Has(e) {
		return false
	}
}
```

**症状**: `FacilityCellFree` は移動拠点キューブの展開空間1マスへ設備を装着できるかを判定する。関数冒頭で `query.GetSpatialIndex` を使い、キャラ・壁の判定は正しく現ステージへ限定しているが、続く prop/item の判定だけ生の `ecs.NewFilter1` で全ステージを走査する。退避中の別ステージ、別のダンジョン階や退避中のオーバーワールド、に同じローカル座標 `(x, y)` の prop か item があると、現ステージのそのマスは実際には何も無いにもかかわらず「空きがない」と誤判定され、装着 UI でそのマスが選べなくなる。プレイヤーから見ると、何もないマスなのに理由も分からず設備を装着できない。

**根拠・失敗シナリオ**: 問題1と同じく、ダンジョン各階が `(0,0)` 起点で生成されローカル座標レンジが重なること、`suspend` が他コンポーネントを残すことから、退避中ステージの prop/item は常に座標検索に紛れ込む余地がある。キューブはオーバーワールドで展開するため、特にオーバーワールド原点付近のチャンク、小さいローカル座標、で展開した場合、そこに退避中のダンジョン階の家具と同じ座標が当たりやすい。

**なぜ lint で捕まらないか**: 問題1と同様、型として正当なクエリであり、`query.ActiveFilter1` という同形の代替の存在と Phase 7 共存方式を踏まえないと欠落が見えない。

**反証の検討**: 「このマスはキューブの展開空間、既にオーバーワールドで固定済みの範囲、なので退避中ステージの座標とそもそも重ならないのでは」と疑ったが、ダンジョン階側が `(0,0)` から `TileWidth × TileHeight` の矩形を無条件に使う以上、オーバーワールドの原点付近のチャンクを使えばローカル座標は普通に重なる。キューブの展開位置を原点付近へ限定する仕組みも見当たらない。

**修正方針案**: `ecs.NewFilter1[gc.LocationOnField](world.ECS)` を `query.ActiveFilter1[gc.LocationOnField](world)` に替える。

## 採用しなかった代替

- **`suspend` 時に `LocationOnField`/`Material` 等を一時的に外す**: 退避中ステージのデータ保持や resume 時の復元が複雑になり、Phase 7 共存方式の単純さ、Suspended マーカー1つで退避を表す、を壊す。既存の `ActiveFilter` 系が確立している以上、各クエリ側で正しいフィルタを使う方が一貫する。
