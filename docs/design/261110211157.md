# raw のスキーマを CUE に移し、TypeSpec と editor-ui をなくす

## 背景

raw のデータの形を3つの言語で持っている。

| 何 | 言語 | 参考 codebase |
|---|---|---|
| スキーマ | TypeSpec。約2,200行 | `oas/typespec/` |
| ゲームが使う型 | Go。TypeSpec から OpenAPI を経て生成し、本番コード76ファイルが使う | `internal/oapi/` |
| エディタ | TypeScript。生成分を除き約5,800行 | `editor-ui/` |

加えて、参照の検証を Go に手で書いている。`internal/raw/validate.go` は954行あり、参照先が無いことや行が欠けることを表すエラーの値が約30ある。関係を1つ足すたびに、検証の関数とエラーの値とテストが増える。

設計 doc 261109215116 と 261110202024 で識別子と調整値を raw へ寄せるたびに、id の集合が TypeSpec の enum と raw の行に二重になるといった重複が新しく見えた。根にあるのは、形と制約と参照を書く場所が言語ごとに分かれていることである。

## 要件

1. raw のデータの形、値の制約、行の間の参照を1か所に書く。
2. ゲームの Go の型はそこから生成する。手で写さない。
3. 参照の検証は宣言から導く。参照を1つ足すたびに Go の検証を書かない。
4. TypeSpec と editor-ui をなくし、Node のツールチェーンへの依存を外す。
5. 段ごとに挙動を変えない。

## 設計

### CUE で持つもの

CUE は型と値と制約を同じものとして扱い、重ねて矛盾すればエラーにする言語である。JSON の上位互換で、Go の API を持つ。参考 normative: https://cuelang.org/docs/introduction/

```cue
// refs.cue。参照先の表の id の索引
_bodyPartIDs: {if bodyParts != _|_ for x in bodyParts {(x.id): true}}

// schema.cue。参照する側は索引を引き、無い id は検証で落ちる
#Condition: {
	id!:   string
	name!: string
	parts?: [...string]
	if parts != _|_ {
		parts_ref: [for x in parts {_bodyPartIDs[x]}] @rawgen(-)
	}
}
```

- 参照は「参照先の表の索引に id がある」という制約として書く。`validate.go` の参照の検証の大半はこの制約に置き換わる。
- 値の範囲は今の TypeSpec の `@minValue` と `@maxValue` と同じく制約で書く。
- 参照以外の決まり、たとえば不調を起こす仕組みごとにちょうど1つの不調があること、は CUE で書けるものは CUE へ、書けないものは Go に残す。

### Go の型

`internal/rawschema/gen` が CUE の定義の構文を読み、`models_gen.go` を書き出す。

- 試作で `cue exp gengotypes` を試したが、列挙の定数と `Valid()`、名前付きスカラーの別名、整数の幅を出せず、本番コード76ファイルが使う形に揃わなかった。自前の生成器で oapi-codegen の出力と同じ形を作り、型・フィールド・タグ・定数の531項目が一致することを確かめた。
- 写し方は属性で変える。`@rawgen(type=int32)` は Go の型を、`@rawgen(prefix)` は定数名の前置を、`@rawgen(enum=float32)` は数の列挙の土台を、`@rawgen(-)` は Go から外すことを指定する。
- `rawschema` パッケージは CUE を import しない。ゲームのバイナリには CUE が入らない。

### データの書式

TOML のまま残す。CUE は TOML を直接読まず、Go へ読み込んだ `Raws` を JSON にしてから検証する。

- 検証の意味は OpenAPI のときと同じになる。TOML で省いた必須フィールドは Go のゼロ値として現れる。
- `raw.toml` と `fmtraw` と yq の編集はそのまま使える。データを CUE にする変換は、得るものが参照の制約の並びだけで、2.3万行の差分に見合わない。

### 検証

- 参照と id の重複は CUE の制約で書く。`refs.cue` に id の索引を置き、参照する側は `<field>_ref` で索引を引く。選言 `or()` は実データで遅いので使わない。実データの検証は約0.13秒で済む。
- 検証は `internal/rawschema/rawcheck` が行い、テストから呼ぶ。ゲームの起動時には CUE の検証をしない。データを変えると CI のテストが止める。
- 複数の表にまたがる集計や件数の決まりは Go の `validateRules` と `validateCodeRows` に残す。`validate.go` は954行から480行になった。

## 採用しなかった方法

- **TypeSpec に `@extension("x-ref", ...)` で参照を宣言し、Go に汎用の検証を作る**: 参照の検証は宣言から導けるが、形を TypeSpec、Go、TypeScript の3つで持つ構成が残る。
- **SQLite に入れる**: 外部キーと CHECK で整合性は得られるが、git での差分が読めず、WASM 版が重くなる。
- **データを Go の構造体リテラルで書く**: 参照の整合性はコンパイルで得られるが、コードを書かずにデータを触れなくなる。
- **`cue exp gengotypes` で型を生成する**: 列挙の定数と `Valid()`、名前付きスカラー、整数の幅が出ず、使う側のコードを大きく書き換えることになる。
- **ゲームの起動時にも CUE で検証する**: バイナリに CUE が入り、起動が遅くなる。データはリポジトリにあり、CI のテストで同じ保証が得られる。
- **editor-ui を残し、CUE から OpenAPI を書き出して TypeScript の型を生成する**: 形の出どころは1つになるが、エディタのために Node のツールチェーンと TypeScript のコードを持ち続ける。
