# 灯りと武器と道具に残量を持たせて有限にする

## 背景

灯りと武器と道具は、一度手に入れると無限に使える。

- 持ち運べる灯りは松明 `torch` と、キューブに置くランタン `deployable_lamp` の2つだけで、どちらも消えない。キューブに置くランタンは置物として照らすが、キューブに置く灯りはわかりにくいので、この設計で消す。マップに置かれた据え付けの灯り、たとえば小型スタンドランプのような `#Prop` の `lightSource` を持つ置物は、残量を持たず今までどおり照らし続け、この設計では変えない。装備した光源は `StatsChanged` のたびにプレイヤーの `LightSource` へ写すだけで、減るものが無い。`internal/systems/stats_changed.go:86`
- 道具は武器の行に `tool` の分類とグレードを持つ。合う道具を構えて置物を殴るとダメージが `1+グレード` 倍になり、壊すと産出が増える。`internal/activity/salvage.go:38`。使っても減らない。

寒く暗い惑星で廃墟を漁るゲームなので、灯りと武器と道具が尽きることを、拾い集める理由と判断の材料にしたい。灯りは種類ごとに性能を変え、選ぶ意味を持たせる。

## 要件

- 灯りと武器と道具は、使うと残量が減り、0で尽きる。
  - 灯りは、点いている間に毎ターン減る。
  - 武器と道具は、振るか撃つたびに減る。敵を殴っても、撃っても、道具として置物を殴っても減る。
- 尽きたときの扱いは2つ。
  - 補充できない物は、尽きると無くなる。松明と武器と道具が例。
  - 補充できる物は、尽きても物は残り、燃料を足すとまた使える。ランタンが例。
- 灯りは種類ごとに性能が違う。照らす半径、色、残量の上限、1ターンに減る量。
- 残量は、一覧では段階、アイテムの詳細では数字で見える。
- 値はすべて raw の行で決め、新しい灯りや武器は行を足すだけで作れる。

## 設計

### 用語

| 用語 | Go | 意味 |
|---|---|---|
| 残量 | `Charge` | 灯りや武器や道具を、あとどれだけ使えるか。使うと減り、0で尽きる。英語の表示は Charge |
| 火の燃焼 | `Burning.Remaining` 既存 | 焚き火があと何ターン燃えるか。`fire.go` の doc は「火の残量」と呼ぶが、この設計の残量とは別物。`fire.go` の doc の15行目と26行目の「残量」を「燃焼の残り」に直す |
| 手持ち | `SlotHand1`〜`SlotHand5`・`query.IsHoldable` | 手に持つ物を入れる5つの欄と、そこに入る物。近接攻撃・遠隔攻撃・灯りのどれかを持つ物 |
| 道具 | raw の `tool` | 採掘・伐採などの分類とグレードを持つ物。つるはしや斧。手持ちの欄に入る物の一部 |
| 耐久 | `HP` 既存 | フィールドにある物が攻撃されると減る。置物の `HP` で、調べる画面の表示は Durability。この設計では変えない |

残量と耐久は、減るきっかけが逆なので別のデータにする。耐久は攻撃「される」側の値で、残量は使う「主体」として使う側の値である。

灯りの残量と武器の残量は、同じデータにする。違うのは減るきっかけと点け消しの有無だけで、値の形は「上限と現在値」で同じだからである。

| 物 | 減るきっかけ | 1回に減る量 | 点け消し |
|---|---|---|---|
| 灯り | 点いている1ターンごと | 1 | 有る。点いている間だけ減る |
| 武器と道具 | 攻撃の行動1回ごと | 1。本来の用途以外は2 | 無い |

### 前提。体の攻撃をアイテムの表から分ける

今は、素手 `bare_hands` や敵の噛みつき・火を吐く・体当たりのような、体に備わった攻撃もアイテムの行として書かれている。敵の攻撃表 `commandTables` から使われる 24 行のうち 17 行は、どの戦利品の表・レシピ・初期装備からも参照されない、拾えない攻撃だけの行である。残りの 7 行は包丁 `cleaver` のように、敵が使い拾える物でもある。

拾えない攻撃がアイテムに混ざっていると、「近接攻撃を持つアイテムは残量を必ず持つ」という規則に例外が要る。例外をアイテムの印で表すと、拾えないという性質をアイテムに持たせることになり、意味が合わない。

そこで、この設計の前に、体の攻撃をアイテムの表から別の表へ分ける。別の設計ドキュメントと PR にして先に入れる。分けた後は、アイテムの行は拾える物だけになり、残量の規則に例外が要らない。敵の攻撃表は、アイテムと体の攻撃のどちらも引けるようにする。素手を取り出す `attack.go` の `NewWeaponSpec(..., "bare_hands")` も、体の攻撃の表から引く。

### 前提。武器の欄を手持ちの欄にする

今の装備の欄のうち、武器の欄 `WEAPON1`〜`WEAPON5` は近接攻撃か遠隔攻撃を持つ物だけを受ける。`internal/states/character_state.go` の `equipableForSlot` が `query.IsWeapon` で絞る。つるはしや斧のような道具は近接攻撃を持つので既に入っているが、近接攻撃を持たない手提げランタンと懐中電灯は、どの欄にも入らない。

そこで、武器の欄を「手持ちの欄」に一般化し、灯りもここに入れる。「道具の欄」と呼ばないのは、raw の `tool`、つまり採掘や伐採の分類を持つつるはしや斧を指す「道具」と、語が重なるためである。手持ちの欄には剣もランタンも入るが、道具の分類を持つのはつるはしや斧だけで、本来の用途以外の倍率はこちらの「道具」で決まる。

- 欄の名前を改める。raw の `#EquipSlot` の `WEAPON1`〜`WEAPON5` を `HAND1`〜`HAND5` に、Go の `gc.SlotWeapon1`〜`SlotWeapon5` を `SlotHand1`〜`SlotHand5` に、`query.IsWeapon`・`GetWeapons` を `IsHoldable`・`GetHeld` に、表示を「手持ち 1」〜「手持ち 5」にする。Go の25ファイルと raw の初期装備の5か所に及ぶ機械的な改名なので、この設計の前に別の PR で入れる。
- 手持ちの欄が受ける物を、近接攻撃・遠隔攻撃・灯りのどれかを持つ物にする。判定は `query.IsWeapon` を一般化した `query.IsHoldable` の1か所に置く。今の `IsWeapon` は `Melee` か `Fire` を持つかだけを見て、装備画面の欄の一覧 `characterEquipSlots`、HUD の表示、選んでいる欄の物 `query.SelectedWeapon` を返す `query.GetWeapons` もこれで絞っている。受ける側の `equipableForSlot` だけを広げると、ランタンを入れた欄が装備画面でも HUD でも空に見え、外せず、空に見える欄へもう1つ入れられてしまう。照らす処理と減る処理は装備の欄を直に見るので、見えず外せないのに燃え続ける灯りになる。判定を `IsHoldable` の1か所にして、入れる側と読む側をそろえる。改名の PR で `IsWeapon` を `IsHoldable` に、`GetWeapons` を `GetHeld` に改め、この設計で `IsHoldable` に `LightSource` を足す。
- 選んでいる欄の物が近接攻撃も遠隔攻撃も持たないとき、攻撃は素手で行う。今の `getAttackParams` も、選んだ物が `Melee` を持たなければ素手に落ちる。この設計で武器の実体も返すようにするとき、素手に落ちたら武器の実体として `gc.InvalidEntity` を返す。ランタンを返し間違えると、殴るたびにランタンの残量が減り、灯りは道具の分類を持たないので置物を殴れば2倍減る。射撃は、`Fire` を持たなければ `getEquippedFire` が error を返すので、今の形のままで足りる。射撃画面の武器情報 `drawWeaponInfo` は、`Fire` を持たない物をすべて「近接武器」と出すので、`Fire` を持つときだけ出す。射撃画面で近接武器を見せる意味は無い。
- `query.LightLit` が「プレイヤーの手持ちの欄か」を判定するときは、`GetHeld` を使わず、灯りの実体の `LocationEquipped.Owner` と欄の番号を直に見る。`GetHeld` は呼ぶたびに装備を全走査するので、灯りの数だけ走査を重ねない。プレイヤーも呼ぶ側で1回だけ解決し、`query.LightLit(world, player, light)` のように渡す。今の `calculateLightSourceDarkness` はタイルごとに光源のクエリを回すので、そこへ `LightLit` を差し込むと、見えるタイルの数 × 灯りの数だけ呼ぶことになる。視界を計算し直す先頭で、`LightLit` が true の灯りの位置・半径・色を1度だけスライスへ集め、タイルのループにはそれを渡す。プレイヤーを解決するのも1回で済み、`LightChargeSystem` の「先に集める」とも同じ形になる。ベンチの `VisionRecompute_*` で前後を比べる。

### データ

raw のアイテムの行に、残量の欄を1つ足す。灯りの性能を表す `#LightSource` は変えない。`#LightSource` は光る敵 `#Member` も使うが、残量はアイテムの行に置くので、敵の内蔵光源は残量を持たず減らない。

```cue
// アイテムの残量。灯りは点いている間に、武器と道具は使うと減り、0で尽きる。減る量は ConsumeCharge が決める。
// refillTag を省くと使い切りで、尽きると無くなる
#Charge: {
	max!:       #ChargeAmount  // 残量の上限。灯りはターン数、武器と道具は回数
	refillTag?: #RefillTag     // 満たせる燃料の種別。同じ種別の燃料ならどれでも満たせる
}

// 燃料の種別。弾薬の口径 #AmmoTag と同じく、灯りと燃料をこの種別で引き合わせる
#RefillTag: "oil" | "battery" @rawgen(prefix)

// 燃料。この種別の残量を持つ灯りを、上限まで満たす
#Refill: {
	refillTag!: #RefillTag
}

#Item: {
	// 既存の欄は省略
	charge?: #Charge
	refill?: #Refill   // この行が燃料であること
}
```

`lightSource`・`melee`・`fire`・`tool` のどれかを持つアイテムの行は、`charge` を必ず持つ。`charge.refillTag` を持てるのは `lightSource` を持つ行だけにする。複数の欄を見る条件なので、CUE でなく `raw.validateRules` に置く。

減るきっかけはアイテムの実体が持つコンポーネントから決まる。`gc.LightSource` を持てば点いている間に減り、持たなければ使うたびに減る。松明は `lightSource` と `melee` の両方を持つが、灯りとして点いている間に減り、振っても減らない。消耗の値を1つにして、何で尽きるかを迷わせない。

Go のコンポーネントは1つ足す。アイテム1個ごとに持ち、セーブに載る。

```go
// Charge はアイテムの残量。灯りは点いている間に、武器と道具は使うと減り、
// Current が0で尽きる。減る量は ConsumeCharge が決める。直す仕組みは Current を戻すだけで足せる。攻撃されて減る HP とは別のデータ。
// Max は生成時に写すので、raw を調整しても生成済みの実体には効かない
type Charge Pool[int]
```

`LightSource` は今の形のまま、照らす半径と色と点灯を持つ。補充の燃料は補充するときだけ raw の行から引く。

`Max` は、将来の修理で上限を変える余地として実体に持つ。生成時の値で固まるので、raw を調整しても、生成済みやセーブ済みの物は古い値のままになる。未リリースなので受け入れる。

1回に減る量は欄にせず、固定の1にする。灯りも武器もすべて1で、行ごとに変える理由が無い。毎ターン2減る灯りのような行が要るときに欄を足せばよい。本来の用途以外の倍率 2 と着火の 30 は、減らす関数の引数で渡す。

### 灯りの減り方

- **照らすなら減る。** `query.LightLit` は「照らしているか」の判定で、置き場所も含めて決める。照らしているのは、`GridElement` を持つ物と、プレイヤーの手持ちの欄にある物だけで、背負っている物は照らさない。手持ちの欄に入れた灯りは、選んでいる欄でなくても点いて照らす。剣を構えたまま、別の欄の松明で照らせる。装備の灯りをその場に写すのはプレイヤーだけなので、`StatsChangedSystem` と同じくプレイヤーの装備に絞る。敵が灯りを装備しても照らさず、減らない。`query.LightLit` が true で `Charge` を持つ物は、毎ターン1ずつ減る。装備している灯りも、床に落とした灯りも同じ規則で減る。照らす物と減る物が必ず一致するので、落とした松明が減らずに照らし続ける抜け穴が無い。手持ちの欄に灯りを複数入れると、すべて点いて減る。プレイヤーの周りを照らす範囲は、`StatsChangedSystem` が写す最も明るい1つで決まり、ほかの灯りは範囲を広げずに燃える。複数入れれば全部燃えるのは自然な帰結として受け入れ、灯りは1つだけ入れる判断になる。光る物を今後足すときも、この規則から漏れない。
- 背負っているだけの灯りは照らさないので減らない。
- 眠っている間も、装備の灯りは照らし続けて減る。点け消しの操作は作らないので、寝る前に外すかを選ぶ判断になる。眠り始めるときに点いている装備の灯りがあれば、ログで知らせる。
- プレイヤーの居ないステージの灯りは減らない。走査は `query.ActiveFilter2[gc.LightSource, gc.Charge]` で退避中のステージを外し、`query.LightLit` で絞る。ダンジョンに潜っている間、地上の床に落とした灯りは減らない。
- 減らすのは新しいシステム `LightChargeSystem` で、ターンの終わりに走る。`ConsumeCharge` は尽きた松明を消し `StatsChanged` を付けるので、クエリの走査中に呼ぶと Ark のロック中の構造変更で panic する。`query.LightLit` が true の灯りを先にスライスへ集め、ループを抜けてから `ConsumeCharge` を呼ぶ。`InitializeSystems` とターン終わりの実行の一覧の両方に登録する。一覧では `FireSystem` の後に置く。`ConsumeCharge` は `lifecycle` の削除の経路で直接消し、`Dead` を経ないので、`DeadCleanupSystem` との前後は問わない。`StatsChangedSystem` はターン終わりの一覧に無いので、眠っている間の fast-forward で燃え尽きた灯りの写し直しは次のフレームになる。視界は毎フレーム計算し直すのではなく、プレイヤーが動いたときか `VisionState.RequestUpdate()` が呼ばれたときだけ計算し直す。`internal/systems/vision.go`。そこで、点いているかが変わるときは必ず `RequestUpdate()` を呼ぶ。`ConsumeCharge` が灯りを0にしたとき、つまり床の松明が燃え尽きて消えたときや、補充できる灯りが0で消えたときに呼ぶ。補充メニューに並ぶのは背負った物と手持ちの欄の物だけで、手持ちの欄の灯りを0から戻すと `StatsChanged` の経路で `RequestUpdate()` が呼ばれ、背負った灯りは照らさない。床の灯りは補充できないので、`LightFuelSink` は自分で呼ばない。
- `query.LightLit` は、置き場所が照らせる所で、`LightSource.Enabled` が true で、`Charge` を持つなら残量が0より多いこと、で true になる。この判定を1か所に置き、視界の計算と装備の灯りを写す処理と `LightChargeSystem` がすべてこれを通る。視界の計算と装備の灯りを写す処理は、今も自分で置き場所を絞っているので、置き場所の条件は重なるが、3つが同じ判定を通ることを優先する。残量が尽きても `Enabled` は書き換えないので、燃料の有無の真実は残量の1つだけになる。
- 装備の灯りを写したプレイヤー自身の `LightSource`、光る敵の内蔵光源、マップに据え付けられた置物の灯りは `Charge` を持たないので、照らしても減らない。減るのは灯りのアイテムの実体だけである。
- 残量を減らす処理は `gameaction.ConsumeCharge(world, item, amount) error` の1つにまとめ、`LightChargeSystem`・`applyAttackDamage` の `defer`・`executeIgnite` の3か所から呼ぶ。0で止めること、段階の比較とログ、0での削除か残置、`StatsChanged` を、この関数が持つ。`StatsChanged` を付けるのは尽きたときだけにする。毎ターン付けると `StatsChangedSystem` が毎ターン走る。攻撃されて減る耐久を適用する `gameaction.ApplyDamage` と並べ、使って減る残量を適用する関数として置く。`lifecycle` は生成・削除・配置の分類でゲームログを出さないので、ログを出すこの関数は置かず、削除だけ `lifecycle` の既存の経路に任せる。ログはプレイヤーのときだけ出す。着火で残量が30未満の松明を使っても、同じ経路で尽きる。
- 残量が0になったら:
  - `refillTag` を持たない灯りは、アイテムを消す。松明は燃え尽きる。消すときは既存の lifecycle の削除の経路を通し、装備の欄から外れることと、総重量の再計算と `StatsChanged` が漏れないようにする。
  - `refillTag` を持つ灯りは、物を残す。残量0なので `query.LightLit` が false になり消える。
  - どちらも、持ち主がプレイヤーならログを出し、`StatsChanged` を付けて灯りを写し直す。
- 補充は、既にある給油メニュー `FeedFuelMenuState` で行う。灯りのくべ先 `LightFuelSink` を、焚き火の `FireFuelSink` とキューブの `CubeFuelSink` の隣に足す。新しい動詞や画面は作らない。
- くべ先によって、燃料のアイテムのどの項目を見るかが違う。

  | くべ先 | 見る項目 | 候補の絞り方 | 1つくべると |
  |---|---|---|---|
  | 焚き火・キューブ。燃焼、既存 | 材質 `material` と重さ | 材質の熱量が0より大きい物。`query.IsCombustible` | 材質の熱量 × 重さだけ増える |
  | 灯り。補充、新規 | 燃料の欄 `refill.refillTag` | 灯りの `charge.refillTag` と同じ種別の物 | 残量が上限まで戻る |

  今の `FuelSink` は増える量とくべる処理だけを持ち、候補は給油メニューの `Fetch` で燃える物に固定している。選んだときの `DoAction` でも同じく `query.IsCombustible` で弾いている。候補の判定を `FuelSink.accepts func(world, fuel) bool` の1つにし、`Fetch` の一覧と `DoAction` の選んだ時の検査の両方から呼ぶ。片方だけ移すと、燃えない電池が一覧に出るのに選ぶと弾かれる。
- 見出しはくべ先ごとに `title` で出す。灯りは「残量 420 / 1500」のように出す。一覧が空のときの文「くべる燃料がない」`ja.po` の `"No fuel to add"` の1行は、焚き火に寄った言い回しなので「足す燃料がない」に改め、どのくべ先でも通じる語にする。周囲への操作の一覧の `"Feed fire (%s)"` は火の専用なのでそのままにする。灯りのくべ先の増える量の列には、満たせる量 `Max-Current` を `+1080` のように出し、焚き火とキューブの数の出し方にそろえる。
- 灯油 `lamp_oil` のように、両方の項目を持つアイテムもあってよい。材質 `OIL` を持てば焚き火にくべて熱にでき、`refill.refillTag = "oil"` を持てばランタンを満たせる。見る項目が違うので、2つの用途はぶつからない。
- 補充は持ち物に対する操作なので、周囲への操作の一覧からは入らない。補充メニュー `RefillMenuState` を新しく足し、ダンジョンのメニュー `dungeonMenuChoices` に「補充」の項目を足して開く。
- 補充メニューは2段にする。
  1. 1段目は、補充できる持ち物の一覧。背負っている物と手持ちの欄に入れた物のうち、`charge.refillTag` を持ち満タンでない灯りを並べる。各行に残量を出す。
  2. 1段目で選ぶと、2段目として給油メニュー `FeedFuelMenuState` を灯りのくべ先 `LightFuelSink` で開く。選んだ灯りに入る燃料、つまり同じ種別の `refill` を持つ物が並び、選ぶと足す。
- 2段目は既にある給油メニューを使い回すので、燃料を選ぶ画面は焚き火・キューブと1つのままになる。焚き火とキューブは今のまま周囲への操作の一覧から開き、灯りだけ補充メニューから開く。どちらも、くべ先をメニューへ直に渡して開くので、イベントや相互作用の種類は足さない。
- 補充できる持ち物が1つも無いときは、1段目に「補充できる物が無い」と出す。
- 1段目は `FeedFuelMenuState` と同じく `menuloop.Screen` の `Fetch` で毎フレーム組み直す。2段目で満タンにして戻ると、その灯りは1段目から消える。
- 灯りは、灯りの `refillTag` と同じ種別の `refill` を持つ燃料を1つ消費して、残量を上限まで戻す。燃料を特定のアイテムの id で指さないので、灯油に別の銘柄を足したり、電池の種類を増やしたりしても、灯りの行は書き換えずに済む。弾薬が口径 `ammoTag` で銃と引き合うのと同じ形である。満タンのときは、補充メニューの1段目に出さない。給油メニューは閉じずに続けて足せるので、メニューの中で満タンになった後に選んだときは、`CubeFuelSink` と同じく燃料を消さず「もう満タンだ」とログだけ出す。減った分だけ燃料を減らすことはしない。燃料にも残量が要り、データが増えるためである。
- 装備したまま補充すると、残量が0から戻って `query.LightLit` が true に変わる。この変化は `ConsumeCharge` の外で起きるので、`LightFuelSink` のくべる処理が `StatsChanged` を付け、プレイヤーの灯りを写し直す。付けないと、装備を付け直すまで暗いままになる。

### 灯りを点ける

- アイテムの灯りは、どこで生まれても消えた状態で作る。マップ生成で床に置く物も、箱の中身も、店の品も、クラフトの品も同じである。廃墟に置かれた松明に火が付いていたり、懐中電灯が点いていたりするのは不自然で、拾う前に床で燃え尽きることも無くなる。`raw.go` がアイテムの灯りを作るときは `Enabled = false` にする。raw の光源の型は CUE で2つに分ける。アイテムの灯りは点けるかを持たず、光る敵と置物の灯りは必ず持つ。

  ```cue
  // アイテムの灯り。点けるかは装備で決まるので、enabled を持たない
  #LightSource: {
  	radius!: #LightRadius
  	color!:  #RGBAColor
  }

  // 光る敵 members と置物 props の灯り。点いているかを行で決める
  #FixedLightSource: {
  	radius!:  #LightRadius
  	color!:   #RGBAColor
  	enabled!: #LightEnabled
  }
  ```

  アイテムの行に `enabled` を書くと、閉じた定義なので CUE の検証で落ちる。光る敵と置物の行で書き忘れても落ちる。どちらもスキーマの段階で機械的に効き、`validateRules` に検査を置かずに済む。`enabled` を省ける欄にすると、生成される Go の型がポインタになり、書き忘れが黙って暗くなるので採らない。`#FixedLightSource` は `#LightSource` を `&` で広げず、欄を書き並べた独立した型にする。`#LightSource` は閉じた定義なので、`&` で持たない欄を足すと CUE の評価で落ちる。埋め込みは、生成器 `internal/rawschema/gen` の `writeStruct` が扱わない。重なるのは `radius` と `color` の2欄だけなので、生成器を広げずに書き並べる。Go では `LightSource{Color, Radius}` と `FixedLightSource{Color, Enabled, Radius}` の別々の型になる。`raw.go` の `toGCLightSource` は、半径と色と点いているかを引数に取る1つの関数にし、アイテムの灯りは点いていないとして、ほかは行の値で呼ぶ。光る敵の内蔵光源は、これまでどおり raw の値で点いている。
- 灯りは装備したときに点く。`lifecycle.MoveToEquip` が `Enabled = true` にする。装備は、装備の画面 `equip_select_state.go`、職業の初期装備 `gameaction/profession.go`、member の行の初期装備 `lifecycle.giveStartingGear` の3つの経路から `MoveToEquip` に入るので、ここに置けば漏れない。初期装備の松明もゲーム開始時から点いている。敵の初期装備の松明も点くが、`query.LightLit` はプレイヤーの装備に絞るので照らさず減らない。`lifecycle` の配置の処理に灯りの状態という副作用が入るが、経路を漏らさないことを優先する。`Enabled` は「一度点けたか」を表し、書き換えるのはこの処理だけである。外しても消さないので、点いた松明を落とせば床でも燃え続け、背負えば照らさないので減らない。
- 手で点け消しする操作は作らない。点けるのは装備するときだけで、消すのは燃え尽きるときだけである。

### 灯りの種類

性能を変えて、選ぶ意味を持たせる。1日は 1500 ターン。

| 灯り | 半径 | 色 | 残量 | 補充 | 役割 |
|---|---|---|---|---|---|
| 松明 `torch` | 6 | 暖色 | 600 | 無し、使い切り | 安く広く照らす。火種も兼ねる |
| 手提げランタン `hand_lantern` 新規 | 5 | 暖色 | 1500 | 種別 `oil`。灯油 `lamp_oil` 新規 | 長持ちし、油で何度も使える |
| 懐中電灯 `flashlight` 新規 | 8 | 白 | 1000 | 種別 `battery`。電池 `battery` 新規 | 最も遠くまで照らすが、電池は貴重 |

- 初期装備の松明は 600 ターン、0.4 日で尽きる。廃墟で灯りを探すことを序盤の目標にする意図どおりである。遊んで残量を詰める。
- 既存の `scrap_battery` は使い切った電池で、売るだけのガラクタとして残す。懐中電灯には新しく足す使える電池 `battery` を使う。
- 着火に使った火種が残量を持つなら、残量を固定で 30 減らす。30 は `execute_interaction.go` の定数に置く。火種は、残量を持たない物を先に、次に背負っている物、最後に装備している物から選ぶ。同じ順位なら残量の多い物を選ぶ。点いている装備の松明を削らずに済むよう、照らしていない物から使う。ライターのような残量を持たない火種を今後足せば、それが最初に選ばれる。`executeIgnite(target, world)` は着火する主体を受け取らないので、署名に actor を足す。火種を選ぶ処理は `query.HoldsFireStarter` の隣に、火種を返す関数として置き、所持の判定と選択を同じ所にそろえる。

### 武器と道具の減り方

- 近接攻撃も射撃も、攻撃の行動1回ごとに1ずつ減る。外れても減る。今のコードは1回の行動で `applyAttackDamage` を1回だけ呼び、`AttackCount` は表示にしか使っていないので、行動1回と当てる試行1回は同じになる。
- 本来の用途以外に使うと、倍の量が減る。倍率は固定の 2 で、`attack.go` の定数に置く。行ごとに変える理由が無いので raw には持たせない。置物を壊すか敵を攻撃するかは、攻撃の対象が `gc.Prop` を持つかで決める。キューブの展開空間に置いた設備も `Prop` を持つので、置物として扱う。銃で置物を撃っても同じ規則に乗る。
- 置物に対して本来の用途かどうかは、ダメージの倍率 `toolDamageMultiplier` と同じく `wieldedTool` で決める。置物の分解の定義と道具の分類が合う物で殴ったときだけ本来の用途で1倍、それ以外で置物を殴ると2倍。ダメージと残量が同じ判定を通るので、斧で岩を殴ってダメージが出ないのに残量は1倍、のようなずれが起きない。

  | 使う物 | 敵を攻撃する | 分類の合う置物 | ほかの置物 |
  |---|---|---|---|
  | 道具の分類 `tool` を持つ物。つるはし・斧など | 2 倍 | 1 倍 | 2 倍 |
  | `tool` を持たない武器。剣・銃など。撃っても同じ | 1 倍 | 合う物は無い | 2 倍 |

  つるはしは岩を壊すため、斧は木を壊すため、剣は戦うため、という使い分けが生まれる。Minecraft も、斧やつるはしで敵を叩くと、剣でブロックを壊すと、それぞれ2回分減らしている。
- 減らす場所は `applyAttackDamage` の1か所にする。関数の先頭で `defer` に減らす処理を積み、`dropSalvage` が error で早く戻った場合も含めて、外れて早く戻る分岐でも、当たって `growWeaponSkill`・`dropSalvage`・`applyInjury` を終えた後でも、最後に1回走るようにする。最後の1回で武器を先に消すと、`dropSalvage` が道具のグレードの産出の上乗せを付けられず、消えた武器の `Melee`・`Fire` を読むことにもなるので、必ず最後に減らす。振った事実は変わらないので、途中の error でも減らす。`defer` の中の削除の error は、名前付きの戻り値へ `errors.Join` で合わせて返し、握りつぶさない。近接 `attack.go` と射撃 `shoot.go` の両方がここを通り、道具として置物を殴るときも同じ経路になる。`applyAttackDamage` は今 `Melee` や `Fire` の値だけを受け取り、武器の実体を知らない。そこで `getAttackParams` と `getEquippedFire` が武器の実体も返し、`applyAttackDamage` の引数で渡す。素手や敵の内蔵攻撃は武器のアイテムを持たないので `gc.InvalidEntity` を渡し、何も減らさない。減らすのは、渡された武器が `gc.LightSource` を持たず `Charge` を持つときだけで、松明で殴っても減らない。殴られた置物の側は、これまでどおり耐久 `HP` が減る。
- 遠隔武器は再装填では減らない。弾薬が尽きるのとは別に、銃そのものも擦り減る。
- 銃が尽きて消えるとき、弾倉に残った弾も一緒に失う。`gc.Fire` は口径と装填のボーナスしか持たず、装填した弾薬の行を知らないので、戻すには弾薬の種類を持たせる変更が要る。作者の判断で、弾は失う。
- 0になったら武器を消し、持ち主がプレイヤーならログを出す。構えていた武器が消えたら素手に戻る。近接攻撃は攻撃のたびに `getAttackParams` で装備から武器を読み直すので、続けて攻撃していても、消えた武器を読み続けることは無い。消すときは、灯りと同じく既存の lifecycle の削除の経路を通す。
- 武器と道具は補充できない。`charge.refillTag` は `lightSource` を持つ行にしか書けない。
- 上限は行で決める。近接の目安は素材の弱い武器で 80、普通で 150、頑丈な武器や道具のグレード3で 250 回。遠隔は撃つ回数が弾薬で限られるので近接より多めにし、目安は 300〜600 発。
- 壊れた武器や道具を直す仕組みは、この設計では作らない。将来、工作台で直す余地を残し、`Charge` は上限と現在値を持つ形にしておく。

### 表示

一覧ではひと目で分かる段階を、詳細では正確な数を見せる。CDDA も、名前の横に傷みの段階を記号と色で出し、数は詳しい説明に回している。

| 場所 | 表示 |
|---|---|
| 一覧の名前の横 | 5段階の短いバー。緑から黄、赤へ変わる。灯りには印を2通り添える。今照らしている `query.LightLit` の物には点灯の印、一度点けたが今は照らしていない `Enabled` だけの物には「点けた」の印。背負った使いかけの松明が新品と別の行に分かれる理由が見え、床に置くと燃えることも伝わる |
| アイテムの詳細 `entityspec` | 灯りは `残量 420 / 600 ターン`、武器と道具は `残量 120 / 150 回` |
| ログ | 段階が下がったときだけ出す。例「つるはしが傷んできた」「松明が燃え尽きかけている」 |

- 残量は減るほど悪い向きの1つの値なので、バーは長いほど良い。割合の数字は一覧に出さない。
- バーの段階とログの段階は同じ境目を使う。上限に対する残量が 80%・60%・40%・20% を割るたびに1段下がる。
- ログの文は、灯りか武器かで言い回しを変える。
- 分解で得られる素材は残量で減らさない。売値と同じく、使いかけでも満タンと同じに扱う。
- 段階は保存しない。減らす前と後の残量からそれぞれ段階を出し、違えばログを出す。状態を増やさずに済む。上限が小さい行では1回で2段下がることがあるが、ログは下がった後の段階で1行だけ出す。
- 床に落とした松明は1本ずつ毎ターン減るので、拾うとすべて別の行になる。一覧の行は増えるが、それぞれの残量が見えるので、仕様として受け入れる。
- 残量か点灯の違う同じ品は、別のスタックに分ける。`query.StackKeyOf` のキーに残量の現在値と `LightSource.Enabled` を足す。一度点けた灯りを外すと、新品と別の行に見える。床に置くと燃える物だとプレイヤーに伝わり、床に置く物が運で決まることも無い。銃は装備の指紋が `Fire` を丸ごと畳むので弾倉の違いで既に分かれており、新しく分かれるのは灯りと近接武器と道具である。装備の指紋が生値で個体を分けているのと同じ考え方で、使いかけの物はそれぞれ別の行になり、バーが1つの値を正しく見せる。
- 売値は残量で下げない。値段の計算を増やさず、使いかけでも売れる。

## 採用しなかった方法

- **灯りの残量と武器の摩耗を別のデータにする**: 値の形はどちらも上限と現在値で同じで、違うのは減るきっかけと点け消しだけ。作者の判断で1つにまとめ、きっかけはアイテムが持つ欄から決める。
- **値の向きを「摩耗が進む」にする**: 灯りは残りが減る向きが自然で、2つの向きが混ざると表示で取り違える。残量の1つの向きにそろえる。
- **減るきっかけを raw の欄で指定する**: `lightSource` を持つかどうかで決まるので、欄を足すと矛盾した行を書ける余地が生まれる。
- **残量を `#LightSource` の中に置く**: 武器も残量を持つので、灯りの欄に置くと武器に置き場が無い。アイテムの行に置く。
- **キューブの `FuelTank` を灯りにも使う**: 単位が熱量で、可燃物をくべて満たす仕組み。灯りは決まった燃料で満たすので、使い方が違う。
- **残量を耐久 `HP` で持つ**: `HP` は攻撃されて減る値で、攻撃の対象の判定にも使う。使う側の消耗と攻撃される側の消耗はきっかけが逆なので、別のデータにする。武器を殴れるものと誤って扱うことも防ぐ。
- **道具として置物に使ったときだけ減らす**: 範囲は小さいが、敵を殴る武器は無限に使えるままになる。作者の判断で、敵を殴っても減らす。
- **遠隔武器には残量を持たせない**: 弾薬で既に有限なので省ける。作者の判断で、銃そのものも擦り減るようにする。
- **残量が尽きたら `LightSource.Enabled` を false にする**: 読む側を変えずに済むが、点いているかを `Enabled` と残量の2つで表すことになり、片方だけ書き換えるとずれる。判定を `query.LightLit` の1か所に置き、真実を残量の1つにする。
- **1回に減る量を行の欄 `drain` にする**: すべての行が1で、同じ値を全行に書くことになる。固定の1にし、要る行が出てから欄を足す。
- **一覧に割合の数字を出す**: 段階のバーのほうがひと目で分かる。数は詳細で見せる。
- **CDDA と同じく `||` のような文字の記号で段階を出す**: 記号の意味を覚える必要がある。バーなら長さで読める。
- **言葉の段階を名前に添える**: 新品・傷んだ・壊れかけのような語で分かりやすいが、日本語の名前が長くなる。ログで同じ語を使う。
- **素材で減り方を変える**: 木の武器は速く減るなど。上限 `max` を行ごとに決めるので、素材の違いはそこで表せる。
- **CDDA のように確率で減らす**: 当てるたびに確率で傷みが進む。運で寿命がぶれて読みにくく、テストも乱数の固定が要る。減る量は決まった値にする。
- **減らす灯りを装備した物に限る**: 床に落とした灯りも照らすので、落とせば減らない灯りになる。照らす物すべてを減らす。
- **床に落ちた灯りは消す**: 落とした松明が消えるのは不自然で、場合分けも増える。
- **連撃の武器を試行の回数だけ減らす**: 今のコードは1回の行動で1回しか当てないので、`AttackCount` 回の試行は無い。連撃を作るのは別の設計にする。
- **呼び出し側の `performAttack` と `ShootBehavior.DoTurn` で減らす**: `applyAttackDamage` の署名を変えずに済むが、減らす所が2か所になる。
- **スタックのキーで残量を5段階に量子化する**: 行は減るが、同じ段階の中で減った物とそうでない物が混ざり、使う順が決まらない。
- **使いかけの物の売値を下げる**: 値段の計算が増える。
- **`ConsumeCharge` を `lifecycle` に置く**: 呼ぶ所は1つで済むが、`lifecycle` が初めてゲームログの文言を出すことになり、生成・削除・配置の分類に例外ができる。
- **`ConsumeCharge` は段階の前後と尽きたかを返し、呼ぶ側がログを出す**: 3か所に同じログの処理が並び、1つにまとめた意図に反する。
- **`query.LightLit` は置き場所を見ず、`LightChargeSystem` の走査だけを置き場所で絞る**: 判定の重なりは無くなるが、照らす物と減る物を決める条件が2か所に分かれ、ずれうる。
- **敵の攻撃表に載る行を `charge` の必須から外す**: 包丁のように、敵も使い拾える道具でもある行があり、見分けられない。
- **銃が壊れたら弾倉の残りを戻す**: 装填した弾薬の行を `gc.Fire` に持たせ、リロードで書く変更が要る。作者の判断で、弾は失う。
- **キャンプランタンを残し、置いた灯りに燃料を足す動詞を設備の画面に出す**: 置物の灯りはわかりにくく、燃料の足し方も2通りになる。作者の判断でキャンプランタンを消す。
- **眠っている間は装備の灯りを照らさない**: 寝ても減らずに済むが、照らすかの判定が置き場所以外の状態に広がる。ログで知らせ、外すかをプレイヤーに任せる。
- **火種は装備している物を先に選ぶ**: 点いている松明が着火のたびに削れる。照らしていない物から使う。
- **燃料を灯りの行から id で指す `refill: #EntityID`**: 燃料の銘柄を増やすたびに灯りの行を書き換えることになり、1つの灯りが複数の燃料を受けられない。種別 `refillTag` で引き合わせる。
- **生来の攻撃の行に印 `innate` を付け、残量の規則から外す**: データは変えずに済むが、拾えないという性質をアイテムに持たせることになり、意味が合わない。作者の判断で、体の攻撃をアイテムの表から分ける。
- **残量の必須を、戦利品の表やレシピから参照される拾える行に絞る**: 拾える経路をすべて辿る検査が要り、新しい種類の表を足したときに辿り忘れると検査が黙って抜ける。
- **残量を必須にしない**: 書き忘れた武器が黙って無限に使えるようになる。
- **燃焼も補充の種別 `refillTag` の1つにする**: 燃焼は、材質の表16行から263のアイテムに当てはまる一般的な性質で、材質と重さから導かれる。種別として行に書くと材質と二重になり、木の行に書き忘れると燃えなくなる。燃焼は材質から導くまま分けておく。
- **灯りの補充に新しい動詞と画面を作る**: 燃料をくべる画面が焚き火・キューブと灯りで2つになる。既にある給油メニューにくべ先を足す。
- **灯りの給油を周囲への操作の一覧から開く**: 焚き火やキューブとそろうが、補充は持ち物に対する操作で、フィールドの物への操作ではない。作者の判断で、補充メニューを足す。
- **灯りの給油を持ち物の操作画面の動詞にする**: 持ち物の画面は背負った物しか見ないので、手持ちの欄の灯りに届かない。補充できる物をまとめて見られる補充メニューにする。
- **灯りの専用の欄を足す**: 灯りは1つしか装備できず複数の問題も消えるが、欄・画面・セーブの変更が増える。作者の判断で、武器の欄を手持ちの欄に一般化して灯りも入れる。
- **選んでいる欄の灯りだけ点ける**: 戦うか照らすかの緊張は生まれるが、攻撃のたびに持ち替えて暗くなり、操作が重い。
- **灯りに弱い近接攻撃を持たせて武器の欄に入れる**: 今の仕組みのまま入るが、懐中電灯で殴る形になる。
- **欄を「道具の欄」と呼ぶ**: raw の `tool` の分類を持つつるはしや斧を指す「道具」と語が重なり、`IsTool` と `FindTool` が別の物を指して並ぶ。作者の判断で「手持ちの欄」にする。
- **本来の用途を道具の分類の有無だけで決める**: 斧で岩を殴るとダメージは出ないのに残量は1倍、剣で道具が要る置物を殴るとダメージ0で残量は2倍、とダメージの判定とずれる。`wieldedTool` の1つの判定にそろえる。
- **光源の `enabled` を省ける欄にし、`validateRules` で置き場所ごとに必須か禁止かを検査する**: 生成される Go の型がポインタになり、検査とそのテストが2つずつ要る。CUE で型を分ければ、スキーマの段階で機械的に効く。
- **`#FixedLightSource` を `#LightSource & {enabled}` や埋め込みで書く**: 閉じた定義に欄を足すと CUE の評価で落ち、埋め込みは生成器が扱わない。生成器を広げるのはこの設計のためだけになるので、2欄を書き並べる。
- **灯りを手で点け消しする**: 残量の節約にはなるが、操作が増える。装備したら点き、燃え尽きたら消える形にする。
- **生成した灯りも点けたまま置き、床で減るのを仕様にする**: 廃墟に火の付いた松明があるのは不自然で、拾う前に燃え尽きる。作者の判断で、生成した灯りは消えた状態で作る。
- **灯りを床に生成せず、箱の中か店だけで出す**: 行を移す手間が増え、拾える場所も減る。消えた状態で作れば床に置いてよい。

## コメント

作者と決めたこと。

- 敵を殴っても武器の残量を減らす。遠隔武器も撃つたびに減る。
- 壊れた武器や道具を直す仕組みは、将来作る可能性がある。この設計では作らず、`Charge` を上限と現在値で持って余地を残す。
- 灯りの残量と武器の摩耗は、データとしては同じ「残量 `Charge`」にする。違いは減るきっかけと点け消しの有無だけ。
- 使う側の消耗は「残量 `Charge`」、攻撃される側の消耗は既存の「耐久 `HP`」とし、データも語も分ける。
- 松明は灯りとして点いている間に減り、振っても減らない。
- 一覧は5段階のバー、詳細は正確な数で見せる。
- 本来の用途以外に使うと、倍の量が減る。
- 武器の欄を手持ちの欄に一般化し、灯りも入れる。入れた灯りはすべて点いて減る。
- 補充は持ち物に対する操作なので、フィールドからでなく補充メニューから行う。補充できる物を選び、入る燃料を選ぶ2段にする。
- 体の攻撃はアイテムの表から別の表へ分け、この設計より先に入れる。
- 生成した灯りは消えた状態で作り、装備したときに点ける。
- 銃が壊れたら弾倉の弾も失う。
- キャンプランタンを消し、キューブに置く灯りは作らない。マップに据え付けられた置物の灯りは今までどおり残る。
