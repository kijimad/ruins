# 疲労・空腹を導出 condition として統一し乗算 funnel へ全面 RimWorld 化

## 背景

身体機能を RimWorld へ全面的に寄せる。現状との差は2軸ある。

1. 局所機能の合成が加算 `意識 − 局所` になっている。RimWorld は乗算 `局所 × 意識`。なめらかな逓減を取り戻す。
2. 疲労・空腹の効果を extraSystemic という匿名の数値で意識へ足しており、怪我・病気と同じ condition として
   扱えていない。RimWorld は need も Hediff に統一し、怪我と同じリストへ並べる。

あわせて「量を変えたら自動で反映される監視機構が欲しい」という要件がある。Ark に値変更イベントは無いが、
**読み取り時に量から condition を materialize する**ことで、常に最新・忘れようがない・怪我と同じ condition として
並ぶ、の3つを同時に満たせる。RimWorld が need→Hediff を毎tick同期するのを、ruins では read 時 materialize に
置き換える。保存＋別システム監視はフレーム内 staleness と二重管理を生むため採らない。

## 要件

- 局所機能を乗算 `(100 − 局所) × 意識 / 100` に戻す。再スケールの漏れは `bodyFuncs` 内に封じ済みで消費側は不変。
- 疲労・空腹を `Exhaustion`・`Malnutrition` の condition として表す。ただし保存せず量から読み取り時に materialize する。
- materialize した need condition を怪我・病気と同じ funnel へ入れる。意識は全 condition の systemic 低下を受ける。
- 回復は意識でなく代謝で決める方針を維持する。代謝 capacity は need condition の低下だけを受ける。
- 疲労・空腹を怪我と同じ条件リストへ並べ、UI と汎用コードが区別なく扱えるようにする。

## 設計

### need を導出 condition として materialize する

量から段階を出し、段階を重症度へ写して condition を組む。保存しない。読むたびに作るので常に最新。

```go
// components: 段階→重症度。conditionDefs の bodyFuncDropPerSeverity と掛け合わさる
func (f *Fatigue) FatigueSeverity() (Severity, bool)     // Tired→Minor, Exhausted→Medium
func HungerSeverity(level HungerLevel) (Severity, bool)  // Hungry→Minor, Starving→Medium
```

```go
// query: 量から need condition を materialize する。保存された need condition は無い
func DerivedConditions(world w.World, entity ecs.Entity) []gc.HealthCondition {
	// Fatigue量→Exhaustion、Hunger量→Malnutrition。段階が無ければ空
}
```

### funnel は全 condition を一様に受ける

`bodyFuncs` は保存 condition に加えて need condition も受け、全 systemic を意識へ集約する。局所は乗算に戻す。

```go
func (hs *HealthStatus) bodyFuncs(needConds []HealthCondition) BodyFuncs {
	// 保存 Parts の condition で pain/bloodDrop/manip/moving/sight/systemic を積む
	// needConds は全身性。systemic に足し、代謝低下 needDrop としても集計する
	consciousness := clamp(100-systemic-pain/painConsciousnessDivisor, 0, 100)
	// 局所は乗算。RimWorld のなめらかな逓減
	withConsciousness := func(local int) consts.Percent {
		return consts.Percent(clamp(100-local, 0, 100) * consciousness / 100)
	}
	return BodyFuncs{
		...,
		Metabolism: consts.Percent(clamp(100-needDrop, 0, 100)), // 代謝は need だけ受ける
	}
}
```

### conditionDefs へ2種を足す

```go
ConditionExhaustion  ConditionType = "Exhaustion"  // 過労。疲労の量から導出
ConditionMalnutrition ConditionType = "Malnutrition" // 栄養失調。空腹の量から導出
```

いずれも painPerSeverity 0、bodyFuncDropPerSeverity 10、部位は全身。Tired/Hungry=Minor で 10、
Exhausted/Starving=Medium で 20。従来の疲労ペナルティ 25 は 20 へ寄せ重症度の刻みに揃える。実プレイで調整する。

### 統一リスト

Health タブは全身の見出しに `DerivedConditions` を並べ、怪我と同じ列で疲労・空腹を出す。need condition は
Timer を持たないので進行度でなく重症度を値に出し、治療状態は付けない。専用の統合リスト関数は今は要らないので
足さない。UI が全身の見出しでだけ `DerivedConditions` を差し込めば統一表示になる。

## 採用しなかった方法

- **保存 condition + 監視システム**: RimWorld 構造に最も近いが、量を保存 condition へ毎ターン同期する二重管理と、
  同期前に読むフレーム内 staleness が残る。read 時 materialize なら両方消える。
- **加算のまま**: 依存は最も浅いが RimWorld のなめらかな逓減を失い、全面 RimWorld 化の方針に反する。乗算へ戻す。
- **回復も意識へ載せる**: 痛み・注意力まで治癒に効く不自然さが出る。代謝を別 capacity に保つ。

## コメント

need を保存せず read 時に condition として materialize することで、RimWorld の「need も怪我も同じ condition」という
観測挙動を、同期漏れもフレーム内 staleness も無い形で再現する。量が唯一の真実で、condition はその読み取りビュー。
乗算へ戻すのは再スケールの漏れが `bodyFuncs` 内に封じられ消費側が不変になったため安全。
