# 食料の腐敗

## 背景

食料を早く取るインセンティブが無く、拾った食料を永遠に溜め込める。時間経過で食料が劣化し、やがて食べる価値を失う仕組みを入れて、次の2つを満たす。

- 早取りのインセンティブ。新鮮なうちに食べるほど得
- 溜め込み防止。放置した食料は栄養を失い、腐敗すると食べると害になる。溜める利点が消える

丸ごとの模倣はせず、ruins の既存基盤に載る最小形にする。

既存の足場:

- `GameTime.TotalTurns` が遺跡内で永続する総ターン数。1500 ターン/日、250 ターン毎に時間帯が変わる。腐敗の時刻基準に使う
- `Hunger` プールに `use_item.go` の `applyNutrition` が `hunger.Increase(栄養)` する。栄養は raw の `providesNutrition`
- 食料は `assets/metadata/entities/raw/raw.toml` に定義。`stackable` な食料が多い
- 体調の仕組みはまだ無い。腐敗食の体調悪化リスクは体調システムの実装後に効かせ、それまでは栄養3割だけを与える

## 要件

- 腐敗する食料は3段階で遷移する。新鮮 → 劣化 → 腐敗。腐敗が終端で、それ以上は変化しない
  - 新鮮: 栄養 100%
  - 劣化: 栄養 50%、無害
  - 腐敗: 栄養は3割。加えて体調悪化のリスクを持つ。体調システムは将来実装で、運次第で何も起きない。飢餓時の非常食としては使える
- 溜め込み防止はエンティティの撤去では行わない。腐敗すると栄養が大きく下がりリスクを伴うことで、溜める利点を消す。ゲームは持ち物を勝手に消さない
- 全ての食べ物は必ず腐敗する。永遠にもつ食料は存在させない。溜め込めると緊張感が消え、食料管理というゲーム要素が薄れるため。保存食は非常に長い保存期間を持つが、いずれ劣化する。`shelfLife` 省略、すなわち非腐敗、は武器など食べ物以外に限る
- 気温非依存の固定速度。寒冷・保存容器による減速は将来拡張
- セーブ/ロードで鮮度が保たれる
- 毎ターン全食料を走査しない。鮮度は参照時に遅延評価する

## 設計

### 時刻基準と遅延評価

各食料に生成時刻と保存期間を持たせ、鮮度は「現在の総ターン数 − 生成時刻 = 経過ターン」で都度求める。カウンタを毎ターン減算する走査を持たないため O(食料数)/ターンの負荷が無く、保存も int 2つで済む。

段階の境界は保存期間 `ShelfLife` の倍数で表す。

| 経過ターン | 段階 | 栄養倍率 |
|---|---|---|
| `[0, ShelfLife)` | 新鮮 | 1.0 |
| `[ShelfLife, 2*ShelfLife)` | 劣化 | 0.5 |
| `>= 2*ShelfLife` | 腐敗 | 0.3 ＋体調リスク |

腐敗が終端で、以降は状態も見た目も変わらない。倍率と倍数はバランス調整用の定数にする。例えばパンの `ShelfLife = 1500`、すなわち1日なら、1日目は新鮮、2日目は劣化、3日目以降は腐敗のまま残る。

### コンポーネント

```go
// Perishable は腐敗する食料が持つ。生成時刻と保存期間から鮮度を遅延評価する。
// 気温非依存の固定速度で、保存する値は consts.Turn だけなので serde 安全
type Perishable struct {
	SpawnedAtTurn consts.Turn // 生成時の GameTime.TotalTurns
	ShelfLife     consts.Turn // 新鮮でいられるターン数。これを基準に段階が決まる
}
```

```go
// FreshnessStage は鮮度の段階
type FreshnessStage string

const (
	FreshnessFresh  FreshnessStage = "fresh"  // 新鮮
	FreshnessStale  FreshnessStage = "stale"  // 劣化
	FreshnessRotten FreshnessStage = "rotten" // 腐敗
)

// Stage は経過ターンから鮮度段階を返す。now は GameTime.TotalTurns。
// 値レシーバで十分。int 2つしか持たず変更もしない
func (p Perishable) Stage(now consts.Turn) FreshnessStage {
	age := now - p.SpawnedAtTurn
	switch {
	case age < p.ShelfLife:
		return FreshnessFresh
	case age < 2*p.ShelfLife:
		return FreshnessStale
	default:
		return FreshnessRotten
	}
}
```

`consts.Turn` だけを持つため serde 安全。`skipComponents()` に入れず保存対象にする。GameTime と同じく遺跡内で永続する。撤去は行わないため `Expired` 相当の判定は持たない。

`SpawnedAtTurn` は生成時に必ず刻印される前提で、`Stage` はそれを刻印済みの値として扱う。ターン 0 に生成した食料の `SpawnedAtTurn` は 0 で、これは正当な値であり `Stage(0)` は新鮮を返す。0 を未刻印のセンチネルにはしないため `== 0` の特別扱いは持たない。未刻印のまま `Stage` を呼ばないことは、刻印を生成の一点に集約し、テストで担保する。

### raw スキーマと生成時の刻印

食料 raw に保存期間 `shelfLife`、ターン数、を追加する。全ての食べ物に付ける。省略、すなわち `Perishable` を付けない非腐敗、は武器など食べ物以外に限る。0 のような特別値は使わず、スキーマも `@minValue(1)` で正の値だけ受ける。保存食のビスケットは非常に大きい `shelfLife` にする。

腐敗の速さは食料ごとの `shelfLife` で決まる。生肉・魚は小さく、乾物や保存食は非常に大きくする。段階境界は `shelfLife` の倍数なので、小さいほど早く劣化・腐敗する。保存食も大きいだけで有限であり、いずれ腐敗する。食べ物ごとに腐敗のしやすさが違うのはこの1つの値で表す。

生成時刻はワールドの時計を読むため、raw→エンティティ変換では確定できない。変換では `shelfLife` を持つ食料に `Perishable{ShelfLife}` を載せ、`SpawnedAtTurn` は 0 のままにする。生成時に `Perishable` を持つエンティティへ `SpawnedAtTurn = GetGameTime(world).TotalTurns` を刻印する。全アイテム生成が通る `spawnItemBase` の1箇所で行う。`spawnItemBase` は `world` を受け取るため `GetGameTime(world)` で時計を引け、シグネチャは変えない。

### 食べる効果

`use_item.go` の `applyNutrition` を鮮度で分岐する。

- 新鮮: 従来どおり満額
- 劣化: 栄養 0.5 倍
- 腐敗: 栄養は満額の3割、`amount * 30 / 100`。加えて体調悪化のリスクを持つが、体調システムは将来実装のため今は栄養だけを与える。満腹をマイナスにはしない。マイナスだと捨てる一択になり腐敗食が選択肢にならないため

食べたゲームログには鮮度を添える。新鮮/古い/傷んだ を名前の前に出し、プレイヤーが何を食べたかを一目で分かるようにする。腐敗しない食料は鮮度を出さない。

鮮度補正は `applyNutrition` の内部で計算する。`applyNutrition` は既に `world` と `item` を受け取るため、`Perishable` と `GameTime` をそこから引けて引数は増えない。呼び出し元は素の栄養値を渡し、鮮度による補正と不調の適用は `applyNutrition` に閉じる。差し替え点が1箇所に収まる。

`Perishable` を持たない食料は従来どおり満額。栄養段階の算出は `Perishable.Stage(現在ターン)` に集約し、食べる処理と表示が同じ判定を通す。

将来 体調システムができたら、腐敗食の体調悪化リスクをそこに載せる。判定は `applyNutrition` の腐敗分岐1箇所に足す。運次第で何も起きない確率的な効果にする。

### 劣化のモデル

腐敗の進み具合は累積劣化量 `RotAccrued` で持つ。`Perishable{RotAccrued, StageLength, RotUpdatedTurn}` とし、`RotAccrued` が 0 の生成直後から、経過ぶんを速度で加えて進める。段階は `RotAccrued` の区間で決まる。新鮮 [0, StageLength) → 劣化 [StageLength, 2*StageLength) → 腐敗 [2*StageLength, )。

実効劣化量は `RotAccrued + (now - RotUpdatedTurn) * 速度` を読み取り時に算出する。走査は増やさず遅延評価のまま、速度を可変にできる。速度は `perishRate(world, entity)` に集約し、v1 は一律 1.0。将来、置き場所の温度でこの値を変える。冷所は遅く、暖所は速い。保存容器も同様。速度が変わる直前と合流の前に `AdvanceRot` で `RotAccrued` を現時点まで前進させ `RotUpdatedTurn` を揃えるので、経歴が変わっても実効値は正しく積み上がる。

生成直後は `RotAccrued = 0`、`RotUpdatedTurn = 生成時の総ターン`。これは旧案の `SpawnedAtTurn` と等価で、速度 1.0 のもとでは実効劣化量が経過ターンに一致する。

### スタックの合流

合流の同一判定は単一の述語 `query.StacksWith(world, a, b)` に集約する。非腐敗は RawID 一致で合流する。腐敗食は RawID 一致かつ現在の鮮度段階が同じときだけ合流する。トレランス付きの合流は同値関係にならないため、ハッシュキーでなく述語で表す。

同じ段階の束を合流するとき、劣化量 `RotAccrued` を個数で加重平均する。段階違いは合流させない。新鮮な束へ腐敗を混ぜて薄める抜け穴を防ぎ、束は常に段階が揃う。CDDA は連続した鮮度％のトレランスで平均するが、ruins は3段階の離散モデルなので段階一致をトレランスに使い、段階内で加重平均する。

当初は「鮮度が違うものを畳んで平均する案は採らない」としていたが、撤回する。厳密一致だと生成タイミングがずれた食料が別々の束に溜まり、CDDA が踏んだインベントリ肥大を再現するため。段階一致に緩め、段階内で加重平均することで、per-item 精度を段階の粒度で保ちつつ肥大を防ぐ。

合流は既存の在庫合流 `mergeStackableItems` に相乗りする。survivor へ出現順に畳み、どのエンティティが残るかを決定的にする。`FindStackableInInventory` は RawID だけで引く個数照会・消費の起点に徹し、鮮度による束の分割は `StacksWith` が一手に担う。腐敗食を除外していた特別分岐は廃した。同定を1箇所へ集約したので、属性が増えても合流処理へ特別扱いが漏れない。

腐敗食は鮮度段階の異なる束が複数ありうる。`FindStackableInInventory` は先頭の1束を返すため、段階違いが複数あるときの個数照会は過少になりうる。段階横断で総数を合算する照会は将来の改善余地とし、v1 は用途上ほぼ非腐敗の材料に限られるため据え置く。

### 表示

アイテムのメニュー行と詳細で鮮度を示す。

- 新鮮: 表示なし、または通常色
- 劣化: 「劣化」を色付きで添える
- 腐敗: 「腐敗」を警告色で添える

腐敗食は自動で消えないため、プレイヤーが状態を見て捨てるか食べるか判断できるよう、表示で鮮度を明確にする。表示は `query.FreshnessStageOf` を通し、食べる処理と判定を共有する。

## 採用しなかった方法

- **腐敗品を消滅、自動撤去、させる**: 腐敗のさらに先で食料を消す案。溜め込み在庫を機械的に片付けられるが、ゲームがプレイヤーの持ち物を勝手に消すのは理不尽に感じられ、うっかり撤去された不満を生む。腐敗食は栄養が下がりリスクを伴う状態で残し、捨てるか非常食にするかは player に委ねる。溜め込み防止は撤去でなく価値低下で満たす。撤去用の走査、`Expired` 判定、End フェーズ処理も不要になる
- **保存食を非腐敗、永遠にもつ、にする**: 保存食に `shelfLife` を付けず腐敗させない案。区分は単純だが、腐らない食料を溜め込めば緊張感が消え、食料管理というゲーム要素が骨抜きになる。同栄養なら非腐敗食が腐敗食の完全上位になり、生鮮を食べる理由も消える。全ての食べ物を有限の `shelfLife` にし、保存食は長くするだけにとどめる
- **2段階、新鮮→腐敗**: 実装は最軽量だが、劣化の緩衝が無く早取りの勾配が急。3段階で滑らかにする
- **連続劣化**: 栄養を経過で線形に減衰させる案。最も滑らかだが段階がプレイヤーに見えにくく、UI で鮮度を伝えづらい。離散3段階にする
- **毎ターンのカウンタ減算**: 各食料の残り時間を毎ターン減らす案。O(食料数)/ターンの走査が要る。生成時刻の遅延評価にして走査を消す
- **気温連動を v1 で作り込む**: 寒冷で腐敗を遅らせる挙動を v1 で入れる案。可動部が増えるため実装は見送る。ただしデータモデルは累積 `RotAccrued`＋`RotUpdatedTurn` にして温度可変に耐える形にし、速度は `perishRate` シームに集約した。将来はこの1関数を置き場所の温度で返すだけで済む。保存容器も同様
- **満腹をマイナスにして腐敗の不調を表す**: 腐敗食で満腹を下げる案。だが下がるだけなら捨てる一択になり、腐敗食が非常食という選択肢にならない。栄養3割は残し、悪影響は体調悪化リスクに寄せる
- **体調システムを腐敗のために先に作る**: v1 の範囲を超える。腐敗は栄養3割にとどめ、体調悪化リスクは体調システムの実装後に足す

## コメント

- 段階境界の倍数と栄養倍率、各食料の `shelfLife` は balance で調整する前提。まずは仮値で通し、プレイして詰める
- 劣化の起点 `RotUpdatedTurn` の刻印を生成経路ごとに散らすと漏れやすい。刻印を1箇所にして、新しい生成経路が増えても担保する
- 腐敗の栄養割合、今は3割、と将来の体調悪化リスクの確率・強さは仮値。プレイして詰める
