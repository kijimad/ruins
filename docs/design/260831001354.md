# コード監査: 装填中断・季節進行・体温HUD・クラフト整合 2026-08-31

## 背景

golangci-lint による静的検査が手厚いリポジトリのため、forcetypeassert・errcheck・nilerr/nilnil・exhaustive・makezero 等の機械検知漏れを補う目的で、internal 配下を6系統（体温/HUD、継続アクティビティ、戦闘/AI/数式、セーブ/serde、アイテム/装備/クラフト、UI/キーバインド）に分けて並列で横断的に精読した。lint がパターンとして捕まえられない、コードの意図と実装のズレを読み解いた誤りだけを対象にしている。

過去の監査doc（`260803144226.md`・`260810001803.md`・`260817001843.md`・`260824001220.md`）は事前に通読し、既出の問題は再度挙げていない。戦闘/AI/数式・セーブ/serde・UI/キーバインドの3系統は敵対的検証の結果、確信を持って報告できる新規の問題が無かったため0件だった。

以下4件を、いずれも実コードを直接確認し失敗シナリオを具体化したうえで報告する。修正はこの doc の範囲外とし、着手は人が取捨選択する。

## 問題1: `ReloadBehavior` だけが継続アクティビティ共通の周囲安全チェックを欠き、装填中に敵の接近へ無反応になる

**file:line**: `internal/activity/reload.go:54-73`（`Validate`）、`:84-126`（`DoTurn`）

**症状**: 複数ターンにまたがる継続アクティビティは `Validate` と `DoTurn` の両方で `isAreaSafe`（`internal/activity/activity.go:210`）を検査し、敵が周囲に現れたら即座に `Cancel` して中断する契約になっている。実際に休息 `rest.go:46,66`、読書 `read.go:81,123`、分解 `disassemble.go:74,116`、待機 `wait.go:64`（`Progress.Max>1` の場合）はいずれもこの検査を持つ。ところが装填 `ReloadBehavior` の `Validate`・`DoTurn` にはこの検査が一切無い。

**根拠・失敗シナリオ**: `NewReloadActivity`（`reload.go:45`）は必要工数を装備中の遠距離武器の `ReloadEffort` からそのまま設定し、`calcEffortPerTurn`（`reload.go:144`）は基本工数 `BaseReloadEffort=10` にDEXと武器スキルレベルを加算した値を1ターン分として消費する。DEX・スキルが低い序盤キャラでは `ReloadEffort=40` 程度の武器で4ターン以上かかる。この間に敵がプレイヤーへ隣接接近しても、`ReloadBehavior.DoTurn` は装填処理だけを行い中断判定をしないため、プレイヤーは無防備なまま装填を続け、実際に攻撃を受けて `CanInterrupt` 経由の割り込みが発生するまで危険に気づく手段が無い。`reload_test.go` にもこの経路のテストは無い。

**根拠**: lint は「同種のBehavior群に共通する防御パターンの欠落」を検知できない。休息・読書・分解・待機の4つが同一ヘルパー `isAreaSafe` を呼び、装填だけが呼ばないという意図と実装の食い違いは、契約を理解して初めて分かる。

**修正方針案**: `Validate` と `DoTurn` の冒頭に他の継続系と同じ `if !isAreaSafe(actor, world) { ... }` ガードを追加し、`&UserError`／`Cancel` パターンに揃える。

## 問題2: `AdvanceToNextSeason` が `noonOffsetFromDawn` を考慮せず、特定のターン範囲では季節が進まない

**file:line**: `internal/components/game_time.go:196-198`（`AdvanceToNextSeason`）、呼び出し元 `internal/states/debug_menu.go:108`

**症状**: デバッグメニューの季節送りが、呼んだタイミングによっては実際には季節を変えない。

**根拠・失敗シナリオ**: `turnsPerSeason = 12000`（`daysPerYear/4 * turnsPerDay`）に対し、`AdvanceToNextSeason` は `(TotalTurns/turnsPerSeason + 1) * turnsPerSeason` で単純に12000の倍数へ丸める。一方、実際に表示される季節 `GetSeason()` は `GetDayNumber()`（`(TotalTurns+noonOffsetFromDawn)/turnsPerDay + 1`、`noonOffsetFromDawn=500`）から導かれ、季節境界は `12000*k - 500` の位置にある。このため `TotalTurns` が `[11500, 12000)` の範囲、すなわち各季節周期の最後の500ターン区間でこの関数を呼ぶと、丸め先の `12000*k` はまだ同じ季節に属し `GetSeason()` の戻り値が変化しない。実際に検算すると `TotalTurns=11700` から呼んでも季節は変わらず、もう一度呼んでようやく次の季節になる。この区間は季節周期の約4.2%を占め、周期ごとに繰り返す。

**根拠**: lint は数値計算のオフセット不整合を検知できない。既存の単体テスト `TestGameTime_AdvanceToNextSeason_季節を1つ進める` は `TotalTurns=0` から始まり常に `12000` の倍数を経由するため、このズレを踏まずに通ってしまう。

**修正方針案**: `AdvanceToNextSeason` も `noonOffsetFromDawn` を考慮した次の季節境界 `k*turnsPerSeason - noonOffsetFromDawn` を計算して設定する。あるいは `GetSeason()` の戻り値をループで確認しながら1日ずつ進める実装に変え、`GetSeason()` を唯一の判定源にする。

## 問題3: 体温ゲージの塗り色が旧・双方向設計のままで、平熱かつ満タン状態が「火照り」の赤で表示される

**file:line**: `internal/widgets/hud/game_info.go:136`（`drawBodyTemperature` のdocコメント）、`:146-152`（`bodyTempFillColor`）

**症状**: 新規キャラクター開始直後など、体温が平熱で `BodyTempRatio == 1.0` のとき、体温ゲージが `HUDTempHot` の赤一色で塗られる。

**根拠・失敗シナリオ**: `BodyTempOffset` は「0が平熱かつ上限、寒さで負へ動く」設計（`internal/components/health_status.go:219`）で、高体温方向は既に廃止されている。`bodyTempRatio`（`internal/systems/hud_extractor.go:63`）は `(offset-bodyTempMin)/(bodyTempMax-bodyTempMin)`、`bodyTempMin=-5.0`・`bodyTempMax=0.0`（`internal/systems/temperature.go:88-90`）で計算され、`offset=0`（平熱）のとき `ratio=1.0` になる。ところが `bodyTempFillColor(ratio)` は `ratio>=0.5` を無条件で `lerpColor(Neutral, Hot, (ratio-0.5)*2)` へ寄せる旧・双方向ロジックのままで、`ratio=1.0` は補間係数1.0の完全な `HUDTempHot` になる。つまり体温が最も健康な状態が、見た目には最も危険な高体温であるかのように表示される。`drawBodyTemperature` のdocコメント（136行目「中央が平熱で、左へ冷え、右へ火照る」）も同じ旧設計を指したままで、実装とコメントの両方が現行の片方向設計に追随していない。

**根拠**: 色計算のロジック誤りで、golden画像テスト（`internal/states/testdata/TestGolden_Dungeon.png`）は差分が固定されていれば通るためこのまま固定化されており、lint・型・エラー処理では検知できない。

**修正方針案**: `bodyTempFillColor` を「`ratio=1` で `HUDTempNeutral`、`ratio` が下がるほど `HUDTempCold` へ寄る」片方向補間に直し、`HUDTempHot` への分岐を削除する。あわせて `drawBodyTemperature` のdocコメントも片方向設計の説明に書き直す。

## 問題4: `Craft` が素材消費より先に完成品を生成しており、`CraftCost` が100%を超えると素材消費に失敗しても完成品だけが残る

**file:line**: `internal/world/gameaction/craft.go:17-44`（`Craft`）、`:47-65`（`CanCraft`）、`:69-78`（`consumeMaterials`）

**症状**: クラフトがエラーで失敗しても、生成済みの完成品がプレイヤーの所持品に残ったままになりうる。

**根拠・失敗シナリオ**: `CanCraft`（54-61行目）はレシピの `recipeInput.Amount` をそのまま所持数と比較して可否判定する。しかし実際の消費量は `consumeMaterials` 内で `craftCostPct.ApplyInt(recipeInput.Amount)`（71行目）と `CraftCost` 倍率がかかった値になる。`CraftCost`（`internal/components/modifiers.go:215`）は `SkillCrafting` レベルにつき-3%、加えて対応する能力値DEXを同じ符号で加算する式（`ablCoeff=-1` のため `bonus += -DEX`）で決まり、100を超えないようクランプする処理は無い。DEXが負に振れれば `CraftCost` は100%を超えうる。実際に装備品には `dexterity = -2` 等の負のボーナスが存在し（`assets/metadata/entities/raw/raw.toml:2897` ほか）、`consts.Percent.ApplyInt`（`internal/consts/percent.go:19`）もクランプせずそのまま倍率をかける。`CraftCost>100%` の状態でクラフトすると、`consumeMaterials` が `CanCraft` の確認した量より多い量の消費を試み、在庫がちょうど必要数しか無い場合は `ChangeStackCount` が不足エラーで失敗する。しかし `Craft`（34行目）はその前に `SpawnBackpackItem` で完成品を既に生成・付与しており、39-41行目で `consumeMaterials` が失敗してもロールバックせずエラーを返すだけ。呼び出し元 `craft_menu.go:206-209` もエラーをそのまま表示するだけで生成済みエンティティを削除しない。結果、素材はそのまま残り完成品だけが手元に増える。

**根拠**: lint は「生成→消費」の順序や、判定に使う量と実消費量の食い違いという意味論的な不整合を検知できない。同じパッケージ内の `gameaction/shop.go` は `BuyStock`/`SellStock` で移動・支払い失敗時に明示的なロールバックを行っており、「失敗時に整合を戻す」規約が `Craft` だけ欠けていることも裏付けになる。`craft_test.go` にも `CraftCost>100%` のケースの検証は無い。

**修正方針案**: `consumeMaterials` を `SpawnBackpackItem` より先に実行する。あわせて `CanCraft` の判定も `craftCostPct` を含めた実消費量で行うよう揃える。それでも消費が失敗しうる経路が残るなら、`consumeMaterials` 失敗時に生成済みエンティティを `RemoveEntity` でロールバックする。
