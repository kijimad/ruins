# コード監査: ダンジョン生成・リロード・セーブ 2026-08-03

## 背景

自律コード監査ルーチンにより `internal/` 配下を横断的に精読した。golangci-lint（forcetypeassert・errcheck・nilerr/nilnil・exhaustive・makezero 等）が既に手厚く効いている前提で、機械的に捕まえられる問題は対象外とし、コードの意図と実装のズレを人手で追った。

並列で6系統に分けて精読し、各候補は敵対的に自己検証した。反証できず、具体的な失敗シナリオを再現できたものだけを以下に残す。修正はしていない。取捨選択はレビューに委ねる。

## 問題

### 1. `RectRoomPlanner` の部屋境界が1タイル大きく、`RoomDraw` が隣接行の左端タイルを誤って床にする

- **file:line**: `internal/mapplanner/rect_room.go:32,49`（原因）、`internal/mapplanner/room_draw.go:24-25`（発現箇所）
- **症状**: マップ上、部屋とは無関係な行の左端列（column 0）に孤立した床タイルが生まれる。
- **失敗シナリオ**: `gc.Rect` は「Max が右下の隅」という inclusive な規約（`internal/components/field.go:28` のコメント、および `big_room.go`・`ruins_planner.go` が一貫して採用する `width-1`/`height-1`）を持つ。ところが `RectRoomPlanner.createRoom`（49行目）だけは `Max.X = consts.Tile(min(x+w, width))` と `-1` を付けずに算出している。部屋が右端付近（`x+w >= width`）にランダム生成されると `Max.X == width` になる。下端固定部屋を作る32行目の `bottomRoom` も同じ誤りを持つ（`Max.X = min(bottomX+bottomW, width)`、`Max.Y = height` とどちらも `-1` なし）。`RoomDraw.rectangle` は `x <= room.Max.X` という inclusive ループで描画するため、本来存在しない列 `x == width` に到達する。`Level.CoordToIndex`（`internal/components/dungeon.go:114-116`）は範囲チェックをしない単純な `y*width+x` 計算なので、`idx = y*width + width = (y+1)*width + 0` となり、**次の行の column 0** に折り返って書き込まれる。`room_draw.go:27` の境界チェックは配列外アクセス（panic）は防ぐが、この折り返し自体は正当な範囲内インデックスなので素通りする。`RectRoomPlanner`＋`RoomDraw` は `NewSmallRoomPlanner`（`lib.go:337-350`）で使われ、複数ダンジョンタイプの `plannerPool` に重みつきで登録されている（`internal/dungeon/registry.go`）ため、通常プレイで到達しうる。
- **修正方針案**: `rect_room.go:32`（`bottomRoom`）と `rect_room.go:49`（`createRoom`）の両方の `Max` 算出を、他の部屋生成コード（`big_room.go:18`、`ruins_planner.go:32`）と同じ `min(x+w, width) - 1` / `min(y+h, height) - 1` に揃える。あわせて `RectRoomPlanner` の単体テストに「右端/下端付近に生成された部屋の `Max` が `width-1`/`height-1` を超えない」検証を追加する。

### 2. ~~`ReloadBehavior` の装填工数が Execute とターン進行のあいだで引き継がれず、複数ターンかかるリロードが弾薬を装填せずに終わる~~ → 別件で解消済み

検出時点（起票コミット時の main）では、`ExecuteReloadAction` が生成するローカルな `&ReloadBehavior{}` インスタンスと、`ProcessContinuousActivities` が `GetBehavior` 経由で取得するシングルトンインスタンスとで、装填工数を積むフィールド `effortAccum` が別々になっており、複数ターンかかるリロードが工数を引き継げず弾薬を装填しないまま完了する不具合があった。

本 PR のレビュー中に base ブランチが進み、PR #579（継続処理を registry シングルトンに一本化し Reload の並行装填バグを直す、`docs/design/20260802_84.md`）で独立に検出・修正済みであることを確認した。現在の `internal/activity/reload.go` は工数の蓄積先を `gc.Activity.Progress.Current`（ECS 側の永続データ）に一本化しており、インスタンスフィールドに進捗を持たない設計に変わっている。このため本項目は追加対応不要。検出したこと自体の記録として残す。

### 3. `RestoreWorldFromJSON` が検証完了前に `world.ECS.Reset()` するため、ロード失敗がアプリ全体のクラッシュに波及する

- **file:line**: `internal/save/manager.go:92-123`
- **症状**: セーブファイルのチェックサム・バージョン検証を通過した後の復元処理（`deserializeWorld`／`reestablishSingleton`／`validateStages`）のいずれかが失敗すると、ロード画面のエラー表示では済まず、アプリケーションが `log.Fatal` で終了する。
- **失敗シナリオ**: `RestoreWorldFromJSON` はチェックサム・バージョン検証の後、`deserializeWorld` を呼ぶ**前**に `world.ECS.Reset()`（`manager.go:107`、ark-serde の要求）を実行する。この後段の3関数のいずれかがエラーを返しても、既にワールドは破棄済みでロールバック手段がない。呼び出し元 `internal/states/factories.go` の `addLoadSlot` はエラーをそのまま choice のアクションから返す。この戻り値は `messagewindow.Window.selectChoice`（`internal/widgets/messagewindow/window.go:668-671`）→ `MessageState.Update` → `StateMachine.Update` → `MainGame.Update`（`internal/maingame/game.go:59-61`）とそのまま伝播し、`ebiten.RunGame` がエラーを返した先の `internal/cmd/play.go:129-131` も `return err` するため、最終的に `main.go:20-23` の `log.Fatal(err)` に到達し、プロセス全体が終了する。到達条件（チェックサム・バージョンは通るが復元は失敗する状態）は `manager_test.go` の `TestRestoreWorldFromJSON_MissingSingleton` で実際に再現されており、「エラーが返ること」はテストされているが「その後アプリが継続できるか」は検証されていない。手編集されたセーブファイルや、`saveDataVersion` を上げ忘れたままのコンポーネント変更で踏みうる。
- **修正方針案**: `world.ECS.Reset()` の前に一旦別の一時ワールド、または deserialize 可能かどうかを検証してから本番の `world` に適用する二段階に分ける。最低限、`RestoreWorldFromJSON` 失敗時に呼び出し側が `log.Fatal` まで到達しないよう、ロード失敗はメッセージ表示のみに留めてアプリを継続させる。なお二段階検証は ark-serde 側が Reset 済みワールドを要求する API 制約上、一時ワールドでの試行が難しい可能性がある。その場合は「呼び出し側が `log.Fatal` まで到達しない」フォールバックのみを採用する。

### 4. ロード後、`CharModifiers.Sources`（効果内訳の表示用データ）が再計算されず空のまま残る

- **file:line**: `internal/save/serde.go:39,74-111`（`skipComponents`/`reestablishSingleton`）、`internal/components/modifiers.go:158-164`、`internal/systems/stats_changed.go:23-30`
- **症状**: セーブをロードした直後、ステータス詳細画面の効果内訳（「刀剣 Lv2」のような算出根拠の表示）が空になる。数値そのもの（`WeaponAccuracy` 等の倍率）は正しく復元されるため、プレイに支障はないが表示だけが欠落する。
- **失敗シナリオ**: `CharModifiers.Sources` は `json:"-"` で除外され、コメントは「派生データのためserde対象外とし、ロード時は再計算する」（`modifiers.go:163`）と意図を明記している。しかし実際に `Sources` を含む `CharModifiers` を再計算するのは `StatsChangedSystem`（`stats_changed.go:101` の `RecalculateCharModifiers` 呼び出し）のみで、これは `gc.StatsChanged` ダーティフラグが立ったエンティティにしか発火しない。ところが `StatsChanged` 自体も `skipComponents()`（`serde.go:39`）でserde除外されており、`reestablishSingleton`（`serde.go:74-111`）は `GameLog`/`SpatialIndex`/`VisionState` は再構築するが、`StatsChanged` を全エンティティへ再付与する処理を持たない。そのためロード後、攻撃・読書・解体・体温変化など何らかの操作で自然に `StatsChanged` が付与されるまで、`Sources` は `nil` のまま画面に表示され続ける。
- **修正方針案**: `reestablishSingleton` の末尾で、`Abilities`・`Skills` を持つ全エンティティに `StatsChanged` を付与し、ロード直後に `StatsChangedSystem` が走るようにする。あるいはロード完了時に `RecalculateCharModifiers` を直接呼んで `CharModifiers` を再構築する。

### 5. `raw.ValidateReferences` が一部の参照だけを検証しておらず、ロード時ではなく実行時に初めて設定ミスが露見する

- **file:line**: `internal/raw/validate.go:44-57`（`ValidateReferences`）
- **症状**: `ItemTable.Entries[].GroupName → ItemGroup`、`ItemGroup.Entries[].ItemName → Item`、`EnemyTable.Entries[].EnemyName → Member`、`CommandTable.Entries[].Weapon → Item` の参照にタイプミス等があっても、`raw.LoadFromFile` はエラーなく成功する。
- **失敗シナリオ**: `ValidateReferences`（`validate.go:44-57`）は `validateDisassemblyReferences`・`validateDropTableReferences`・`validateSpawnDice`・`validateCommandTableReferences`（Member→CommandTable の存在のみ）は呼ぶが、上記4種の参照には対応する検証関数が無い。コメントは「実行時の解決失敗をロード時エラーに前倒しする」ことを目的として明記しているため、これは対称性を欠く。例えば `ItemTable.groupName` のタイプミスは、実際にその ItemTable を参照する収納 prop が生成されるタイミング（`internal/mapspawner/spawner.go` の `populateStorageLoot`）で初めて `GetItemGroup` のエラーとしてフロア生成全体を失敗させる。`CommandTable.Weapon` のタイプミスは `internal/activity/attack.go` の `getAttackParams` がエラーを素手攻撃へフォールバックして握り潰すため、設定ミスがログにすら残らず静かに劣化する。いずれもロード時に一括検出できていれば防げる。
- **修正方針案**: `validateItemTableReferences`・`validateItemGroupReferences`・`validateEnemyTableReferences`・`validateCommandTableWeaponReferences` を追加し、既存の `validateDropTableReferences` 等と同様に `ValidateReferences` から呼ぶ。
