# タイルを指すオーバーレイを3D投影へ一本化する

## 背景

ダンジョンの世界描画は `Render3DSystem` のローポリ3Dに置き換わった。`DungeonState.Draw` は
`dungeon3D.draw` で世界レイヤを描き、`RenderSpriteSystem` の真上視点2D描画はダンジョンでは
もう通らない。通るのはマップ生成デバッグの `MapGenVisualizerState` だけである。

ところが「タイルを指す」描画は2Dカメラ変換のまま残っている。`gs.SetTranslate` は
`Camera.Pos` と `Camera.Scale` による平行投影で、3Dの透視投影とも Yaw 回転とも無関係である。
そのため射撃の照準、観察のカーソル、ダメージテキストなどが実際のタイルからずれた位置に出る。

### ずれている箇所

| 箇所 | 描くもの | 現在の変換 |
| --- | --- | --- |
| `internal/states/shooting.go:241` | 射撃の照準カーソル | `gs.SetTranslate` |
| `internal/states/look_around.go:164` | 観察のタイルカーソル | `gs.SetTranslate` |
| `internal/systems/visual_effect.go:192` | ダメージテキスト | `gs.SetTranslate` |
| `internal/systems/visual_effect.go:284` | 撃破時の白シルエット | `gs.SetTranslate` |
| `internal/systems/hud_extractor.go:153` | AI状態テキスト・視界円 | `consts.WorldToScreen` |
| `internal/systems/hud_extractor.go:202` | 敵のHP表示 | `consts.WorldToScreen` |

`hud_extractor` の2件はデバッグオーバーレイ限定で、`DebugOverlay.enabled` が偽なら描かれない。
残り4件は本番のプレイで常に見える。

### ずれの実測

既定カメラ `Yaw=0, Pitch=0.62, Dist=16`、画面 960x720、プレイヤーがタイル (25,25) にいるとき、
あるタイル中心の投影先を両方式で比べる。ゴールデン `TestGolden_LookAround` と同じ条件である。

`Camera.Scale` は 0.8 を使う。`spawn.go` の初期値 `cameraNormalScale = 0.6` は
`CameraSystem.Update` の下限クランプ 0.8 を下回るため、最初の1フレームで 0.8 へ引き上げられる。
初期値 0.6 はどのフレームでも観測されない死んだ値で、これ自体も整理の候補である。

```
=== Yaw=0度 / Camera.Scale=0.8 ===

  (25,25)  ( 480.0, 374.8)  ( 480.0, 360.0)   14.8px      46.6px        25.6px
  (26,25)  ( 525.5, 374.8)  ( 505.6, 360.0)   24.8px      46.6px        25.6px
  (30,25)  ( 707.4, 374.8)  ( 608.0, 360.0)  100.5px      46.6px        25.6px
  (20,30)  ( 176.6, 556.1)  ( 352.0, 488.0)  188.2px      62.8px        25.6px
  (25,15)  ( 480.0, 193.9)  ( 480.0, 104.0)   89.9px      30.8px        25.6px

=== Yaw=45度 / Camera.Scale=0.8 ===
  (25,25)  ( 480.0, 374.8)  ( 480.0, 360.0)   14.8px      32.2px        25.6px
  (25,24)  ( 511.1, 356.3)  ( 480.0, 334.4)   38.0px      32.2px        25.6px
  (30,25)  ( 675.4, 491.5)  ( 608.0, 360.0)  147.8px      47.9px        25.6px
  (20,30)  ( 158.5, 374.8)  ( 352.0, 488.0)  224.2px      20.3px        25.6px
  (25,15)  ( 717.4, 233.0)  ( 480.0, 104.0)  270.2px      30.1px        25.6px
```

2D側の数値はゴールデン画像の実測と一致する。`TestGolden_LookAround.png` のカーソル枠は
中心 (479.5, 359.5)、外形 26x26 px で、上表のプレイヤータイル行 (480.0, 360.0)、幅 25.6px に合う。
モデルが現物を再現できているので、3D側との差分もそのまま実機のずれとみなせる。

読み取れることは3つある。

1. **プレイヤー自身のタイルでも 14.8px ずれる**。3Dのカメラ注視点は `y=0.4` の高さにあり、
   地面 `y=0` は画面中心より下に落ちる。2D変換はカメラ位置を必ず画面中心に置くので、
   この分だけ常時ずれる。ゴールデン画像 `TestGolden_LookAround.png` でカーソル枠が
   プレイヤーの頭側へ寄って見えるのはこれである
2. **離れるほどずれが増える**。5タイル横で100px、斜め5タイルで188px。タイル1枚が画面上で
   46.6px なので、2タイルから4タイル分ずれて別のタイルを指すことになる
3. **回転すると方向ごと壊れる**。2D変換に Yaw が無いので、カメラを45度回すと上下左右の
   対応が崩れる。観察カーソルは右キーで画面の右へ動かず、射撃の照準は別の敵の上に出る

さらに大きさも合っていない。3Dのタイルは透視で 20〜63px と可変なのに、カーソル画像は
`consts.TileSize * Camera.Scale` の固定 25.6px で、プレイヤー自身のタイルですら一致しない。

### 根本原因

投影の一次情報が `Render3DSystem` の非公開フィールド `Yaw/Pitch/Dist` にあり、その持ち主
`dungeon3D` は `DungeonState.three` という非公開フィールドである。`ShootingState` と
`LookAroundState` は `DungeonState` の上に積まれる別の state で、`VisualEffectSystem` と
`HUDExtractor` は systems 側にいる。どちらからも3Dのカメラへ手が届かない。

届かないので、届く唯一の変換である2Dカメラを使い続けている。ずれの直接の原因は
「2D変換を呼んでいること」だが、構造上の原因は「タイル座標からスクリーン座標への変換が
2系統あり、正しいほうが到達不能な場所にあること」である。個々の呼び出しを差し替えるだけでは、
次にタイルを指す描画を足したときに同じことが起きる。

## 要件

- タイルを指すオーバーレイが、3Dで実際に描かれた位置と大きさに一致する
- カメラを回転・ズームしても一致が保たれる
- タイル座標からスクリーン座標への変換が1箇所にあり、state からも systems からも呼べる
- 変換が純関数として単体テストできる。3Dの `Draw` を通さずに投影先を検証できる
- 真上視点2D描画を使う `MapGenVisualizerState` は壊さない

## 設計

### 投影の一次情報を Camera へ移す

3Dオービットカメラのパラメータを `Render3DSystem` の所有から外し、ECS の `Camera` へ移す。
`Camera` はプレイヤーエンティティに1つだけ載るカメラで、`getCamera` で誰からでも引ける。
視点の一次情報が1箇所に集まり、描画側と参照側が同じ値を読む形になる。

```go
// internal/components/components.go
// 変更前
type Camera struct {
	// ズーム率
	Scale   float64
	ScaleTo float64
	// カメラ位置。ワールド空間のピクセル単位
	Pos    consts.Coord[consts.WorldPixel]
	Target consts.Coord[consts.WorldPixel]
}

// 変更後
type Camera struct {
	// Scale/ScaleTo/Pos/Target は真上視点2D描画のカメラ。マップ生成ビジュアライザが使う
	Scale   float64
	ScaleTo float64
	Pos     consts.Coord[consts.WorldPixel]
	Target  consts.Coord[consts.WorldPixel]

	// Orient はカメラの向きを45度刻みで表す0-7。水平角の一次情報で、移動キーの向き解決にも使う
	Orient int
	// Pitch は見下ろし角、Dist は注視点からの距離。右ドラッグとホイールで動かす
	Pitch, Dist float64
}

// Yaw は水平角をラジアンで返す。Orient から導出するので、両者がずれることはない
func (c Camera) Yaw() float64 { return float64(c.Orient) * (math.Pi / 4) }
```

`Yaw` はフィールドにしない。現在 `Yaw` へ代入しているのは `dungeon3D.rotate` の
`d.sys.Yaw = float64(d.orient) * (math.Pi / 4)` 一箇所だけで、値は常に `Orient` の従属変数である。
両方を持つと同じ情報が2箇所に生まれ、片方だけ更新した瞬間に世界描画とオーバーレイが食い違う。
本設計はまさにその食い違いを消すためのものなので、ここで新しい二重管理を作らない。
将来スムーズ回転を入れるなら、そのとき `Yaw` を一次情報へ昇格させ `Orient` を導出側へ倒す。

`Render3DSystem` の `Yaw/Pitch/Dist` フィールドは削り、`buildScene` は `getCamera(world)` から
読む。`dungeon3D` の `orient` も `Camera.Orient` へ移し、`rotate` と `moveDir` はそこを読む。
`dungeon3D` に残るのは3D固有の入力状態、すなわち右ドラッグ中かを示す `dragging` と `lastCurY`
だけになる。

`Camera` は serde 対象なので、カメラの向きとズームがセーブに乗る。セーブは破壊的に移行し、
旧フォーマットとの後方互換は持たない。`Camera` は spawn が既定値で生成し、見下ろし角と距離は
入力ハンドラが毎フレーム可動域へクランプ、向きは45度刻みで巡回させる。したがってセーブに
乗る3D値は常に可動域内で、ロード時や投影時の正規化は要らない。

### 投影 seam を独立した package に置く

タイル座標からスクリーン座標への変換を、`internal/render3d` package の `Projector` に集約する。
`systems` はECSシステムを置く package なので、そこへ座標変換を同居させると、カーソルを描く
`states` が変換のためだけに `systems` を import することになる。幾何は幾何だけの package に分ける。

`Render3DSystem` は `systems` に残す。視界の明暗 `computeTileRenderMap` と寒波前線の
`frostAlpha` に依存しており、レンダラごと移すと `systems` との相互参照になるためである。
移すのは純粋な幾何と、壁の高さに関する述語だけにする。
`Render3DSystem.buildScene` が組む行列と同じものを、同じ入力から組み直す純関数にする。
毎フレームの行列を共有メモリへ書き戻す方式は採らない。書き戻すと「今フレームで誰が先に
描いたか」に結果が依存し、state の積み順を壊した瞬間に静かにずれるためである。

幾何そのものは world を知らない純関数にし、world から値を集める入口を別に置く。
こうすると行列のテストがワールド構築なしで書ける。

```go
// internal/render3d/projector.go 。world を知らない純粋な幾何
func NewProjector(orbit gc.Camera, center consts.Coord[consts.Tile], sw, sh int) Projector

// internal/render3d/world.go 。world から値を集める入口
// 画面寸法は引数で受けず world から読む。呼び出し側ごとに寸法の取り方が分かれると、
// 世界レイヤと重ねるレイヤが違う行列を持ち、片方だけ静かにずれる余地ができる。
// 投影の入口を1つにする以上、その入力も1つに絞る。
// カメラが無ければ既定の視点で組む。投影を諦めるとカーソルが消え、位置がずれるより
// 分かりにくい壊れ方になる。
func ProjectorFor(world w.World) Projector

// TileCenter はタイル中心をスクリーン座標へ写す。height はタイル上面の高さで、床は0、壁は
// WallHeight を渡す。カメラ後方なら ok=false。
func (p Projector) TileCenter(c consts.Coord[consts.Tile], height float64) (consts.Coord[consts.ScreenPixel], bool)

// TileCorners はタイルの四隅を高さ y でスクリーン座標へ写す。並びは北西・北東・南東・南西。
// 透視で台形になるので、タイルを囲う枠はこの4点を結んで描く。4隅すべて投影できたときだけ ok。
func (p Projector) TileCorners(c consts.Coord[consts.Tile], height float64) ([4]consts.Coord[consts.ScreenPixel], bool)

// BillboardTop はタイル上の立て板の頭をスクリーン座標へ写す。エンティティの上に出す
// ダメージテキストやHP表示の基準点にする。
func (p Projector) BillboardTop(c consts.Coord[consts.Tile]) (consts.Coord[consts.ScreenPixel], bool)
```

`buildScene` の行列組み立てを `NewProjector` へ切り出し、`buildScene` はそれを呼ぶ。
これで世界描画とオーバーレイが同じコードを通り、片方だけ直して片方が取り残される形を消す。

### カーソルは四隅を結ぶ線で描く

透視投影のタイルは画面上で台形になる。正方形画像を貼ると、どこに置いても形が合わない。
`TileCorners` の4点を `vector.StrokeLine` で結ぶ枠に変える。`shootingCursorCache` と
`cursorImageCache` の `sync.Once` 画像キャッシュは不要になるので消す。
点滅は線の色のアルファで表現し、`DisableAnimation` の分岐は今のまま残す。

観察カーソルと射撃照準は太さと色が違うだけなので、枠を描く処理は
`internal/widgets/hud` へ `TileFrame(screen, corners, width, color)` として置き、両者から呼ぶ。

#### 壁タイルは天面に描く

`LookAroundState.moveCursor` はマップ範囲しか見ないので、カーソルは壁タイルへも乗る。
壁は3Dでは高さ `r3wallHeight = 1.0` の箱として描かれるため、地面 `y=0` に枠を描くと箱の中へ
沈み、壁に隠れて見えなくなる。位置を直しても見えないのでは修正になっていない。

`TileCorners` は高さを引数に取り、呼び出し側が `TileTopHeight` で決めた高さを渡す。

どのタイルが箱になるかの判定は `IsWallTileEntity` 1つに集約する。箱を積む `collectTiles` と、
タイルを指す `TileTopHeight` が同じ述語を通ることで、認識が2箇所に分かれない。投影の二重管理を
消すのが本設計なので、その隣に壁ジオメトリの二重管理を作らない。

判定は `Tile` と `BlockPass` を併せ持つことである。`SpatialIndex.IsBlockPass` は扉やキューブも
拾うが、それらは箱にならないので流用してはいけない。ただし通行できるタイルは箱にもならないので、
索引で先に落として全走査を避ける。

#### カメラ後方と画面外

`emitQuad` は4頂点のうち1つでも投影できなければクアッドごと捨てる。同じ規則を `TileCorners`
にそのまま持ち込むと、カメラのすぐ足元のタイルで枠が丸ごと消え、点滅して見える。
`TileCorners` は「4隅すべて投影できたときだけ ok」とし、ok=false のときカーソルを描かないのは
そのままでよいが、その状態が実際に起きるのは注視点の背後だけである。既定カメラの `Pitch` 範囲
0.15〜1.45 と `Dist` 範囲 3〜25 で足元タイルが後方へ回るかは、実装時に `Projector` の
単体テストで境界を固定して確認する。回るなら枠の描き方でなくカメラの下限側を調整する。

### 呼び出し側の書き換え

| 箇所 | 変更後 |
| --- | --- |
| `shooting.go` の照準 | `TileCorners` + 枠線。カメラ後方なら描かない |
| `look_around.go` のカーソル | 同上 |
| `visual_effect.go` のダメージテキスト | `BillboardTop` を基準に、`Offset` を画面座標のまま足す |
| `visual_effect.go` の白シルエット | `BillboardTop` と `TileCenter` の差から立て板の高さを求め、その倍率で拡大して中央に置く |
| `hud_extractor.go` のAI状態・HP・視界円 | `BillboardTop` / `TileCenter`。視界円の半径は `TileCenter` 同士の距離から求める |

`consts.WorldToScreen` は `hud_extractor` からの参照が消え、真上視点2Dのミニマップ側だけが残る。

ダメージテキストの `Offset` は挙動が変わる点に注意する。現在は `Offset` をワールドピクセルへ
足してから `SetTranslate` を通すので、浮き上がり量に `Camera.Scale` が掛かっている。
`Offset.Y` は `DamageTextEffect.Update` が毎フレーム `VelocityY` を積む画面演出の量であり、
ズーム率で浮き上がる速さが変わるのは元々おかしい。投影後の画面座標へ足す形に改め、
ズームに依存しないようにする。見た目が変わる変更なので、独立したコミットに分けて理由を残す。

## 採用しなかった方法

### カーソルを ECS のマーカーとして3Dシーンへ積む

`ShootingState` と `LookAroundState` がカーソル用コンポーネントを書き、`Render3DSystem` が
床クアッドと同じ画家アルゴリズムで描く案。投影経路が完全に1本になり、壁の陰に入った
カーソルが正しく隠れるという利点もある。

採らない理由は2つある。カーソルは「今どこを指しているか」を必ず見せる UI で、壁に隠れて
見えなくなるのは機能後退である。もう1つは、描画のためだけに state がエンティティを作り、
`OnStop` で消す責務を負う点で、state の寿命とエンティティの寿命がずれたときにゴーストが
残る。オーバーレイは世界の一部ではないので、世界のシーングラフへ入れない。

### 毎フレームの行列を共有スロットへ書き戻す

`Render3DSystem.Draw` が組んだ `vp` をシングルトンコンポーネントへ書き、オーバーレイが
それを読む案。行列組み立てが1回で済み、`Camera` を触らないので serde への影響も無い。

採らない理由は、結果が state の積み順という暗黙の前提に依存することである。今は
`StateMachine.Draw` が下から順に描くので `DungeonState` が先に走るが、この前提が崩れても
コンパイルは通り、テストも初回フレーム以外は通ってしまう。ずれが静かに再発する形なので、
同じ入力から組み直す純関数にする。行列組み立ては1フレーム数回で、費用は問題にならない。

### `Render3DSystem` を `world.Renderers` へ登録して型アサーションで引く

`MapGenVisualizerState` が `world.Renderers` からレンダラを名前で引いているのと同じ手で、
`Render3DSystem` を登録して state から取り出す案。`Camera` を変えずに済む。

採らない理由は、`w.Renderer` インターフェースから具象型へ落とす型アサーションが必要で、
登録漏れや型違いが実行時まで表面化しないこと。カメラのパラメータはレンダラの実装詳細では
なく世界の状態なので、置き場所は ECS が正しい。

### `Camera3D` を別コンポーネントとして足す

2Dと3Dのカメラを別コンポーネントに分ける案。`Camera` の2Dフィールドが3D側から見て
不要という点は正しい。

採らない理由は、カメラという1つの概念が2つのコンポーネントに割れ、追従処理が
`CameraSystem` で `Camera.Target` を、別のどこかで注視点を更新する形になり、
同期のずれを作りやすいこと。注視点はどちらもプレイヤー位置で同一なので、1つに保つ。
2Dフィールドが真上視点デバッグ専用になったことは、フィールドのコメントで示す。

### 3D表示をやめて2Dへ戻す

ずれは消えるが、3D表示は既に本番の見た目として確定しており、これは修正ではなく撤回である。

## コメント

`hud_extractor` のデバッグオーバーレイはフラグで隠れているため、本番の見た目としては
射撃・観察・エフェクトの4件を直せば足りる。ただし同じ根本原因から出ているので、
`Projector` へ寄せる範囲に含める。デバッグ表示だけ2D変換に取り残すと、次に触った人が
そこを手本にして2D変換を新しい箇所へ広げる。

`RenderSpriteSystem` と `FrostRenderSystem` はダンジョンの描画経路から外れ、
`InitializeSystems` に登録されたまま `MapGenVisualizerState` からしか呼ばれない。
本設計の対象ではないが、整理の候補として記録しておく。
