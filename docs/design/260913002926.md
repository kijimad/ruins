# バランスベースライン。目標×導出×照合のゲート化

## 背景

ゲームバランスを決定論的に決めてベースラインを作りたい。過去に2つの試みがあったが、意思決定に繋がらなかった。

- `simulate-balance` cmd。モンテカルロ戦闘の勝率・TTK を balance.json に出力する。目標値がどこにも宣言されていないため、レポートを眺めても正誤を判定できない
- editor-ui の BalancePage / DPSPage。balance.json をグラフ表示する。CI にも make check にも入らず、パラメータ変更の影響が機械検知されない

欠落は共通して「目標が無い」「戦闘だけ」「ゲートでなくレポート」の3点にある。一方で `internal/formula` は実ゲームの activity と balance シミュレーションの両方から使われる計算式の単一ソースとして確立しており、土台に使える。

パラメータの相互関係は `docs/balance/ruins_balance.dot` に交換性マップとして整理してある。この図は本設計で3つの役割を兼ねる。導出式のカバレッジ台帳、時系列カーブの計算経路、パラメータ探索の依存構造。矢印1本が「どのパラメータがどの指標に効くか」を表す。

人間の開発者が表と関係グラフで行うバランス検討は、次の3段に分解するとほぼ機械化できる。

```
目標の宣言          ×   実測の導出            ×   照合
「TTK 3〜6ターン」      実コードの式から           範囲内かを機械判定
（人間が決める値）       期待値を閉形式で計算        make check で落ちる
```

## 要件

- 目標は体験指標の上下限で宣言する。点でなく範囲。宣言は Go の table-driven テストに置く
- 実測は実コードの式・定数だけから導出する。並行実装を持たない。`formula` の関数、`consts` の定数、raw.toml の実値を直接参照する
- 導出は乱数試行でなく閉形式にする。決定論的でミリ秒で完了し、seed に依存しない
- 期待値だけでなく裾も出す。ローグライクの体感は平均でなく最悪側で決まる。命中確率 p の幾何分布なら P(TTK > k) は閉形式で書けるので、90%タイルの TTK を乱数なしで出せる。`internal/balance/stats.go` の既存パーセンタイル機構も流用する
- 照合ゲートは用途が定着してから足す。最初はレポートだけにする。下記「段階」を参照
- 人間向けに目標 vs 実測 vs 余裕率の表を出力できる

## 段階

過去2回の失敗の本質は「道具を先に完成させたが実際の判断に使われなかった」ことにある。ゲートまで一気に作らず、用途先行で組む。実在する1つの疑問に答える形で作り、役立ったら広げる。

初回の照準は生存圧と序盤戦闘の2つに絞る。

- **Phase 0**。導出器と baseline.md の表だけ。ゲートなし。生存圧と序盤戦闘の指標を出し、実際のバランス判断に1回使う
- **Phase 1**。Phase 0 が役立ったら、その判断で使った指標だけを targets_test.go でゲート化する
- **Phase 2**。感度表と、導出できない相互作用の扱いを検討する

ゲートの位置づけを取り違えない。これは「数値が正しいことの証明」ではなく「今この数値であるという事実の凍結と、変化の検知」である。正しさはプレイでしか検証できない。目標範囲は仮説であり、緑=正しいではない。

## 設計

### 目標表

`internal/balance/targets_test.go` に置く。1行が1つの意思決定で、根拠を必ず書く。

```go
// target は体験指標1つの目標範囲。actual が [min, max] を外れたらゲートが落ちる。
type target struct {
	name      string  // 指標名。日本語で体験を表す
	actual    float64 // metrics.go の導出関数で計算した実測値
	min, max  float64 // 目標範囲。人間が決める意思決定そのもの
	rationale string  // なぜこの範囲か
}

targets := []target{
	{"初日素手TTK対最弱敵", m.ExpectedTTK(ash, bareHands, weakest), 3, 6, "序盤戦闘は緊張感を持たせつつ消耗戦にしない"},
	{"無補給生存日数", m.SurvivalDaysWithoutFood(), 2, 4, "食料確保を毎日の課題にする"},
	{"満載時航続タイル", m.DriveRangeTiles(fullLoad), 80, 150, "1日の進行で燃料補給を1回強制する"},
	{"最弱敵からの被弾で死ぬまでの被撃数", m.HitsToKillPlayer(weakest, ash), 8, 15, "事故死は許すが即死はさせない"},
}
```

### 導出器

`internal/balance/metrics.go` に期待値ベースの導出関数を集める。すべて実コードの式・定数の参照だけで構成し、モンテカルロを使わない。

```go
// ExpectedTTK は攻撃側が防御側を倒すまでの期待ターン数を返す。
// 命中率は formula.CalcHitRate、ダメージ分布は formula の定数から期待値を閉形式で計算する。
func ExpectedTTK(attacker, defender CombatantStats, weapon WeaponStats) float64 {
	hitRate := float64(formula.CalcHitRate(attacker.Dexterity, defender.Agility, weapon.Accuracy)) / 100
	expectedDamage := expectedDamagePerHit(attacker, defender, weapon) // 乱数幅・クリティカルの期待値込み
	return float64(defender.HP) / (hitRate * expectedDamage)
}

// SurvivalDaysWithoutFood は食料なしで餓死状態異常に至るまでの日数を返す。
// 満腹度の上限と1ターンあたりの減耗から導出する。
func SurvivalDaysWithoutFood() float64

// DriveRangeTiles は所持燃料と総重量から運転できるタイル数を返す。
// query.DriveFuelCost をそのまま使い、燃費式の変更に自動追従する。
func DriveRangeTiles(fuel consts.Heat, load consts.Milligram) float64
```

導出の対象は交換性マップ `docs/balance/ruins_balance.dot` の辺に対応する。矢印1本が導出式1つに相当し、グラフは導出器のカバレッジ台帳を兼ねる。

### 難易度カーブ。時系列

指標は1つの数値でなく進行軸 d の関数にできる。`dangerLevel(d) = 1 + d/3` から日ごとの敵プールが決まり、敵テーブルは重み付きなので重み付き期待値で決定論的に「その日の代表的な敵」を導ける。これに対し `ExpectedTTK(player, enemyOf(d))` や `PDeath(d)` を全 d で評価すれば、難易度の軌跡が乱数なしで描ける。

ベースラインは1点でなく軌跡になる。目標も1本の範囲でなく時間軸に沿った回廊で宣言する。プレイヤーの成長速度が敵の強化速度に追随できているか、序盤から終盤まで手応えが回廊内に収まるかを、カーブが回廊を外れた地点として検出できる。

```go
// DifficultyCurve は各日の難易度指標を返す。dangerLevel(d) から敵プールの重み付き期待を作り、
// 対プレイヤーの ExpectedTTK と PDeath を評価する。RNG は使わない。
func DifficultyCurve(master oapi.Raws, player CombatantStats, days int) []DayMetric
```

### 発見と最適化の範囲

導出器がすべて純関数なので、raw パラメータ空間の探索でできることと、できないことを区別する。

- できる。宣言した回廊を満たすパラメータ集合を機械的に探索する。関係図の矢印がどのパラメータがどの指標に効くかを示すので、探索の依存構造として使える
- できる。目標同士が両立不能になる地点を検出する。この不能レポートは設計の緊張を暴くので、それ自体が発見になる
- できない。「最適すなわち面白い」は式にならない。回廊の値は仮説で、プレイでしか検証できない。目標そのものの発見を機械に委ねると緑イコール正しいの錯覚になる

Claude Code の役割はこの探索の実行にある。回廊を人間が決め、回廊を満たす raw 値の探索と不能地点の報告を機械が回す。

### 照合ゲート

targets_test.go の table-driven テストが全指標を照合する。`make check` に自動で含まれる。

```go
for _, tg := range targets {
	t.Run(tg.name, func(t *testing.T) {
		assert.GreaterOrEqual(t, tg.actual, tg.min, tg.rationale)
		assert.LessOrEqual(t, tg.actual, tg.max, tg.rationale)
	})
}
```

### レポート

`go run . balance-report` を既存の cmd 機構に足し、目標 vs 実測 vs 余裕率の markdown 表を `docs/balance/baseline.md` へ生成する。パラメータを変更した PR では baseline.md の diff がバランスへの影響を示す。生成漏れは当面ゲートにしない。運用が定着したら make generate への組み込みを検討する。

### 感度表

第2段階。各 raw パラメータを±10%振って各指標の変化率を出し、「この指標を動かすつまみはどれか」を表にする。導出器が純関数なので数値微分するだけで得られる。初期実装では見送る。

### 既存 simulate-balance の扱い

当面残置する。期待値の閉形式は分布の裾（運が悪い連鎖）を表現できないため、創発的な検証用としてモンテカルロには別の役割が残る。ゲート運用が定着した時点で、editor-ui の表示も含めて整理を判断する。

### 運用ループ

```
人間: 目標範囲を決める・見直す（体験の意思決定。targets_test.go の1行）
Claude Code: ゲート赤 → 感度表を参照して raw.toml を調整 → 緑まで反復（機械的探索）
CI: 以後のパラメータ変更が目標を壊したら make check で即検知
```

## 採用しなかった方法

- **表を正とする生成方式**。バランス値を単一の表で決めて raw.toml を生成する。TTK や航続距離は式から導出される量で表に直接書けず、決めたいのは体験指標であってパラメータ生値ではないため不採用
- **モンテカルロ拡張方式**。既存 simulate-balance を生存・経済込みに拡張する。遅く seed 依存で、目標が無い限りレポート止まりになる。前回の失敗の直接延長のため主軸にしない
- **目標表を TOML に置く方式**。データと見た目は良いが、指標名と導出関数の紐付けに登録表が要り一段回りくどい。開発者が単独のプロジェクトでは Go のテスト表が最短
- **tsp スキーマ拡張で editor-ui 表示**。editor のグラフが役立たなかった反省に逆行し、生成パイプラインの保守も重い

## コメント

- 目標範囲そのものが「決定論的に決めたベースライン」になる。狙いの数値観は交換性マップと合わせて読む
- 上下限つきの範囲で宣言するのが要点。点で決めると調整のたびに目標を書き換えることになり硬直する
