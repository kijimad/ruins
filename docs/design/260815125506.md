# 腐敗システムの将来拡張

## 背景

`260813080544` で腐敗の基盤を入れた。累積劣化量 `RotAccrued` と遅延評価、合流の単一述語 `CanStackWith`、同段階の加重平均マージまでを実装済み。その際に v1 の範囲を絞って意図的に見送った2件を、基盤が用意した接続点とともにここへ移す。着手時はこの doc を起点にする。

- **温度連動の劣化速度**: データモデルは温度可変に耐える形にしたが、速度 `perishRate` は一律 `1.0` を返すだけ。置き場所で速度を変える部分は未着手。
- **段階横断の在庫個数合算**: `FindStackableInInventory` は `RawID` 一致の先頭1束を返す。腐敗食は鮮度段階の違う束が複数ありうるため、所持数照会がその1束ぶんに過少計上される。

## 要件

### 温度連動

- 置き場所によって劣化速度が変わる。冷所は遅く、暖所は速い。冷蔵の保存容器も減速する。
- 既存の遅延評価を壊さない。毎ターン全食料を走査する処理を増やさない。
- 速度が変わる瞬間までの劣化を確定してから新速度へ移る。区間ごとに正しい速度で積み上がること。

### 個数合算

- 同一 `RawID` の全束を合算する所持数照会を持つ。合成の所持数判定と一覧表示がすべての束を数える。
- 合流先を1つ探す用途の `FindStackableInInventory` はそのまま残す。責務が違う。

## 設計

### 温度連動の劣化速度

速度は既に1箇所へ集約してある。ここを置き場所依存にするだけで拡張が閉じる。

```go
// 現状。一律 1.0
func perishRate(_ w.World, _ ecs.Entity) float64 { return 1.0 }

// 拡張後。entity の現在地から温度を引き、速度係数へ写す。1.0 が基準
func perishRate(world w.World, entity ecs.Entity) float64 {
	// 冷所 < 1.0 < 暖所。温度源は下記の決定に従う
	...
}
```

速度が変わる契機で `query.AdvanceRot` を呼び、`RotAccrued` を現時点まで確定してから新速度に入る。これで区間ごとの速度が正しく積み上がる。契機はエンティティの移動、すなわちフィールドとバックパックと収納をまたぐ移動、および将来の時間帯連動。移動は `lifecycle` の `MoveTo*` を通るので、焼き付けをこの経路の1点へ寄せる。

温度源は未決定。人の判断が要る。候補:

- `GameTime` の時間帯から全体の外気温を出す。最も軽いが、置き場所の差が出ない
- タイルやステージに温度属性を持たせる。場所差は出るが、地形データの拡張が要る
- 冷蔵の収納コンポーネントを持たせ、その中の食料だけ減速する。溜め込み対策と噛む

v1 は温度自体が無いので、どれを採るかはここで詰める。

浮動小数の扱いに注意する。`EffectiveRot = RotAccrued + Turn(float64(elapsed) * rate)` で、`rate` が非整数だと丸めが入る。累積は焼き付け時に確定するので誤差は1ステップ1未満に収まるが、係数の刻みは詰める。

### 段階横断の在庫個数合算

`RawID` 一致の全束を合算する照会を足す。

```go
// 追加。RawID 一致の全束を合算する。鮮度段階をまたいで総数を返す
func CountInInventory(world w.World, id string) int {
	total := 0
	q := ecs.NewFilter3[gc.Stackable, gc.LocationInBackpack, gc.RawID](world.ECS).Query()
	for q.Next() {
		e := q.Entity()
		if world.Components.RawID.Get(e).ID == id {
			total += world.Components.Stackable.Get(e).Count
		}
	}
	return total
}
```

合成の所持数判定 `CanCraft` と一覧の所持数表示をこれに差し替える。`FindStackableInInventory` は合流先を1つ返す用途で存置する。

## 採用しなかった方法

- **毎ターン全食料に温度を適用して減算する**: 走査が復活し `O(食料数)/ターン` の負荷が戻る。移動時の焼き付けと遅延評価で避ける
- **`FindStackableInInventory` を段階横断合算に作り替える**: 合流先探索は1束でよく、合算とは責務が違う。1関数に混ぜると呼び出し側の意図が曖昧になる。別関数として足す

## コメント

- 温度源の決定が温度連動の前提。ここが決まらないと `perishRate` の実装も温度源のデータ拡張も動かせない
- 速度係数の値と刻みはバランス調整用の仮値で始め、プレイして詰める
