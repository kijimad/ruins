# コード監査: 健康タブの過労・栄養失調詳細 2026-09-07

## 背景

golangci-lint による静的検査が手厚いリポジトリのため、forcetypeassert・errcheck・nilerr/nilnil・exhaustive・makezero 等の機械検知漏れを補う目的で、internal 配下を4系統に分けて横断的に精読した。lint がパターンとして捕まえられない、コードの意図と実装のズレを読み解いた誤りだけを対象にしている。

対象にしたのは、直近で急速に何度も再設計が入った領域を中心に据えた4系統。

- 身体機能・疲労・空腹・体温の funnel と不調モデル
- 移動拠点キューブの運転・燃料機構
- 修飾子パイプライン
- ダンジョン・マップ生成・オーバーワールド

過去の監査doc（`260711000833.md`・`260719100100.md`・`260803144226.md`・`260810001803.md`・`260817001843.md`・`260824001220.md`・`260831001354.md`）は事前に通読し、既出の問題は再度挙げていない。特に `260824001220.md` が扱った `internal/overworld/dungeon_entrance.go`・`settlement.go`・`schematic.go` のチャンク種別優先順位問題、`260831001354.md` が扱った継続アクティビティ・季節進行・体温ゲージ色・クラフト整合の4件はいずれも該当doc内で `[x]` 済みであることを確認し、対象から除外した。

キューブ運転・燃料機構、修飾子パイプライン、ダンジョン・マップ生成・オーバーワールドの3系統は敵対的検証の結果、確信を持って報告できる新規の問題が無かったため0件だった。キューブ運転機構は追加のみで既存挙動を変えない段階であり、`Driving`/`DriveFuelCost` を消費する呼び出し元がまだ存在しないため、危険な経路自体が未実装だった。修飾子パイプラインは全ての `Percent` 適用箇所に `max(..., 下限値)` の床処理があり、符号反転や二重適用は見つからなかった。ダンジョン・マップ生成は境界チェック・collect-then-mutate・空スライスガードが一貫していた。

以下1件を、実コードを直接確認し失敗シナリオを具体化したうえで報告する。修正はこの doc の範囲外とし、着手は人が取捨選択する。

## 問題1: 健康タブで過労・栄養失調の行を選んでも詳細が常に空になる

**file:line**: `internal/states/character_state.go:355-366`（`healthDetailContent`）、`internal/states/character_info.go:252-299`（`createHealthItems`）、`internal/world/query/body_funcs.go:22-35`（`DerivedConditions`）

**症状**: 健康タブで疲労・空腹による「過労」「栄養失調」の行を選択すると、一覧には重症度が表示されているにもかかわらず、詳細ポップアップには名前だけが出て概要・進行度・治療状況・能力低下の内訳が一切表示されない。

**根拠・失敗シナリオ**: 一連の再設計「疲労・空腹を不調保存でなく読み取り時の導出へ戻す」「疲労・空腹を導出 condition として統一し乗算 funnel へ全面 RimWorld 化」により、`ConditionExhaustion`・`ConditionMalnutrition` は `HealthStatus.Parts[...].Conditions` に保存されなくなり、`query.DerivedConditions`（`body_funcs.go:22`）が `Fatigue`・`Hunger` の値からその場で組み立てる値だけになった。一覧生成側 `createHealthItems`（`character_info.go:252`）はこれに追随済みで、全身部位について `query.DerivedConditions(world, playerEntity)` を明示的に呼び出し、`ConditionType: cond.Type` を設定した選択可能な行を作っている（`character_info.go:269,279-286`）。

一方、詳細ポップアップを組む `healthDetailContent`（`character_state.go:355`）は追随していない。363行目で

```go
cond := world.Components.HealthStatus.Get(player).Parts[item.BodyPart].GetCondition(item.ConditionType)
```

と、保存済み条件だけを線形探索する `BodyPartHealth.GetCondition`（`health_status.go:408-415`、`bph.Conditions` を走査するだけ）を呼んでいる。過労・栄養失調はこの `Conditions` スライスに一度も追加されないため、`cond` は常に `nil` になり、364-366行目のガードに落ちて名前だけの空詳細を返す。

具体的には、`Fatigue.Current` が `Max` の80%以上に達し `FatigueExhausted` 相当になると、一覧には「過労　中」のような行が並ぶ。カーソルをこの行に合わせて詳細を開くと、骨折など保存済み不調と同じ操作のはずが、概要文・進行度・「意識」「代謝」の低下内訳・治療アイテム欄がすべて欠落した空の詳細になる。栄養失調も同じ経路で同様に空になる。

**根拠**: これは一覧生成と詳細生成という独立した2箇所が、同じ「統一した」条件モデルを異なる前提で読んでいるために起きる意味論的な食い違いで、forcetypeassert・errcheck・exhaustive のいずれも指摘できない。364行目の `nil` ガード自体は文法的に正しい防御的コードに見えるため、データモデルを追わない限り気づけない。既存テスト `TestCharacterState_健康タブは不調の概要と影響を詳細に持つ`（`character_state_test.go`）は骨折など保存済み条件だけを検証しており、過労・栄養失調の詳細表示はテストされていない。

**修正方針案**: `healthDetailContent` が全身部位かつ `ConditionType` が `ConditionExhaustion`/`ConditionMalnutrition` のときは、`query.DerivedConditions(world, playerEntity)` から一致する条件を取得するようにする。あるいは `createHealthItems` で組み立てた `gc.HealthCondition` 値そのものを `statusItemData` に持たせて呼び出し元へ渡し、詳細側で再取得しないようにする。

**実施**: 第1案を、追随漏れが再発しない形へ一般化して採用した。保存条件と導出条件を同じ引き口で解決する `query.FindCondition` を新設し、`healthDetailContent` はこれ経由で条件を引く。導出不調かどうかの判定は `gc.ConditionIsDerived` に単一化し、一覧側 `createHealthItems` のインライン比較もこれへ差し替えた。導出不調は Timer と治療状態を持たないので、詳細は進行度・治療でなく重症度と、意識・代謝の低下ぶんを出す。`derivedConditionDetail` がこの描画を担う。回帰は `TestCharacterState_過労の詳細は重症度と意識代謝の低下を出す` で固定した。
