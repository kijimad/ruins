# コード監査: マップ生成境界とUIヒント整合性 2026-09-14

## 背景

自律コード監査エージェントによる定期監査タスク。golangci-lint は forcetypeassert・errcheck・nilerr/nilnil・exhaustive・makezero 等が有効で機械的な問題は既に捕捉しているため、今回は internal 配下を対象に lint が捕まえられない意味論的な誤り、条件の取り違え・境界計算・Ark strict semantics 違反・serde 不整合・リソースリークの観点で横断的に読み込んだ。

ECS コア（systems/activity/aiinput/components/world/engine）、マップ生成（dungeon/mapplanner/mapspawner/maptemplate/worldstream/overworld/geometry）、save/serde、ゲームルール（balance/formula/skill/states/menuloop/input/inputmapper）、リソースライフサイクル（render3d/screeneffect/widgets/loader/raw/steam/logger/gamelog/vrt）の5系統に分けて精読した。

検出した候補のうち、ebiten の `*ebiten.Image` を Dispose せず生成する箇所は当初リークの疑いで挙がったが、`image.go` の `Dispose` doc コメントに明記の通り「Dispose の呼び出しは必須ではなく、GC が内部リソースを自動回収する」設計であり、`internal/atlas/image.go` で `runtime.AddCleanup` によるGC連動の解放が実装されていることをソースで確認した。ebiten の意図した使用法の範囲内であり誤りとして扱わなかった。同様に、Ark の `Get` 結果のポインタを構造変更後も保持し続ける類似パターンも1件見つけたが、実害がデバッグログの表示値が壊れる程度に留まり、ゲームロジックへの影響がないため今回は見送った。

以下の2件は、実際に誤った状態が発生するシナリオを特定できたため報告する。

## 検出した問題

### 1. `internal/mapplanner/room_draw.go:27` — 部屋描画の境界チェックが2箇所の角だけを不必要に除外する

```go
func (b RoomDraw) rectangle(planData *MetaPlan, room gc.Rect) {
	for x := room.Min.X; x <= room.Max.X; x++ {
		for y := room.Min.Y; y <= room.Max.Y; y++ {
			idx := planData.Level.CoordToIndex(consts.Coord[consts.Tile]{X: x, Y: y})
			if 0 < int(idx) && int(idx) < int(planData.Level.TileWidth)*int(planData.Level.TileHeight)-1 {
				planData.Tiles[idx] = planData.GetTile("floor")
			}
		}
	}
}
```

**症状**: 有効なタイルインデックスの範囲は `[0, W*H)` だが、ガードは `0 < idx && idx < W*H-1` になっており、フラットインデックスの先頭 `idx==0`（座標 `(0,0)`、マップ左上角）と末尾 `idx==W*H-1`（座標 `(W-1,H-1)`、マップ右下角）の2点だけを floor 化の対象から除外する。同じ用途で境界を判定している `internal/mapplanner/line_corridor.go:97` の `isValidTileIdx` は `idx>=0 && idx<W*H` で正しく全域を対象にしており、比較するとこのガードだけが2要素狭い。

**根拠・失敗シナリオ**: `internal/mapplanner/rect_room.go:19` の `RectRoomPlanner.PlanRooms` はコメント「上端(y=0)と下端(y=height)に必ず各1つの部屋を配置し、上下端への接続を保証する」の通り、上端部屋の `Min.Y` を `0`、下端部屋の `Max.Y` を `height-1` に密着させて生成する。上端部屋の `Min.X` は `RNG.IntN(width)` で決まるため、これが `0` を引くと `Min` が `(0,0)` になり、そのタイルの `idx` はちょうど `0`。ガードにより該当タイルだけ `floor` 化されず、生成時の初期値（`wall`）のまま残る。下端部屋も `bottomX+bottomW >= width` のとき `Max.X` が `width-1` となり、`Max` が `(width-1, height-1)` に一致すれば `idx == W*H-1` で同様に除外される。

さらに `internal/mapplanner/convert_isolated_walls.go:27` の `ConvertIsolatedWalls` はマップ端のタイル（`x==0 || x==width-1 || y==0 || y==height-1`）を「境界として残す」ために変換対象から常に除外する設計なので、この孤立した壁タイルは後段のオートタイル処理でも修復されない。結果として、本来床であるべき部屋の角に1タイルだけ壁が残り、その角付近の通行や視界が意図と異なる状態になる。

**なぜ lint で捕まらないか**: 配列外アクセスや型の問題ではなく、意図された範囲より2要素狭いだけの「文法的に正当な」整数比較であるため、makezero や境界チェック系の静的解析は反応しない。`RectRoomPlanner` がどの座標に部屋を密着させるかという設計意図と突き合わせて初めて気づける誤りである。

**反証の検討**: 「マップ外周は常に壁であるべき」という設計であれば正当な可能性を検討したが、`RectRoomPlanner` は上下端に明示的に部屋を密着させて床を通す設計であり、実際その行の大部分（角以外の `x=1..width-2`）はこのガードに抵触せず floor 化される。角の2点だけが矛盾して除外されるのは意図した境界保護ではなく実装ミスと判断した。また「4隅を保護する意図だった」という可能性も検討したが、フラットインデックスの `0` と `W*H-1` は4隅のうち左上と右下の2つにしか対応せず、右上 `(W-1,0)` と左下 `(0,H-1)` は保護されない。どちらの意図で見ても現状の実装は一貫していない。`internal/mapplanner/big_room.go` の `BigRoomDraw` は同様のガードを持たず全域を floor 化しており、この不整合は `RoomDraw` 固有である。

**修正方針案**: `isValidTileIdx` 相当の `idx>=0 && idx<W*H` に統一するか、`line_corridor.go` の `isValidTileIdx` をそのまま再利用する。

### 2. `internal/states/look_around.go:199` — 見回しモードのヒント文言が実際の束縛と食い違っている

```go
drawText(query.T(world, "Arrows: Move  X/Esc: Close"))
```

**症状**: 画面下部のヒントは「X/Esc: Close」と表示され X キーでも閉じられるように読めるが、同ファイル73行目の `lookAroundBindings` には `ebiten.KeyEscape` しか閉じる束縛が登録されておらず、X キーの束縛は存在しない。`doAction`（82行目）の switch も Escape と方向キー以外は扱わない。

**根拠・失敗シナリオ**: この見回しモードは `internal/states/dungeon_input.go:32` で `ebiten.KeyL`（`ActionOpenFieldInfo`）によって開く。同ファイル31行目のコメント「視界情報表示。調べる X すなわち Shift+x へ X を譲り、フィールド情報は L に置く」から、かつて視界情報が X キーに割り当てられていたが、後に調べる操作（`ActionVerbExamine`、Shift+X）へ X を譲り、視界情報自体は L キーへ移した経緯が読み取れる。この移行時にキー割り当ては直したが、ヒント文言だけ更新されずに残った。プレイヤーが L キーでこのモードを開き、画面のヒントを見て X を押しても何も起きず、閉じるには表示されていない Esc を使う必要がある。CLAUDE.md の方針「閉じるキーは Esc と、その画面を開いたキーだけにする」から見ても、X はこの画面を開いた鍵でも閉じる鍵でもなく、表示が実態と乖離している。

**なぜ lint で捕まらないか**: 単なる文字列リテラルであり、コンパイル・型・未使用変数のいずれの静的検査にも引っかからない。束縛表 `lookAroundBindings` の内容とヒント文字列の対応関係はコードの「意味」の話であり、機械的な相関チェックの対象にならない。

**反証の検討**: `lookAroundBindings` 以外の束縛表がマージされて X が有効になっていないか確認したが、`Update`（62行目）は `keybind.ReadInput(world, lookAroundBindings)` を直接呼ぶのみで、`menuloop.Screen` のような共通束縛合成の仕組みも使っていない。X キーが機能する経路は存在せず、反証は見つからなかった。

**修正方針案**: ヒント文字列を `"Arrows: Move  Esc: Close"` に修正する。CLAUDE.md の「1つの意味に1つのキー」「閉じるキーは Esc とその画面を開いたキーだけ」の方針上、X を新たに閉じる束縛として追加するのは適切でない。

## 採用しなかった代替

- ebiten `*ebiten.Image` の Dispose 漏れ疑い箇所: ebiten は Dispose 非呼び出しを許容する設計であり GC 連動の解放機構を持つことをソースで確認したため、問題として採用しなかった。
- `internal/activity/activity_manager.go:214` の `stored.Progress.Max` ログ出力: `behavior.Start` がアクター自身へコンポーネントを Add すると Ark strict semantics により `stored` の Get ポインタが構造変更後に無効化される可能性を確認したが、実害はデバッグログの表示値が乱れる程度に留まり、ゲームロジックへの影響が無いため今回のタスク doc には含めなかった。将来同じ変数を後続処理で使う変更が入ると顕在化しうるため、レビュー時の参考として残す。
