# コード監査: 市街地敵湧き・ステージ跨ぎ漏れ・散布境界 2026-10-05

## 背景

自律コード監査エージェントによる定期監査タスク。golangci-lint は forcetypeassert・errcheck・nilerr/nilnil・exhaustive・makezero 等が有効で機械的な問題は既に捕捉しているため、今回は internal 配下を対象に lint が捕まえられない意味論的な誤りを横断的に読み込んだ。oapi と editor-ui は対象外。

天候・深度難易度（weather・balance/skilldepth）、移動拠点キューブの展開・燃料（world/lifecycle/cube*・states/cube_*）、内装・prop のデータ化（mapplanner/interior・overworld/interior_furnish・prop/item マーカー分離）、ECS コア戦闘・AI（activity・aiinput・systems の戦闘関連）、マップ生成・worldstream・overworld の5系統に分けて並列で精読した。過去の監査doc（`260803144226.md` から `260921001438.md` まで）は事前に通読し、該当する file:line の問題は対象から除外した。

検出した候補のうち、`internal/mapplanner/interior/split.go` の `splitSpan` が内部境界を `minRoomSideSplit` 未満にならないよう押し戻す際、固定端であるはずの `bounds[0]`/`bounds[n]` も一緒に動かしてしまい base 矩形をはみ出す潜在的な欠陥を見つけたが、実際に `PlanStore`/`PlanClinic` を本番の footprint 範囲（17〜20角、前庭差し引き後の building も12角が下限）で多数 seed 検証した結果、はみ出しは一度も再現しなかった。テンプレ発火の下限 `minW=12, minH=9` ちょうどの矩形を人為的に作らない限り到達しないため、現行データでは到達不能と判断し見送った。

以下4件は、実際に誤った状態・欠落が発生するシナリオを再現テストで確認できたため報告する。修正はしていない。取捨選択はレビューに委ねる。

## 問題1: 市街地チャンクの敵複数湧きが座標重複を避けず、2体目以降が1体目を踏み潰す

**file:line**: `internal/overworld/urban.go:291-318`（`spawnUrbanEnemies`）

**症状**: 市街地チャンクに敵を複数湧かせるループが、空き座標判定に使う `occupied` マップへ自分がこのループで配置した敵の座標を一度も書き込まない。`occupied` は呼び出し側から渡される建物 footprint・壁の静的占有だけを持つ。

**根拠・失敗シナリオ**: `count := 1 + rng.IntN(int(size))` で2体以上湧く市街地チャンク（`size>=2`）で、2体目を置く `urbanSpawnTries`（24回）の試行のいずれかが1体目と同じ `(lx,ly)` を引くと、`isWall(lx,ly) || occupied[pos]` は両方falseのまま通過し、同じタイルへ2体目の `lifecycle.SpawnEnemy` を呼んでしまう。`buildSpatialIndex`（`internal/world/query/singleton.go:250`）の `si.Characters[*grid] = entity` は座標キーの map なので後に構築された側が勝ち、先に湧いた敵が `FindNearestCharacter`（`internal/world/query/nearest.go:65`、`si.Characters` を直接走査）から見えなくなる。`aiinput/planner_solo.go` の群れ行動・プレイヤー捜索はこの関数に依存するため、踏み潰された敵はAIが仲間として認識できず、群れ連携が機能しない個体として取り残される。エンティティ自体は消えないため `GetEntitiesAt` のような線形走査では見えるが、空間索引経由の探索からは一方だけが脱落する。

**反証の検討**: 同種の重複配置防止は `internal/mapplanner/lib.go:87` の `slices.ContainsFunc(bm.NPCs, ...)` がダンジョン側で既に実装しており、配置済みNPC座標を動的に追跡している。urban.go だけこの更新が欠けているのは意図的な仕様差でなく実装漏れと判断できる。1チャンクあたり候補タイル数は数百、試行24回なら衝突確率はゼロでなく、市街地探索を続けていれば到達する。lint はこの種の「ループ内で状態更新を1箇所忘れる」誤りを検知しない。

## 問題2: 退避中ステージのエンティティが、キューブの展開判定・畳み込み・設備装着判定に混入する

**file:line**: `internal/world/lifecycle/cube_deploy.go:72`（`deploySpaceFree`）、`internal/world/lifecycle/cube_deploy.go:103`（`stowNearbyItems`）、`internal/world/lifecycle/facility.go:35`（`FacilityCellFree`）

**症状**: いずれも `ecs.NewFilter1[gc.LocationOnField](world.ECS).Query()` を生の `ecs.NewFilterN` で書いており、`internal/world/query/active.go` が提供する `query.ActiveFilter1` を使っていない。本プロジェクトは「共存方式」で全ステージのエンティティが同一 world に存在し、退避中ステージのものは `Suspended` マーカーで除外する決まりになっている。`query/active.go` のドキュメント自身が「生の `ecs.NewFilterN` でなくこれを使う。付け忘れは silent な leak になる」と明言しているが、この3箇所だけ守られていない。

**根拠・失敗シナリオ**: ダンジョン階Aのタイル `(11,10)` に Prop を置いたまま退避すると、`stage.go` の `suspend` は `Suspended` マーカーを付けるだけで `GridElement` の座標は変えない。退避中の階と現ステージ（オーバーワールド等）は別の「ステージ」だが、タイル座標はどちらも原点付近の小さい整数レンジを使うため、オーバーワールドでキューブを `(10,10)` に置いて半径2で「展開」すると、`deploySpaceFree` が階Aの退避済み Propを現ステージの障害物として数えてしまい、本来空いているはずのオーバーワールドの野営スペースの展開が偽で拒否される。逆に `stowNearbyItems` では、座標が重なる退避中ステージの Item/Prop を「自分が置いた貨物」と誤認して `LocationStowed{Owner: cube}` へ畳み込んでしまい、他ステージ所属のエンティティの Owner だけがキューブへ書き換わる。該当ダンジョン階に再訪すると、そのアイテムは消えている。`FacilityCellFree` も同様に誤って「使用中」と判定し、設備装着を拒否しうる。

**反証の検討**: `GetEntitiesAt`（`query.go:85`）等の座標系クエリは全て `ActiveFilterN` 経由になっており、この3箇所だけが例外である。forcetypeassert/errcheck/exhaustive 等では検知できない、フィルタの選択ミスという意味論の問題であり、`query/active.go` 自身が「付け忘れは silent leak になる」と明言する既知のリスクが実際に顕在化した3例と言える。同種の指摘が3箇所で繰り返されている。

## 問題3: 荒れ地チャンクの草・樹木・岩・屋外loot散布が、チャンク外周1タイルに一切出現しない

**file:line**: `internal/overworld/scatter.go:171`（`openTerrainFeature.place`）、`internal/overworld/loot_scatter.go:52`（`scatterOutdoorLoot`）。根本原因は `internal/mapplanner/interior/room.go:29`（`Rect.interiorTiles`）が外周1マスを除外する実装を、壁の無い屋外チャンクにまで流用していること。

**症状**: `scatter.go`・`loot_scatter.go` はどちらも `area := interior.Rect{X: 0, Y: 0, W: g.chunkW, H: g.chunkH}` というチャンク全域を `interior.ScatterArea(area, accept, seed, count)` へ渡す。`ScatterArea`（`placement.go:44`）は候補タイルを `area.interiorTiles()` から取るが、この関数は「部屋は外周が壁」という前提で `x∈[X+1, X+W-2], y∈[Y+1, Y+H-2]` だけを候補にする。壁の無い開けた地形に同じ関数を再利用したため、意味論がずれている。

**根拠・失敗シナリオ**: 標準のチャンク幅24で再現テストを書いて検証したところ、`ScatterArea({0,0,24,24}, 常にtrue, seed, 10000)` が返す候補はちょうど `22*22=484` 件で、外周ヒットは0件だった。結果、荒れ地チャンクは出現しうる全チャンクで常に外周1タイル（24x24なら92タイル、約16%）が草も木も岩もloot一切置かれない「裸の土」の帯になる。隣接チャンクも同じ理由で自分の外周を空けるため、チャンク境界では実質2タイル幅の裸地の格子線が全マップに渡って常時出現する。`scatter.go` のコメントが意図する「草が濃く自然の野原にする」「原野を埋め尽くさない」という自然な景観と矛盾し、見た目に周期的なグリッドパターンとして現れる。

**反証の検討**: 境界に余白を残す意図的設計、たとえばシーム処理との衝突回避の可能性を検討したが、`RecalcChunkSeams`／`RecalcAutotileInXRange` が触るのは地形タイルのオートタイルだけで、prop の散布とは無関係。両コメントにも境界マージンの意図説明は無い。両chunk側が外周を空けるので境界沿いが逆に不自然に目立つ結果になり、意図的な緩和策としても一貫しない。`ScatterArea` のもう一つの呼び出し元 `placement.go` の `selectTiles`（`PlaceFullArea`）は建物内部の `Room.Rect`（外周=壁）に対して正しく使われており、`interiorTiles` の「外周除外」はそちらの意味論に合わせた実装である。scatter.go/loot_scatter.go が壁の無いチャンク全域に同じ関数を再利用したことで意味論がずれたと判断できる。

## 問題4: 内装レシピ `convenience_store` の散らかり装飾 `litter` が raw prop 対応表に無く、常に出現しない

**file:line**: `internal/mapplanner/interior/prop.go:14-87`（`propRaw`）、`assets/metadata/entities/raw/raw.toml:16096`（`ref = "litter"`）、`internal/overworld/interior_furnish.go:110-113`

**症状**: `raw.toml` の内装レシピ `convenience_store` の `pick_one` グループが唯一の item として参照する `kind="decor", ref="litter"` が、spawn と VRT 描画の単一ソースである `interior.propRaw`（prop.go）に存在しない。`PropRawName("litter")` は `ok=false` を返し、`furnishBuilding`（`interior_furnish.go:110`）はこの decor 配置を無言でスキップする。

**根拠・失敗シナリオ**: `convenience_store` は `store` 施設の3バリアントの1つ（1/3）であり、`antique` 施設では唯一のバリアントとして100%選ばれる（`raw.toml` の `facilityContents`）。この内装が選ばれるたび、`pick_one` グループに item が1つしかないため必ず `"litter"` が選ばれ `1d3+1`（2〜4枚）のタイルに割り当てられるが、spawn 時に `PropRawName` が見つからず該当タイルには何も置かれない。`internal/mapplanner/interior/archetype.go:23` には `"litter": {Default: PlaceFullArea}` という配置既定が明示的に定義されており、同種の decor `candle`・`carpet`・`plant`（raw.toml 中で実際に使われる decor ref）は全て `propRaw` に対応を持つのに `litter` だけが欠けている。設計上の除外ではなく登録漏れと判断できる。クラッシュせず「ちらかり装飾が常に消える」という静かな劣化になる。

**反証の検討**: `propRaw` のコメントは「KindLoot の戦利品と raw の無い装飾は含めない」という意図的な除外パターンの存在を認めているが、実際に raw.toml の `kind="decor"` 参照を全て洗うと `candle`/`carpet`/`litter`/`plant` の4種類のみで、`litter` 以外は全て `propRaw` に対応を持つ。同じ `KindDecor` の兄弟 ref が全て解決できるのに `litter` だけ解決できないのは一貫性が無く、`archetype.go` が明示的な配置既定を持つことからも意図的な除外ではない。既存テスト（`interior_furnish_test.go` 等）は `KindFurniture` だけを対象にしており、`KindDecor` の raw 対応漏れを検査していないため機械検知の網から漏れていた。

## コメント

問題1〜3はいずれも「ある箇所でだけ規約・パターンが守られていない」という同系統の欠落で、問題2は3箇所で繰り返されている。`query.ActiveFilterN` のような座標系ヘルパーの使用漏れは、`grep -rn "ecs.NewFilter" internal/ | grep -iE "LocationOnField"` のような横断検索で機械的に洗える余地がある。
