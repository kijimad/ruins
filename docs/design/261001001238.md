# OSS 調査 2026-10

## 背景

月1回、ruins に役立ちそうな OSS を GitHub Trends と検索から探し、調査結果をドキュメントにまとめて PR で提出する定期調査の今月分。採用の判断と実装は人が行い、このドキュメントは提案に留める。

## 要件

- ruins に実際に役立つこと。Ebiten・ECS・ゲーム・ローグライク、または Go の開発・テスト・CI・シリアライズ・生成に関わるもの
- ある程度のスター数、活発なメンテナンス、使えるライセンス
- 既存依存と重複しないこと。`go.mod` を確認して除外する
- 3〜7件に絞る。関係しそうな候補が無ければ0件で終了してよい

## 調査方法

`gh search repos` はこのセッションではリポジトリ検索APIが使えず、`sessions are bound to their configured repositories` というエラーで失敗した。代替として WebSearch と WebFetch でドメイン検索を行った。

GitHub Trending の月間 Go ランキングも WebFetch で取得した。上位にはコードレビューツール・LLM 基盤・ペネトレーションテストツールなど ruins と無関係な項目が並び、該当する候補は無かった。

## 設計

既存依存を `go.mod` で確認した。ebiten・ark・ark-serde・testify・urfave/cli・goldie・gotext・go-steamworks・kin-openapi・go-text/typesetting・BurntSushi/toml・pelletier/go-toml・caarlos0/env・tablewriter・pkg/profile・golang.org/x/perf・golang.org/x/tools・golang.org/x/vuln・avito-tech/go-mutesting などが既に入っており、これらと重複する提案はしない。

以下の3件を候補とする。

### 1. quasilyte/go-ruleguard

- リポジトリ: https://github.com/quasilyte/go-ruleguard
- 概要: Go の構文パターンを宣言的な DSL で書き、golangci-lint の `gocritic` ruleguard チェッカーまたは単体の `ruleguard` コマンドから実行できるリンタ。型情報を使ったフィルタも書ける
- ruins での用途: `internal/lintrule` には `go/parser` を直接歩く手書きの検査が複数ある。たとえば同じ `Logger` への隣接 `Markup` 呼び出し禁止を検査する `TestNoAdjacentMarkup` や、並列サブテストでの `world` 共有を型情報付きで検査する `TestNoSharedWorldInParallelSubtests` は、ruleguard の `dsl.Matcher` パターンで宣言的に書き直せる見込みがある。宣言的ルールに移せば `make lint` の1系統に集約でき、`go test` 側に検査ロジックを持つ現状より保守箇所が減る
- 成熟度: スター約880、BSD-3-Clause。直近もリリースが続いており活発
- ライセンス: BSD-3-Clause
- 採用時の注意: 全面置き換えではなく、ruleguard の DSL で表現しやすい構文パターンの検査から段階的に移すのが安全。型情報を要する複雑な検査は既存の `go/parser` + `go/types` 実装のままで良い場合もある

### 2. pgregory.net/rapid

- リポジトリ: https://github.com/flyingmutant/rapid
- 概要: Go のプロパティベーステスト用ライブラリ。ジェネリクスで型安全な値生成器を書き、与えた性質が大量のランダム入力で成り立つかを検査する。失敗時は失敗例を自動で最小化する。標準ライブラリ以外に依存しない
- ruins での用途: `internal/geometry` や `internal/formula` の純粋関数、`internal/mapplanner` の各種プランナーは入力に対する不変条件を持つ。たとえば生成したマップが常に連結である、経路探索が負のコストを返さない、といった性質はテーブルテストより性質ベーステストの方が境界値を広く拾える。既存の `serde_fuzz_test.go` は標準の `testing.F` によるバイト列レベルのファズで、こちらはドメインレベルの構造化データに対する性質検査を担うので役割が分かれる
- 成熟度: スター約890、411コミット。活発にメンテされている
- ライセンス: MPL-2.0
- 採用時の注意: 既存のテーブルテストを置き換える必要はなく、不変条件が明確な一部の純粋関数から追加する形で導入する

### 3. ebitengine/debugui

- リポジトリ: https://github.com/ebitengine/debugui
- 概要: Ebitengine アプリ向けのデバッグ用 UI ツールキット。immediate mode で書け、ボタン・テキストフィールド・スライダーなどのウィジェットを持つ。Ebitengine 公式組織が開発している
- ruins での用途: 開発時にバランス調整用の数値を実行中に変更したり、ECS のエンティティ数や FPS/TPS を画面に出したりする用途に使える。本番 UI である `internal/widgets` やゴールデン比較基盤である `internal/vrt` とは役割が異なり、開発ビルド限定のオーバーレイとして独立に使える
- 成熟度: スター約100。Ebitengine 公式組織の管理下だが開発中でAPIが頻繁に変わる旨が明記されている
- ライセンス: Apache License 2.0。内部で使う Microui 部分は MIT
- 採用時の注意: API が安定していないため、本番コードパスに組み込まず開発者用デバッグビルドの一部に閉じて使うのが無難

## 採用しなかった代替

- GitHub Trending 月間 Go ランキングに載った項目全般: コードレビューツール・LLM 基盤・ペネトレーションテストツールなどが中心で、ruins のゲーム開発やGo開発基盤に関係する候補が無かったため除外した
- mlange-42/ark-tools: Ark ECS 向けのスケジューラ・システム基盤を提供するが、ruins は `internal/engine` に独自のスケジューラとステート機構を持ち、`engine_guard` の depguard 設定でも依存先を意図的に絞っている。既存設計と役割が重なり置き換えのメリットが薄いため見送る
- SolarLune/resolv などの2D衝突判定ライブラリ: ruins のダンジョン・オーバーワールドはタイル・チャンク単位のグリッドベースで、連続座標の衝突判定を要する箇所が見当たらなかったため見送る
- go-tiled・ldtkgo などのタイルマップフォーマットローダー: `internal/mapplanner` や `internal/maptemplate` で独自のマップ生成・テンプレート機構を既に持ち、外部エディタ形式への依存が設計に合わないため見送る
- EbitenUI などの Ebiten 向け UI ウィジェットライブラリ: `internal/widgets` と `yohamta/furex` による自前のレイアウト・テーマ機構が既にあり、`ui_core_guard` 等の depguard で接続点を1箇所に絞る設計方針とも衝突するため見送る
