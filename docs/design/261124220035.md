# 否定形のコンポーネントを肯定形にする

## 背景

通れるかどうかは、通れない印 `BlockPass` と、通るときの移動コスト `PassCost` の2つのコンポーネントで表している。raw の行も `blockPass` と `passCost` の2欄に分かれる。「通れないのに移動コストがある」という矛盾した組が書けてしまうので、CUE の制約 `passCostAbsent` で塞いでいる。

本来は、素通り・移動コストを払って通る・通れない、という1つの性質の3つの値である。通る側の肯定形の1つにまとめれば、矛盾した組がそもそも書けない。

同じ否定形の印がほかにもある。見通せない印 `BlockView` と、まだ探していない収納の印 `Unsearched` である。これらも肯定形にそろえる。

長く効くのは、値が付く側に印を置くことである。通り方は移動コストで最初の値を得た。湖の区域で浅瀬と深い水が入り、泳げる敵だけが入れる、小さな生き物だけが抜けられる、装備で遅くなる、のように通り方の値は増えていく見込みが高い。否定形の印は値を持てないので、値が増えるたびに別のコンポーネントと、通れないこととの組を禁じる制約が増える。肯定形なら通る側の構造体に値を足すだけで済む。見通しも、草や煙の部分的な遮りのように見通す側に値が付きうる。

肯定形にすると、新しい地形と置物は通り方を宣言しないと通れない。付け忘れは壁としてすぐ目に付く。否定形では付け忘れが、塞ぐべき物を素通りできる床になり、見落としやすい。データの誤りが目に付く向きに倒れるのも、長く保つ上での利点である。

## 要件

- 通れるかと移動コストを、通る側の1つのコンポーネントで表す。矛盾した組が書けない
- 見通せるかを、見通す側の印で表す
- 探したかを、探した側の印で表す
- raw の行も同じ形にし、`passCostAbsent` の制約を要らなくする
- 遊びの挙動は変えない。今の golden が変わらない

## 設計

### 対象

| 今 | 肯定形 | 対象にする理由 |
|---|---|---|
| `BlockPass` と `PassCost` | `Passable{Cost}` | 通れない印と、通るときの値が別で、矛盾した組が書ける |
| `BlockView` | `SeeThrough` | 見通せない印 |
| `Unsearched` | `Searched` | まだ探していない印 |

`Dead` と `Suspended` は、死んだ、退避した、という出来事の結果を表す肯定の状態なので対象にしない。

### データ

```go
// 変更前
type BlockPass struct{}             // あれば通れない
type PassCost struct{ Value int }   // あれば移るときに足す
type BlockView struct{}             // あれば見通せない
type Unsearched struct{}            // あればまだ探していない

// 変更後
// Passable は通れる地形と置物の印。Cost は上へ移るときに標準の移動に足す移動コストで、0 なら素通り
type Passable struct{ Cost int }
// SeeThrough は見通せる地形と置物の印
type SeeThrough struct{}
// Searched は探し終えた収納の印
type Searched struct{}
```

raw の行も通る側の欄にまとめる。

```cue
// 変更前
#Tile: {
	blockPass!: #BlocksPassage
	blockView!: #BlocksView
	passCost?:  #PassCost
	if blockPass {
		passCostAbsent: true & passCost == _|_ @rawgen(-)
	}
}

// 変更後
#Tile: {
	// 通り方。省くと通れない
	passable?: #Passable
	// 見通せるか
	seeThrough!: bool
}

#Passable: {
	// 上へ移るときに足す移動コスト。省くと素通り。0 と省略で同じ意味を2通りに書けないよう1以上にする
	cost?: #PassCost & >=1
}
```

```toml
# 変更前
blockPass = false
blockView = false
passCost = 100

# 変更後
seeThrough = true
[tiles.passable]
  cost = 100
```

### 誰が印を持つか

否定形の印は、持たない実体を「関係なし」として無視できる。肯定形にすると、印を持たないことが「通れない」「見通せない」を意味するので、それを判定する対象を決める必要がある。同じマスにはアイテム・飾り・跡など、通れるかと無関係な実体も乗る。

- 通れるか: そのマスの地形と置物のうち、`Passable` を持たないものが1つでもあれば通れない。地形は `Tile`、置物は `Prop` で見分ける
- 見通せるか: そのマスの地形と置物のうち、`SeeThrough` を持たないものが1つでもあれば見通せない
- 移動コスト: そのマスの地形と置物の `Passable.Cost` を足す
- 射線の遮蔽物: そのマスの地形と置物のうち、`SeeThrough` を持ち `Passable` を持たないものを数える

壊れた置物は掃除されるまで `Dead` のままマスに残る。今のコードで `Dead` を除くのは、通れるかの空間索引と塞ぐもののログだけで、見通し・移動コスト・射線・散布の占有は除かない。置き換えの段では判定ごとの今の扱いをそのまま写す。`Dead` の扱いをそろえるのは挙動が変わるので、進め方の段 4 に分ける。置き換えと挙動の変更を同じ段でやると、golden が変わったときに原因を切り分けにくい。

Ark のフィルタは「または」を書けないので、地形と置物を引くクエリは `Tile` と `Prop` の2本に分かれる。通れないマスは `With(Tile).Without(Passable)` と `With(Prop).Without(Passable)` の2本で集める。Ark は archetype で絞るので、走査するのは通れない実体、つまり壁と通れない置物だけで、今の `BlockPass` を持つ実体と同じ集合になる。見通せないマスと散布の占有も、同じく `Without(SeeThrough)` と `Without(Passable)` で書く。

否定形を裏返すと、対象が地形と置物の外へ広がる所がある。印の有無を見る前に、地形か置物かで絞る。

- 射線 `checkLineOfSight` は、マスの全実体を `GetEntitiesAt` で回している。素直に `!SeeThrough.Has(e)` と裏返すと、射線上の敵や落ちているアイテムが壁になる
- 閉じた壁にはめる置物 `closedInsets` のクエリは `Without(Tile)` を使う。`Without(Tile, Passable)` と裏返すとキャラクターやアイテムも入るので `With(Prop)` にする
- 壁の影 `render_sprite.go` のクエリも、`Tile` に絞る

移動コストは床のタイルの全てが `Passable` を持つので、`Passable` を持つ実体を走査すると1歩ごとに床を全てなめる。移動コストは空間索引に `map[GridElement]int` で載せ、移動のたびに座標から引く。段 2 の必須の作業にする。今の `getPassCostAt` の全走査もこれで無くなる。

印が無いことを「通れない」と読むので、付け忘れや失った印は黙って壁になる。今の否定形では付け忘れは通れる床になるだけで、失敗の向きが逆になる。`passable` を省くと通れないので、床の系統のタイルの行が `passable` を持つことを確かめるテストを置く。`seeThrough!` は必須にし、書き忘れを CUE で落とす。

空間索引 `SpatialIndex` は、今は `BlockPass` を持つ実体を集めて通れないマスの集合を作る。変更後は上の2本のクエリで通れないマスの集合を作る。集合の形は変えない。索引を引く `IsBlockPass` は否定形の印に依らない `IsBlocked` に名前を変え、引く側の名前だけを直す。

### 扉

扉は今、開くと `BlockPass` と `BlockView` を外し、閉じると付ける。変更後は、開くと `Passable` と `SeeThrough` を付け、閉じると外す。付け外しの向きが逆になるだけで、空間索引と視界の更新の印 `StatsChanged` などは同じである。閉じると `Passable` ごと消えるので、開くときに作り直す。開いた扉の移動コストは 0 とし、`Passable{}` を付ける。扉の行は通れない形で書き、`passable` を持たず `seeThrough = true` とする。閉じた扉が見通せないのは今と同じく生成のときに付け外しで決め、閉じた状態で生まれる扉は生成のときに `SeeThrough` を外す。

### 収納

`Unsearched` は置物の行から作るときに `NewPropSpec` が収納へ付け、探し終えると外れる。キューブに置く設備の収納 `deployable_storage` は、アイテムを `PlaceFacility` で置物へ変えるので `NewPropSpec` を通らず、`Unsearched` を持たない。つまりプレイヤーが置いた収納は最初から探し終えている。変更後は、行から作る収納は `Searched` を持たずに生まれ、探し終えると付く。`PlaceFacility` は置くときに `Searched` を付ける。付け忘れると、空の収納が未探索の飾りで出るので、置いた収納が `Searched` を持つことをテストで確かめる。

### 地図の計画

`mapplanner` はタイルの行の `BlockPass` で通れるかを判定する。行の欄が `passable` に変わるので、`Passable == nil` を通れないとして読む。計画の中のタイルの通れるかは実体のコンポーネントでなく行から読むので、印の向きを変えるだけで済む。

### セーブ

`BlockPass`・`BlockView`・`PassCost`・`Unsearched` はどれも保存している。名前を変えると古いセーブは読めない。未リリースなのでセーブの互換は考えず、`saveDataVersion` を上げて古いセーブを読まない。肯定形では印を失うと全てのマスが通れなくなるので、置き換えた印がセーブの往復で残ることをテストで確かめる。

### 進め方

1. `Unsearched` を `Searched` にする。収納の生成と探す行為と装飾だけで閉じ、小さい
2. `BlockPass` と `PassCost` を `Passable{Cost}` にする。raw の行・空間索引・扉・計画・描画・射線を変え、`passCostAbsent` を消す
3. `BlockView` を `SeeThrough` にする。2 と同じく地形と置物を対象にする
4. 見通し・移動コスト・射線・散布の占有でも `Dead` の置物を除き、通れるかとそろえる。挙動が変わるので、この段だけは golden が変わってよい

段 1 から 3 では golden が変わらないことを確かめる。射線や影は golden で拾えないことがあるので、射線上のキャラクターやアイテムが遮らないことを `checkLineOfSight` の単体テストで固定する。raw の行の移行は、欄を読み替える短いスクリプトで一度に書き換える。

## 採用しなかった方法

| 案 | 理由 |
|---|---|
| 否定形のまま、矛盾を CUE の制約で塞ぐ | 今の形。矛盾した組が書ける形のまま、塞ぐ決まりを足し続けることになる |
| 通り方を1つの列挙 `free`・`blocked` と移動コストの数で持つ | 移動コストの数が、通れるときにしか意味を持たない。通る側の構造体に入れれば、通れないときは構造体ごと無い |
| `Dead` と `Suspended` も肯定形にする | 出来事の結果を表す肯定の状態で、否定形ではない。生きている印を全ての実体に付けることになる |
| 印を全ての実体に付け、持たない実体を無くす | アイテムや飾りまで通れる印を持つことになり、印の意味が薄れる。判定の対象を地形と置物に絞る |
| `passable!: #Passable \| "none"` のように、通れないことも明示させる | 書き忘れは CUE で落ちるが、欄の書き方が2通りに増え、生成する Go の型が和型になる。書き忘れは壁として目に付き、床の系統のテストでも拾える |
| 見通しも `seeThrough?: {}` の有無で表し、通り方と形をそろえる | 見通しは値を持たないので有無で表す理由が無く、書き忘れまで黙って壁になる。必須の真偽値にして CUE で落とす |

## コメント

- 空間索引の構築は `Without(Passable)` のクエリで通れない実体だけを走査する。今の `BlockPass` を持つ実体と同じ集合なので、走査の量は変わらない
- 深い水は通れて見通せるので、置き換えの前後とも遮蔽物に数えない。射線の遮蔽物は見通せるが通れない地形と置物で、置き換えの前後で同じ物を数えることを確かめる
- 移動コストの走査の重さは、湖の区域の設計 doc 261124195212 の進捗の先頭にある。`Passable.Cost` を地形と置物から引く形にするとき、座標から引く索引に一緒に載せられる
