# 一定ターンごとのオートセーブと新規開始時の復帰点

## 背景

現状、オートセーブ機構 `SerializationManager.AutoSave` は実装済みだが、ゲームプレイからの
発火点が一つも無い。手動セーブだけがセーブメニューのスロット選択で書かれる。クラッシュや
不意の終了で進捗が失われる。

Continue 機能は起動時に最新オートセーブを読み込むが、書き込み契機が無いため読むデータが
生まれない。書き込みと読み込みは相補的で、両方揃って初めて機能する。

本タスクは書き込み契機を足し、あわせて Continue のロード対象を手動と自動の全スロットから
最新を選ぶ形に広げる。

## 要件

- 一定ターンごとに自動でセーブする。間隔は150ターン。1日=1500ターンなので約0.1日ごと。
- 睡眠や休息などの fast-forward 中、すなわち継続アクティビティ中は保存を抑止し、活動が
  終わった直後に1回だけ保存する。1フレームに複数回のフルワールド直列化を避ける。
- 新規ゲーム開始直後にも1回オートセーブし、最初の復帰点を作る。
- オートセーブ失敗はターン進行を止めない。ログに残して続行する。
- 体験版などセーブ無効時、`SaveLoadEnabled=false` では何もしない。
- 開発時の Continue は手動と自動の全スロットから最新のデータを読み込む。

## 設計

### 発火規則を1つに畳む

間隔判定を「モジュロ」でなく「前回保存からの経過ターン」にする。継続中に見送った複数の
150境界が、活動完了時の1回へ自然に畳み込まれる。加えてゼロ値を未保存の合図に使い、新規
開始直後の初回保存を特別扱いなしで同じ規則から出す。

```go
// 発火条件。すべて満たしたとき AutoSave し、LastAutoSaveTurn を現在ターンへ進める
!playerHasActivity(world) &&
    (turnState.LastAutoSaveTurn == 0 || // 0 は未オートセーブ。新規開始直後に1度保存する
        turnState.TurnNumber-turnState.LastAutoSaveTurn >= autoSaveInterval)
```

- 新規開始: `LastAutoSaveTurn` はゼロ値 0、`TurnNumber` は1。継続中でなければ初回フレームで
  保存し `LastAutoSaveTurn=1` になる。これが新規開始直後の復帰点。
- 以後: `TurnNumber-LastAutoSaveTurn` が150に達するたび保存する。
- 継続中: `playerHasActivity` が真の間は見送り、活動終了後の通常ターンで畳んで保存する。
- ロード復帰: `LastAutoSaveTurn` はセーブ時の値を持ち越すので、直後の余計な保存は起きない。

### 前回保存ターンの持ち方

`TurnState` にフィールドを1つ足す。ターン番号と同じ「ランの時計」なのでここに置く。
`TurnState` は serde 保存対象なのでセーブ/ロードで持ち越せる。

```go
// 変更前
type TurnState struct {
	Phase      TurnPhase
	TurnNumber consts.Turn
}

// 変更後
type TurnState struct {
	Phase            TurnPhase
	TurnNumber       consts.Turn
	LastAutoSaveTurn consts.Turn // 最後にオートセーブしたターン。0 は未オートセーブ
}
```

### autoSaver を states に置く。import 循環を避ける

`SerializationManager` を `Resources` に置くと `save → world → resources → save` の import
循環になる。かといって `systems` にも置けない。`save` のテストはテストヘルパ `vrt` を経由して
`systems` と `maingame` を引くので、この2パッケージから `save` を import すると
`save.test → vrt → systems → save` のテスト循環になる。

`states` は `save` を既に import しており循環しない。`vrt` は `internal/states` を引かないため。
そこで `internal/states/autosave.go` に置き、`DungeonState` が所有して毎フレーム呼ぶ。

```go
// autoSaver は SerializationManager を1つ所有し、セーブ無効時や生成失敗時は何もしない。
type autoSaver struct {
	manager *save.SerializationManager // nil なら no-op
}

func newAutoSaver(world w.World) *autoSaver {
	if !world.Resources.Config.SaveLoadEnabled {
		return &autoSaver{}
	}
	m, err := save.NewSerializationManager()
	if err != nil {
		logger.New(logger.CategorySave).Warn("autosave: failed to init manager", "error", err.Error())
		return &autoSaver{}
	}
	return &autoSaver{manager: m}
}

func (a *autoSaver) maybeSave(world w.World) {
	if a.manager == nil {
		return
	}
	if playerHasActivity(world) {
		return
	}
	ts := query.GetTurnState(world)
	if ts.LastAutoSaveTurn != 0 && ts.TurnNumber-ts.LastAutoSaveTurn < autoSaveInterval {
		return
	}
	if err := a.manager.AutoSave(world); err != nil {
		logger.New(logger.CategorySave).Warn("autosave failed", "error", err.Error())
		return // 失敗はゲーム進行を止めない
	}
	ts.LastAutoSaveTurn = ts.TurnNumber
}
```

`query.GetTurnState` は可変ポインタを返すので `ts.LastAutoSaveTurn` の書き込みが反映される。

### 実行契機

`DungeonState` が `autoSaver` を `OnStart` で構成し、`Update` の `runUpdaters` 後に `maybeSave`
を呼ぶ。ゲームプレイ中の唯一のステートである `DungeonState` が、盤面が動くフレームで判定する。
新規開始とロード復帰のどちらも `OnStart` を通るので、両方で同じ経路が効く。

### 再生時は書かない

VRT とベンチは `DungeonState.Update` を回すので、放置すると golden の副作用でセーブファイルを
書いてしまう。全ての再生は `vrt.InitReplayWorld` を単一の入口として通るので、そこで config の
`DisableAutoSave` を立て、`newAutoSaver` がこれを見て no-op になる。`SaveLoadEnabled` を落とすと
Load や Save のメニュー項目が消えて別の golden とシナリオが壊れるため、UI に影響しない専用フラグに
する。`DisableAnimation` や `DisableScreenFilter` と同じ、再生時に挙動を安定させる config の並び。

### Continue のロード対象を広げる

`NewContinueState` は今 `ListAutoSaves()[0]` を読む。`ListSaves()` は手動と自動を混ぜて
タイムスタンプ降順で返すので、`ListSaves()[0]` に替えるだけで全スロットから最新になる。

```go
// 変更前: 自動のみ
saves, err := saveManager.ListAutoSaves()
// 変更後: 手動と自動から最新
saves, err := saveManager.ListSaves()
```

## なぜこの形か

- 発火を1規則に畳むのは、間隔判定と継続中抑止と新規開始初回を別々の分岐で持たないため。
  分岐が増えるほど取りこぼしと二重発火の隙が増える。経過ターンとゼロ値合図で1式に閉じる。
- マネージャを状態持ちシステムに所有させるのは、import 循環を避けつつグローバル可変状態も
  作らないため。`InputSource` を world 単位で持つ既存方針と同じ考え。
- 前回保存ターンを `TurnState` に置くのは、オートセーブの間隔がセッションでなくランの性質
  だから。セーブ/ロードで cadence を正しく持ち越す。
- Continue を `ListSaves` に替えるのは、最新の復帰点が手動か自動かに依らず一番新しいものを
  読むのが利用者の期待だから。既存の並び替えをそのまま使い、新たな比較ロジックを足さない。

## 採用しなかった方法

- **`Resources` にマネージャを載せる**: `save → world → resources → save` の import 循環。却下。
- **`systems` に AutoSaveSystem を置く**: `save.test → vrt → systems → save` のテスト循環になる。
  `vrt` は `systems` と `maingame` を引くので、その2パッケージから `save` は import できない。
  既存で安全な `states → save` を使う。
- **`runEndPhase` に保存を直に埋め込む**: ターン確定点に副作用を足すと、ターン進行と永続化の
  責務が混ざる。マネージャの持ち場も無い。`DungeonState` から独立した `autoSaver` に分ける。
- **再生の抑止に `SaveLoadEnabled` を落とす**: Load や Save のメニュー項目が消え、別の golden と
  シナリオが壊れる。UI に影響しない `DisableAutoSave` にする。
- **再生の抑止を `InputSource != nil` で判定する**: `PlayScenario` は捕まえるが、`InputSource` を
  差さない単フレーム golden を取りこぼす。全再生が通る `InitReplayWorld` のフラグにする。
- **前回保存ターンを AutoSaveSystem の struct フィールドに持つ**: セッション限りになり、ロード
  ごとに直後の余計な保存が出る。実装は小さいが cadence の持ち越しが崩れる。`TurnState` に置く。
- **新規開始初回を states 層から save 直呼び**: マネージャが二重になり発火点が分散する。ゼロ値
  合図で同じシステムの同じ規則に畳む。
- **別コンポーネント `AutoSaveState` に分離**: 責務は綺麗になるが、単一のターン番号のために登録表
  追加と生成の儀式が増える。`TurnNumber` と密結合なので `TurnState` の1フィールドで足りる。
- **モジュロ `TurnNumber % 150 == 0` で判定**: 150境界が継続中の抑止区間に落ちると取りこぼし
  二度と発火しない。経過ターン方式にする。

- `make check`。
- AutoSaveSystem のユニットテスト: 新規開始で初回保存が出る・150未満では出ない・150到達で
  出る・継続アクティビティ中は出ない・`SaveLoadEnabled=false` で no-op。

## リスク・影響範囲

- 未リリースなのでセーブ後方互換は考慮不要。旧オートセーブに `LastAutoSaveTurn` が無くても
  ゼロ値に落ちるだけで、ロード直後に1度保存が出る。無害。
- フルワールド直列化のコスト。150ターンごと、かつ継続中抑止なので1フレームに複数回は起きない。
  実測で跳ねが出たら間隔調整で対処する。
- `internal/states` の `TestGolden` はローカルでフォント AA と GL 実装差により落ちるが、本変更前の
  ブランチ先端でも同数落ちる既存の環境依存で、CI では緑。本変更起因ではない。
