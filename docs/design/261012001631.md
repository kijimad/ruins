# コード監査: 地物重複とセーブ書き込み 2026-10-12

## 背景

自律コード監査エージェントが internal 配下を横断的に精読した。golangci-lint は forcetypeassert・errcheck・nilerr/nilnil・exhaustive・makezero 等で機械的な誤りを広く捕まえているため、今回は **lint が意味を理解しないと分からないロジック・意味論の誤り** だけを狙った。activity/aiinput/systems、dungeon/mapplanner/mapspawner/maptemplate/geometry、overworld/raw/balance/formula、save/world/loader/components、states/menuloop/input/widgets、render3d/engine/screeneffect/resources の6領域を調査し、各候補を敵対的に検証したうえで3件に絞った。修正はせず、この doc にタスクとして起こす。

## 設計

### 1. 遺跡入口が市街地・集落の優先度判定を無視して重複配置される

- **file:line**: `internal/overworld/dungeon_entrance.go:23-38`（`dungeonEntranceFeature.place`）
- **症状**: 地物の優先度は `internal/overworld/schematic.go:101-118` の `chunkTypeAt` が「市街地 > 遺跡入口 > 集落 > 点在ランドマーク > 荒れ地」として一元管理すると明言している。実際に `settlementFeature.place`（`settlement.go:47-57`）は市街地当選と重なったら明示的に譲り（`urbanRegionOf` を確認）、`wildernessLandmarkFeature.place`（`landmark.go:69-71`）は `chunkTypeAt` を直接問い合わせて全上位種別に譲る。しかし `dungeonEntranceFeature.place` だけは `dungeonEntrancePlacement.At` しか見ず、市街地・集落との重なりを一切確認しない。
- **根拠・失敗シナリオ**: `dungeonEntrancePlacement`（Spacing4/Separation1）と `urbanPlacement`（Spacing6/Separation2）は独立したハッシュで当選チャンクを決めるため、帯を北進するほど同一チャンクが両方の当選になる座標が現れる。`features()`（`feature.go:64-67`）の評価順は `settlementFeature, urbanFeature, dungeonEntranceFeature, wildernessLandmarkFeature, roadFeature, openTerrainFeature` で、`urbanFeature.place`（`urban.go:170-182`）が建物の壁・街路タイルを先に敷いた後、`dungeonEntranceFeature.place` がチャンク中心に無条件で `SpawnDungeonEntrance` を置く。`SpawnDungeonEntrance`（`internal/world/lifecycle/spawn_prop.go:106-126`）は occupied や BlockPass を確認せず `GridElement` をそのまま設定するため、中心が建物の壁タイル上やどの部屋からも到達できない場所になれば、遺跡入口が永久に到達不能になる。地図側は `chunkPlace` が `chunkTypeAt` の優先度に従って市街地記号を表示するため、プレイヤーには遺跡入口の存在自体が見えない。さらに `dungeonEntrancePlacement` と `settlementPlacement`（Spacing5/Separation1）の当選が重なるケースでは、`settlementFeature` は市街地にしか譲らないため、集落の建物と遺跡入口の両方が同じチャンクに生成される。
- **修正方針案**: `dungeonEntranceFeature.place` の先頭で `urbanRegionOf` および `settlementPlacement.At` による重なりチェックを追加し、`chunkTypeAt` の優先度と一致させる。あるいは `place` の判定自体を `chunkTypeAt(...) == chunkDungeonEntrance` に一本化し、優先度の単一出典を徹底する。

### 2. セーブファイルの書き込みが非アトミックで、中断時に既存セーブを破壊する

- **file:line**: `internal/save/desktop.go:24-33`（`saveDataImpl`）
- **症状**: `os.WriteFile(fileName, data, 0644)` が対象スロットのファイルへ直接・インプレースで書き込む。一時ファイルに書いてから `os.Rename` で置き換える atomic write パターンを使っていない。
- **根拠・失敗シナリオ**: プレイヤーが既存のマニュアルセーブ、またはローテーションするオートセーブがある状態で再度セーブした際、`os.WriteFile` の書き込み中にプロセスが kill される・OS がクラッシュする・ディスクフルになるなどで中断すると、対象スロットのファイルは新データでも旧データでもない不完全な gzip バイト列になる。次回ロード時は展開や checksum 検証で失敗しエラーにはなるが、**上書き前に存在していた有効なセーブデータそのものが失われる**。オートセーブは定期的に同じ少数スロットへ上書きするため発生機会が多く、進行がまとめて失われるリスクが高い。
- **なぜ lint で検出できないか**: `os.WriteFile` の戻り値エラーは適切にチェック・ラップされており errcheck 上は健全。問題は「失敗時に副作用として対象ファイルの既存内容を破壊する」という操作の耐障害性であり、静的解析では判断できない。
- **修正方針案**: `os.CreateTemp` で同ディレクトリに一時ファイルを作り、書き込み・`Sync`・`Close` 後に `os.Rename` で対象ファイル名へ差し替える。rename は同一ファイルシステム内であれば原子的なので、書き込み中断時も旧ファイルがそのまま残る。WASM 側（`localStorage` ベース）はキー単位の書き込みでこの種の部分破壊が起きにくいため対象外でよい。

### 3. テンプレート検証のエラーメッセージで引数の対応が入れ替わっている

- **file:line**: `internal/maptemplate/template.go:719-722`（`validateRectangle`）
- **症状**: `fmt.Errorf` のフォーマット文字列 `"identifier '%s': invalid char '%c' in placeholder region [%d,%d]; expected '@' or '%s'"` に対し、渡す引数が `id, x, y, ch, id` の順になっている。`%c` には不正文字 `ch` を渡すべきだが座標 `x`（int）を渡し、2つ目の `%d` には `y` でなく `ch`（rune）を渡している。
- **根拠・失敗シナリオ**: テンプレート TOML のマップ内で `@` でも識別子でもない文字が矩形プレースホルダ領域に混入した際に呼ばれるエラーで、表示される「invalid char」が実際の不正文字ではなく x 座標を文字化した無関係な値になり、`[%d,%d]` の2つ目も y でなく文字コードになる。テンプレート作者がエラーメッセージから原因を誤認する。
- **なぜ lint で検出できないか**: `x`（int）は `%c` の型要件を満たし、`ch`（rune）は `%d` の型要件を満たすため、printf 系 linter・`go vet` の型チェックを通過する（`go vet ./internal/maptemplate/...` で無警告を確認済み）。引数の並び順という意味的な誤りで、機械的検出は不可能。
- **修正方針案**: `fmt.Errorf` の引数順を `id, ch, x, y, id` に直す。
