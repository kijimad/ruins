# 天気システムを設計する

## 背景

ruins にはオーバーワールドの一般天気、晴・曇・雨・雪・霧などが無い。既にある関連要素は次のとおり。

- `GameTime{TotalTurns}` シングルトン。`GetTimeOfDay` で時間帯6区分、`GetTemperatureModifier` で時間帯ごとの気温修正を持つ。`turnsPerDay=1500`、時間帯あたり250ターン。季節は未実装。
- `TileTemperature{Shelter, Water, Foliage}` コンポーネント。タイル環境ごとの気温修正。
- `CalculateEnvTemperature = ステージ基本気温 + タイル修正 + 時間帯修正`。摂氏で算出する。
- `TemperatureSystem` が快適温度域と断熱値から寒暑ダメージを与える。
- 寒波前線 `FrostRenderSystem` と temperature 系。空間的に西へ動く極低温ハザード。特定の演出であり一般天気ではない。
- `IsOnOverworld` が霜・寒波前線などオーバーワールド固有の効果を gate する。現ステージが帯データ `SeamlessBand` を持つかで判定する。
- 視界は `VisionSystem`、視界半径 `VisionRadiusTiles=24`、暗さ `DarknessVisible=0.15`。
- ワールドは `config.Seed` と PCG RNG で決定論的に生成される。

目的は、オーバーワールドに一般天気を足し、視界・環境気温・光・降水演出へ効かせること。既存の気温・寒波前線・帯という抽象に天気を重ねる。

## 要件

- オーバーワールドに一般天気を出す。初期は晴・曇・雨・雷雨・雪・霧。
- 決定論的にする。`(時刻, seed)` から再現でき、保存状態を増やさない。非決定論を持ち込まず全量を純関数にする。
- 天気は視界・環境気温・光・降水演出へ効く。
- 屋内・ダンジョン・遺跡は天気の影響外。`IsOnOverworld` で gate する。
- 既存の寒波前線・気温と共存する。天気は前線を置き換えない。

## 設計

### 全体方針

天気を「生成 → 型 → 効果」の3層に分ける。ruins の既存システムがこの分割に素直に対応する。生成は時刻と seed から天気の元になる量を出し、型はその量から離散的な天気を選び、効果は天気の値を各システムへ配る。

- **決定論を全面採用する**。ruins はオーバーワールドを `SeamlessBand.RunSeed`、`internal/components/dungeon.go`、と PCG RNG で決定論生成している。チャンク生成も散布もこの seed を起点にする。天気もオーバーワールド固有なので `RunSeed` を起点にし、状態を保存せず `GameTime.TotalTurns` と `RunSeed` から都度算出する純関数にする。天気を「ピリオド」に区切り、periodIndex ごとに1つ固定する。セーブを増やさず再現でき、予報も同じ関数で出せる。
- **連続量を ruins の気温に寄せて2つに絞る**。ruins は `CalculateEnvTemperature` で気温を既に持つ。天気選択の連続量は「気温」と「降水ポテンシャル」の2つにする。降水ポテンシャルは雲・湿りの代理で 0..1、決定論ハッシュから出す。雨か雪かは気温閾値で分ける。湿度・気圧・風など他の気象量は ruins の他所で使わないため導入しない。
- **空間変化はしない**。現オーバーワールドで単一の天気にする。時刻に依存し位置に依存しない。空間的な寒暖差は ruins 既存の寒波前線が担うので、天気は時刻依存の一様な状態に徹する。

### データ定義

```go
// PrecipClass は降水の強さ
type PrecipClass int

const (
	PrecipNone PrecipClass = iota
	PrecipLight
	PrecipHeavy
)

// WeatherPoint は決定論的に算出する連続量。ruins の気温に降水ポテンシャルを足した2量へ絞る。
type WeatherPoint struct {
	Temperature     int     // ℃。天気オフセット前の環境気温
	PrecipPotential float64 // 0..1。雲・湿りの代理。決定論ハッシュから
}

// WeatherType はデータ駆動の天気型。効果を値で宣言し、効果側の各システムがこれを読む。
type WeatherType struct {
	ID           WeatherID
	Name         string                  // 表示名
	Priority     int                     // 高いほど優先
	RequiredPrev []WeatherID             // 前提天気チェーン。空なら無条件
	// 発生条件。func でなく閾値の値にし、シリアライズ・比較・テーブルドリブンテストを可能にする。
	// precip は降水ポテンシャル 0..1、temp は気温。未設定の端は ±無限のセンチネルで無制限にする
	MinPrecip, MaxPrecip float64
	MinTemp, MaxTemp     int

	// 効果
	VisionScale  float64     // 視界半径の倍率。1.0で無影響、1未満で狭まる
	Darkness     float64     // 追加の暗さ 0..1。曇・雨で薄暗く
	TempModifier int         // 環境気温オフセット ℃
	Precip       PrecipClass // 降水の強さ
	Snow         bool        // 降水が雪か。見た目と将来の積雪用
}
```

### 天気の決定 : 決定論・状態レス

```go
// CurrentWeather は現在の天気型を返す。状態を保存せず、時刻と seed から都度算出する。
func CurrentWeather(world w.World) *WeatherType {
	if !IsOnOverworld(world) {
		return weatherClear // 屋内・ダンジョンは常に無天気
	}
	period := int(GetGameTime(world).TotalTurns) / turnsPerWeatherPeriod
	p := computeWeatherPoint(world, period)
	prev := selectWeather(computeWeatherPoint(world, period-1)) // 前ピリオドの天気
	return selectWeather(p, prev)
}
```

- `turnsPerWeatherPeriod = 500`。turnsPerDay=1500 の約1/3、時間帯2区分ぶん、を初期値にする。1日に約3回天気が変わる。プレイ感を見て調整する。
- `computeWeatherPoint(world, period)`: 気温は代表点の環境気温、天気オフセット前の値を使う。降水ポテンシャルは `smoothHash(RunSeed, period)` で、隣接ピリオドを**線形補間**して境界での急変を避ける。線形で足り、コサイン等は要らない。
- `selectWeather`: WeatherType 一覧を Priority 昇順に走査し、`RequiredPrev` と閾値の両方を満たす最高優先度を採用する。`RequiredPrev` は **OR** で、前ピリオド天気がリストのいずれかに一致、またはリストが空なら通す。閾値は precip と temp が範囲内かで判定する。既定は clear。優先度と前提のラダーで、穏やかな天気から段階的に荒れる天気へ上がる。
- 予報は同じ関数へ未来の period を渡すだけで出せる。
- 1ターン内の多重呼び出しは、SpatialIndex と同じくメモ化で再計算チャーンを避ける。

### カタログ 初期案

数値は初期値で調整前提。気温は天気オフセット前の値で判定する。

| ID | 優先 | 前提 | 条件 | VisionScale | Darkness | Temp | Precip | Snow |
|---|---|---|---|---|---|---|---|---|
| clear | 0 | - | 既定 | 1.0 | 0 | 0 | none | - |
| fog | 15 | clear | precip 0.3..0.5 | 0.55 | 0.10 | 0 | none | - |
| cloudy | 20 | - | precip≥0.4 | 1.0 | 0.10 | -1 | none | - |
| rain | 50 | cloudy | precip≥0.7 かつ temp≥1 | 0.80 | 0.20 | -2 | heavy | 否 |
| storm | 60 | rain | precip≥0.85 かつ temp≥1 | 0.65 | 0.30 | -3 | heavy | 否 |
| snow | 100 | cloudy,rain | precip≥0.7 かつ temp<1 | 0.75 | 0.15 | -2 | heavy | 是 |

- 前提の複数指定、snow の `cloudy,rain`、は OR。前ピリオドがそのいずれかなら通す。
- **霧は快晴からのみ**にする。地形霧の演出として快晴時に限定し、荒天や雨上がりからの霧は当面出さない。現実の曇天・雨上がりの霧より単純さを採る。将来プレイ感を見て前提を広げる余地は残す。

### 効果の配線

1. **気温**: `CalculateEnvTemperature` に天気の `TempModifier` を1項加える。`base + tile + time + weather`。`TemperatureSystem` の寒暑ダメージへ自動反映される。判定用の気温は天気オフセット前を使い、循環を避ける。
2. **視界**: `VisionSystem` の `visionRadius` に `VisionScale` を掛ける。屋外のときのみ。ruins の視界はタイル半径ベースなので、天気の視界効果は不透明度でなく視界半径の縮小で表す。天気が変わった period では `vs.RequestUpdate()` で視界を再計算する。
3. **光・暗さ**: `computeTileRenderMap` の可視タイル `Darkness` に `WeatherType.Darkness` を加える。上限を **0.60** にクランプする。可視の基準 `DarknessVisible=0.15`、`vision.go`、に嵐の 0.30 を足しても記憶タイルの `DarknessRemembered=0.75` を超えず、可視と記憶の境界が壊れないようにする。曇・雨で薄暗くなる。
4. **降水演出**: `RainRenderSystem` を `FrostRenderSystem` と同じ雛形で新設する。`IsOnOverworld` で gate し、可視かつ屋外のタイルへ雨・雪の粒を描く。`helper.go` の Renderers へ登録する。
5. **gate**: すべて `IsOnOverworld` で屋外限定にする。帯データを持たないダンジョン・屋内・遺跡は自動的に影響外になる。

### 状態の持ち方

`WeatherState` シングルトンは持たないことを推奨する。`GameTime.TotalTurns` と `Seed` から算出する純関数へ寄せ、キャッシュは1ターン内のメモ化のみにする。SpatialIndex と同じ再構築パターン。

### 寒波前線との関係

別機構として共存する。天気は時刻依存で一様な環境状態、寒波前線は空間的に動く極低温ハザード。両者とも気温と視界へ加算合成する。天気は前線を置き換えない。天気を前線に紐づけない理由は「採用しなかった方法」に記す。

### 実装フェーズ

天気は生成層と効果層に分けられ、依存の向きが異なる。効果は天気を1つ与えれば独立に動くが、生成の地域差はバイオーム、地域ごとの気候の解像度に品質が縛られる。バイオームはまだ本格実装が無いので、生成の作り込みは早い。よって2フェーズに分ける。

- **フェーズ1: 効果層を先に実装する**。`WeatherType` の効果を視界・気温・降水演出へ配線する。駆動源は当面、時刻から決定論的に選ぶ一様な天気の薄い cycler をプレースホルダに置く。バイオームにも #587 のメニュー統一にも依存せず、`internal/systems` 中心で main ベースに独立して進められる。
- **フェーズ2: 生成層をバイオーム設計後に作る**。地域や気候に依存した本格生成に差し替える。効果層は駆動源を差し替えるだけで載る。フェーズ1で効果を天気型から読む形にしておくのが要。

## 先行事例

決定論的な天気生成と、データ駆動の天気型を効果へ配線する層構造は、複数のローグライクで採られる一般的な手法である。設計にあたり Cataclysm-DDA を主な先行事例として調査した。ライセンスは CC-BY-SA。移せる知見は次の2点で、本設計もこの考え方を採る。

- 天気を保存状態でなく時刻の純関数として持つと、再現と予報が素直になる。
- 天気型をデータで宣言し効果側が値を読む形にすると、型と効果が疎結合になる。

一方、連続量を2つへ絞る、空間一様にする、寒波前線と共存させる、視界を半径ベースで扱うといった選択は ruins の既存システムに合わせた本設計固有のものである。先行事例の内部実装をそのまま移植はしない。

## 採用しなかった方法

- **気象量を温度・湿度・気圧・風の多変数で持つ**: 2D 単一オーバーワールドには過剰。ruins は気温を既に持つので、気温と降水ポテンシャルの2量で足りる。多変数は非決定論の風も呼び込みがちで持ちたくない。
- **天気を寒波前線に紐づける**: 前線の周辺で荒天、遠方で穏やか、という空間構造も検討した。しかし前線は回避対象のハザードなので「常に前線から離れる」が最適解になり、天気そのものを体験させられない一本道の誘因を生む。天気は前線と独立の一様な状態にし、前線は前線として残す。
- **現在天気をシングルトンへ保存し duration で切り替える**: 状態とセーブが増え、再現性の管理コストがかかる。決定論なら不要。
- **空間的に変化する天気**: 初期は不要。空間差は寒波前線が担う。導入は将来の判断で、バイオーム後の生成層に委ねる。
- **雷・濡れ・積雪・音・風冷え**: 初期スコープ外。将来フェーズで分割する。

## コメント

- 決定論の要は、ピリオド境界での急変を避けるため降水ポテンシャルを隣接ピリオド補間すること。天気変化は視界再計算を要求するので、ピリオド長で頻度を抑える。
- 視界効果は ruins の視界半径ベースで表す。半径縮小は屋内へ効かせない。`IsOnOverworld` gate で担保する。
- 雨か雪かは気温閾値で分ける。天気の `TempModifier` が雨雪判定へ再帰しないよう、判定には天気オフセット前の気温を使う。適用順に注意する。
- 予報 UI・積雪・アイテム濡れ・音・風は、本 doc の初期スコープ外とし将来の設計 doc で分割する。
