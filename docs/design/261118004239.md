# 壊した後に破片・血痕を残す

## 背景

敵を倒しても物を壊しても、跡が何も残らない。HP が尽きると `Dead` が付き、`DeadCleanupSystem` が実体を消す。参考 codebase: `internal/world/gameaction/damage.go` の `dealHP`、`internal/systems/dead_cleanup.go`。

消すまでに起きることは次のとおりである。

| 場面 | 起きること |
|---|---|
| 敵が死ぬ | ドロップ表から抽選したアイテムと持ち物を足元へ出し、撃破数を数え、絵をフェードアウトさせて消す |
| 物が壊れる | 同じ経路で消える。収納の中身は足元へ出すが、物そのものの素材は何も残らない |
| 物を道具で解体する | 壊すのとは別の操作で、raw の `disassembly` の素材が取れる |
| 火が燃え尽きる | 行の `burnoutItem` のアイテムを足元へ落とす。参考 codebase: `internal/systems/fire.go` の `spawnBurnoutItem` |

当てたときの手応えはダメージの数字だけで、音を鳴らす仕組みは無い。

爽快感を3つの層に分けて考える。

| 層 | 中身 | 今 |
|---|---|---|
| 当てた瞬間の手応え | 揺れや光、音、ノックバック | 数字だけ。音は無い |
| 結果が残る | 壊した・倒した跡が床に残る | 何も残らない |
| 報酬 | 落とし物や素材 | 敵はドロップ表、物は壊すと何も無い |

ターン制のローグライクでは、1つ目の層が弱くても成り立つ。この doc は2つ目の層だけを扱い、壊した・倒した跡を見た目だけの装飾として世界に残す。1つ目の層と3つ目の層は別に扱う。解体して素材や肉を取れる死体や残骸は、3つ目の層の別の機能として後で設計する。

## 要件

- 敵や物が死んだ・壊れたマスに、その種類に応じた跡を残す。
- 跡は見た目だけの装飾にする。通るのを遅くせず、殴れず、解体できず、拾えない。草など、すでにマスにある置物と並んで置ける。
- 跡は置物と違う種類の実体にし、置物やアイテムを数える処理に巻き込ませない。
- 跡を残すか、何を残すかは raw の行で決める。新しい種類は raw の行と絵で足し、コードは変えない。
- 跡を置く場所は死んだマスに決め、乱数を使わない。
- `remainsId` を省けば何も残さない敵も作れる。今は全ての敵に跡を持たせる。

## 設計

### 跡は置物でない専用の種類にする

地上の草・雑草・土の散らかりは、描画順 0 の置物である。参考 codebase: raw.toml の `grass`・`weeds`。跡を置物にして「置物があるマスには置かない」とすると、草のマスに跡が出ない。また、実行中に `Prop` や `LocationOnField` で地面の物を数える処理が3つある。

| 箇所 | 跡が置物だと起きること |
|---|---|
| `internal/world/lifecycle/facility.go` の設備を置けるかの判定 | 野営の中で敵を倒すと、跡のマスに設備を置けなくなる |
| `internal/world/lifecycle/cube_deploy.go` の `stowNearbyItems` | キューブを畳むと、範囲内の血痕も積み荷として畳まれ、展開のたびに出し直される |
| `internal/world/lifecycle/cube_deploy.go` の `deploySpaceFree` | `LocationOnField` を持つ実体が範囲にあると、キューブを展開できない。跡は消えないので、跡のある場所で二度と野営できなくなる |

そこで、跡は raw の専用の表 `remains` の行から作り、実体には印 `Remains` を付ける。`Prop` も `Item` も `LocationOnField` も付けないので、上の3つの処理は跡を見ない。

座標の実体を引く `GetEntitiesAt` を使うほかの処理は、どれも `Interactable`・`BlockView`・`BlockPass`・`Bedding`・`Item` などの印で絞っているので、それらを持たない跡は入らない。近接攻撃と相互作用の対象、射線の遮り、寝床の質、扉を閉められるか、設備を引く処理、地図を作るときの置物の判定である。影は `TurnBased` か `Prop` を持つ実体にだけ描くので、跡には付かない。

```cue
// 敵や物が消えた跡に床へ残す装飾
#Remains: {
	id!:          #EntityID
	name!:        #EntityName
	spriteSheetName!: #SpriteSheetName
	// 跡の形の候補。置くマスの座標から1つを選ぶ
	spriteKeys!: [...#SpriteKey] & [_, ...]
}

#Raws: {
	// ...
	remains?: [...#Remains]
}
```

```go
// Remains は敵や物が消えた跡に床へ残す装飾であることを示すマーカーコンポーネント。
// 置物でもアイテムでもなく、通行・操作・拾得・積み込みのどれにも関わらない
type Remains struct{}
```

跡の実体は `GridElement`・`SpriteRender`・`Name`・`Remains` を持つ。置物の説明文は実体に入っても表示する経路が無いので、跡の行は説明文を持たない。`LocationOnField` は、地面にあって拾ったり積んだりする物の位置を表すので、跡には付けない。3D 描画は `SpriteRender` と `GridElement` で描く物を集めるので、`LocationOnField` が無くても跡は描かれる。参考 codebase: `internal/systems/render3d.go`。`Remains` は保存する印で、保存から外す一覧には入れない。跡は `RawID` を持たない。跡から行を引く処理が無いためで、跡の種類で見回しの説明を変えるなど、引く処理ができたら足す。`SpriteRender` の描画順は、次の節で足す跡専用の段 `DepthNumRemains` にし、3D で地面に寝かせて描く。描画順は行に持たせず、跡を組む関数で決める。`Name` を持つので、見回しで「血痕」と分かる。見回しの分類に `CategoryRemains` を足し、置物やアイテムと見出しで見分けられるようにする。参考 codebase: `internal/components/invariant.go` の `FieldLookCategoryKey`。

跡の行の `name` は、ほかの raw の表と同じく英語原文にし、`internal/i18n/locale/ja.po` で訳す。raw の訳の検査 `internal/i18n/raw_coverage_test.go` は検査する表を名前で並べているので、跡の表を足さないと訳の漏れを黙って通す。分類の名前も、見回しが変数で `query.T` に渡すので、文字列リテラルの msgid の検査に引っかからない。そこで、`Categories()` の全ての分類の名前に訳があることを確かめるテストを足す。今ある `Prop`・`Item` などの分類も同じ理由で守られていないので、まとめて守れる。

### 跡専用の描画の段を足す

raw には描画順が床の模様、つまり `DepthNumDecal` の置物がある。ワープの穴 `warp_next`・`warp_prev`・`warp_escape`・`dungeon_entrance` と、土の模様 `soil_*` である。跡を同じ段にすると、同じマスで寝かせた2枚は描画順が同じ値になり、どちらが上かはクエリの走査順で決まる。参考 codebase: `internal/systems/render3d.go` の `sortQuadsByDepth`、`internal/systems/render_sprite.go` の `renderObjectLayer`。ワープのマスで敵が死ぬと、跡がワープの穴を隠しうる。

そこで、床と床の模様の間に跡専用の段を足す。跡は常に床の模様より先に描かれ、ワープや土の模様を隠さない。3D と 2D のどちらも描画順の比較だけで決まるので、並べ方に副キーを足さずに済む。

```go
const (
	// DepthNumFloor は床。最背面に表示する
	DepthNumFloor DepthNum = iota
	// DepthNumSnow は地面に重ねる雪の層。3D の描画だけが使い、実体は持たない
	DepthNumSnow
	// DepthNumRemains は敵や物が消えた跡。床の模様より下に描き、ワープの穴を隠さない。3D では地面に寝かせて描く
	DepthNumRemains
	// DepthNumDecal は床の模様。例: 土のしみ、ワープホール。3D では立て板にせず地面に寝かせて描く
	DepthNumDecal
	// DepthNumRug は床に置くもの。例: アイテム、焚き火
	DepthNumRug
	// DepthNumTaller は高さのあるもの
	DepthNumTaller
	// DepthNumPlayer は操作キャラを最も手前に表示する
	DepthNumPlayer
)

// LiesFlat はその段を 3D で地面に寝かせて描くかを返す
func (d DepthNum) LiesFlat() bool {
	return d == DepthNumRemains || d == DepthNumDecal
}
```

- **raw の描画順を名前の列挙にする**: 今の raw は描画順を数値で持ち、`gc.DepthNum(int(s.Depth))` でそのまま段に写している。参考 codebase: `internal/raw/raw.go`。このままでは、段を途中に足すたびに raw.toml の全ての `depth` を繰り上げることになる。そこで `#SpriteDepth` を名前の列挙にし、raw の名前から段へ写す関数を1つ置く。列挙には跡の段を入れないので、raw の行に跡の段を書けないことを型で守れる。プレイヤーの段も raw の行は使わないので入れない。

```cue
// スプライトの描画順。跡とプレイヤーの段は raw の行が使わないので持たない
#SpriteDepth: "floor" | "decal" | "rug" | "taller" @rawgen(prefix)
```

```go
// depthOf は raw の描画順の名前を段に写す。CUE が列挙を検査するので未知の値は来ないが、raw から来る値なので
// panic せず床に落とす
func depthOf(d rawschema.SpriteDepth) gc.DepthNum {
	switch d {
	case rawschema.SpriteDepthFloor:
		return gc.DepthNumFloor
	case rawschema.SpriteDepthDecal:
		return gc.DepthNumDecal
	case rawschema.SpriteDepthRug:
		return gc.DepthNumRug
	case rawschema.SpriteDepthTaller:
		return gc.DepthNumTaller
	}
	return gc.DepthNumFloor
}
```

  raw.toml の `depth` の数値は、一度だけ名前に置き換える。今の raw が使っているのは 0〜3 だけで、プレイヤーの段の 4 は使っていないので、列挙から外しても壊れる行は無い。タイルが高さを持つかを返す `TileIsTall` も、描画順を数値で写しているので `depthOf` を通し、raw から段へ写す経路を1つにする。
- **寝かせる判定**: 3D の `sr.Depth == gc.DepthNumDecal` を `sr.Depth.LiesFlat()` に変える。同じ箇所の「奥行きが床と同値になるので、副キーの描画順で床の直後に描く」というコメントも、寝かせる段が2つになるので、描画順の副キーで床の後に段の順に描く、という内容に直す。
- **雪の層の段**: 3D の雪の層は、今は描画順 `1` を直に書いている。参考 codebase: `internal/systems/render3d.go` の `snowLayer.add`。雪は地面のタイルの loop で積み、跡や床の模様は後の loop で積むので、同じ描画順なら積んだ順に並び、今はワープの穴や土の模様が雪の上に描かれている。段の名前 `DepthNumSnow` に書き直し、床 < 雪 < 跡 < 床の模様 の順を描画順の比較だけで決める。跡は雪の上に出す。冬に戦った跡が雪に隠れると、跡を残す意味が薄れるからである。雪と床の模様の上下は今と変わらない。
- **セーブの版を上げる**: `SpriteRender` は保存され、`Depth` は段の数値のまま残る。段を途中に足すと、古いセーブの値の意味がずれ、アイテムが寝かせて描かれたり、壁が箱にならなかったりする。そこで `internal/save/manager.go` の `saveDataVersion` を `"2.0.0"` から `"3.0.0"` に上げ、古いセーブは読み込みのときに版の違いで弾く。未リリースなので、古いセーブを読み替える仕組みは作らない。版の違いで弾くことは、版の定数を参照する既存のテスト `internal/save/manager_test.go` が確かめているので、テストは足さない。
- **影**: 影を落とすかの判定 `Depth <= DepthNumRug` は、段の順だけを見るので変えなくてよい。

### 跡を残す欄を敵と物の行に足す

敵も物も、`Dead` が付いてから `DeadCleanupSystem` で消える同じ経路を通る。そこで、敵の行と物の行の両方に、跡の行の id を持つ任意の欄 `remainsId` を足す。燃え尽きたときの `burnoutItem` と同じ形にする。

```cue
#Member: {
	// ...
	// 死んだときに足元へ残す跡。省くと何も残さない
	remainsId?: #EntityID
	if remainsId != _|_ {
		remainsId_ref: _remainsIDs[remainsId] @rawgen(-)
	}
}

#Prop: {
	// ...
	// 壊れたときに足元へ残す跡。省くと何も残さない
	remainsId?: #EntityID
	if remainsId != _|_ {
		remainsId_ref: _remainsIDs[remainsId] @rawgen(-)
	}
}
```

`remainsId` は跡の行を参照する。無い id は CUE の参照の検査で落ちる。`#Prop` では、同じ形の `burnoutItem` の隣に置く。

燃え尽きた火も、`internal/systems/fire.go` で `Dead` が付いて同じ経路で消える。火の置物の行に `remainsId` を書けば、焦げ跡を残せる。燃え残りの `burnoutItem` とも並べて持てる。

### 消すときに跡を置く

`DeadCleanupSystem` で実体を消す直前に、実体の raw の行が `remainsId` を持てば、その座標に跡を置く。行は `RawID` から引く。`RawID` は敵・置物・アイテム・タイルで同じ文字列の形を持つので、引く表は実体の種類で決める。`Prop` を持てば置物の行、持たなければ敵の行を引く。こうすると、敵と置物の id が重なっても誤らない。

`Dead` を付けるのは、HP が尽きたときの `gameaction` の `dealHP` と、燃え尽きた火の `FireSystem` だけで、`DeadCleanupSystem` はプレイヤーを消さない。そのため、`RawID` を持って消えるのは敵か置物に限られる。HP を持つ別の種類の実体を足すときは、`placeRemains` の行の引き方も直す。

`GridElement` か `RawID` を持たない実体は、跡を置かずに進む。raw から作る実体は必ず `RawID` を持つので、整合性の誤りは隠さない。燃え残りを落とす `spawnBurnoutItem` も、同じ2つが無ければ飛ばしている。参考 codebase: `internal/systems/fire.go`。

ただし、キューブに置いた設備は `Prop` を持つが、`RawID` はアイテムの行の id のままである。参考 codebase: `internal/world/lifecycle/facility.go` の `PlaceFacility`。設備はアイテムの行から作られ、`remainsId` を持てない。そこで、`Deployable` を持つ実体は行を引かずに跡を置かない。それ以外で行が見つからなければ、ロードのときに検証済みの参照が引けない整合性の誤りとして、エラーを返す。ドロップ表を引けないときにエラーを返す `DeadCleanupSystem` の今の扱いにそろえる。燃え残りを落とす `spawnBurnoutItem` も置物の行が無ければエラーを返すので、設備の火を燃え尽きさせる経路を足すときは、2つの関数で `Deployable` の扱いをそろえる。

```go
// placeRemains は死んだ実体 e の行が持つ跡を、e の座標へ置く
func placeRemains(world w.World, e ecs.Entity) error {
	// e が Prop を持てば置物の行、持たなければ敵の行を RawID で引く。
	// remainsId があり、その座標にまだ跡が無ければ lifecycle.SpawnRemains で置き、今のステージへ束縛する
}
```

- **置く順**: ドロップと持ち物を足元へ出した後、実体を消す前にする。ドロップの loop は `DropTable` が無い実体や何も出なかった実体を `continue` で飛ばすので、跡を置く処理はその loop に入れず、独立した loop にする。
- **重ねない**: そのマスにすでに跡があれば置かない。置物やアイテムがあっても置く。3D では跡は床に寝かせて描くので、立て板の草や扉の根元に見える。2D は描画順の比較だけで重ねるので、描画順が床の草の上に跡が重なる。2D は今のままにする。
- **跡を引く関数**: 座標の跡を引く関数を `query` に足す。`Remains` を持つ実体だけを見る。
- **見えない所の跡**: 3D では、床に寝かせて描く絵を、記憶しているマスにも今の世界のまま描く。参考 codebase: `internal/systems/render3d.go`。そのため、視界の外で敵が死ぬと、記憶しているマスに跡が現れる。今ある床の模様と同じ扱いにそろえ、これを許す。漏れるのは「そこで何かが消えた」ことだけである。2D の描画は、タイル以外の物を見えているマスにだけ描くので、記憶しているマスに跡は出ない。2D は今のままにする。
- **ステージへの束縛**: 跡を組む関数は、置いた直後に `StageBound{CurrentStage}` を付け、今のステージのクエリにすぐ乗るようにする。帯の南端で実体を消す `RemoveEntitiesInYRange` と、ステージへ束縛する `stage.Bind` は、どちらも `GridElement` を持つ実体全てを見るので、跡も漏れなく扱われる。

### 跡の種類

| 跡 | 例 |
|---|---|
| 体から出る跡 | 赤・緑・青の血痕、油の染み、粘液、焦げ跡、霊の残滓 |
| 物の破片 | 木くず、金属の削りくず、砂利、ガラス片、植物のくず、布きれ |

物の破片の行の例を示す。

```toml
[[remains]]
  id = "wood_splinters"
  name = "Wood Splinters"
  spriteKeys = ["wood_splinters_a", "wood_splinters_b", "wood_splinters_c", "wood_splinters_d", "wood_splinters_e"]
  spriteSheetName = "field"
```

壊した家具の行には `remainsId = "wood_splinters"` を足す。壊れない階段・脱出口・遺跡の入口を除き、壊せる置物の全ての行が `remainsId` を持つ。窓と鏡はガラス片、鉢植えや低木や作物は植物のくず、絨毯は布きれ、火とろうそくは焦げ跡にする。

### 敵の跡

跡の行が敵や置物のカテゴリになり、敵や置物の行はカテゴリを指す。血痕は色ごとに行を分け、それぞれ5つの形の候補を持つ。形は置くマスの座標から選ぶので、同じ敵でも倒した場所によって形が変わる。

`[[members]]` の行には、プレイヤーの行と中立の行も入っている。`DeadCleanupSystem` はプレイヤーを消さないので、プレイヤーの行の `remainsId` は使われない。敵対する行ごとに `remainsId` を書く。raw に体の種類の欄は無い。

| 敵の種類 | 跡 |
|---|---|
| 獣・人・竜など | 赤い血痕 |
| 虫・両生類・植物 | 緑の血痕 |
| 甲殻・蜘蛛・氷の生き物・青い異形 | 青い血痕 |
| 戦車や機械 | 油の染み |
| スライム | 粘液 |
| 火の玉 | 焦げ跡 |
| 霊・骸骨 | 霊の残滓 |
| ゴーレムや木の精 | 体の素材の破片。金属片・石くず・木片 |

### 絵

| 跡 | 絵 |
|---|---|
| 血痕 | 色ごとに `blood_red_a`〜`e`・`blood_green_a`〜`e`・`blood_blue_a`〜`e`。溜まりの大きさ・伸びる向き・飛び散りの数を変えた5つの形。`blood_.png` は血の入った瓶のアイテムなので使わない |
| 油の染み・粘液・焦げ跡・霊の残滓 | `oil_stain`・`slime_puddle`・`scorch_mark`・`ectoplasm` の1つずつ |
| 木くず・金属の削りくず・砂利 | `wood_splinters_*`・`metal_fragments_*`・`stone_rubble_*` の5つずつ。淡い粉の広がりに細かな粒を散らす |
| ガラス片・植物のくず・布きれ | `glass_shards_*`・`plant_debris_*`・`cloth_scraps_*` の5つずつ。小さな欠片や葉を散らす |

どれも手続きで描いた仮の絵である。差し替えるときは、`assets/file/textures/single/` の同じ名前の画像を置き換えて `make aseprite` を回す。

置物の跡は、置物と見分けられる形にする。立体の欠片を描くと小さな置物と同じに見え、跡と読めない。血痕や植物のくずのように、平たく縁の崩れた散らばりにすると、立てて描く置物と違うことが一目で分かる。既存の置物の絵 `debris`・`rubble`・`scrap_metal` は立てて描く絵なので、跡には使わない。

敵が消えるときは、敵の絵がその座標で白いシルエットになってフェードアウトする。跡は同じターン末に置かれ、床に寝かせて描くので、薄れていく敵の足元に跡が見える。`TestGolden_Remains_Fadeout` でこの重なりを固定する。

### 消えない作りにする

跡は消えずに残す。地上は北へ進むと帯の南端のチャンクごと実体が消えるので、自然に片付く。ダンジョンの階は有限である。`BenchmarkRemains` で、大部屋の階に跡を 0・300・1000 個置いて測ると、1ターンはどれも約 2.0ms、1フレームの描画は約 2.6〜3.3ms でばらつきの範囲に収まる。1つの階に1000個溜まっても重くならないので、時間で消す仕組みは足さない。

## 採用しなかった方法

- **跡を置物にし、遮る置物だけを重ね置きの判定に使う**: 草のマスにも置けるようになる。ただ、置物の印の doc は「1タイルに1つ置かれる」としていて、その前提を緩めることになる。設備の判定やキューブを畳む処理も、跡を除く分岐を個別に足すことになる。
- **跡に `LocationOnField` を付け、`deploySpaceFree` に `Prop` と `Item` の絞り込みを足す**: 地面にある物は `LocationOnField` を持つという慣習を保てる。ただ、`LocationOnField` を数える処理ごとに跡を除く分岐が要り、新しい処理を足したときに漏れやすい。
- **草などの下地の置物を消して跡に置き換える**: 戦ったマスから草が消え、跡が残る代わりに地面の見た目が崩れる。
- **残骸に通りにくさと解体の素材を持たせる**: 壊すのは速いが取れる量は少なく、解体は遅いが多く取れる、という選択が生まれる。ただ、戦った通路が残骸で埋まって経路が遅くなるなど、遊びへの影響を調整することになる。跡はまず見た目だけにし、素材を取れるものは解体できる死体と合わせて別の機能として扱う。
- **死体のアイテムを残し、解体で肉を取る**: 食料という生存の資源と結び付いて面白いが、腐敗や重さや解体の手間まで決めることになり重い。跡の装飾とは別の機能として、後で設計する。
- **跡の種類を敵の体の種類から導く**: raw に体の種類の欄が無く、足すと敵の分類の設計から始めることになる。行ごとに `remainsId` を書くほうが、何も残さない敵のような例外も素直に書ける。
- **跡を1つの絵にし、色だけを行で変える**: 絵は1枚で済むが、血と油と粘液で形が同じになり、見分けにくい。色を持たせる欄も別に要る。
- **床の模様の置物があるマスには跡を置かない**: 判定の関数は小さく済むが、ワープや土の模様の上で倒しても跡が残らない。
- **跡を雪の下にし、雪に埋もれさせる**: 時間がたつと跡が雪に隠れる見た目にもなる。ただ、雪の量は日々の気温で決まり、跡ができてからの時間とは関係しない。冬は戦ってすぐの跡も隠れる。
- **raw の描画順を数値のまま繰り上げる**: 写す関数が要らないが、raw.toml の全ての `depth` を書き換えることになり、段を足すたびに同じ書き換えが要る。範囲を広げると、跡の段の数値を raw の行に書けてしまう。
- **跡の印と表を `Decal`・`decals` と呼ぶ**: 今の段 `DepthNumDecal` は跡でない床の模様を指すので、取り違えやすい。跡の側を `Remains` にそろえ、跡の行を指す欄は `dropTableId` などと同じく `remainsId` にして、表の名前 `remains` と区別する。
- **同じ描画順のときに跡を先に描く副キーを足す**: raw の値を繰り上げずに済むが、3D の並べ方の要素に欄が増え、2D の並べ方にも同じ規則が要る。描画の順を2か所で別に決めることになり、段の意味が描画順の値だけで読めなくなる。
- **跡に見たかどうかを持たせ、見えたときに初めて記憶しているマスへ描く**: 見えない所の死が漏れない。ただ、跡ごとに状態が増え、視界の更新で書き換える処理も要る。
- **跡だけは見えているときだけ描く**: 状態は増えないが、今ある床の模様と見え方が分かれ、見えなくなると跡が消えて見える。
- **跡を時間で消す**: 片付けの仕組みが要る。地上は帯の南端で自然に消えるので、まず消えない作りで始める。
- **壊したときに素材をそのままアイテムで落とす**: 跡が床に残らない。素材の報酬は別の機能で扱う。

## コメント

- 当てた瞬間の手応え、たとえば揺れや光、音は、この doc とは別に扱う。音を鳴らす仕組みはまだ無い。
- 解体できる死体や残骸は、この装飾とは別の置物か別の仕組みとして後で設計する。装飾の跡はそのとき置き換えず、両方を残せる。
- 出血の状態の敵が歩いた跡に血を落とすと、手負いの敵を追える。この doc の跡の仕組みを使う別の機能として扱う。
- 敵の行に `remainsId` を書く作業は漏れやすい。敵対する行のうち `remainsId` を持たない行を一覧で固定するテストで、意図して省いた敵だけが残ることを確かめる案がある。
- 跡を置く頻度は1ターンに数体の死に限られるので、座標の跡を引く関数は全走査でよい。
- 跡は `GridElement` を全て走査する処理に実体を足すが、1つの階に1000個溜まっても重さは変わらないことを `BenchmarkRemains` で確かめた。
