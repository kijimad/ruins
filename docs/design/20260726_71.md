# 隊員の空腹と自動飲食

## 背景

空腹は現状プレイヤー専用で、隊員は腹が減らない。`docs/plan/design.md` は「隊員が多いほど食料消費が
増える。維持コストの主要因」と宣言しており、隊の人数がビルド判断になるための前提が実装されていない。

生存への対立軸が隊に接続されないかぎり、隊にやらせたい活動にも需要が生まれない。その第一歩として、
本 doc では**隊員の腹減りと自動飲食だけ**を検討する。作業指示・採取・調理・生産・協力といった広い
活動システムの企画は本 doc の対象外とし、この最小の需要が回ってから改めて検討する。

企画から設計確定・実装の進捗管理まで本 doc 1本で扱う。個別 doc への分割はしない。

## 現状

- `internal/components/hunger.go`: `Hunger` は `Pool[int]`。コメントでプレイヤー専用と明記。
  `HungerLevel` は満腹/普通/空腹/飢餓の4段階、`GetStatusPenalty` で空腹時の Speed 低下がある。
  `DefaultMaxHunger=500 / DefaultInitial=400 / HungerDrainTurns=3`
- `internal/activity/activity.go` の `progressHunger`: プレイヤーのみ進行。`CharModifiers.HungerProgress`
  と耐餓スキルで倍率が変わり、確率ゲートで進む
- 隊員AI `internal/aiinput/planner_squad.go` の優先チェーンに飲食は無い
- 食料アイテムと `UseItem` activity は実装済み。プレイヤーが隊員に使うことはできる

## 設計

### 隊員への Hunger 付与

`SpawnSquadMember` で隊員にも `Hunger` を付与し、プレイヤー専用の但し書きを外す。進行は
`progressHunger` をプレイヤー限定から Hunger 保持エンティティ全体へ広げ、倍率・確率ゲートの
仕組みは共通のまま使う。隊員ごとの耐餓スキルと `CharModifiers` がそのまま効く。

```go
// 変更前: progressHunger はプレイヤーのみ進行させる
// 変更後: Hunger を持つ全エンティティを進行させる。倍率は各自の
//         CharModifiers.HungerProgress と耐餓スキルから求める
```

### 自動飲食 —— 事前ポリシーと共有プール

隊員は空腹レベルに達したら、**事前に設定したポリシーに従って共有プールから食料を自動で受け取り、
食べる**。リーダーが毎回配給・給餌する micro はしない。プレイヤーの仕事は、プールに food を
確保しておくことと、ポリシーを決めておくことの2つになる。

- **補給ポリシー**: 既存4ポリシーに並ぶ第5のポリシーとして `SquadAI` に持たせる。事前設定・
  巡回 UI という既存の型を踏襲する

```go
// SupplyPolicy は隊員の補給方針。既存4ポリシーと同じく事前設定する
type SupplyPolicy string

const (
	SupplyAuto   SupplyPolicy = "auto"   // 空腹になったら共有プールから自動で受け取り食べる
	SupplyManual SupplyPolicy = "manual" // 自動補給しない。プレイヤーが持たせた分だけ食べる
)
```

- **共有プールの所在**: リーダーの所持品をプールとする。既存の分配ポリシーが戦利品をリーダーへ
  集約する設計なので、集約先＝プールで整合する。運搬役や収納エンティティへの一般化は将来の
  拡張余地として残す
- **発火条件**: `HungerLevel` が空腹に達したとき。飢餓まで放置しない。閾値はプレイヤーの
  ペナルティ開始と同じ段に揃え、挙動を予測可能にする
- **自動運搬の行動**: 空腹の隊員はまず自分の背嚢から食べる。無ければプール保持者へ BFS で
  接近し、隣接で食料を1食受け取り、食べる。接近・受領・飲食はすべて既存の Move・Transfer・
  UseItem activity の組合せで、新しい activity 型は作らない
- **何を食べるか**: 栄養価の低いものから消費し、高価値食料を温存する
- **プール枯渇時**: 受け取れず空腹が進む。警告をログで出す。食料確保はプレイヤーの兵站判断の
  まま残る
- **優先チェーンの位置**: HP 低下による後退の次、戦闘より前。戦闘中は食べない、すなわち
  敵が視界にいる間は発火を抑止する
- **提示**: 受け取り・飲食をログ1行で出す。誰が何を食べたか分かることが、food 残量の管理と
  隊員への目配りにつながる

### 圧の強さ —— スラック原則

- 進行速度はプレイヤーと同一。隊員だけ早く減る特別扱いはしない
- 空腹のペナルティは既存の `GetStatusPenalty` と同じ Speed 低下。**餓死はさせない**。飢餓は
  衰弱ペナルティ止まりにし、欠員は劣化であって即死の壁にしない。失敗は柔らかく、立て直しは
  食料を持たせるだけでよい
- 隊員数 × 食料消費が維持コストとして働けば本 doc の目的は達成で、それ以上の圧は足さない

## 採用しなかった方法

- **広い活動システムを一括で企画する** —— 当初は作業ポリシー・採取・調理・生産・協力・訓練まで
  含めて検討したが、範囲を隊員の腹減りと自動飲食だけに絞った。最小の需要が回る手応えを見てから
  次を検討する
- **手動分配のみで賄う** —— 一次案は「隊員は自分の背嚢の分だけ食べ、配分はプレイヤーが行う」
  だったが、10人へ食料を持たせ直す配給 micro が残り、事前ポリシー中心の設計思想と合わない。
  事前ポリシー＋共有プールからの自動運搬に改めた。食料の確保とポリシー設定という上流の判断は
  引き続きプレイヤーに残る
- **餓死** —— 欠員は劣化であって即死の壁にしない。opaque な数字での即死は savescum を生むという
  design.md の方針に従う
- **専用の Eat activity 型** —— 既存 UseItem で表現できる。型を増やさない
- **手動給餌の micro** —— 10人へ毎回食べさせる操作は負荷で破綻する。直接 micro はしない方針とも
  矛盾する
