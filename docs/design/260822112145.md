# config を Resources へ移し状態の持ち方を揃える

## 背景

実行設定 config は `config.Load()` が環境変数とユーザ toml から読み、`World.Config *config.Config`
という World 直下のフィールドで保持していた。一方でゲーム中の状態は singleton コンポーネントに載せ、
`query.GetSingleton[T]` で引く。config だけが World 直下で、状態の持ち方が二本立てだった。

## 設計

config を `Resources.Config *config.Config` へ移し、他の共有データと同じ棚に置く。
`world.Resources.RawMaster` や `world.Resources.I18N` と同様に `world.Resources.Config` で読む。

singleton コンポーネントではなく Resources にするのが要点。理由は config の寿命にある。

- `ResetForNewGame` は全エンティティを消して singleton を作り直す。singleton コンポーネントに
  config を載せると新規ゲームのたびに消え、復元の小細工が要る。Resources は reset を跨いで生き残る。
- config は起動時に注入された1個のインスタンスで、env の写しではない。VRT とテストは
  `cfg.Seed = 12345` や `DisableAnimation` を struct で注入して決定性を作る。reset で env から
  読み直すと注入した seed がランダム化し再現性が壊れる。Resources なら注入インスタンスが持続する。
- config は per-game 状態でなくアプリ生存期間の設定なので、RawMaster や I18N マスタと同じ寿命。
  設定画面で変える可変設定 UserSettings は singleton のままにする。今は言語しか持たないが
  可変設定の器で、寿命に応じて棚を分ける。

serde は変更不要。serde は ECS のコンポーネントを対象とし、Resources は対象外なので config は
保存されない。UserSettings が config 由来のランタイムミラーとしてロード時に再構築される既存の
仕組みもそのまま効く。

## 変更箇所

| ファイル | 変更内容 |
| --- | --- |
| `internal/resources/resources.go` | `Config *config.Config` を追加 |
| `internal/world/world.go` | `World.Config` フィールドを撤去し、`InitWorld` で `Resources.Config` へ格納 |
| 参照側 各パッケージ | `world.Config` を `world.Resources.Config` へ移行 |

## 採用しなかった方法

### config を singleton コンポーネントにする

当初案。`GetSingleton` で引ける利点はあるが、`ResetForNewGame` で消え、注入した seed も
reset で失われ VRT 決定性を壊す。config の寿命が per-game でないため singleton は不適。

### env から毎回読み直す

reset のたびに `config.Load()` する案。singleton の消滅は回避できるが、VRT が struct で注入する
固定 seed が env 読み直しでランダム化し、ゴールデンが再現しなくなる。

## コメント

#676 のカメラ姿勢を Camera へ集約した「状態は ECS へ寄せる」流れの延長で起票した。ただし
config は per-game 状態でなくアプリ設定なので、ECS の singleton でなく Resources が正しい棚だった。
寿命で棚を選ぶ判断が要点。
