# Prop タグを廃し固定物を独立状態 Fixed で表す —— 効果の門は能力ごと

## 背景

`Prop` コンポーネント、`internal/components/components.go:322` の `type Prop struct{}`、は空の種別タグである。だが実際に
担っているのは「フィールド上の物体が拾える loot か、漁って壊す恒久固定物か」の1ビットで、しかも
`IsPickable = LocationOnField && !Prop`、`internal/world/query/query.go:50-58`、と**陰性**で表現されている。曖昧さの元は
loose な loot も世界の固定物も両方 `LocationOnField` を持つ重なりで、そのため `!Prop` で分けている。

`Item` タグは既に撤去済みである。`bf30966ff`「冗長なカテゴリタグComponentを削除した」で `Item` と `Weapon` のマーカーを
消し、「アイテムか」を単一タグでなく、状態 `LocationOnField` と能力コンポーネント、Melee・Fire・Consumable・Ammo・Book・
Material・Wearable、へ分解した。Prop はこの整理から取り残された恣意的な種別タグである。

当初は Minecraft 型の item↔設置統合、item を置くと固定物になり壊すと item に戻る、を検討した。だがローグライクには
item と block の鋭い区別が無く、家具を運んで置き直す動機も無い。設置は「ステーションをキューブの収納に入れておくと発動」
に還元でき、可逆遷移の機構は over-engineering だった。検討の結論として却下し、採用しなかった方法に残す。

本 doc の方針は2点。**固定物の役割を曖昧なカテゴリタグから意味の明確な独立状態へ移す**。固定物か loot かは、漁る/壊すか
運ぶ/使うかの本物の役割で残すが、`Prop`、置物という漠然としたカテゴリ、を廃し、location と直交する独立状態 `Fixed`、
係留・非可搬、へ差し替える。もう1点、
**据え置きで利益を出すステーションは固定物でなく item にし、キューブの収納内での存在で効果を発動する**。設置サブシステムを
作らない。

## 要件

- **固定物の役割を `Prop` カテゴリタグから独立状態 `Fixed` へ移す**。役割は残し、曖昧なタグを直交する状態へ差し替える。
- **`Fixed` は location と直交させる**。固定物は `LocationOnField` ＋ `Fixed`、loose loot は `LocationOnField` のみ。
  拾得は `IsPickable = LocationOnField && !Fixed` にする。`clearLocation` は変更しない。
- **load-bearing な3経路を先に反転する**。拾得・分解・破壊回収の `!Prop` 依存を固定物状態基準へ移してから `Prop` を
  削除する。反転前に消すと家具・樽・扉が拾得やスタック消費の対象になり静かに壊れる。
- **材料化の動詞は分解1本**。破壊、`HP`→0 のダメージ、は分解の発火条件に畳む。破壊と分解を別動詞にしない。
- **効果の門は能力ごとに状態で切る**。効果を一律に紐づけず、能力ごとに関係する状態で門を切る。ランタンの光は世界に
  タイルを持てば働き、溶接機はキューブ収納内に在れば働く。設置・取り外し・可逆遷移は作らない。
- **段階的で各段が make check green**。追加→反転→従属移行→削除→serde の段に割る。
- **serde 互換**。ark-serde の skipComponents 除外の自動登録、`internal/save/serde.go:31-45`、で `Prop` を移行する。
- **Ark strict semantics 遵守**。空タグの `Has`、生成登録、serde を規約どおりにする。

## 設計

### 弁別子: `Prop` タグ → `Fixed` 独立状態

`Fixed` は location と直交する独立状態にする。Location 家族、`InBackpack`/`Equipped`/`InStorage`/`OnField`、は「どこに
在るか」の排他軸。固定かどうかは別の問いで、固定物も物理的には世界に在る、`LocationOnField`、から、両者を重ねて持つ。

```go
// Fixed は item が世界に固定され拾えない固定物であることを表す独立状態。location と直交し、LocationOnField と
// 重ねて持つ。世界に在ることは LocationOnField、固定されて拾えないことは Fixed、と別軸で表す。Prop 種別タグの
// 後継だが、曖昧な「置物」カテゴリでなく「係留・非可搬」という意味の明確な状態。可逆遷移は持たず、生成時に付くだけ。
type Fixed struct{}
```

- 世界の固定物、家具・壁・棚・doc 82 の屋外散布、は `LocationOnField` ＋ `Fixed` で spawn する。プレイヤーは運ばず、
  漁って壊す。loose な loot は `LocationOnField` のみで `Fixed` を持たない。「世界に在るか」は `LocationOnField` で統一される。
- `Fixed` は location と直交するので `clearLocation` の排他には加えない。固定物は破壊まで遷移せず所持へ移らず、拾得経路が
  `!Fixed` で弾くので、所持中に `Fixed` が残る事故は起きない。破壊時も `Dead` 付与後の `clearLocation` は `Fixed` を除去
  しないので、`dead_cleanup` が判定する時点で `Fixed` が残ることが保証される。

### load-bearing な3経路の反転

`Prop` を消す前に `!Prop` 依存を `!Fixed` へ置き換える。判定の形は変わらず、曖昧なカテゴリタグを意味の明確な直交状態に
差し替えるだけ。固定物は `LocationOnField` を保つので「世界に在るか」の判定は影響を受けない。

| 経路 | 現状 | 反転後 |
|---|---|---|
| 拾得可否 `query.go:50-58` | `LocationOnField && !Prop` | `LocationOnField && !Fixed` |
| 分解 `disassemble.go:170` | `Prop && GridElement` → 実体除去＋収納こぼし / else スタック消費 | `Fixed` → 実体除去＋収納こぼし / else スタック消費 |
| 破壊回収 `dead_cleanup.go:91` | `Prop && GridElement` の死骸を素材回収 | `Fixed` の死骸を素材回収 |

### 材料化は分解1本、破壊はその発火条件

- 材料を出す動詞は**分解**のみにする。工具での分解も、`HP`→0 のダメージによる破壊も、同じ「固定物を材料化する」経路へ
  畳む。破壊は分解の1カテゴリ、ダメージ起因の発火、として扱い、別動詞にしない。
- 収納固定物、`Storage`、を材料化するときは、既存の `SpillStorageItems` で中身を床へこぼしてから実体を処理する。

### 効果の門は能力ごとに状態で切る

item の効果は「持っているだけ」で一律に出すのでなく、能力ごとに関係する状態で門を切る。設置という別状態は作らず、既存の
Location 状態と `GridElement` で表す。効果の門は `Fixed` に一律に紐づけない。少なくとも2つの門がある。

- **位置効果**。ランタンの明かりのように、世界にタイルを持てば働く。`LightSource && GridElement` で発動し、loose に落ちて
  いても、`LocationOnField`、固定物として据えても、`Fixed`、同じく周囲を照らす。loose か固定物かは拾えるかどうかを
  分けるだけで、光には効かない。
- **拠点効果**。溶接機・調理器のように、キューブの収納内に在ることで働く。`LocationInStorage(キューブ) && ステーション能力`
  で発動する。物理タイルは要らず、我が家に在ることが条件。棚に入れれば workshop が立ち上がり、持ち出せば止まる。設置や
  固定物化の行動は要らない。

効果の軸は相互作用の軸と直交する。`Fixed` は「拾える loot か漁る固定物か」の相互作用を分けるだけで、どの効果が
働くかは各能力が自分の門で決める。ランタンが loose でも固定物でも光るのがその直交性の証である。doc 80 の「presence 効果を
持つ prop」と重量経済は、拠点効果の一例、「presence 効果を持つ item、キューブ収納内で発動」、に化ける。重量は運搬コストの
ブレーキとして残る。能力は capability コンポーネント、`LightSource` やステーション能力、で表し、具体は実装時に既存の効果系
から詰める。

### 従属する表示・分類の移行

- 影 `render_sprite.go:254`、`TurnBased || Prop` → `TurnBased || Fixed`。
- 文言 `damage.go:57`・`look_around.go:296`、壊れた/耐久 の分岐を `Fixed` 述語へ。
- カテゴリ `invariant.go`。`Prop` は3か所で参照されるが、観点で扱いが分かれる。`InventoryCategoryKey` の
  `CategoryGoods`、165行目、は所持中の item を分類する観点で、固定物は所持へ入らないから `c.has(c.Prop)` は
  **削除するだけ**にする。`Fixed` へ置換しても所持中の `Fixed` は存在せずマッチしない死んだ述語になる。
  `ItemTypeCategoryKey`、173行目、と `FieldLookCategoryKey`、185行目、の `CategoryProp「置物」` は `c.has(c.Fixed)` へ
  **置換**する。あわせて定数名 `CategoryProp` は移行後に実装と乖離するので `CategoryFixed「固定物」` へ改名する。

### 生成側

- `NewPropSpec`、`raw.go:625-706`、は固定物の spawn 経路として残すが、`Prop{}` でなく `LocationOnField` ＋ `Fixed` を付ける。
  raw の `[[props]]`、116件、はそのまま固定物定義として使える。
- ステーションは固定物でなく item として `NewItemSpec` にステーション能力を付けて定義する。

## 採用しなかった方法

- **Minecraft 型の item↔設置統合** —— item を置くと固定物になり、壊すと item に戻る可逆遷移。だがローグライクには
  item と block の鋭い表現差、ボクセル対スタック、が無く、棚 item と設置棚はどちらもスプライト付きエンティティで違いが
  薄い。家具を運んで置き直す動機も無い。設置は「ステーションを収納内 item で発動」に還元でき、`Placed`/`Placeable`/
  `Retrievable`/可逆遷移は薄い区別のための儀式になる。探索の結論として却下する。
- **`Prop` をそのまま削除する** —— 3経路が `!Prop` に陰性依存し、削除すると家具・樽・扉が拾得とスタック消費の対象になり
  静かに壊れる。固定物状態の陽性判定へ反転してから消す。
- **曖昧な `Prop` カテゴリタグのまま残す、現状維持** —— `Prop` は「置物」という漠然とした種別タグ。意味の明確な直交状態
  `Fixed`、係留・非可搬、へ改め `LocationOnField` と合成できるようにする。`Item`・`Weapon` を状態と能力へ分解した
  `bf30966ff` の、恣意的タグを消す路線と揃える。
- **固定を Location 家族の排他状態にする** —— `Fixed` を `OnField` と排他な第5 Location 状態にする案、本 doc の初期案。
  だが固定物は遷移しないので排他の必要が無く、固定は location と直交する属性である。排他にすると固定物が
  `LocationOnField` を失い「世界に在る」を location で表せなくなる。独立状態にして `LocationOnField` と重ねる。
- **ステーションを固定物にする** —— 設置・取り外しのサブシステムが要る。収納内 item での発動で足り、既存の
  `LocationInStorage` 状態を門に使える。
- **破壊と分解を別動詞にする** —— 破壊は分解の1カテゴリ、ダメージ起因の発火、である。材料化の動詞を1本に畳む。

## コメント

- 本 doc の核は「固定物の役割を曖昧なカテゴリタグから、location と直交する意味の明確な独立状態 `Fixed` へ移す」ことで
  ある。`Item`・`Weapon` を状態と能力へ分解した `bf30966ff` の、恣意的タグを消す路線の続き。
- 固定物の役割自体は消えない。漁る/壊す固定物か、運ぶ/使う item か、はローグライクの本物の役割区別で、能力に還元
  できない。消すのは曖昧なカテゴリタグ `Prop` だけで、区別は location と直交する `Fixed` 状態が担う。
- 相互作用の軸、`Fixed`、location の軸、`LocationOnField` ほか、効果の軸、能力ごとの門、の3つは直交する。ランタンの光が
  `Fixed` の有無に依らず `LightSource && GridElement` で決まるのがその証で、1つの軸に混ぜないことが設計の芯である。
- raw の prop 定義と item 定義は残す。world-object、塞ぐ・扉・収納・光、と inventory-object、食べる・撃つ・装備・スタック、は
  フィールド群が凝集して分かれ、`NewPropSpec`/`NewItemSpec` は統一エンティティモデルへの2つの焦点ファクトリになる。分かれ目は
  authoring 層にあり、エンティティ層は `Fixed` 状態で統一のまま。「prop は別種のエンティティ」という種別 ontology の再輸入では
  ない。ランタンは固定物とし、両方の性質を持つ重なりオブジェクトは当面想定しない。重なりが増えたら定義の統合を再検討する。
- ステーションは doc 80 の presence 効果を、設置でなくキューブ収納内 item の存在で実現する。溶接機を持ち歩いても効かず、
  キューブの棚に据えて初めて workshop になる。
- Minecraft を検討して却下した経緯は採用しなかった方法に残す。看板にせず着想と対比に留める。
- Ark strict semantics に留意する。状態のコンポーネント差し替え、空タグの `Has`、serde 登録の除外リストを規約どおりにする。
