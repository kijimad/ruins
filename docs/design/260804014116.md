# 全メニュー state を単一の UI ランタイムへ統一し state と描画を分離する

## 背景

doc 260802202800.md でメニューの**部品**は共通化できた。正準キーマップ、`newTabScreenUI` によるタブ骨組み、`menuscreen.Detail`、`menuscreen.ActionWindow`、1カラム一覧が揃い、各画面の見た目と操作は一貫した。

しかし部品を**動かすランタイム**は各 state が手書きのままで、state と描画がまだ混ざっている。さらに全 state を調査すると、メニューが**2系統に分裂**していることが判明した。

### メニュー state の全数調査

| state | ランタイム | 描画 | 系統 |
|---|---|---|---|
| ShopMenuState | hooks.Mount | tabScreen + menuscreen | A |
| CraftMenuState | hooks.Mount | tabScreen + menuscreen | A |
| TavernMenuState | hooks.Mount | tabScreen + menuscreen | A |
| StorageMenuState | hooks.Mount | tabScreen + menuscreen | A |
| ItemActionState | hooks.Mount | tabScreen + menuscreen | A |
| CharacterState | hooks.Mount | tabScreen相当 + menuscreen | A |
| SettingsMenuState | hooks.Mount | 独自テーブル | A |
| MainMenuState | hooks.Mount | 独自縦リスト | A' |
| ComponentDebugState | hooks.Mount | 独自テーブル | A' |
| CharacterJobState | hooks.Mount | 独自縦リスト | A' |
| CharacterNamingState | hooks.Mount | テキスト入力 | A' |
| DungeonMenuState | messagedata | PersistentMessageState | B |
| DebugMenuState | messagedata | MessageState | B |
| InteractionMenuState | messagedata | MessageState | B |
| LanguageMenuState | messagedata | MessageState | B |

- 系統A: `hooks.Mount` + `tabScreen`/`menuscreen` のタブ・一覧メニュー。
- 系統A': `hooks.Mount` は使うが `tabScreen` を使わず独自レイアウトを組む一覧・入力メニュー。
- 系統B: `messagedata` + `MessageState`/`PersistentMessageState` で「本文＋選択肢」を出す選択メニュー。`hooks.Mount` を使わない。

### 現状の結合（コード調査で確定した事実）

| 症状 | 実態 |
|---|---|
| 構造体にドメイン状態とUI機構が同居 | 系統A・A' の全 state に `rebuild bool` / `*hooks.Mount[Props]` / `widget *ebitenui.UI` が機械的に入る。本物のドメイン状態は `target`・`subState`・`resultEntity`・`candidates` だけ |
| `Update()` がほぼ丸ごと重複 | `shop_menu.go` と `storage_menu.go` の `Update` は9割同一。差は「systemsを回すか」「overlayがdetailだけかactionWinもか」だけ |
| 入力ゲートが手書きの if/else 連鎖 | 各 state が `detail.Active()` → `actionWin.Active()` → 通常入力、を毎回書く |
| overlay の重ねも手書き | `buildUI` の末尾で `if detail.Active(){ AddWindow }` を各 state が書く |
| View が state を直接読む | `buildUI` が `st.mount`・`st.subState` を触るため純粋関数でない。character だけ本 doc 着手前に `character_view.go` へ純粋分離済み |
| メニューのランタイムが2つある | 系統A・A' は `hooks.Mount`、系統B は `messagedata`。**同じ「選択して実行する」操作が2つの実装で二重管理**されている |

Model と View と Update の3層は既に7割できているのに、3層を回すランタイムを各 state が自前で持つため、構造体と Update に UI 機構が漏れ出している。加えて系統B が別ランタイムで並存している。**実装が分かれたままでは「メニューを統一した」とは言えない。全メニューを1つのランタイムへ寄せる。**

## 要件

- 系統A・A'・B の**全メニュー state を1つのランタイム `menuscreen.Screen` の上に載せる**。系統B の `messagedata` によるメニュー実装は廃し、`messagedata`/`MessageState` は本文提示のナラティブ用途だけに残す。
- 各 state の構造体から `rebuild`・`widget`・`*Mount` などUIランタイムを消し、ドメイン状態だけを残す。
- `Update()` の6手順の骨格を1箇所へ集約し、各 state から重複を除く。
- View を純粋関数に強制する。描画は state を受け取らず、Props と選択位置だけから組む。純粋化により VRT が `View(props)` を state 構築なしに直接検証できる。
- overlay の入力専有と window 重ねを、登録制の1ループに畳む。相互排他と優先順位を不変条件として定義する。
- state 固有差、`Skips`・対象切替・追加systems・1ページ件数・タブ無し・テキスト入力・本文付き選択肢、をランタイムを分岐させずに吸収する。
- 挙動は不変を基本とする。系統B は描画系統が変わるため見た目が寄るが、操作は等価に保つ。VRT ゴールデンと `make check` で担保する。

## 一般解の調査（他ゲーム・ライブラリ）

UI の組み方は、ゲーム・GUI ライブラリを横断して確立した型がある。他実装を調査し、本 doc の設計判断に対応づけた。

### 2層に分ける。部品ライブラリ層とアプリ実行層

主要エンジンはどれも「再利用可能な部品ライブラリ層」と「画面ごとの薄いロジック層」を明確に分ける。Unity UI Toolkit は UXML/USS/C#、Unreal は部品の Slate と画面の UMG、Godot は Control ノードとシーン、RmlUi は「ドキュメントを描くライブラリを呼び出し側がループで駆動する」。本プロジェクトも同じ2層で捉える。部品層は既にある ebitenui・styled・theme、アプリ実行層がこれから作る `menuscreen.Screen`。「UI をライブラリに作り込んで抽象的に呼ぶ」という一般像はこの2層構造そのもので、欠けているのは後者の実行層である。

### View は状態の純粋関数。MVU と宣言的 UI

React・SwiftUI・Jetpack Compose・Elm はいずれも「View = 状態の純粋関数」を核に、状態と UI の結合を断つ。中でも Elm Architecture、すなわち MVU の Model / View / Update が本 doc の Fetch / View / Act に最も近い。Go では TUI フレームワークの Bubbletea が MVU をそのまま実装しており、次のインターフェースを持つ。

```go
type Model interface {
	Init() Cmd
	Update(Msg) (Model, Cmd)
	View() string
}
```

`Screen[P]` は Bubbletea の Program に当たる「ループを所有するランタイム」、`Model[P]` は Bubbletea の Model に当たる。Go の暗黙インターフェースで state 構造体がメソッドを持つだけで Model を満たす点も同じ。Go のゲームで MVU ランタイムを自作する方向には強い先例がある。

一点補正する。本 doc の `Fetch(world) Props` は Elm の Model、状態の本体、ではない。ECS world から表示用の値を射影する selector に当たり、Redux の mapStateToProps や MVVM の ViewModel 導出に近い。状態の源は ECS world 側にあり、Props はその毎フレームのスナップショットである。

### 即時モードと保持モード

GUI は即時モード、Dear ImGui・egui・ratatui のように毎フレーム UI を再宣言する系、と、保持モード、Qt・DOM・ebitenui・Godot のようにツリーを保持しイベント駆動する系、に大別される。中間に React・Compose・iced の「宣言的に書くが内部で保持ツリーを差分適用する reconciler」がある。ebitenui は保持モードで、本プロジェクトの「dirty フラグで再構築」は保持ツリー上の粗い自作 reconciler に当たる。ローグライクのメニューはターンやメニュー開閉の離散的タイミングでしか変わらないため、粗い全再構築で十分安く、妥当な選択である。注意点は2つ。再構築でフォーカスやスクロールなどのウィジェット局所状態が失われること、dirty が広すぎると些細な変化で全再構築することである。困ったら React 風の細粒度差分でなく、dirty 領域の細分化か部分的なウィジェット直接更新へ寄せる。

### データ駆動メニューと画面スタック

RPG では「メニュー = データ」、項目のラベルと実行のテーブルを汎用レンダラが描き汎用コントローラが入力を捌く、が定石で、これは Fetch、データ、View、描画、Act、実行、の分解そのものである。`ChoiceModel` で系統B を吸収する方針はこの定石に沿う。メニューの入れ子は「画面スタック」、push/pop で最上位だけが更新と入力を受ける、で扱うのが一般的で、既存の state スタックがこれに当たる。

### 誤った抽象への警戒

調査は強い警告も返した。「3画面に合った抽象を4画面目の変則画面へ無理に広げ、パラメータと条件分岐で歪ませると、どの単一の概念も表さないもろい抽象になる」。Sandi Metz の「重複は誤った抽象よりはるかに安い」、Kent Dodds の AHA すなわち早すぎる抽象を避ける、rule of three が該当する。実務指針は次のとおり。

- 抽象して安全なのは**部品**、リスト・カーソル・枠・選択行。危険なのは**画面の実行ループ**を単一の巨大コントローラへ一本化すること。
- 変則画面、character の入れ子モーダルと第2カーソル、は生の条件分岐で driver に埋め込まず、**入力レイヤとモーダルのスタック**として合成する。最上位のフォーカスが入力を専有し下位を gate する、という一般的な入力優先度スタックで表す。
- `isCharacterScreen` のような画面固有フラグが driver に生え始めたら、それが誤った抽象の警報である。そのときは inline へ戻して分割する。

この警告を本 doc は次のように吸収する。全メニューを1ランタイムに載せる方針は保つが、**driver は薄いランタイムと部品と入力レイヤスタックに徹し、太いコントローラにしない**。character の変則性は driver 本体でなく `Overlay` と入力スタックの合成で吸収する。段階3で character を先行検証する狙いは、この「器が変則画面に条件分岐なしで耐えるか」を早期に殴ることにある。耐えられなければ character を driver 対象から外し、部品と入力スタックだけ再利用する退避策へ切り替える。

## 設計

### 3層の明確化

既にある3つに名前を与え、責務境界を型で固定する。

```
Model  : Fetch(world) Props            world からUIに要る値だけを取り出す純粋スナップショット
View   : View(props, sel) *ebitenui.UI Props と選択位置から widget を組む純粋関数。state を読まない
Update : Act(world, action) Transition  入力に応じてドメインを変更する
```

足りないのは3層を回す**ランタイム**。これを `menuscreen.Screen[Props]` に集約し、全系統がこの上に載る。MVU の Model / View / Update に対応し、`Screen[Props]` はループを所有する Bubbletea の Program に相当する。`Fetch` は状態の本体でなく ECS world からの射影 selector であり、状態の源は world 側にある点を設計の前提とする。

### overlay インターフェースの統一

`Detail` と `ActionWindow` を1つのインターフェースに揃える。入力ゲートと window 重ねが「登録リストのループ」になる。

```go
// Overlay はメニュー本体に重ねる小窓の共通契約。
// Active なら入力を専有し、閉じるまで下位の overlay とメニュー本体の操作を止める
type Overlay interface {
	Active() bool
	HandleInput(world w.World) (dirty bool, err error)
	Window(world w.World, rect image.Rectangle) *widget.Window
}
```

`ActionWindow.HandleInput` は既にこの形。`Detail.HandleInput` は現在 `bool` を返すので `(bool, error)` へ揃える。返す error は常に nil でよく、シグネチャだけ合わせる。

**不変条件**: overlay は登録順が優先順位。入力は「Active な最上位の overlay」だけが専有する。window は Active なものを登録順に重ねる。overlay 同士は原則相互排他とし、あるものを開くときは同時に開けたい下位以外を閉じる。ネストを許すのは character の「装備選択中に詳細を開く」のような明示ケースだけで、その場合は詳細を装備選択より上位に登録する。

### ランタイム `menuscreen.Screen[Props]`

UI機構の保持と6手順の駆動を担うジェネリックなドライバ。系統A・A'・B の全 state から UI 機構をここへ集める。

```go
// Selection は描画に要るカーソル位置。全メニュー共通
type Selection struct {
	TabIndex  int
	ItemIndex int
}

// MenuConfig は Fetch 済みの props から決まるメニュー構成。state 固有差はここで吸収する。
// TabCount が 0 のときは一覧を持たない画面、テキスト入力など、として UseTabMenu を呼ばない
type MenuConfig struct {
	Key          string
	TabCount     int      // 0 なら一覧なし。UseTabMenu を登録しない
	ItemCounts   []int
	ItemsPerPage int      // 0 なら既定値 menuItemsPerPage
	Skips        [][]bool // カーソルを飛ばす見出し行。nil 可
}

// TransitionCarrier は遷移の受け渡し口。es.BaseState が満たす。
// Model に es.State を丸ごと要求すると Update/Draw が循環するため、遷移アクセサだけを切り出す
type TransitionCarrier[T any] interface {
	SetTransition(es.Transition[T])
	ConsumeTransition() es.Transition[T]
}

// Model はメニュー1画面が満たす契約。UI機構は持たず純粋な部品だけを提供する。
// Input は正準キーマップに画面固有キーを重ねる入口。既定実装を埋め込みで配り、
// 画面固有キーが要る character などだけ上書きする
type Model[P any] interface {
	TransitionCarrier[w.World]
	Fetch(world w.World) P
	Menu(props P) MenuConfig
	Input() (inputmapper.ActionID, bool)
	View(props P, sel Selection, res resources.UIResources) *ebitenui.UI
	Act(world w.World, action inputmapper.ActionID) (es.Transition[w.World], error)
}

// Screen はメニューのUIランタイム。mount・widget・rebuild と overlay・systems を保持し、
// 毎フレームの6手順を回す
type Screen[P any] struct {
	mount    *hooks.Mount[P]
	widget   *ebitenui.UI
	rebuild  bool
	overlays []Overlay   // 入力専有と window 重ねの優先順
	systems  []w.Updater // 毎フレーム回す systems。空可
}
```

駆動の本体は1つ。各 state の `Update` はこれへの1行委譲、`Draw` も委譲になる。

```go
func (s *Screen[P]) Update(world w.World, m Model[P]) (es.Transition[w.World], error) {
	// systems は登録済みインスタンスを名前で引いて回す。値を直接呼ぶと状態を持つ system が壊れる
	for _, u := range s.systems {
		if sys, ok := world.Updaters[u.String()]; ok {
			if err := sys.Update(world); err != nil {
				return es.Transition[w.World]{}, err
			}
		}
	}

	// 入力ゲート。Active な最上位 overlay が専有。無ければ Model.Input を Act へ流す
	if ov := s.activeOverlay(); ov != nil {
		dirty, err := ov.HandleInput(world)
		if err != nil {
			return es.Transition[w.World]{}, err
		}
		if dirty {
			s.rebuild = true
		}
	} else if action, ok := m.Input(); ok {
		if tr, err := m.Act(world, action); err != nil {
			return es.Transition[w.World]{}, err
		} else if tr.Type != es.TransNone {
			return tr, nil
		}
		s.mount.Dispatch(action)
	}

	props := m.Fetch(world)
	s.mount.SetProps(props)
	cfg := m.Menu(props)
	if cfg.TabCount > 0 {
		hooks.UseTabMenu(s.mount.Store(), cfg.Key, s.tabConfig(cfg))
	}

	if s.mount.Update() || s.widget == nil || s.rebuild {
		s.widget = m.View(props, s.selection(cfg.Key), world.Resources.UIResources)
		for _, ov := range s.overlays {
			if ov.Active() {
				if win := ov.Window(world, getCenterWinRect(world)); win != nil {
					s.widget.AddWindow(win)
				}
			}
		}
		s.rebuild = false
	}
	s.widget.Update()
	return m.ConsumeTransition(), nil
}

// Draw は保持中の UI を描く。各 state の Draw はこれへ委譲する
func (s *Screen[P]) Draw(screen *ebiten.Image) { s.widget.Draw(screen) }
```

`Input` の既定実装は埋め込み用の小さな型で配る。正準キーの `HandleMenuInput` をそのまま返すだけ。`x` 詳細や `, .` 対象切替のような画面固有キーは、生キー直読みを各所へ散らすのでなく、この `Input` を上書きして「正準 + 宣言的な追加キー表」を返す形に閉じる。doc 260802202800.md の「入力の入口は1系統」を保ったまま、追加分を1メソッドに集約する。

### 系統B と A' を載せる仕組み

**選択メニュー（系統B）は `ActionWindow` と同型**、ラベルと実行の並び、なので、共通の Model アダプタで吸収する。

```go
// Choice は選択メニューの1項目。Run が選択時の実行
type Choice struct {
	Label string
	Run   func(world w.World) (es.Transition[w.World], error)
}

// ChoiceModel は本文と選択肢だけの単純メニューを Model として提供する共通アダプタ。
// DungeonMenu・DebugMenu・InteractionMenu・LanguageMenu はこれに choices を渡すだけになる
type ChoiceModel struct {
	es.BaseState[w.World]
	Body    string
	Choices []Choice
}
```

これで系統B の各 state は `messagedata` を組む代わりに `[]Choice` を作るだけになり、`MessageState`/`PersistentMessageState` はナラティブ本文の提示に用途を絞れる。ランタイムは系統A と同一になる。

**独自レイアウトの系統A'** は、`Screen` の `View` が任意の `*ebitenui.UI` を返せるため tabScreen 非使用でも載る。`MainMenu`・`CharacterJob` は `TabCount=1` の一覧、`ComponentDebug` は現行のテーブル描画をそのまま `View` に移す。`CharacterNaming` はテキスト入力で一覧を持たないので `TabCount=0` とし、`Input`/`Act` でキー入力を扱う。一覧の有無に関わらず mount・widget・rebuild・入力→Act の**ランタイムは共有**する。

### state 固有差の吸収方針

| 差分 | 吸収先 |
|---|---|
| 見出し行スキップ | `MenuConfig.Skips`。character の情報タブだけ使い他は nil |
| 1ページ件数 | `MenuConfig.ItemsPerPage`。0 で既定、別値の画面だけ明示 |
| 追加 systems | `NewScreen` の登録。storage の `WeightDirtySystem` 等 |
| 画面固有キー | `Model.Input` の上書き。正準 + 宣言的追加キー |
| 一覧なし・テキスト入力 | `MenuConfig.TabCount = 0` で UseTabMenu を呼ばない |
| 本文付き選択肢 | `ChoiceModel.Body` |
| 第2 mount（装備選択） | equipMount を内部に持つ overlay に閉じ込め、`Screen` は本体 mount だけを見る |

### 対象範囲

**全メニュー state を対象とする。** 上表の系統A 7本、系統A' 4本、系統B 4本の計15本すべてを `Screen` へ移す。系統B は `messagedata` によるメニュー実装を廃する。

対象外は非メニューの state のみ、`DungeonState`・`ShootingState`・`LookAroundState`・`OverworldMapState`・`CubePanelState`・`MapGenVisualizerState`・`DemoStartState`、およびナラティブ専用に用途を絞った `MessageState`・`PersistentMessageState`。

### 段階移行

1. `Overlay` インターフェースを定義し `Detail`・`ActionWindow` を適合させる。`Detail.HandleInput` を `(bool, error)` へ。
2. `menuscreen.Screen[P]`・`Model[P]`・`MenuConfig`・`Selection`・`TransitionCarrier`・`ChoiceModel` を新設し、ユニットテストを付ける。
3. **器を最も試す2本で先行検証し、ゲート判断する**。`CharacterState`、overlay 入れ子の最難関、と `InteractionMenuState`、系統B の代表、を移行し、抽象が両極に耐えるか確認する。ここで型と `Overlay`/`ChoiceModel` を確定させる。character が条件分岐なしに載らなければ、character を driver 対象から外し部品と入力スタックだけ再利用する退避策へ倒す。
4. 残りを1本ずつ移行する。系統A の `settings`・`storage`・`shop`・`tavern`・`craft`・`item_action`、系統A' の `main_menu`・`component_debug`・`character_job`・`character_naming`、系統B の `dungeon`・`debug`・`language`。各移行で `make check` と VRT ゴールデンで確認する。
5. `messagedata` のメニュー用途を撤去し、`MessageState`/`PersistentMessageState` をナラティブ専用に整理する。

## 採用しなかった方法

### character を driver 対象から外し、部品だけ再利用する

調査は、変則画面を汎用コントローラへ載せるのが誤った抽象の典型的な入口だと警告する。character の入れ子モーダルと第2カーソルは driver の器を条件分岐で歪めうる。それでも本 doc は全メニュー統一のため character も対象に含める。ただし無条件ではない。段階3で先行検証し、`Overlay` と入力レイヤスタックの合成で条件分岐なしに載るかを確認する。載らなければこの案、character は `Screen` を使わず部品と入力スタックだけ再利用する、へ退避する。判断を段階3のゲートに置き、`isCharacterScreen` 型のフラグが driver に生えたら退避へ倒す。

### 系統A だけを対象にし、系統B は messagedata のまま残す

本 doc の初版はこれだった。だが「選択して実行する」同一操作が2ランタイムで二重管理される状態が残り、「メニューを統一した」とは言えない。実装が分かれたままでは意味がないので、全系統を1ランタイムへ寄せる方針に改めた。

### 全画面を単一の宣言的 Spec で置換する

タブ・一覧・詳細・アクション窓を1つのデータ構造で宣言し共通ランタイムが解釈する案。doc 260802202800.md で退けた。character の対象切替や craft の合成結果窓、系統B の本文付き選択肢のような画面固有の振る舞いを Spec に押し込むと、Spec が巨大な条件分岐になり読みにくい。振る舞いはコード、構成はデータ、の分業を保つ `Model` 方式を採る。

### 基底構造体の埋め込みによる共通化

`type baseMenu struct{ mount; widget; rebuild }` を各 state に埋め込む案。フィールド重複は減るが `Update` の駆動は各 state に残り、View の純粋化も強制できない。ジェネリックな `Screen[P]` が Props 型を保ったまま駆動を1箇所に持てるのに対し、埋め込みは駆動を集約できないので採らない。

### ebitenui 標準のイベント駆動へ全面委譲

ゲームの毎フレーム `Update`/`Draw` と二重ループになり、VRT の決定性も崩れる。hooks.Mount による明示的な再構築を保つ。

## コメント

- 本 doc は doc 260802202800.md の後継。85 は部品、87 は全メニューのランタイム統一を扱う。
- 器を決めるのは最も歪な画面。易しい画面から作ると器が小さくなり最後に破綻するため、段階3で character、overlay 入れ子、と系統B、別ランタイム統合、の両極を先に殴る。
- `Screen[P]` は state 構造体に値で埋め込む。コピーすると overlay ポインタが旧実体を指すため、コピー禁止とし `OnStart` で `NewScreen` して overlay を登録する不変条件を守る。
- 系統B は描画系統が message から menu へ変わるため見た目が寄る。操作は等価に保ち、VRT ゴールデンを再生成する。
- スタイルは `styled`・`theme` に集約済みで、`View` はそのヘルパ経由で描き生のスタイル値を持たない。Godot Theme や Unity USS に相当するスタイル分離層を保つ。
- 抽象して安全なのは部品、危険なのは画面の実行ループの一本化。driver が `isCharacterScreen` 型の画面固有フラグを持ち始めたら誤った抽象の警報とみなし、その画面は inline へ戻して部品だけ再利用へ退避する。
- 本 doc の方向、MVU すなわち Model/View/Update と Go の Bubbletea 先例、2層構造、データ駆動メニュー、画面スタック、は他ゲーム・GUI ライブラリの一般解と一致する。詳細は「一般解の調査」節。

## 実装で判明した精緻化

- ランタイムは `menuscreen` でなく `states` パッケージに置いた。`Screen` は `getCenterWinRect`・`HandleMenuInput`・`newTabScreenUI` を使うため、states→menuscreen の一方向依存を保つには states 側に置くのが正しい。overlay 部品、`Overlay`・`Detail`・`ActionWindow`、は menuscreen に残す。
- `screenModel` のメソッド `fetch`・`menu`・`view` は非公開にした。全 model が states 内にあり、公開すると props 型を返す exported メソッドが unexported-return lint に触れるため。
- `view` は `(world, props, sel, res)` を取る。craft の詳細・説明が raw 参照に world を要するため。world は読み取り専用で state 構造体は読まないので分離は保つ。
- `MenuConfig.InitialTab` と `Screen.Dispatch` を足した。item_action の初期タブ寄せとタブジャンプを宣言的・明示的に表すため。
- character の装備選択は `characterEquipOverlay` として Overlay 化し、第2カーソル mount と x での詳細入れ子を overlay に閉じ込めた。Screen 本体に条件分岐は無い。
