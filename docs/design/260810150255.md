# UI アーキテクチャの一貫性を回復する

## 背景

UI の作り方が画面ごとにばらついていて一貫性が無い。乱れの実体は「抽象の数が概念の数を上回っている」ことにある。ひとつの概念に複数の実装が対応している。

- **一覧を出す** に 4 抽象。`states.renderMenuList`+`styled.table`、`tabmenu.View`、`views.RenderSpecRows`、`character_job` の手組み。
- **ページを繰る** に 3 実装。`pagination` パッケージ、`menuscreen` の独自 `detailPageCount`、`tabmenu` 独自。矢印記号も `consts.IconArrow*` と生の `↑↓` で不一致。
- **1 行ぶんの表示データ** に 4 型。`menuRow`、`SpecRow`、`tabmenu.Item`、`statusItemData`。
- **UI 構築の入口** が 8 通り。menurt、`newTabScreenUI`、`newPanelScreenUI`、state 独自 root、`menuscreen.Detail`、`tabmenu`、hud 直描き、state ローカル直描きパネル。

層の境界も乱れている。共通レイアウトビルダ `newTabScreenUI`・`newPanelScreenUI` が `widgets/` でなく `states/lib.go` にあり、UI 部品なのにデータ層へ同居する。`menuscreen` は overlay 契約・詳細窓構築・画面レイアウト計算 `LogTopY`・`CenterWindowRect` の異質 3 責務を同居する。`SpecRow` は `views` と `menuscreen` の 2 名で参照できてしまう。

パラダイムも混在する。retained な ebitenui の上で menurt が毎フレーム全再構築している。これは immediate のコストを払いながら retained の恩恵を捨てる既知のアンチパターンで、dirty を廃した簡素化が散らばった再構築の温床になっている。一方 tabmenu は差分更新 `UpdateFocus` を持ち、相反する 2 思想が同居する。ただし本作はターン制のメニュー主体で、毎フレーム再構築の CPU 浪費は実害が薄い。乱れの主因は perf でなく一貫性にある。

ebitenui の活用も浅い。対話・状態を持つ widget、`List`・`Button`・`TabBook`・`Checkbox`・focus・`event` パッケージ、はコード上どれも使用ゼロで、`TextInput` が名前入力に 1 箇所あるだけ。一覧・選択・タブ・ボタンを全て自前で再実装し、ebitenui は `Text`・`Container`・`Layout` の描画エンジンとしてのみ使っている。つまり「retained ライブラリの上で毎フレーム作り直す」ことと「対話層を使わない」ことの、二重の過小活用になっている。ただし入力は menurt が持ち、キーボード駆動なので、ebitenui の event/focus、ポインタ寄り、を採らないこと自体は正当。過小活用として直すべきは毎フレーム再構築のほうで、入力モデルとは別問題。

HUD は `screen.DrawImage` の直描きだが、メッセージ枠・武器スロット枠・ステータスバッジといった **メニュー系の chrome まで手描き** していて、統一 widget と直描きが混在する。`look_around`・`shooting`・`cube_panel` は `ebiten.NewImage`+`Fill` の自作パネルを各自で持つ。

図解版はアーティファクトにまとめた: https://claude.ai/code/artifact/18747792-42c6-4587-b4be-49fb27ad4abc

## 要件

- 1 概念 1 抽象に収斂する。一覧入口・ページング・行モデルをそれぞれ 1 つにする。
- 層の境界を引き直す。states は Fetch のデータ提供に純化し、レイアウトと一覧の部品は `widgets/` に集約する。
- UI の境界を「メニュー vs HUD」でなく「UI chrome か、ゲーム世界の canvas か」で決める。chrome は統一 widget へ、canvas だけ直描きに残す。
- 挙動を変えない。既存メニューの見た目・操作・golden は保つ。段階ごとに独立してマージできる単位に切る。
- 大規模な作り替えを一度にやらない。まず構造整理で乱れの主因を潰し、パラダイム判断は土台ができてから行う。
- 入力はキーボード駆動のまま menurt が持つ。ebitenui の event/focus と対話 widget、`List`・`Button`、はポインタ寄りで矢印カーソルに噛み合わないため採らない。マウス対応は当面ロードマップに入れない。
- ebitenui を retained として使う。画面のツリーを 1 度組み、状態変化ではプロパティ更新に留め、毎フレーム作り直しをやめる。

## 設計

### 目標アーキテクチャ

states の Fetch が返すデータから UI の記述を組み、1 つの renderer が ebitenui へ反映する。ゲーム世界の描画は独立した canvas 層に分ける。

```
states.Fetch（データ提供に純化）
        │
        ▼
UI 記述 / コンポーネント          Canvas 層（直描き）
  Panel / List(row/cell) / Detail   ダンジョン・ミニマップ中身・演出
  1 行モデル / 1 一覧 / 1 ページング   screen.DrawImage
        │
        ▼
1 つの renderer → ebitenui（retained）
```

### パラダイムの選択（案 A: ebitenui を retained として正しく使う）

メニュー主体でカーソルと選択状態を持ち、しかもキーボード駆動なので、**入力は menurt が持ったまま、ebitenui を retained として使う案 A を採る**。二重の過小活用のうち直すのは「毎フレーム作り直し」で、入力を自前で持つことは変えない。

- **A. retained 正攻法（採用）**: 画面のツリーを入場時に 1 度組み、以後は状態変化に応じてプロパティ更新、選択ハイライト・テキスト・可視、で回す。menurt の Fetch/DoAction とキーボード入力はそのまま。dirty 追跡を再導入し、毎フレーム View の全再構築を撤回する。ebitenui 本来の使い方に寄せる。
- **B. 宣言的 + reconciliation（不採用・次点）**: View が UI 記述木を返し 1 renderer が差分反映する第 3 の道。構造と再構築を同時に解決するが、小さな reconciler の自作というミニフレームワーク化が要り実装量が最大。案 A で retained の恩恵は得られ、キーボードのみなら記述木の抽象度は過剰なため見送る。
- **C. 再構築を許容し構造だけ統合（第 1 段の中身）**: 一覧・行・ページング・レイアウトを 1 本に畳む。パラダイム決定と独立に効くので、案 A の前段として先に行う。

対話 widget、`List`・`Button`・`TabBook`、はキーボードのみで進めるため採らない。矢印カーソルを ebitenui の focus に載せると噛み合わず、自前の一覧・カーソルの方が素直。将来マウスを入れるなら再検討する。

retained 化の骨子は、View を「毎回組んで返す」から「1 度組んだツリーへ状態を書き込む」へ移すこと。

```go
// 案 A: 画面ごとに widget を 1 度組み、状態変化でプロパティだけ更新する
type screenView struct {
	root *widget.Container
	rows []*rowWidget // 保持した行 widget。作り直さず選択色やテキストを書き換える
}

// Screen は毎フレーム View を作り直す代わりに update を呼ぶ。dirty なら反映、無ければ何もしない
func (v *screenView) update(props Props, cursor Selection) { /* 変わった箇所だけ書き込む */ }
```

### 段階計画

第 1 段は案 C の内容。パラダイム決定と独立に効くので先行する。

1. 行モデルを 1 つに。`Cell` 化した行を土台に `SpecRow`・`tabmenu.Item`・`statusItemData` を吸収し、描画は `styled.table` 一本にする。
2. 一覧入口とページングを 1 つに。`renderMenuList` を唯一の一覧入口にし、tabmenu 選択肢と `character_job` 手組みを寄せる。ページングは `pagination` に統一する。
3. レイアウト層を `widgets/` に新設する。`newTabScreenUI`・`newPanelScreenUI`・`LogTopY`・`CenterWindowRect`・`wrapModalRoot` を states と menuscreen から集約し、states をデータ提供へ純化する。
4. HUD の chrome を統一 widget へ移す。メッセージ枠・武器スロット枠・バッジ・自作パネルを共通部品にし、canvas はダンジョン・ミニマップ中身・演出だけに絞る。
5. 命名と重複を是正する。`SpecRow` の二重輸出を解消、`nameWithCount` へ整形統一、ハードコード色を theme へ、dead 気味の tabmenu を縮退する。

第 2 段は案 A の retained 化。第 1 段で 1 本化した一覧・行・レイアウトを土台に、画面の widget ツリーを保持してプロパティ更新で回す形へ移し、menurt の毎フレーム View 全再構築をやめる。dirty 追跡を再導入する。入力と Fetch/DoAction は変えない。

## 採用しなかった方法

- **B. 宣言的 + reconciliation**: View を記述木にして 1 renderer で差分反映する第 3 の道。構造と再構築を同時に解決するが、reconciler の自作というミニフレームワーク化が要る。案 A で retained の恩恵は得られ、キーボードのみなら記述木の抽象度は過剰なため次点として見送る。
- **対話 widget、`List`・`Button`・`TabBook`、を採用する**: キーボードのみで進めるため。矢印カーソルを ebitenui の focus に載せると噛み合わず、自前の一覧・カーソルが素直。マウス対応を入れるなら再検討する。
- **D. 別 UI ライブラリへ移植する**: furex は Flexbox 思考、ebiten-imgui は immediate だが開発ツール向けで意匠が ImGui 調。ebitenui が既に機能する以上、全面移植の利は薄い。Go 圏の immediate は実質 Dear ImGui バインディング一択でプレイヤー向けメニューに不向き。
- **HUD をメニューと別レイヤのまま直描きで残す**: 当初案だが、メッセージ枠などの chrome を手描きし続けると統一の穴が残る。境界は描画対象、chrome か canvas か、で引くべきで、HUD かどうかでは引かない。

## コメント

- 乱れの主因は perf でなく重複と層の乱れ。だから第 1 段の構造整理を最優先にする。ここだけでも体感は大きく変わる。
- 各段は独立してマージできる単位に切り、`make check` と golden で挙動不変を担保する。特に一覧・行の統合は golden の差分が「意図した見た目変更」に限られることを確認する。
- アイテムアイコン対応で導入した `styled.Cell` は、この収斂の第一歩でもある。記述木に格上げする土台になる。
- 図解版はアーティファクトにある。設計判断の共有には図を、版管理される計画にはこの doc を使う。
