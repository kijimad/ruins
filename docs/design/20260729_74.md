# state ゴールデンを画像一致から ECS 状態一致へ移す

## 背景

`internal/states/golden_test.go` の約30本の `TestGolden_*` は、State スタックを ebiten で描画した PNG を、ピクセル・トレランス比較でゴールデンと突き合わせている。これがフレーキーで、退行検知力も低い。

- **環境依存でフレーキー**。描画は xvfb + フォントラスタライズに依存し、CI と手元、CI 同士でも微差が出る。PR #545 では散らかりの生成を surgical に変えただけで、オーバーワールド背景を描く8本の states ゴールデンが「ピクセル差分がトレランス(0.96%)超過」で落ちた。内容変化と環境差が同じ土俵で混ざり、切り分けられない。
- **トレランスの盲点で退行を見逃す**。`internal/vrt/golden.go:167` のコメントが自認するとおり、`pngPixelEqualFn` は「広域に及ぶ中振幅の変化を、各画素が許容振幅内なら見逃す」。背景色の微変更やタイル1枚の入れ替えのような、意味のある構造変化を素通しする。つまり画像ゴールデンは**フレーキーである一方で鈍感**という最悪の組み合わせ。
- **更新が高コスト**。フレークのたびに `make updategolden` を canonical 環境で回して再生成し、バイナリ差分をコミットする必要がある。差分レビューも人力の目視に頼る。

一方、リポジトリには既に理想形の先例がある。`TestGolden_MapGenSnapshot`(`golden_test.go:399`) は生成中間データを `json.MarshalIndent` で `.json` ゴールデンにし、対の `TestMapGenImages`(`golden_test.go:426`) は画像を**比較せず目視用に保存するだけ**。`internal/maptemplate` の `FormatResolvedMap`(`template.go:64`) はセル配列を決定的な ASCII テキストにして `.txt` ゴールデンにしている。これらは環境非依存で、diff が人に読め、構造変化に敏感。本設計はこの方式を states ゴールデン全体へ広げる。

## 要件

- **決定的・環境非依存**。同じ seed なら CI・手元・OS を問わず同一のゴールデンになる。xvfb やフォントに依存しない。
- **画像は残すが比較しない**。見た目の確認のため PNG は今までどおりレンダリングして保存する。ただしピクセル一致検証はかけない。フレークの源である「画像の assert」を外す。
- **退行検知力を上げる**。タイル配置・エンティティの位置と種別・メニュー項目といった構造を assert し、トレランスが見逃していた変化を捉える。
- **30本すべてをカバー**。世界主体・背景付きメニューはテキスト assert、純UIメニューは画像のみ(assert なし)と、類型ごとに検証方法を割り当てる。
- **手法の選択基準を仕組み化**。どの状況でどの手法を使うかを skill に明記し、今後フレーキーな pixel-assert を新規に増やさない。

## 設計

### 3類型と assert 対象

state ゴールデンは描画内容で3つに分かれる。決定的に assert したい情報は類型ごとに違うので、対象を変える。画像は全類型で共通に「レンダリングして保存・比較なし」。

| 類型 | 例 | テキストゴールデンの対象 |
|---|---|---|
| 世界主体 | Overworld / OverworldFrost / Dungeon / LookAround / Shooting / Pickup / Place | **WorldSnapshot**（タイルグリッドのテキスト + エンティティ一覧） |
| 背景付きメニュー | Inventory / Save / Status / Message / ComponentDebug / Squad / Storage 等18本 | 前面 State の**論理内容**（メニュー項目・選択・本文）。背景 world は画像のみ |
| 純UIメニュー | MainMenu / Settings / Language / CharacterNaming / CharacterJob | **テキスト assert しない。画像のみ（目視用に保存、比較なし）** |

### WorldSnapshot: spawn 後 world の決定的テキスト化（新規の核）

現状、spawn 後の world ECS を決定的にテキスト化する関数は無い（`FormatResolvedMap` は生成前の `MapCell`、`mapplanner.Snapshot` は生成前の `MetaPlan` が対象）。世界主体の類型のために新設する。

```go
// WorldSnapshot は spawn 後の world ECS を決定的にテキスト化したゴールデン対象。
// 画像に依らず、タイル配置とエンティティの内容で退行を捉える。
type WorldSnapshot struct {
	Grid     []string         // Level の各行をタイル記号で。y→x の固定順
	Entities []EntitySnapshot // 座標→ID の固定順に並べたタイル以外のエンティティ
}

// EntitySnapshot はエンティティ1体の決定的要約。座標と種別と Name、
// および golden で追いたい主要コンポーネントの値だけを持つ。
type EntitySnapshot struct {
	Pos  consts.Coord[consts.Tile] // GridElement 由来
	Kind string                    // "player" / "enemy" / "prop" / "item" ...
	Name string
	// 追加の決定的要約。例: HP、AI ポリシー。まず最小限で始める
	Extra string
}

// SnapshotWorld は現ステージの world を WorldSnapshot にする。
//   - グリッド: Level.TileHeight × TileWidth を y→x で走査し、GridElement→タイル名を引いてテキスト化
//   - エンティティ: タイル以外を集め、(Y, X, entity.ID()) の順にソートして決定化
func SnapshotWorld(world w.World) WorldSnapshot
```

決定性の担保:

- **グリッドは Level を基準に全域走査**する。`Level.TileWidth/TileHeight`(`components/dungeon.go:106`) と `GridElement`(`components/field.go:24`) から `map[GridElement]タイル名` を作り、`y→x` で記号化する。map 反復でなく座標の二重ループなので順序は固定。
- **エンティティは座標とIDでソート**する。ark の `FilterN.Query()` の反復順は決定的と保証されない(調査で確認)。既存の決定化手段 `query.SortEntities`(Name 順, `sort.go:13`) と `entity.ID()` タイブレーク(`nearest.go:75`) に倣い、`(Pos.Y, Pos.X, ID)` の辞書順で並べる。
- タイルのテキスト表現(タイル名をそのまま出すか短い記号へ写すか)は**本PRでは決めない**。世界主体の実装時に定める。ゴールデンは `.txt`(グリッド + エンティティ行) にして diff を人に読ませる。

### 背景付き・純UIメニュー: 論理内容の取得

メニューの assert したい本体は前面 State のウィジェットではなく、その**論理モデル**（項目・選択・本文）。ウィジェットツリーの汎用ダンプは脆く実装も重いので採らず、State 側が決定的な論理内容を返す小さなインタフェースを導入する。

```go
// GoldenText を実装する State は、その決定的な論理内容を返す。vrt はこれをテキストゴールデンにする。
// world を引数に取るので、ECS 由来のメニュー(ComponentDebug/Storage 等)は world から内容を組める。
type GoldenText interface {
	GoldenText(world w.World) string
}
```

- ComponentDebug は既存の集計 `fetchProps`(`component_debug_state.go:112`, 種別→数を降順ソート) をそのまま文字列にできる。Storage/Squad/Formation/Status/MemberStatus は ECS 由来データを列挙して返す。
- **純UIメニュー(MainMenu/Settings/Language/CharacterNaming/CharacterJob) は `GoldenText` を実装せず、テキスト assert もしない。画像を目視用に保存するだけ**にする。ウィジェットだけの画面に決定的な論理内容を組む authoring コストに見合わないため、退行検知は目視に委ねる。
- スタックに複数 State があるときは、`GoldenText` を実装する各 State の出力を上から連結する。どの State も `GoldenText` を実装しないスタック(純UIメニュー)は、テキストゴールデンを作らず画像のみにする。

### vrt API: テキスト assert + 画像は保存のみ

`vrt.AssertStateGolden`(`state.go:33`) を、ピクセル比較から次の2段へ組み替える。`TestGolden_MapGenSnapshot`+`TestMapGenImages` の分離を一般化したもの。

```go
// AssertStateGolden は State スタックの決定的な論理内容を .txt ゴールデンと突き合わせる。
// ピクセル一致比較は廃止する。Draw は毎回実行して描画のパニック/エラーだけ検出し、画像は更新時のみ保存する。
func AssertStateGolden(t *testing.T, buildStates func(w.World) []es.State[w.World]) {
	world := InitVRTWorld(t)
	sm := driveStates(t, world, buildStates)
	// 決定的な論理内容があれば .txt を assert。純UIメニューは ok=false でテキストを持たず assert しない
	if text, ok := snapshotStates(world, sm.GetStates()); ok { // GoldenText 実装を連結、無ければ WorldSnapshot
		goldie.New(t, goldie.WithNameSuffix(".txt")).Assert(t, t.Name(), []byte(text))
	}
	// Draw を毎回実行し、パニック/エラーがあれば落とす smoke check。ピクセルは比較しない。画像は更新時のみ保存
	img := drawStates(t, world, sm)
	if isGoldieUpdate() {
		writeImageArtifact(t, encodePNG(t, img))
	}
}
```

- **通常実行は決定的なテキスト assert が本体**で、ピクセル一致比較をしないのでフレークしない。`Draw` は毎回実行するが結果を比較しないため、描画の非決定性はフレークにならず、描画の破綻(パニック/エラー)だけを smoke check で捉える。
- **画像は `GOLDIE_UPDATE` 時のみ**保存する。毎回書くと testdata が実行ごとに変わりノイズになるのを避ける。既存の `TestMapGenImages` が使う「assert しない描画」と同じ扱い。
- 純UIメニューは `snapshotStates` が `ok=false` を返し、テキスト assert をしない。画像は他と同じく `GOLDIE_UPDATE` 時のみ保存する。
- `assertPNGGolden`/`pngPixelEqualFn`/`toleranceForSize`/`channelTolerance16` は state ゴールデンから使われなくなる。ウィジェット単体の `AssertGolden`(`golden.go:37`) が残る場合は温存し、使われなければ削除する。

### 手法の選択基準（skill にも明記する）

| 手法 | assert 対象 | 使う状況 | 備考 |
|---|---|---|---|
| テキスト golden(ECS/グリッド) | WorldSnapshot | world/ECS を描く state。**第一選択** | 環境非依存・構造に敏感 |
| テキスト golden(論理モデル) | GoldenText の返り値 | メニュー等、world は無いが論理内容がある | ウィジェットの汎用ダンプはしない |
| 画像は保存のみ | 比較しない | 上記と常に併用。見た目の目視用 | フレークの源を断つ |
| ピクセル・トレランス比較 | 画像 | 原則新規禁止 | 見た目そのものが不変条件のUI部品だけ例外的に |

## 採用しなかった方法

- **serde(セーブ) の JSON をそのまま golden**。`serializeWorld`(`serde.go:48`) は arkserde でワールド全体を JSON 化するが、(1)エンティティ列挙順の決定性が保証されない、(2)checksum やタイムスタンプなどゴールデンに不要なノイズを含む、(3)golden が巨大で diff が読めない。決定化と枝刈りを自前でやるなら専用の WorldSnapshot の方が読みやすく壊れにくい。
- **ウィジェットツリーの汎用ダンプ**。ebitenui のコンテナ木を再帰的に文字列化する案。実装が重く、UI ライブラリの内部構造に密結合で壊れやすい。State ごとの `GoldenText` の方が意図が明示的で安定する。
- **ピクセル・トレランスを緩める**。閾値を上げればフレークは減るが、`golden.go:167` が自認する「広域中振幅の見逃し」が悪化し退行検知がさらに鈍る。フレークと鈍感さの両方が悪化するので不可。
- **画像ゴールデンを単に消す**。フレークは消えるが退行検知がゼロになる。テキスト golden で構造を守るのが本設計の主眼。

## コメント

- **移行順序**。まず世界主体7本(`WorldSnapshot`)を移す。フレークの主因かつ ECS テキスト化の効果が最大。次に ECS 由来メニュー(ComponentDebug/Storage/Squad/Formation/Status/MemberStatus)、最後に残りの背景付きメニュー。1本ずつ「旧 .png の assert を外し .txt を足す」ので途中でも緑を保てる。純UIメニューは assert を外すだけ。
- **決定事項(レビューで確定)**:
  - 画像のピクセル一致比較は廃止する。画像の保存は `GOLDIE_UPDATE` 時のみ。
  - ただし `Draw` は毎回実行し、描画のパニックやエラーを検出する smoke check は保つ。ピクセルは比較しないので描画の非決定性はフレークにならない。
  - 純UIメニューはテキスト assert をせず、画像のみ(目視用)にする。
- **タイル記号表は本PRでは触れない**。タイルのテキスト表現(記号か名前か、overworld/dungeon の語彙共通化)は、世界主体を実装する段で別途決める。
- **コードレビューで確認した制約(受容する)**:
  - テキストゴールデンは view-model を捉え、描画ピクセルは捉えない。スプライト・色・レイアウトだけが壊れ view-model が同じ退行は、テキストでは検出できない。`Draw` smoke check(パニック/エラー)と、更新時に保存する画像の目視でカバーする。これは「一致率検証をやめる」決定の裏返しで、意図した割り切り。
  - `TestGolden_OverworldFrost` の frost は描画オーバーレイで ECS に無いため、テキストは `Overworld` と同一になり判別力を持たない。frost の見えは画像目視に委ねる。
  - Save/Load のスロット表示は実 `./saves` と実時刻に依存し world の関数ではない。ゴールデンはクリーンな `./saves`(CI とチェックアウト直後の状態)を前提とする。ローカルにセーブがあると golden 不一致で落ちるが silent なバグではない。
- この設計と並行して、手法一覧と採用基準を `ruins-code`/`ruins-review` に明記する(変更箇所参照)。機械検知できる部分(例: states の新規 golden が `.png` の pixel-assert を使っていないか)は将来 lint 化を検討する。
