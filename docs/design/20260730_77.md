# 拡張可能な移動拠点を中核に据える

## 背景

design.md の原点は、凍った日本のキャラバン交易サバイバルで、必須目的をあえて定めないことでロールプレイの自由を成立させる、というものである。

長らく、帯の一方向強制移動やターン制限が、ロールプレイの自由や拠点への愛着と衝突して見えて迷っていた。議論の末に、迷いの正体が分かった。確信を「キャラバン」という皮に結びつけていたことである。皮はどこか恣意的なので、皮を疑うたびに全部が揺れた。

錨を下ろすべきは皮でなく、皮が抽象していた楽しみのほうだった。この doc は、まず守るべき楽しみを仕様として固定し、その上で現在の器を記録する。器が変わっても、楽しみへの錨は残る。実際、器はキャラバンの隊列から押すキューブへ、内装は建設から家具付けへと変わったが、下の楽しみの仕様はそのつど満たしたまま進めた。

## 要件

### 守るべき楽しみ

これが本当の仕様である。どんな器を選んでも、以下を満たすなら合格とする。

1. **育つ家への愛着** — 投資し、個性を与え、持続する我が家
2. **家を連れて行ける** — 移動しても愛着を失わない。積み上げた家が常に共にある
3. **代償のある蓄積** — 集めるのは楽しい、ただし必ず対価を払う。「何を残すか」が本物の決断になる
4. **意味のある仲間** — 明確な役割を負い、彼らへの愛着が生まれる
5. **賭けのある前進** — 一方向、背後に破滅、安全な籠城なし。緊張して前へ進む推進力
6. **旅の中の自由** — 何をするか、どう生きるかを選び、システムがそれを表現する
7. **停まって暮らす律動** — 停泊して家を使い、道具を使い、また進むリズム

### 避けるべき反・楽しみ

- 単調な作業、いわゆるトイル。際限のない最適化や運搬の細作業
- 移動の抽象化による、一続きの手触りの喪失
- 多タイルの乗り物が持つ実装の複雑さ
- ターン制限のような盤外のハードルールによる、鎖の感触

## 設計

現在の器は、押して進める1つのキューブである。

### 器 — 押すキューブと異次元の内装

- **外**: 3x3 のキューブ。フィールド上を4方向に押せる。回転しない。押し先に物があれば、壊して進むか、方向を変えて迂回する。下辺の1マスが異次元への扉になる
- **中**: キューブの内側は異次元の静止した空間。扉をくぐって入る。ここに物を置き、道具を置く

多タイルの複雑さは「歩いて入れる」と「動く」を同時に成立させることから生まれる。キューブはこれを分ける。守るべき不変条件は「回転しない」「移動中に内部を歩かない」の2つで、外で押すのは回転しない footprint、中で歩くのは静止した異次元、という分離がそれを満たす。3x3 を4方向に押すのは、押し込みブロックに破壊床を足した程度で、走行しながら中を歩ける多タイル乗り物の複雑さには遠く及ばない。回転と内部歩行を持ち込まない限り安く収まる。

押しはタクタイルなままで、抽象化しない。プレイヤーはキューブを離れて周囲のチャンクを徒歩で探索し、戻って押す。内装は異次元という世界内の虚構で正当化されるので、扉をくぐる感覚であり管理画面ではない。

障害はナビゲーションを押しの経済の一部にする。壊せば追加のコスト、迂回すれば余分な距離で、どちらもAPを食い寒波の時計に効く。かさばる3x3を凍原のどこを通すかが、決断になる。

### 皮 — 無地のキューブに確定する

見た目は無地のキューブに固定する。これは最小の皮であり、凝った絵・大きな器の描画・物語の下地を、まとめて先送りにするための選択である。中が広い謎の箱は異次元の内装をそれ自体で正当化し、説明されない箱は穴に見えない。

代償として、凍った日本というテーマへの手触りの結びつきは今は薄くなる。これは意識的に払う対価である。錨は皮でなく楽しみに置いてあるので、まず押しの機構が楽しみを届けるかをキューブで確かめ、美術と物語への投資はそれが証明された後に行う。機構が先、皮は後。物語の統合は破棄でなく先送りで、後から蔵でも遺物でも被せ直せる。

### 内装 — 建てず、置いて表現する

部屋は建てない。内装は単なる空間で、そこに item や prop を置くことで部屋を表現する。料理器具を置いた一角が台所になり、溶接機を置けば工房になる。部屋の意味は、建てた構造でなく、置いた物から立ち上がる。

- **効果は「置いてあること」から出す。配置からは出さない**。ストーブがあれば暖、溶接機があれば溶接ができる。どこに置いたかは効かせない。自由配置は、位置が何かを最適化した瞬間にトイルへ戻る。presence ベースに徹すれば、家具付けは純粋な自己表現でトイルにならない
- **空間は固定で寛容**。異次元なので広さは最初から余裕があってよい。実質の上限は面積でなく重量が担う。空間を増やしたいなら、建設でなく、より大きなキューブを得るなど非建設の手段にする
- **既存の機構を流用する**。このゲームには prop も item も配置・相互作用の仕組みもある。専用の建設システムを作らず、内装マップに既存の prop エンティティを置く形で済ませる

置くのは世界内の所作で、拾った品を部屋に持ち込んで据える。建設待ち行列のような計画メニューは無い。プレイヤーが読むべき一覧は、総重量と前線への余裕を映す HUD の数字だけである。飾るのは手触り、読むのは重量、と役割が分かれる。

### 重量押し経済 — 1つの比較に全部を集約する

この器の心臓は、移動に要するターン数と寒波の速さの比較である。1タイルの押しコストは総重量だけで決まって不変で、使えるAPの総量がそれを何ターンで払えるかを決め、寒波がその締切を決める。3つが「移動に要するターン数 対 寒波の速さ」という1つの比較に集約し、別々に設計していた要求を同時に解く。

- **移動圧力**: 1タイルの押しは高コストで、歩行の10倍規模のAPを食う。余裕を持って押さないと、いくら前線が遅くても呑まれる。ハードなターン制限は要らない。移動が重い決断で、滞在は無料、遅い凍結がいつか押しを強いる
- **代償のある蓄積**: 置いた物すべてが重量になり、1タイルのコストが上がる。無限の溜め込みが、恣意的な重量上限でなく移動コストとして自分を罰する。あらゆる獲得が「この重さを押す価値があるか」の決断になる
- **仲間の価値**: 所持APの総量。人数を集め強化するとAPが増え、同じコストをより少ないターンで払えて速く進める。1タイルの押しコスト自体は不変で、変わるのは何ターンで払えるかである。ゲーム内で費やすAPの総量も同じで、寒波への露出ターン数が減る

押しは1タイルずつでよい。1歩ごとに歩行の10倍規模のAPを費やすので、踏むたびに重さが体感できる。連打の煩わしさは、通常移動と同じく押しっぱなしで解く。押し続ければプレイヤーの実時間では高速に進むが、ゲーム内のコストは1タイルあたり不変で、連打でも長押しでも同じAPを食う。実時間の手間とゲーム内のコストを切り離す考え方である。長押し中もターンが進み寒波が迫るので、コストは目に見えたまま、余裕が削れていくのが分かる。

**ブレーキには釣り合う引力が要る**。押しコストは重い物に代償を課すが、良い決断になるのはプレイヤーが重い物を本気で欲しがるときだけである。飛ばせるだけなら最適解は空のキューブを軽く押すになる。だから設計の半分は、道具や戦利品を「重さを承知で連れて行きたい」ものにすることに向く。ブレーキと引力は一対で、片方だけでは成立しない。

### 労働と仲間 — AP供給が主の役割

建設が無いので、仲間の役割は所持APの供給・戦闘・運搬になる。使えるAPを増やして同じ押しを少ないターンで払えるように、人数を集め強化する。solo でも押せて暮らせる、ただしAPが少ないぶん同じ距離に多くのターンがかかり、寒波への露出が増える。建てる物が無いので「仲間がいないと拡張できない」問題は生じない。規模はそのまま旅のスタイルの表現になり、一匹狼は簡素、大所帯は賑わう。

### 圧力 — 寒波と押しコスト

移動を強いる圧力は、盤外のハードルールでなく、押しコストと迫る寒波の組み合わせで発生させる。

- 押しが高コストなので無限の最適化は成立しない。反トイルの終端圧をこれが担う
- 背後は凍り、戻っても無に帰す。一方向はレーンのルールでなく寒波が担保する。局所は4方向に操れるが、後ろへ戻り続けると呑まれるので、後戻りとバックトラック・ファーミングが割に合わない
- 置く物は旅の道すがら拾う。戻れないので採取は機会主義に留まり、専用の grind にならない
- **内装に籠っても締切は止まらない**。ダンジョンと同じく、内装には前線が入らない(異次元なので凍らない安全な我が家)が、中で行動すればターンは進む。前線は総経過ターンから決まるので、内装で時間を使って外へ出ると前線は進んでいる。滞在はAP的には無料だが、凍結の時計は籠っている間も動く。籠って凍結から逃げる、という抜け穴をこれが塞ぐ

これは以前保留していた「寒波は一方向ロック無しでトイルを止められるか」への、具体的な機構としての答えでもある。ロックは無い。移動は重量で高コストで、遅い凍結がいつか押しを強いる。残るのは押しの重さと前線速度のチューニングで、遊んで確かめる。

### 防衛 — 行わない

キューブそのものを守る防衛機構は設けない。賭けと緊張は、押しの余裕を切らせば前線に呑まれること、および徒歩で巡るチャンクでの遭遇戦から生まれる。キューブは安全な我が家・保管庫のままにし、守る対象としては扱わない。スコープを絞り、押しと寒波の緊張に一本化する。

## データ定義

置ける物のための専用の種別 enum やラッパー型は設けない。ECS なので、キューブはフィールド上の位置コンポーネントを持つ 3x3 のエンティティで、内装は prop エンティティを置く空間になる。置いた物の効果も重量も、各エンティティが既存のコンポーネントから出す。ストーブは暖のコンポーネントを持つ prop、というだけで足りる。

以下は、この概念を実装可能な粒度へ落としたコア機構(器・重量押し経済・内装の出入り)の詳細である。当初は別 doc へ分けようとしたが、実装未着手の設計段階なので概念と同じ doc に置き、実装に着手する時点で領域ごとに個別 PR へ割る。HUD の作り込み・仲間のAP供給の作り込み・押しと前線速度の本格チューニングは、この詳細の外に置く。

### 既存機構への接続

実装の大半は既存部品への素直な拡張で足りる。調査で確認した接続先を先に固定する。

| 必要な機能 | 既存で乗るもの | 新設 |
|---|---|---|
| 内装 = 別ステージ | `StageKey`/`StageBound`/`Suspended`/`SwapTo`(共存方式) | 内装の生成 |
| 入る・出る | `PortalConnection` 結線 + descend/ascend 同型経路 | 遷移用 `InteractionKind` とハンドラ |
| 退避中も状態保持 | `Suspended` + `query.ActiveFilterN` | そのまま流用 |
| 1タイルの可変APコスト | `gc.PassCost` 加算経路(`activity_manager.go`) | 押し専用の消費経路 |
| 個体のAP・毎ターン回復 | `gc.TurnBased{AP, Speed}` + `query.RestoreAllActionPoints` | そのまま流用 |
| 締切としての総経過ターン | `GameTime.TotalTurns` | そのまま流用 |
| 帯の一方向前進 | `worldstream.Band` シフト | そのまま流用 |
| 寒波 = 締切・進入不可・凍結 | `gc.SeamlessFront`(完全実装) | そのまま流用 |
| 重量の型・パース | `consts.Milligram` / `gc.Weight` | 集計軸の追加 |
| **3x3 footprint** | — | **新設(既存に該当なし)** |
| **総重量 → 押しコスト換算** | — | **新設** |
| **パーティAP総量の集計** | — | **新設** |

新設は「3x3 footprint」「重量→押しコスト換算」「パーティAP集計」「遷移扉」の4点に集約される。寒波・帯・ステージ共存という重い部分がすべて既存の完成品だったのが効いている。

### 器 — 3x3 footprint と押し

エンティティは常に単一 `gc.GridElement`(`consts.Coord[consts.Tile]` を埋め込む)に存在し、複数マス占有を表す既存コンポーネントは無い。占有範囲は `GridElement` を拡張するのでなく、別コンポーネント `Footprint` として新設する。`GridElement` はアンカー位置(どこにいるか)、`Footprint` は占有範囲(どれだけ占めるか)で関心が別だからである(GridElement 拡張案の却下理由は採用しなかった方法に残す)。回転しないので幅・高さは生成後に不変。

```go
// Footprint はエンティティが GridElement の基準タイル(左上)から占める矩形範囲。
// GridElement を持つが Footprint を持たないエンティティは 1x1 とみなす。
// キューブは 3x3 なので Footprint{W:3, H:3}。回転しないため W・H は生成後に変わらない。
type Footprint struct {
	W, H consts.Tile
}

// Dir は押しの4方向。回転を持たないので方向はこの4値に閉じる。
type Dir int

const (
	DirNorth Dir = iota
	DirSouth
	DirEast
	DirWest
)
```

キューブ本体は `GridElement`(左上)・`Footprint{3,3}`・`Prop`・`gc.BlockPass`・後述の内装リンク・押し進捗を持つ1エンティティとする。占有9タイルは footprint から導出し、別エンティティを9個並べない(押すたびに9体を平行移動させると一体性が崩れる)。

**占有タイルの窓口を単一化する。** 空間索引(`SpatialIndex` コンポーネント。ロード時再構築)・通行判定・視界は現状「1 `GridElement` = 1タイル」を前提に entity→タイルを索引する。3x3 をアンカー1タイルにしか登録しないと、残り8タイルを座標検索しても見つからない silent な不具合になる(ruins-review の散在クエリ・ハザード)。占有の導出を1つの窓口に集約し、各システムが `GridElement.Coord` を直読みするのをやめてここを通す。「Footprint 未所持=1x1」を単一の真実にすることで、GridElement を拡張せずとも多タイルが安全に扱える。

```go
// OccupiedTiles はエンティティが占有する全タイルを返す。Footprint を持たなければ
// GridElement の1タイルを、持てば footprint の矩形を返す。占有の唯一の窓口にする。
// 空間索引・通行判定・視界はここを通り、GridElement.Coord を直読みしない。
func OccupiedTiles(world w.World, entity ecs.Entity) []consts.Coord[consts.Tile]

// LeadingTiles は指定方向へ1タイル押すとき新たに踏み込む前縁タイルを返す。
// 3x3 を東へ押すなら東端の3タイル。押しの衝突判定はこの前縁だけを見る。
func LeadingTiles(world w.World, cube ecs.Entity, dir Dir) []consts.Coord[consts.Tile]
```

空間索引・通行判定・視界を `OccupiedTiles` 経由へ寄せる改修は、`grep -rn "GridElement" internal/` で座標検索・破壊的操作の箇所を洗って対象を確定する(exhaustive linter では強制できないので手動監査になる)。

押しは新規のアクティビティ(`internal/activity/push.go`)にする。既存に押し機構は無い。プレイヤーがキューブに隣接しキューブへ向かう方向へ移動入力すると、1タイル押しの試行になる。判定手順:

1. `LeadingTiles` で前縁3タイルを求める。
2. `query.ActiveFilter` 経由で前縁に `gc.BlockPass` があるか調べ、退避中ステージを混ぜない。
3. 前縁が寒波前線以西を含むなら押せない(`gc.SeamlessFront.IsWestOfFront`。既存 `frontAllowsMoveTo` と同じ規約)。
4. 前縁が空いていればキューブの `GridElement` を1タイル進め、押しコストを支払う。
5. 前縁が破壊可能(`gc.Hp` を持つ prop 等)なら、破壊して進む(追加AP)か、迂回する(方向を変える)。どちらもAPを食い寒波の締切に効く。

### 内装 — 別ステージとして SwapTo に乗せる

内装は1つの `StageKey` として扱い、階段昇降(`descend`/`ascend`)と同型の `SwapTo` 経路で出入りする。共存方式なので退避中の内装は world に残り、置いた物・総重量が保存される。扉はキューブ下辺の中央タイルに載せ、遷移用のインタラクション種別を新設する(既存の `InteractionDoor` は開閉であって遷移ではない)。

```go
// CubeInterior はキューブ本体に付き、そのキューブ固有の異次元内装ステージを指す。
// 内装から外へ出るとき、この逆引きでキューブ本体の現在位置を求め、着地タイルを解決する。
type CubeInterior struct {
	Stage StageKey // このキューブの内装ステージ
}

// InteractionKind に追加する種別。既存の InteractionDungeonEnter/Portal と同じく、
// Config() の switch と ExecuteInteraction の switch へ case を足す(exhaustive 強制)。
//   InteractionEnterCube — 外 → キューブ内装。下辺の扉に付ける
//   InteractionExitCube  — 内装 → 外。内装の出口に付ける
```

**前線と時間の扱いはダンジョンと同型にする。** 前線の凍結ダメージ・進入不可はオーバーワールド稼働時のタイルにしか効かない(内装は異次元でコールドゾーン判定の外)。だから内装には前線が入らず、凍らない安全な我が家になる。一方、前線位置は `GameTime.TotalTurns` から決定的に導出され(`worldstream.FrontAt`)、TotalTurns はどのステージが稼働中でも毎ターン進む。したがって内装で行動して時間を使い外へ出ると、前線は進んでいる。籠って凍結から逃げる抜け穴を、これが新規実装なしで塞ぐ。ダンジョン滞在で外の前線が進むのと同じ挙動である。

**移動キューブ特有の出口座標問題**を明示する。固定 `Coord` で外への着地点を結線すると、キューブが動いた後に破綻する。ただし内装滞在中は外ステージが `Suspended` で、帯シフトも走らない(帯ドライバはオーバーワールド稼働中のみ動く)ため、キューブの位置は入った瞬間から不変である(進むのは前線で、キューブではない)。したがって出口は固定座標を持たせず、`CubeInterior.Stage == 現在の内装` でキューブ本体を逆引きし、その現在の下辺扉タイルへ着地させる。これで「移動中に内部を歩かない」不変条件と整合し、キューブがどこで停まっていても正しい外へ出る。出た先の前線が近づいていることは、この着地解決とは独立に成立する。

### 重量押し経済 — 総重量・押しコスト・パーティAP

**総重量の集計軸を新設する。** 現状 `gc.Weight` は item だけが持ち、prop は持たない。既存の合計処理 `calculateOwnedWeight` は所有者(Backpack/装備/Storage)で集計しフィールド上の item を除外する。キューブの総重量はこれと別軸で、内装ステージに束縛された全 `gc.Weight` 保有エンティティの総和とする。効果を持つ prop も重量を持つよう拡張し(raw の Prop に任意 `weight` を足し `NewPropSpec` で `gc.Weight` を付与)、置けば item も prop も等しく重量になる。

```go
// CubeWeight は内装ステージに束縛された全 gc.Weight 保有エンティティの重量総和。
// item も、暖や作業の効果を持つ prop も、内装へ置けば等しく重量になる。
// 所有者ベースの calculateOwnedWeight とは別軸で、StageBound.Key で集計する。
func CubeWeight(world w.World, interior gc.StageKey) consts.Milligram

// PushCost は総重量から1タイル押すのに要するAPを返す。歩行(StandardActionCost=100)の
// 10倍規模を基準に総重量へ比例させ、重いほど高い。仲間・強化ではこの値は変わらない。
func PushCost(total consts.Milligram) int

// PartyPushPower はこのターン押しへ充てられるAP総量。Player と SquadMember の
// TurnBased.AP.Current を合算する。仲間を増やし強化すると増え、同じ PushCost を
// より少ないターンで払えて速く進む。押しコスト自体は不変。
func PartyPushPower(world w.World) int
```

押しは複数ターンにまたがって払える。1タイルの `PushCost` が1ターンのパーティAPを超えるなら、貯めて払う。キューブに押し進捗を持たせ、押しっぱなしの間ターンごとにパーティAPを充て、`PushCost` に達したら1タイル前進して差し引く。solo でも押せるが、AP総量が小さいぶん同じ距離に多くのターンがかかり寒波への露出が増える。

```go
// PushProgress はキューブが次の1タイルへ前進するために貯めた押しAP。
// 押しっぱなしの間、毎ターン PartyPushPower を Accumulated へ加え、
// PushCost(CubeWeight) に達したら1タイル進めて差し引く。Held は押している向きで、
// 手を離す(別行動)と押しは中断する。長押し中もターンが進み寒波が迫る。
type PushProgress struct {
	Accumulated int
	Held        Dir
	Holding     bool
}
```

## 採用しなかった方法

- **建設システム、資材と労働で建てる** — 部屋を建てる仕組みを持つと、材料集めと配置の細作業がトイルへ近づき、仲間がいないと建てられない問題も抱える。空間に既存の item/prop を置いて表現すれば足り、YAGNI にも適う
- **キャラバン・橇の隊列の器** — 運搬を可視化する利点があったが、キューブの重量押し経済のほうが蓄積の代償・移動圧力・仲間の価値を1つの数字に統合でき、より直接で体感的。機構と皮は分離できるので、これは皮の選択であって機構の否定ではない
- **サンドボックス化** — 滞在を全面的に許す。テーマの心臓である迫る凍結を捨て、賭け金の発生装置を失い、埋めるべき空間も激増する
- **移動を抽象アイコンやメニューにする** — 実装は安いが、一続きの手触りを失う。キューブは外の押しをタクタイルに保つことでこれを避ける
- **多タイルの乗り物** — 走行しながら中を歩ける器。最も豊かだが実装が複雑すぎる。キューブは外を回転しない footprint、中を異次元に分けて複雑さの本体を避ける
- **配置が効果を最適化する位置依存** — 隣接ボーナスや動線効率は、逃げ出した拠点建築のトイルへ戻る。効果は置いてあることから出し、配置は表現に留める
- **ターン制限などハードなロック** — 従来は反トイルのためにロックしていたが、押しコストと遅い寒波の経済的圧力が同じ役割を、鎖の感触なしに担う

実装レベルで却下した案:

- **`GridElement` を `W,H` で拡張して占有範囲を持たせる** — 位置と同じ場所にサイズがあれば読み忘れない、という利点があるが割に合わない。`GridElement` は非テストで360箇所参照され serde 保存対象(`skipComponents` に無い)なので、struct を変えると全エンティティのセーブ形が変わり全構築箇所が検討対象になる。さらに Go のゼロ値で既存構築が `W=0,H=0`=0タイル footprint になり、ロード時に旧エンティティが消える罠を負う。読み忘れ防止の利得も幻で、空間索引は `ge.W` を読むか `fp.W` を読むかに関わらず「矩形を回して各タイルを索引する」新ロジックが要る。別 `Footprint`(未所持=1x1)なら波及がキューブに閉じ、ゼロ値の罠も無い。読み忘れは `OccupiedTiles` 窓口の一本化で防ぐ
- **9タイルに `BlockPass` を並べて 3x3 を表す** — footprint コンポーネントを作らずに済むが、押すたびに9エンティティを平行移動させ、一体としての衝突判定・扉追随・重量帰属が壊れる。1エンティティ + `Footprint` のほうが一体性を保てる
- **内装を専用のインメモリ構造にする** — 既存の `SwapTo`/`Suspended`/`StageBound` が退避・再訪・状態保存をすでに解いており、prop/item 配置もそのまま使える。専用構造は二重実装で YAGNI に反する
- **出口座標を固定 `Coord` で結線する** — 実装は単純だが移動キューブでは入った後に位置がずれると破綻する。内装滞在中はキューブ位置が不変(外は退避中で帯シフトも走らない)という条件を使い、キューブ本体を逆引きして現在位置から解決するほうが堅い
- **押しコストをパーティAPや人数で変える** — 「大人数だと1タイルが安い」は直感的だが、「押しコストは不変、変わるのは何ターンで払うか」という1比較への集約を崩す。人数はAP総量にだけ効かせ、コスト関数は総重量のみの純関数に保つ
- **prop に重量を持たせず item だけで総重量を測る** — 既存モデルに近いが、暖・作業の効果を持つ prop が重量ゼロだと重い戦利品だけが代償を負い、家具は無料で増やせてしまう。prop へ `gc.Weight` を拡張して置いた物すべてを重量にする
- **押しを1回のインスタント行動にする** — 1タイル=1ターンで即決すると `PushCost` が1ターンのAPを超える重いキューブを表現できない。複数ターンにまたがる `PushProgress` 蓄積で、solo は遅く大所帯は速い、という仲間の価値が出る

## コメント

- 迷いが何度も再燃したのは、確信を皮に結びつけていたためだった。楽しみに錨を下ろすと、器は合否を見るだけの交換可能な実験になり、危機にならない。キャラバンからキューブへ、建設から家具付けへと替えても、そのつど要件節の7つに通して進められた
- 建設を消したことで、長く行き来した「リストか手触りか」の対立も解けた。建設待ち行列が無いので、家具付けは純粋な世界内の所作になり、残る一覧は重量と余裕を映す HUD の数字だけになる
- 異次元の内装は、以前「同じ世界の手触りを失う」として却下した入れ替え式の内装インスタンスと同型である。今回受け入れられるのは、却下の理由だった移動の抽象化が無く、外の押しがタクタイルに保たれ、内装が虚構で正当化されるからである
- 皮は無地のキューブに確定した。キューブの防衛機構は設けない。賭けは押しの余裕と寒波、および徒歩探索の遭遇戦が担う
- これは意思決定の記録である。コンセプトに迷ったら、まず要件節の楽しみへ戻る

コア機構の詳細化で得た知見:

- 新設は「3x3 footprint」「重量→押しコスト換算」「パーティAP集計」「遷移扉」の4点に集約された。寒波・帯・ステージ共存という重い部分がすべて既存の完成品だったのが効いている。「既存機構を流用する」という繰り返しの主張は、調査で裏づけられた
- 最大の設計判断は総重量の集計軸だった。所有者ベースの `calculateOwnedWeight` とは別に、ステージ束縛ベースの `CubeWeight` を新設し prop に重量を拡張する。ここを誤ると「家具は無料」という抜け穴が空き、ブレーキと引力の一対が崩れる
- 移動キューブの罠は出口座標だった。内装滞在中は外が退避中でキューブ位置が不変になる条件に気づけば、固定結線をやめてキューブ逆引きで解ける。共存方式の「退避中も world に残る」性質を逆手に取った解である。前線だけは総経過ターンから進むので、出た先は入ったときより締切が迫っている
- `InteractionKind` に2種別足すので、`Config()` と `ExecuteInteraction` の switch(いずれも default 無し)へ case を足さないと `make lint` が止まる。遷移種別の対応漏れを機械検知する意図した安全網である
- 占有範囲は `GridElement` を拡張せず別 `Footprint` にした。決め手は codebase 固有の事情で、`GridElement` は360箇所参照・serde 保存対象なうえ、W/H を足すと Go のゼロ値で旧エンティティが0タイル footprint になってロード時に消える。多タイルは滅多にないので、未所持=1x1 の別コンポーネントが素直。読み忘れは `OccupiedTiles` 窓口の一本化で防ぐ。これは exhaustive で強制できない散在クエリ・ハザードなので、監査対象として進捗に明記した
