# キューブのコア機構 — 3x3の押し・重量押し経済・異次元内装の出入り

## 背景

[doc77](20260730_77.md) は「拡張可能な移動拠点」の概念を固定した。守るべき7つの楽しみを仕様とし、現在の器を「押す3x3キューブ + 異次元の静止内装」と定めた。ただし doc77 自身が「本 doc は概念の記録で、以下は実装の見取りである。着手時に個別 doc へ分割する」と明記している。

この doc は、その分割の第一弾として**コア機構**を実装可能な粒度で詳細化する。対象は doc77 の変更箇所テーブルのうち、器・重量押し経済・内装(の出入り)の3領域である。HUD・仲間のAP供給の作り込み・チューニングは後続 doc に分ける。皮(無地キューブ)と防衛(行わない)は doc77 で決着済みなので触れない。

コア機構を先に固めるのは、doc77 の進捗で未着手の先頭が「3x3・4方向の押しと、障害の破壊・迂回、重量押しコストのプロトタイプ」だからである。この土台が動いて初めて、余裕対前線の緊張がチューニングできる。

### 既存機構の調査結果

実装の大半は既存部品への素直な拡張で足りる。調査で確認した接続先を先に固定する。

| 必要な機能 | 既存で乗るもの | 新設 |
|---|---|---|
| 内装 = 別ステージ | `StageKey`/`StageBound`/`Suspended`/`SwapTo`(共存方式) | 内装の生成 |
| 入る・出る | `PortalConnection` 結線 + descend/ascend 同型経路 | 遷移用 `InteractionKind` とハンドラ |
| 退避中も状態保持 | `Suspended` + `query.ActiveFilterN` | そのまま流用 |
| 1タイルの可変APコスト | `gc.PassCost` 加算経路(`activity_manager.go`) | 押し専用の消費経路 |
| 個体のAP・毎ターン回復 | `gc.TurnBased{AP, Speed}` + `query.RestoreAllActionPoints` | そのまま流用 |
| 締切としての総経過ターン | `GameTime.TotalTurns` | そのまま流用 |
| 帯の一方向前進 | `worldstream.Band` シフト | そのまま流用 |
| 寒波 = 締切・進入不可・凍結 | `gc.SeamlessFront`(完全実装) | そのまま流用 |
| 重量の型・パース | `consts.Milligram` / `gc.Weight` | 集計軸の追加 |
| **3x3 footprint** | — | **新設(既存に該当なし)** |
| **総重量 → 押しコスト換算** | — | **新設** |
| **パーティAP総量の集計** | — | **新設** |

新設は「3x3 footprint」「重量→押しコスト換算」「パーティAP集計」「遷移扉」の4点に限られる。それ以外はステージ共存・寒波・帯という既存の完成品に乗せる。

## 要件

doc77 の「守るべき楽しみ」のうち、コア機構が直接担うものを実装要件へ落とす。

1. **押しはタクタイル**（楽しみ2・7）— キューブは4方向に1タイルずつ押せる。回転しない。押しっぱなしで連続移動でき、実時間の手間とゲーム内コストを切り離す。
2. **1つの比較への集約**（楽しみ3・4・5）— 1タイルの押しコストは総重量だけで決まり不変。パーティAP総量がそれを何ターンで払うかを決め、寒波がその締切を決める。3つが「移動に要するターン数 対 寒波の速さ」の1比較に集約する。
3. **くぐって入り、また出る**（楽しみ1・2）— 下辺の扉から異次元内装へ入り、外へ戻れる。内装は静止空間で、退避中も状態を保つ。移動中に内部を歩かない。
4. **障害はナビゲーションの一部**（楽しみ5）— 押し先に通行不可があれば、壊して進む（追加コスト）か迂回する（余分な距離）。どちらもAPを食い寒波の時計に効く。
5. **一方向は寒波が担保**（楽しみ5）— レーンのハードロックを置かず、寒波前線以西へキューブを押せないことと、前線が追いつくと呑まれることで前進を強いる。

### 不変条件

- キューブは**回転しない**。footprint の幅・高さは不変。
- **移動中に内部を歩かない**。押しはオーバーワールド(外)でのみ起き、内装滞在中は外ステージが `Suspended` で凍結する。この分離が多タイル乗り物の複雑さの本体を避ける。
- 内装の総重量・置いた物は、退避・再訪をまたいで保存される（共存方式なので world に残る）。

## 設計

### 器 — 3x3 footprint とキューブ本体

エンティティは常に単一 `gc.GridElement`(`consts.Coord[consts.Tile]` を埋め込む)に存在し、複数マス占有を表す既存コンポーネントは無い。これを新設する。

```go
// Footprint はエンティティが GridElement の基準タイルから占める矩形範囲。
// 基準タイルは footprint の左上とする。キューブは 3x3 なので Footprint{W:3, H:3}。
// 回転しないため W・H は生成後に変わらない。
type Footprint struct {
	W, H consts.Tile
}
```

キューブ本体は、`GridElement`(左上タイル)・`Footprint{3,3}`・`Prop` マーカー・後述の内装リンクを持つ1エンティティとする。占有する9タイルは footprint から導出し、タイルごとに別エンティティを並べない。9個の `BlockPass` タイルで表す代替は、押すたびに9エンティティを平行移動させ、footprint の一体性が崩れるので採らない。

占有タイルの導出と、他エンティティとの衝突判定はクエリのヘルパに集約する。

```go
// CubeTiles はキューブが占有する全タイル座標を、基準タイルと footprint から導出する。
func CubeTiles(base gc.GridElement, fp gc.Footprint) []consts.Coord[consts.Tile]

// LeadingTiles は指定方向へ1タイル押すとき、新たに踏み込む前縁タイルを返す。
// 3x3 を東へ押すなら東端の3タイル。衝突判定はこの前縁だけを見る。
func LeadingTiles(base gc.GridElement, fp gc.Footprint, dir Dir) []consts.Coord[consts.Tile]
```

### 器 — 押しと衝突

押しは新規のアクティビティとして実装する。既存に押し機構は無い。プレイヤーがキューブに隣接し、キューブへ向かう方向へ移動入力すると、キューブを押す試行になる。

```go
// Dir は押しの4方向。回転を持たないので方向はこの4値に閉じる。
type Dir int

const (
	DirNorth Dir = iota
	DirSouth
	DirEast
	DirWest
)
```

1タイル押しの判定手順:

1. `LeadingTiles(base, fp, dir)` で前縁3タイルを求める。
2. 各前縁タイルを検査する。`query.ActiveFilter` 経由で `gc.BlockPass` を持つエンティティを引き、退避中ステージを混ぜない。
3. 前縁が寒波前線以西を含むなら押せない（`gc.SeamlessFront.IsWestOfFront`。既存 `frontAllowsMoveTo` と同じ規約）。
4. 前縁が空いていれば、キューブの `GridElement` を1タイル進め、後述の押しコストを支払う。
5. 前縁に破壊可能な障害（`gc.Hp` を持つ prop 等）があれば、破壊して進む選択肢を出す。破壊は追加APを課す。破壊不能なら迂回、すなわち方向を変えるしかない。

破壊と迂回はどちらもAPを食い、寒波の締切に効く。障害配置がナビゲーションを押しの経済へ織り込む、という要件4をこの手順が満たす。

### 器 — 下辺の扉

キューブ下辺の中央タイルを扉にする。扉は独立のインタラクション種別を持ち、隣接から発動すると内装ステージへ遷移する。既存の扉(`gc.Door` + `InteractionDoor`)は開閉であって遷移ではないので、遷移用の種別を新設する。

```go
// InteractionKind に追加する種別。既存の InteractionDungeonEnter/Portal と同じく、
// Config() の switch と ExecuteInteraction の switch へ case を足す(exhaustive 強制)。
InteractionEnterCube  // 外 → キューブ内装。下辺の扉に付ける
InteractionExitCube   // 内装 → 外。内装の出口に付ける
```

扉はキューブ本体とは別の小エンティティにし、キューブの現在位置から毎フレーム下辺中央へ追随させる。キューブが動くと扉も動くので、扉の `GridElement` はキューブの `GridElement` + footprint から導出して更新する。

### 内装 — 別ステージとして SwapTo に乗せる

内装は1つの `StageKey` として扱い、階段昇降(`descend`/`ascend`)と同型の `SwapTo` 経路で出入りする。共存方式なので、退避中の内装は world に残り、置いた物・総重量が保存される。

```go
// CubeInterior はキューブ本体に付き、そのキューブ固有の異次元内装ステージを指す。
// 内装から外へ出るとき、この逆引きでキューブ本体の現在位置を求め、着地タイルを解決する。
type CubeInterior struct {
	Stage StageKey  // このキューブの内装ステージ
}
```

内装ステージのキーは `NewDungeonStage("cube_interior", depth)` 相当で作る。初回進入時に `SwapTo` の generate コールバックで内装を生成し、生成物すべてに `StageBound{内装キー}` を付ける責務を負う(既存 `stage.Bind` を呼ぶ)。2回目以降は退避してあるステージを `resume` するだけで、状態が復元される。

**移動キューブ特有の出口座標問題**を明示する。固定 `Coord` で「外への着地点」を結線すると、キューブが動いた後に破綻する。ただし内装滞在中は外ステージが `Suspended` で凍結し、帯シフトも走らない(帯ドライバはオーバーワールドが稼働中のときだけ動く)ため、キューブ位置は入った瞬間から不変である。したがって出口は固定座標を持たせず、`CubeInterior.Stage == 現在の内装` で**キューブ本体を逆引きし、その現在の下辺扉タイルへ着地させる**。これで「移動中に内部を歩かない」不変条件と整合し、キューブがどこで停まっていても正しい外へ出る。

### 内装 — 置いて表現する

内装は既存の prop/item 配置機構をそのまま使う空間にする。専用の建設システムは作らない。ストーブを置けば暖、溶接機を置けば工房で、効果は「置いてあること」から出し配置に依存しない(doc77 の presence ベース)。ここは doc77 で決着済みなので、この doc では**内装が prop/item を受け入れる別ステージであること**だけを固定し、個々の効果 prop は後続 doc と authoring に委ねる。

### 重量押し経済 — 総重量・押しコスト・パーティAP

doc77 の心臓部。1タイルの押しコストは総重量だけで決まり不変、パーティAP総量がそれを何ターンで払うかを決める。

**総重量の集計軸を新設する。** 現状 `gc.Weight` は item だけが持ち、prop は持たない。合計処理 `calculateOwnedWeight` は所有者(Backpack/装備/Storage)で集計し、フィールド上の item を除外する。キューブの総重量はこれと別軸で、**内装ステージに束縛された全 `gc.Weight` 保有エンティティの総和**とする。効果を持つ prop も重量を持つよう拡張し、置けば item も prop も等しく重量になる、という doc77 の意図を満たす。

```go
// CubeWeight は内装ステージに束縛された全 gc.Weight 保有エンティティの重量総和。
// item も、暖や作業の効果を持つ prop も、内装へ置けば等しく重量になる。
// 所有者ベースの calculateOwnedWeight とは別軸で、StageBound.Key で集計する。
func CubeWeight(world w.World, interior gc.StageKey) consts.Milligram
```

prop に重量を持たせるため、raw の Prop 定義に任意の `weight` を足し、`NewPropSpec` で `gc.Weight` を付与する(Storage prop が `WeightCapacity` を得るのと同じ経路)。

**押しコストは総重量だけの関数。** 歩行の標準コスト `StandardActionCost = 100` の10倍規模を基準に、総重量へ比例させる。仲間や強化はこの値を変えない。

```go
// PushCost は総重量から1タイル押すのに要するAPを返す。歩行(StandardActionCost=100)の
// 10倍規模を基準に総重量へ比例させ、重いほど高い。仲間・強化ではこの値は変わらない。
// 係数は暫定で、余裕対前線の緊張を見てチューニングする(後続 doc)。
func PushCost(total consts.Milligram) int
```

**パーティAP総量を集計する。** これも新設。Player と `gc.SquadMember` の `TurnBased.AP.Current` を合算する。人数を集め強化するとAPが増え、同じ `PushCost` をより少ないターンで払える。押しコスト自体は不変で、変わるのは何ターンで払えるかである。

```go
// PartyPushPower はこのターン押しへ充てられるAP総量。Player と SquadMember の
// TurnBased.AP.Current を合算する。仲間を増やし強化すると増え、同じ PushCost を
// より少ないターンで払えて速く進む。押しコスト自体は不変。
func PartyPushPower(world w.World) int
```

**押しは複数ターンにまたがって払える。** 1タイルの `PushCost` が1ターンのパーティAPを超えるなら、貯めて払う。キューブに押し進捗を持たせ、押しっぱなしの間ターンごとにパーティAPを充て、`PushCost` に達したら1タイル前進して差し引く。solo でも押せるが、AP総量が小さいぶん同じ距離に多くのターンがかかり、寒波への露出が増える。

```go
// PushProgress はキューブが次の1タイルへ前進するために貯めた押しAP。
// 押しっぱなしの間、毎ターン PartyPushPower を Accumulated へ加え、
// PushCost(CubeWeight) に達したら1タイル進めて差し引く。Held は押している向きで、
// 手を離す(別行動)と押しは中断する。長押し中もターンが進み寒波が迫る。
type PushProgress struct {
	Accumulated int
	Held        Dir
	Holding     bool
}
```

押しっぱなしはターンを進め、寒波(`GameTime.TotalTurns` から決定的に前進)が迫る。連打でも長押しでも1タイルあたりのAPは不変で、実時間の手間だけが変わる。これで「実時間の手間とゲーム内コストの分離」を満たす。

**ブレーキには引力が要る**（doc77）。押しコストは重い物に代償を課すが、良い決断になるのはプレイヤーが重い物を本気で欲しがるときだけである。空のキューブを軽く押すのが最適解にならないよう、道具・戦利品を「重さを承知で連れて行きたい」ものにする設計は、効果 prop の authoring 側(後続)の責務として明記する。

### 圧力 — 寒波と帯への接続

既存の寒波・帯にそのまま乗せる。新規の圧力機構は作らない。

- **一方向の担保**: 押しの前縁が `SeamlessFront.IsWestOfFront` を満たすなら押せない。前線が追いつけばキューブの占有タイルが極低温ゾーンに入り、押すプレイヤーが凍える(既存 `temperature.go` の frost 効果)。背後に破滅、という賭けをこれが担う。
- **東進**: プレイヤーはキューブを押しながら東へ進む。プレイヤーが帯の中央を東に出れば既存の帯シフト(`worldstream.Band.ShiftEast`)が走り、キューブは field エンティティとして `TranslateAllEntities` で西へリベースされる(除去されない)。キューブが帯の rows 内に留まる限りシフトで失わない。
- **締切**: 前線位置は `GameTime.TotalTurns` から決定的に導出される。押しに費やすターン数が多いほど前線が迫る。AP総量を使い切る前に呑まれるかどうかが緊張になる。

## 採用しなかった方法

- **9タイルに `BlockPass` を並べて 3x3 を表す** — footprint コンポーネントを作らずに済むが、押すたびに9エンティティを平行移動させ、一体としての衝突判定・扉追随・重量帰属が壊れる。1エンティティ + `Footprint` のほうが footprint の一体性を保てる。
- **内装を専用のインメモリ構造にする** — ステージ共存機構を使わず、内装を別データとして持つ。だが既存の `SwapTo`/`Suspended`/`StageBound` が退避・再訪・状態保存をすでに解いており、prop/item 配置もそのまま使える。専用構造は二重実装で YAGNI に反する。
- **出口座標を固定 `Coord` で結線する** — 実装は単純だが、移動キューブでは入った後に位置がずれると破綻する。内装滞在中はキューブが凍結する不変条件を使い、キューブ本体を逆引きして現在位置から解決するほうが堅い。
- **押しコストをパーティAPや人数で変える** — 「大人数だと1タイルが安い」は直感的だが、doc77 の「押しコストは不変、変わるのは何ターンで払うか」という1比較への集約を崩す。人数はAP総量(何ターンで払うか)にだけ効かせ、コスト関数は総重量のみの純関数に保つ。
- **prop に重量を持たせず item だけで総重量を測る** — 既存モデルに近いが、doc77 は「暖・作業の効果を持つ prop も置けば重量」を要件にしている。効果 prop が重量ゼロだと、重い戦利品だけが代償を負い、家具は無料で増やせてしまう。prop へ `gc.Weight` を拡張して置いた物すべてを重量にする。
- **押しを1回のインスタント行動にする** — 1タイル=1ターンで即決すると、`PushCost` が1ターンのAPを超える重いキューブを表現できない。複数ターンにまたがる `PushProgress` 蓄積にすることで、solo は遅く大所帯は速い、という仲間の価値が出る。

## コメント

- この doc は doc77 の分割第一弾で、コア機構(器・重量押し経済・内装の出入り)に絞る。HUD・仲間のAP供給の作り込み・押しと前線速度のチューニングは後続 doc に分ける。皮と防衛は doc77 で決着済み。
- 新設は「3x3 footprint」「重量→押しコスト換算」「パーティAP集計」「遷移扉」の4点に集約された。寒波・帯・ステージ共存という重い部分がすべて既存の完成品だったのが効いている。doc77 の「既存機構を流用する」という繰り返しの主張は、調査で裏づけられた。
- 最大の設計判断は総重量の集計軸だった。所有者ベースの `calculateOwnedWeight` とは別に、ステージ束縛ベースの `CubeWeight` を新設し、prop に重量を拡張する。ここを誤ると「家具は無料」という抜け穴が空き、ブレーキと引力の一対(doc77)が崩れる。
- 移動キューブ特有の罠は出口座標だった。内装滞在中は外が `Suspended` で凍結する不変条件に気づけば、固定結線をやめてキューブ逆引きで解ける。これは共存方式の「退避中も world に残る」性質を逆手に取った解である。
- exhaustive 強制の対象が増える。`InteractionKind` に2種別足すので、`Config()` と `ExecuteInteraction` の switch(いずれも default 無し)へ case を足さないと `make lint` が止まる。これは意図した安全網で、遷移種別の対応漏れを機械検知する。
