# CharModifiers を都度計算ビューと宣言的スペック表へ再設計する

## 背景

CharModifiers は Skills・Abilities・HealthStatus から純粋に導出できる効果倍率の集約だが、現在は保存コンポーネントとして持ち、StatsChanged ダーティフラグで再計算している。この持ち方の税金が随所に現れている。

- 入力を変えるすべての箇所が StatsChanged を立てる義務を負う。付与箇所は現在11箇所あり、忘れると古い倍率のまま黙って動く。TemperatureTrend 廃止で確立した「導出可能な一時状態は component にしない」原則に反している
- `Sources` は `json:"-"` で serde 除外し、ロード時再計算という特例を抱える
- `stats_changed.go` に「Upsert の構造変更で abils ポインタが無効化される前に行う」という Ark 固有の順序制約コメントが2箇所ある。導出値を書き戻すから構造変更が発生し、その危険を人間がコメントで守っている
- `Capacities` フィールドは `hs.Capacities()` の単なるキャッシュで、同じ値が2箇所に存在する

計算の書き方にも重複がある。倍率を1つ追加するには struct フィールド・ModifierKey 定数・係数定数・calcEffect 呼び出し行の4箇所を書く。`Sources` の記帳は calcEffect 内の副作用と命中畳み込みの手動 append に分かれ、「最終値 = 基準 + Σ内訳」の不変条件は規約でしか守られていない。

## 要件

- 効果倍率は読み取り時に純関数で導出し、保存しない。無効化バグを構造的に不可能にする
- 表示される倍率と適用される倍率が同じ関数から出る。表示=適用の一致を構造で保証する
- 倍率1つの定義が1箇所で完結する。値と内訳が同じループから生成され、記帳漏れが起きない
- 敵もプレイヤーも同じ経路を通る
- セーブ後方互換は考慮しない。未リリースのため

## 設計

### データの形

変更前。保存コンポーネントで、名前付きフィールドが倍率ごとに並ぶ。

```go
// 保存コンポーネント。StatsChanged 契機で再計算し Upsert する
type CharModifiers struct {
	WeaponDamage   map[SkillID]consts.Percent
	WeaponAccuracy map[SkillID]consts.Percent
	ElementResist  map[ElementType]consts.Percent
	ColdProgress   consts.Percent
	HungerProgress consts.Percent
	// ... 名前付きフィールドが計16個続く
	Capacities BodyCapacities
	Sources    map[ModifierKey][]ModifierSource `json:"-"`
}
```

変更後。コンポーネントではなく、読み取りのたびに計算して捨てる導出ビュー。ModifierKey が唯一の参照軸になる。

```go
// CharModifiers は効果倍率の導出ビュー。コンポーネントではなく保存しない。
// Skills・Abilities・HealthStatus から読み取り時に計算する
type CharModifiers struct {
	Values     map[ModifierKey]consts.Percent
	Capacities BodyCapacities
	Sources    map[ModifierKey][]ModifierSource
}

// Value は効果倍率を返す。未定義キーは等倍を返す
func (m *CharModifiers) Value(key ModifierKey) consts.Percent
```

武器系・元素系は既存の `WeaponDamageKey(id)`・`WeaponAccuracyKey(id)`・`ElementResistKey(elem)` でキーを引く。名前付きフィールド参照は `m.Value(ModMoveCost)` の形に置き換わる。

### 宣言的スペック表

倍率1つの定義を1行に束ねる。値と内訳を同じ汎用ループが生成するため、「最終値 = 基準 + Σ内訳」が構造で保証される。

```go
// modifierSpec は倍率1つの定義。キー・元スキル・スキルLv1あたりの係数を束ねる
type modifierSpec struct {
	Key   ModifierKey
	Skill SkillID
	Coeff int
}

var modifierSpecs = []modifierSpec{
	{ModColdProgress, SkillColdResist, -3},
	{ModHungerProgress, SkillHungerResist, -2},
	{ModHealingEffect, SkillHealing, 5},
	// ... 単発の倍率をすべて並べる
}
```

武器の行はスキルIDの直積なので init で生成し、手書きの列挙を持たない。

```go
for _, id := range weaponSkillIDs {
	modifierSpecs = append(modifierSpecs,
		modifierSpec{WeaponDamageKey(id), id, coeffWeaponDamage},
		modifierSpec{WeaponAccuracyKey(id), id, coeffWeaponAccuracy})
}
```

能力値補正は現行どおり係数の符号方向に±1%で、汎用ループ内で処理する。命中への身体機能の乗算畳み込みは加法の枠外なので、加法パスの後の後処理ステージとして明示的に置く。内訳へ加法差分を載せる現行の方式を維持する。

### 計算関数と置き場所

純関数の核は components に置き、world を見る入口は query に置く。components は world に依存できないため。

```go
// components 側。現 RecalculateCharModifiers の改名。再計算でなく単なる計算になる
func CalcCharModifiers(skills *Skills, abils *Abilities, hs *HealthStatus) *CharModifiers

// query 側。エンティティから入力コンポーネントを集めて計算する。
// Skills が無ければ全て等倍のビューを返すので、呼び出し側の Has ガードは不要
func Modifiers(world w.World, entity ecs.Entity) *gc.CharModifiers
```

消費側は `world.Components.CharModifiers.Has/Get` の対を `query.Modifiers(world, entity)` の1呼び出しに読み替える。

### 消えるもの

- **コンポーネント登録**: registry から CharModifiers の行を削除し `make generate`。EntitySpec のフィールドと `raw.go` の spawn 時設定、`profession.go` の作成時 Upsert が消える
- **StatsChangedSystem の Upsert ブロック**: CharModifiers の再計算と書き戻しが消え、Ark の構造変更が減るため abils ポインタの順序制約コメント2箇所も不要になる。システムは能力値 Total 集計・装備効果・HP上限・光源転写・AP に痩せる
- **CharModifiers 目的だけの StatsChanged 付与4箇所**: `condition.go`・`injury.go`・`read.go`・`debug_menu.go`。いずれも HealthStatus かスキルの変化で、Abilities や HP 上限には効かない。装備変更など Abilities に効く契機は残す
- **serde 特例**: `serde.go` の Sources 除外コメントとロード時再計算の規約

## 採用しなかった方法

- **能力値補正の係数を modifierSpec に持たせる**: 現行仕様は能力値補正が常にスキル係数と同符号で、特例が1つも無い。スペック表へ `AblCoeff` を足すのは存在しない仕様変更への保険になるため見送る。特例が現れたときに1フィールド足せばよい

- **保存コンポーネントのままスペック表だけ導入する**: 書き方の重複は減るが、無効化バグ・serde 特例・Ark の順序制約は残る。税金の大半は持ち方から派生しているため、半分だけの回収になる
- **要因ごとの provider interface**: スキル・能力値・身体機能を interface 実装として差し込む形。拡張点としては最も開いているが、要因は3つで固定的で追加予定が無い。構造的に起きない問題への保険であり、serde とテストの複雑さも連れてくる
- **名前付きフィールドを維持する**: コンパイラのフィールド網羅検査は保てるが、スペック表と struct の二重管理に戻り、4箇所散在が再発する。ModifierKey 定数による参照で型安全は概ね保てる
- **版数キャッシュを最初から組み込む**: 計算は整数演算30個程度で、戦闘・移動・情報タブの読み取り頻度なら無視できる。実測で問題が出たら menuloop の Store.version と同様の版数比較キャッシュを後付けできるので、先回りしない

## コメント

- 敵もプレイヤーも同じ Modifiers ビューを通る。専用の敵パスは作らない
- `aiinput/vision_system.go` は敵ごと・視界更新ごとに EnemyVision を読む。頻度が最も高い消費者なので、性能懸念が出るならここを起点に実測する
- 上記の懸念は bench-compare が即日検出した。全量ビューは内訳ラベルの整形を伴い敵ごとに呼ぶには重いため、内訳を作らない単キー導出 `CalcModifierValue` と `query.ModifierValue` を追加し vision を移した。版数キャッシュは引き続き不採用
- 最終形はさらに縮んだ。内訳ラベルの整形を表示側へ移して ModifierSource を事実だけの構造化データにすると、最終値 = 基準 + Σ内訳 の不変条件により Values は Sources から導出可能になり、CharModifiers struct と全量ビューを丸ごと廃止できた。公開 API は `CalcModifierValue` / `CalcModifierSources` と query 側の対だけになり、両者は同じ計算実体 `forEachModifierSource` の畳み方違い。表示の%も適用も `ModifierValue` を読むため、表示=適用は同一関数で保証される。不変条件は全キー×入力3種のテストでも固定する
- 命中への身体機能畳み込みで達成した表示=適用の一致は、ビュー化後は「表示も適用も同じ関数を呼ぶ」ことでより強く保証される
- 実装で判明した追加事項。StatsChanged 付与は設計時の4箇所に加え `attack.go` の growWeaponSkill にもあり5箇所目として削除した。削除が安全なのは、残った StatsChangedSystem の仕事である装備ボーナス集計・HP上限・APがいずれもスキル値を参照せず、スキル値の影響先が効率倍率だけになったため。無属性攻撃が `ElementResistKey` の panic を踏むため comma-ok 版 `ElementResistKeyOK` を追加した。UI の武器列挙のため `WeaponSkillIDs` を公開した。副次的な修正として、spawn 時スナップショットは能力値 Total が集計前で計算されており、売買価格やクラフト消費に能力値補正が効いていなかった。ビュー化で常に現在値から導出され正しくなった。CraftCost が 100% を超える経路は構造的に消えたため、該当テストは消費減の正のテストへ置き換えた
