# 移動キューブのコア機構 実装設計

## 背景

企画は [77](20260730_77.md)。拡張可能な移動拠点、すなわち押して進むキューブと異次元の内部、という方向をゲームデザインとして固定した。本 doc はそれを実装可能な粒度へ落としたコア機構の実装設計である。対象は器の押し・重量押し経済・内部の出入りの3つ。

実装は **1x1 のキューブから始める**。3x3 footprint は拡張として保留する。HUD・仲間のAP供給の作り込み・押しと前線速度の本格チューニングはこの範囲の外に置く。実装は領域ごとに個別 PR へ割る。

## 設計

### 既存機構への接続

実装の大半は既存部品への素直な拡張で足りる。調査で確認した接続先を先に固定する。

| 必要な機能 | 既存で乗るもの | 新設 |
|---|---|---|
| 内部 = 別ステージ | `StageKey`/`StageBound`/`Suspended`/`SwapTo`(共存方式) | 内部の生成 |
| 入る・出る | `PortalConnection` 結線 + descend/ascend 同型経路。キューブ↔内部のリンクもこれに載せる | 遷移用 `InteractionKind` とハンドラ。入場時に出口 `Coord` を貼り直す |
| 退避中も状態保持 | `Suspended` + `query.ActiveFilter1`〜`ActiveFilter4`(arity 別) | そのまま流用 |
| 1タイルの可変APコスト | `gc.PassCost` 加算経路(`activity_manager.go`) | 押し専用の消費経路 |
| 個体のAP・毎ターン回復 | `gc.TurnBased{AP, Speed}` + `query.RestoreAllActionPoints` | そのまま流用 |
| 締切としての総経過ターン | `GameTime.TotalTurns` | そのまま流用 |
| 押しの多ターン進行 | `gc.Activity{TurnsTotal, TurnsLeft, Target, Destination}` 継続アクティビティ | `BehaviorPush` の追加 |
| 帯の一方向前進 | `worldstream.Band` シフト | そのまま流用 |
| 寒波 = 締切・極低温ダメージ | `gc.SeamlessFront`(完全実装)。極低温ゾーンは通行可で寒いだけ、その西の破棄域のみ進入不可でプレイヤーと共通 | そのまま流用 |
| 重量の型・パース | `consts.Milligram` / `gc.Weight` | 集計軸の追加 |
| キューブの本体タイル(1x1) | `gc.GridElement` + `gc.BlockPass`(壁・ドアと同じ形) | そのまま流用 |
| **総重量 → 押しコスト換算** | — | **新設** |
| **パーティAP総量の集計** | — | **新設** |
| 3x3 footprint | — | 保留(拡張。1x1 では不要) |

1x1 を出発形にするので、新設は「重量→押しコスト換算」「パーティAP集計」「遷移ハンドラ」の3点に集約される。寒波・帯・ステージ共存という重い部分はすべて既存の完成品で、キューブ本体も 1x1 なら既存の「`GridElement` + `BlockPass`」に乗る。

### 器 — 押しと入る(1x1 出発)

コア機構は器のサイズに依存しないので 1x1 から始める。push と enter が両立するなら 1x1 が一番単純で、footprint の複雑さを経済の検証が済むまで背負わずに済む。

**押しはモードレスのバンプにする。** キューブへ向かって移動入力すると押す。専用の「乗る／降りる」モードは設けない。歩き込みが押しと入るを両方誘発する衝突は、**入るを歩き込みでなく手動アクションにする**ことで避ける。キューブへ歩き込めば押し、明示的に「入る」を選べば内部、と入力経路が別なので混ざらない。乗降モードは持たないので状態も操作も最小になる。バンプとモードの比較は採用しなかった方法に残す。

**引きは詰み回避の補助として持つ。** 当初 1x1 では引きを見送ったが、実プレイで押しだけだと壁際・角でキューブが倉庫番のように詰むと分かった。倉庫番的な押し主体の手触りは活かしつつ、隣接して「引く」を選ぶとキューブが自分のタイルへ入り自分は1タイル後退する動作を足して詰みを解く。押しはバンプ、引く/入るはメニューと入力経路を分ける。

1x1 のキューブ本体は、単一 `GridElement`・`Prop`・`gc.BlockPass`(壁と同じく乗れない)・内部への遷移を担う既存 `gc.PortalConnection`(後述)を持つ1エンティティとする。押しの進捗はキューブに持たせず、押し手であるプレイヤーの継続アクティビティ(後述)が持つ。専用の内部リンクコンポーネントも footprint も持たない。既存の壁・ドアと同じ形なので、空間索引・通行判定・視界は無改修で正しく扱う。

**押しの方向は新設せず既存の `gc.Direction`(`internal/components/field.go`)を使う。** 基本4方向・斜め4方向・None を持ち、`GetDelta()` で方向→タイル差分を返す。押しは基本4方向の部分集合を使い、前進先タイルの算出も `GetDelta()` を流用する。名前が North/South でなく Up/Down/Left/Right な点だけ読み替える。

押しは他の長期アクティビティ、たとえば分解と同じ継続アクティビティ `BehaviorPush` にする。専用の進捗コンポーネントは設けず、既存の `gc.Activity{TurnsTotal, TurnsLeft, Target, Destination}` に載せる。プレイヤーが隣接する押せるキューブへ向かって移動入力すると、通常の「塞がって動けない」でなく押しアクティビティが始まる。本体は `internal/activity/push.go` に置き、移動の衝突判定から呼ぶ。手順:

1. 前進先タイル(押し方向へ1つ)を `gc.Direction.GetDelta()` から求める。
2. **押せる先はプレイヤーが行ける先に一致させる。** `CanMoveTo`(通常移動の判定)で前進先へ行けるかを調べる。キューブはプレイヤーが行けるところへしか行けない。押し専用の前線チェックは持たない。前線は移動を止める壁でなく、極低温ゾーンの寒さ、既存の temperature 系のダメージで圧力を与えるだけだからである。極低温ゾーンは通行でき、進入不可なのはその西の破棄域だけで、それはプレイヤーも入れない。だから移動判定を共有すれば、前線が壁でないなら押しも通れ、破棄域なら押しも通れず、判定が食い違わない。
3. 行けるなら `Activity{BehaviorPush, Target: キューブ, Destination: 前進先}` を開始し、所要ターン `TurnsTotal = ceil(PushCost(CubeWeight) / PartyPushPower)` を着手時に算出する。以後は他の長期アクティビティと同じくカウントダウンし、完了時に**キューブの `GridElement` だけ**を1タイル進める。押し手は追随させない。プレイヤーは次の移動入力で空いたタイルへ通常移動で一歩進む。押し(ターン課金)と移動(AP課金)を別アクティビティに分け、方向を押し続けると押しと一歩が交互に起きてキューブが進む。重いキューブほど所要ターンが増え、パーティAPが多いほど減る。別行動での中断は既存のアクティビティ中断に一任し、進行中の1タイルは失われる。所要ターンは着手時のパーティAPで固定する、他の長期アクティビティと同じ近似である。
4. 前進先が破壊可能(`gc.Hp` を持つ prop 等)なら、破壊して進む(追加ターン)か迂回する。どちらも時間を食い寒波の締切に効く。1x1 は迂回が安いのでこの決断は弱い(3x3 で強まる)。

### 内部 — 別ステージとして SwapTo に乗せる

内部は1つの `StageKey` として扱い、階段昇降(`descend`/`ascend`)と同型の `SwapTo` 経路で出入りする。共存方式なので退避中の内部は world に残り、置いた物・総重量が保存される。1x1 では扉を別に切らず、キューブ本体タイル自体に遷移用のインタラクションを載せる(既存の `InteractionDoor` は開閉であって遷移ではないので種別を新設)。本体は `gc.BlockPass` で乗れないため発動は隣接・手動にする。歩き込みは押し、明示的な「入る」は内部、と入力経路が別なので両者は衝突しない。

**専用の内部リンクコンポーネントは新設せず、既存 `gc.PortalConnection` に載せる。** ダンジョンの階段が上り/下りを `PortalConnection{Stage, Coord}` で相互結線するのと同型にする。キューブ本体が「下り階段」、内部の出口 prop が「上り階段」に相当する。

- キューブ本体: `PortalConnection{Stage: 内部, Coord: 内部の入場点}`。入場点は動かないので固定でよい。内部キーはこの `Stage` が持ち、`PortalConnection` は serde 保存対象なのでキューブ↔内部の永続リンクが新コンポーネントなしで保存される。
- 内部の出口 prop: `PortalConnection{Stage: オーバーワールド, Coord: キューブの現在隣接タイル}`。この `Coord` は入場のたびに貼り直す(後述)。

```go
// 追加する InteractionKind の種別。既存の InteractionDungeonEnter/Portal と同じく、
// InteractionKind を散在 switch する4箇所すべてへ case を足す(いずれも default 無しで
// exhaustive 強制。1つでも漏れると make lint が止まる):
//   interactable.go Config()、activity/execute_interaction.go ExecuteInteraction、
//   states/action_handlers.go getInteractionActions(選択肢に出すか)、
//   activity/player_actions.go 足元ログ。
// 特に getInteractionActions を埋めないと「入る/出る」が行動選択肢に現れない。
//   InteractionEnterCube — 外 → キューブ内部。本体タイルに付ける(隣接・手動)。
//                          ハンドラは「出口 prop の Coord をキューブ現在隣接へ貼り直す →
//                          キューブ PortalConnection の Stage/Coord へ SwapTo」を行う。
//   InteractionExitCube  — 内部 → 外。出口 prop に付ける。ハンドラは出口 prop の
//                          PortalConnection を辿るだけ(ascend/ポータル追従と同じ経路)。
// 押しはモードレスのバンプで、インタラクションでなく移動解決の延長で扱う。
```

**前線と時間はダンジョンと同型にする。** 前線の凍結ダメージ・進入不可はオーバーワールド稼働時のタイルにしか効かない(内部は異次元でコールドゾーン判定の外)。だから内部には前線が入らず、凍らない安全な我が家になる。一方、前線位置は `GameTime.TotalTurns` から決定的に導出され(`worldstream.FrontAt`)、TotalTurns はどのステージ稼働中でも毎ターン進む。したがって内部で時間を使って外へ出ると前線は進んでいる。籠って凍結から逃げる抜け穴を、これが新規実装なしで塞ぐ。

**籠り中に前線が本体を追い越した場合の帰結を定義する。** 内部滞在中も前線は進むので、出た瞬間に本体が既に極低温ゾーンに入っていることが起こりうる。前線は壁でないので出ること自体は妨げないが、着地タイルが極低温ゾーンなら通常のオーバーワールド歩行と同じ寒さのダメージを受ける。内部は前線判定を免れるが、外へ一歩出た時点で通常のフィールドと同じ扱いに復帰する、というだけである。着地は下段のとおりプレイヤーが立てるタイルへ出す(破棄域には出さない)。凍結の具体挙動は既存の temperature 系に委ね、内部側に新規の敗北判定は設けない。

**出口座標は入場時にキューブの現在隣接タイルへ貼り直す。** ダンジョン入口は永久に動かないので固定 `Coord` で足りるが、キューブは訪問と訪問の間に押されて動くので固定座標は古くなる。そこで `InteractionEnterCube` のハンドラで、SwapTo の前にキューブ本体の現在位置を読み、通行可能な隣接タイルを1つ決め、出口 prop の `PortalConnection.Coord` へ書き込む。内部滞在中は外ステージが `Suspended` で帯シフトも走らない(帯ドライバはオーバーワールド稼働中のみ)ため、キューブ位置は入場から退場まで不変で、入場時に貼った座標は退場時も有効。出るときは出口 prop の `PortalConnection` を辿るだけで逆引きは要らない。出口 prop は内部キーで引ける(`StageBound{内部}` を持つ出口 prop を一意に置く)。本体タイルは `BlockPass` なので着地は隣接へ出す。

**着地タイルの選択は決定的にする。** 空き隣接が複数あるとき任意に選ぶとセーブ・ロードやリプレイで着地位置がぶれる。`gc.Direction` の基本4方向を固定順(例: 南→北→東→西)で走査し、最初に見つかった通行可能タイルを入場時に貼る。4隣接すべて塞がっている場合は本体タイルにも出せないため、既定案として**空き隣接が無ければ入場を許さない**(出られなくなるため)。入場を許さないなら貼り直しも起きず整合する。実装時に確定する。

### 重量押し経済 — 総重量・押しコスト・パーティAP

> 見送り中: prop への重量付与は現状は行わない。prop をまだ拾って自由に置けず、自由に置ける prop は item との違いが不明瞭になるため。総重量は当面 item の重量だけで回す。prop の設置操作を実装してから、以下の prop 重量の設計を戻す。以下は将来像として残す。

**総重量の集計軸を新設し、prop にも重量を持たせる。** 物である以上 prop も重量を持つのが自然なので、item と同じく raw に weight を持たせ `NewPropSpec` で `gc.Weight` を付与する。任意の付け足しでなく prop の通常の属性として扱う。キューブの総重量は、所有者ベースの `calculateOwnedWeight`(Backpack/装備/Storage で集計しフィールド item を除外)とは別軸で、内部ステージに束縛された全 `gc.Weight` 保有エンティティの総和とする(`StageBound.Key` で集計)。置けば item も prop も等しく重量になる。

内部に置ける prop の重量ゼロや未設定は「効果を持つ家具を無料で増やせる」抜け穴になり、ブレーキと引力の一対を崩す。だから置ける prop に実重量は必須とし、重量ゼロは authoring の誤りとして扱う。壁・ドアなど内部に入らない構造 prop は `StageBound{内部}` を持たず総重量に効かないので、重量の有無は集計に無関係。キューブ本体は prop だが、その重さは内部の総和 `CubeWeight` で導出するので intrinsic な重量は持たせない。

```go
// CubeWeight は内部ステージに束縛された全 gc.Weight 保有エンティティの重量総和。
// item も、暖や作業の効果を持つ prop も、内部へ置けば等しく重量になる。
// 所有者ベースの calculateOwnedWeight とは別軸で、StageBound.Key で集計する。
func CubeWeight(world w.World, interior gc.StageKey) consts.Milligram

// PushCost は総重量から1タイル押すのに要するAPを返す。歩行(StandardActionCost=100)の
// 10倍規模を基準に総重量へ比例させ、重いほど高い。仲間・強化ではこの値は変わらない。
func PushCost(total consts.Milligram) int

// PartyPushPower はこのターン押しへ充てられるAP総量。Player と SquadMember の
// TurnBased.AP.Current を合算する。仲間を増やし強化すると増え、同じ PushCost を
// より少ないターンで払えて速く進む。押しコスト自体は不変。
func PartyPushPower(world w.World) int
```

1タイルの押しに要する時間は `PushCost` とパーティAPから決まる。`TurnsTotal = ceil(PushCost(CubeWeight) / PartyPushPower)` を押しアクティビティ着手時に算出し、以後は他の長期アクティビティと同じくカウントダウンする。重いほど所要ターンが増え、パーティAPが多いほど減る。専用の進捗コンポーネントは持たず、進捗は `gc.Activity.TurnsLeft` が表す。`Activity` は既に `skipComponents` なので、押しの進捗も自然に保存対象外になり、再ロードは押し直しから始まる。

**引力側を最低1つ 1x1 コアの検証に含める。** ブレーキ(押しコスト)と引力(重い物を承知で連れて行きたくなること)は一対で、引力ゼロなら最適解は「空のキューブを軽く押す」に収束し経済の検証が空回りする。したがって presence 効果を持つ prop、例えば暖のストーブを最低1つ実装対象に含め、置けば重量が増えて効果も得られる対を最小構成で回せる状態を検証のゴールにする。

### 3x3 への拡張(保留)

3x3 に寄せる価値は、凍原でかさばりを取り回す手触り(破壊/迂回の決断が重くなる)と、威圧感のある見た目。どちらもコアループには不要で、1x1 で経済を検証し、かさばりの摩擦が要ると分かってから着手する。以下は着手時の設計で、今は実装しない。

複数マス占有を表す既存コンポーネントは無いので、占有範囲は `GridElement` を拡張せず別コンポーネント `Footprint` として新設する。`GridElement` はアンカー位置、`Footprint` は占有範囲で関心が別だからである。

```go
// Footprint はエンティティが GridElement の基準タイル(左上)から占める矩形範囲。
// GridElement を持つが Footprint を持たないエンティティは 1x1 とみなす。
// 3x3 キューブは Footprint{W:3, H:3}。回転しないため W・H は生成後に変わらない。
type Footprint struct {
	W, H consts.Tile
}
```

**footprint の展開は索引ビルダーだけで行い、リーダーには両方チェックを課さない。** 通行判定は既に単一のチョークポイントを通っている。`CanMoveTo` は `si.IsBlockPass(to)` を読むだけで、リーダーはタイルをキーに索引を引く。その `SpatialIndex.BlockPass` は `buildSpatialIndex`(`singleton.go`)で構築され、現状は entity ごとに1タイルだけ登録している。ここを footprint の全タイルへ広げれば、全消費者が無改修で9タイルすべてを塞がれたと見る。`buildSpatialIndex` は単一ループでなく `BlockPass` 用ループとキャラクター位置用ループに分かれているので、キューブが乗るループ(prop は `BlockPass` 側)で展開する。

```go
// OccupiedTiles はエンティティが占有する全タイルを返す。Footprint を持たなければ
// GridElement の1タイルを、持てば footprint の矩形を返す。呼ぶのは索引ビルダーだけ。
func OccupiedTiles(world w.World, entity ecs.Entity) []consts.Coord[consts.Tile]

// LeadingTiles は指定方向へ1タイル押すとき新たに踏み込む前縁タイルを返す。
// 3x3 を東へ押すなら東端の3タイル。押しの衝突判定はこの前縁だけを見る。
func LeadingTiles(world w.World, cube ecs.Entity, dir gc.Direction) []consts.Coord[consts.Tile]
```

3x3 化では下辺中央タイルだけを扉にし、扉を小エンティティに切り出してキューブ位置から追随させる。「回転しない」を不変条件として持ち込む。

## 変更箇所

1x1 コア(今やる)。`InteractionKind` を散在 switch する箇所は4つで、種別を足すと全4箇所へ case が要る(default 無しで exhaustive 強制。漏れは `make lint` が止める)。

| ファイル | 変更 |
|---|---|
| `internal/components/interactable.go` | `InteractionEnterCube`/`InteractionExitCube` を `InteractionKind` に追加し `Config()` の switch へ case(隣接・手動) |
| `internal/states/action_handlers.go` | `getInteractionActions` の switch へ case。埋めないと「入る/出る」が行動選択肢に現れない |
| `internal/activity/player_actions.go` | 足元ログの switch へ case |
| `internal/components/activity.go` | `BehaviorName` に `BehaviorPush` を追加。Behavior のディスパッチ switch へ case |
| `internal/consts/consts.go` | 押しコストの基準係数(歩行の10倍規模)を定数化 |

## 採用しなかった方法

- **最初から 3x3 で作る** — footprint・多タイル衝突・索引展開・扉追随を、押しと経済の緊張がまだ確かめられていない段で背負う。push と enter は enter を手動にすれば 1x1 でも両立するので 3x3 はコアループに不要。コア(重量・AP・遷移)はサイズに依存しないので器だけ後から差し替えられる
- **`GridElement` を `W,H` で拡張して占有範囲を持たせる**(3x3 化する場合) — `GridElement` は非テストで360箇所参照され serde 保存対象なので、struct を変えると全エンティティのセーブ形が変わり全構築箇所が検討対象になる。さらにゼロ値で既存構築が0タイル footprint になりロード時に旧エンティティが消える罠を負う。別 `Footprint`(未所持=1x1)なら波及がキューブに閉じ、ゼロ値の罠も無い
- **9タイルに `BlockPass` を並べて 3x3 を表す** — 押すたびに9エンティティを平行移動させ、一体としての衝突判定・扉追随・重量帰属が壊れる。1エンティティ + `Footprint` のほうが一体性を保てる
- **内部を専用のインメモリ構造にする** — 既存の `SwapTo`/`Suspended`/`StageBound` が退避・再訪・状態保存をすでに解いており、prop/item 配置もそのまま使える。専用構造は二重実装で YAGNI に反する
- **出口座標を一度だけ固定 `Coord` で結線する** — ダンジョン入口は永久に動かないので固定でよいが、キューブは訪問の合間に押されて動くので古くなる。`PortalConnection` は流用しつつ、入場のたびにキューブ現在隣接へ `Coord` を貼り直す
- **`StageBound` にキューブ↔内部リンクを持たせる** — `StageBound` は「どのステージに住むか」の所属で `Key` は1つ。キューブ本体はオーバーワールドに住み押される必要があるので `Key` は overworld で埋まり、どの内部を所有するかを載せる余地が無い。所属と所有は別の関係
- **逆引きリンク `CubeInterior{Stage}` を新設し出口で逆引きする** — キューブに内部キーを持たせ live な現在位置から着地を解く案。貼り直しが要らず不変条件にも依存しない堅さがあるが、新コンポーネントを1つ増やす。`PortalConnection` 流用(貼り直し)なら新設ゼロで、内部滞在中はキューブ不動という同じ不変条件のもと正しく動きダンジョンと完全同型になる。将来キューブが留守中にも動く仕様が入るなら逆引き方式へ移す
- **押しコストをパーティAPや人数で変える** — 「押しコストは不変、変わるのは何ターンで払うか」という1比較への集約を崩す。人数はAP総量にだけ効かせ、コスト関数は総重量のみの純関数に保つ
- **prop に重量を持たせず item だけで総重量を測る** — 効果を持つ prop が重量ゼロだと家具を無料で増やせる。prop へ `gc.Weight` を拡張して置いた物すべてを重量にする
- **押しを1回のインスタント行動にする** — `PushCost` が1ターンのAPを超える重いキューブを表現できない。多ターンにまたがる継続アクティビティにすることで、solo は遅く大所帯は速い、という仲間の価値が出る
- **押し進捗に専用コンポーネント(`PushProgress` 等)を持たせる** — 当初はキューブに蓄積APを持たせたが、押しは他の長期アクティビティと同じ多ターン行動なので、専用の状態を作らず既存 `gc.Activity{TurnsTotal, TurnsLeft}` のカウントダウンに載せれば足りる。中断・完了・毎ターン検査も Activity 機構をそのまま使え、`Activity` は既に `skipComponents` なので保存の扱いも自動。新設コンポーネントはゼロになる
- **乗る/降りるの移動モードにする** — モード中は方向入力＝キューブ操作と一意に決まり引きも表現できるが、`PushMode` マーカーとモード開始/解除の入力、乗車中の入る分岐など状態と操作が増える。1x1 では入るを手動アクションにすればモード無しのバンプでも押しと入るは衝突せず、引きも回り込みが安く必須でない。楽な実装を優先しモードレスにする。3x3 でかさばりの取り回しに引きが要ると分かればそのとき足す
- **引きを最後まで見送る** — 当初は 1x1 では回り込みが安く不要と判断したが、実プレイで押しだけだと壁際・角で詰むと分かり採用した。倉庫番の詰み回避の定石で、自由移動でないので押し主体の手触りは保たれる。BehaviorPull として押しと重量・所要ターンを共通化して足した
- **押し専用の方向 enum を新設する** — 既存 `gc.Direction`(基本4方向 + 斜め + None、`GetDelta()` 付き)があり、専用型は移動方向と二重表現になる。押しは基本4方向の部分集合を使えば足りる
- **寒波前線を押し専用の進入不可の壁にする** — 前線は移動を止める壁でなく、極低温ゾーンの寒さ(ダメージ)で圧力を与えるものにする。押せる先はプレイヤーの `CanMoveTo` に一致させ、キューブはプレイヤーが行けるところへ行ける。極低温ゾーンは通行でき、進入不可はその西の破棄域だけでプレイヤーと共通。押しに独自の前線チェックを持たせると判定が二重になり食い違う

## コメント

- 最大の設計判断は総重量の集計軸だった。所有者ベースの `calculateOwnedWeight` とは別に、ステージ束縛ベースの `CubeWeight` を新設し prop に重量を拡張する。ここを誤ると「家具は無料」という抜け穴が空き、ブレーキと引力の一対が崩れる
- 出口座標は移動キューブの罠だった。内部滞在中はキューブ位置が不変になる条件を使えば、逆引き用の専用コンポーネントを新設せず既存 `PortalConnection` の貼り直しで解け、ダンジョンの出入りと完全同型になる。堅い逆引き方式は不変条件が崩れる将来に取っておく
- 新しい型・コンポーネントを足す前に既存を確認する。方向は `gc.Direction`、キューブ↔内部リンクは `PortalConnection`、退避は `StageBound`/`Suspended`、押しの多ターン進行は `gc.Activity` と、いずれも既存で足りた。押しのために新設するコンポーネントはゼロになった
- 押しはモードレスのバンプに絞り、進捗も既存の Activity に載せた。当初は乗る/降りるモードと `PushMode`・`PushProgress` を足したが、1x1 には過剰だった。歩き込みが押しと入るを両方誘発する衝突は入るを手動アクションにするだけで解け、多ターン進行は他の長期アクティビティと同じ `Activity{TurnsTotal, TurnsLeft}` で足りる。引きも回り込みが安い 1x1 では要らない。結果、押しは既存の移動・衝突・アクティビティ経路の延長に載り、新設状態はゼロ。引きとモードは 3x3 拡張の判断材料として保留した
- 前線は移動を止める壁でなく寒さ(ダメージ)で圧力を与える。押せる先はプレイヤーの `CanMoveTo` に一致させ、キューブはプレイヤーが行けるところへ行ける。極低温ゾーンは通行でき、進入不可はその西の破棄域だけでプレイヤーと共通なので、押しに独自の前線チェックを持たせず判定を一本化した。doc 77 の「ロックは無い」とも整合する
- `InteractionKind` を足すと散在 switch 4箇所すべてで `make lint` が止まる。特に `getInteractionActions` を漏らすと「入る/出る」が行動選択肢に出ない。対応漏れを機械検知する意図した安全網
