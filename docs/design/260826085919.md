# 並列テストの不安定問題: ebitenui グローバル状態の競合

## 背景

ruins のテストは `make test` で `-shuffle=on` を効かせ、並列化を進めている。しかし UI に触れるテストを `t.Parallel()` で並列にすると競合し、間欠的に失敗する。原因は ebitenui がウィジェットツリーの外にプロセス全体で1つの可変状態を持つことにある。遅延イベントキュー、入力ハンドラ登録、NineSlice の描画キャッシュがそれで、ウィジェット生成・`AddChild`・描画・World 初期化のいずれもこの共有状態に触れる。複数テストが同時に触れると読み書きが交差し、`-race` で競合検出、あるいは実行順が変わるたびに間欠失敗する。

現状、この競合を避ける手段が2系統に分裂している。

- **並列を諦める系統**: `//nolint:paralleltest` で `t.Parallel()` を抑制する。`internal/maingame/integration_test.go` に3件残る。`internal/widgets/entityspec/spec_test.go` にも18件あったが、下記の WithUILock 系統へ移して解消した。この置換をしていた PR #709 はこの設計の決着を待つためクローズし、ブランチ `auto/test-entityspec-20260825` に退避してある。
- **区間を直列化する系統**: `vrt.WithUILock` で共有状態に触れる区間だけをミューテックスで囲み、`t.Parallel()` を許す。現在8つのテストファイルで使っている。

問題は、どちらを使うかの規約が無いことだ。手段が2つあるため選択がばらつく。囲み漏れがあれば競合が残り、テストが不安定になる。そして囲み漏れを機械的に検知する仕組みも無い。

なお `internal/logger/logger_test.go` の `//nolint:paralleltest` はグローバルなロガー設定を書き換えることが理由で、ebitenui とは別問題である。本設計の対象外とする。

## 要件

- ebitenui に触れるテストが競合せず、`-race -shuffle=on` で安定して通る。
- 競合を避ける手段を1つに統一する。囲み漏れを機械検知できる。
- 並列度を不必要に落とさない。直列化するのは共有状態に触れる最小区間だけにする。
- 既存の `WithUILock` 資産を捨てない。

## 設計

現在の直列化ヘルパは共有状態全体を1本のミューテックスで守っている。

```go
// internal/vrt/golden.go
var ebitenuiMu sync.Mutex

// WithUILock は ebitenuiMu を取得して fn を実行する。ebitenui のグローバル状態に触れる
// 生成・初期化・描画をこのヘルパに通し、ロックを取る箇所を1つに集約する。
func WithUILock(fn func()) {
	ebitenuiMu.Lock()
	defer ebitenuiMu.Unlock()
	fn()
}
```

このヘルパは正しく機能している。問題はヘルパの実装でなく、使い方の規約と、触れる面積の広さにある。そこで「触れる面積を減らす」「唯一の正規手段に統一する」「機械検知で強制する」の3層で解く。

### 1. seam で pure ロジックとウィジェット生成を分ける

共有状態に触れるのはウィジェット生成だけである。表示すべき値を組み立てる算出は pure で、共有状態に触れない。両者を分ければ、算出はロック無しで自由に並列検証でき、ロックが要るのは実際にウィジェットを作る最小区間だけになる。

entityspec は既にこの形になっている。データの形は次のとおり。

```go
// pure: 共有状態に触れない。ロック不要で並列検証できる。検証の主対象
type SpecRow struct {
	Label  string
	Value  string
	Header bool
	Color  *color.RGBA
}

func SpecRows(world w.World, e ecs.Entity) []SpecRow // 何を表示するかを決める。ここを厚くテストする

// ebitenui 共有状態に触れる。WithUILock で囲む最小区間。表示の有無だけ最小限に確認する
func RenderSpecRows(c *widget.Container, rows []SpecRow, res resources.UIResources)
```

ロジックの検証は `SpecRows` の戻り値に対して行い、`RenderSpecRows` はラベルがツリーに載るかの最小確認に絞る。これで並列に走る本体はロック不要の pure 部分になり、直列区間が痩せる。

### 2. WithUILock を唯一の正規手段にする

ebitenui 共有状態に触れる区間は必ず `t.Parallel()` と `vrt.WithUILock` の組で書く。`//nolint:paralleltest` を ebitenui 由来の理由で使うことは禁止する。`integration_test.go` のように囲む単位が大きいものは、駆動ヘルパ側でロックを取るか、テスト本体全体を `WithUILock` で囲む。

### 3. 機械検知で囲み漏れを防ぐ

CLAUDE.md の「機械検知可能なものは linter 化する」に沿い、規約を人手のレビューでなく `make check` で守る。ebitenui を import する `*_test.go` で、`WithUILock` を経由せずにウィジェット生成 API を呼ぶ箇所を go/parser ベースのカスタム linter で検出する。既存の AST lint 方針と同じく標準ライブラリで fail-closed にする。あわせて ebitenui 由来の `//nolint:paralleltest` の新規追加を禁止する。

## 採用しなかった方法

- **ebitenui グローバル状態を毎テストでリセット・隔離する**: 遅延キューと NineSlice キャッシュはパッケージ内部に隠れ、外部からリセットできない。上流に手を入れる保守コストが大きく、版追随も要る。却下。
- **ebitenui 依存テストを build tag で直列グループに隔離する**: テスト実行系統が2つに割れ、CI 設定と実行時間が複雑化する。囲み漏れの検知にもつながらない。却下。
- **`WithUILock` を薄く包んだ `ParallelUI(t)` ヘルパを新設する**: `t.Parallel()` とロック取得を1行にまとめるだけの薄いヘルパは固有の責務が無く、薄いテストヘルパを作らない方針に反する。直書きの方がどこが直列化対象かを読み取れる。却下。
- **全テストを直列化して `-parallel 1` にする**: 競合は消えるが、増え続けるテストの実行時間が悪化する。要件の「並列度を落とさない」に反する。却下。

## コメント

短期は「WithUILock への統一と nolint 廃止」で不安定を止め、中期に seam で触れる面積を減らして並列度を回復する二段構えとする。実行順やタイミングに依存しない安定が先で、速度回復は後に置く。

entityspec のカバレッジ増強はこの設計の決着後に再開する。退避先は `auto/test-entityspec-20260825`。
