# 並列テストの ebitenui 競合を源で断つ: フォークして競合グローバルをスレッドセーフ化する

## 背景

ruins のテストは `make test` で `-shuffle=on` を効かせ並列化を進めている。しかし UI に触れるテストを `t.Parallel()` で並列にすると、ebitenui がウィジェットツリーの外にプロセス全体で1つ持つ可変状態が競合し、間欠的に失敗する。

現状の対処 `vrt.WithUILock` は、共有状態に触れる区間をミューテックスで直列化するものだ。競合は止まるが、直列化した区間ぶんの並列度を失う。ウィジェット構築やレイアウト計算まで一緒に直列化されるため、テストが増えるほど実行時間が悪化する。これは競合を「避ける」対症療法であって、競合そのものを消してはいない。

目標を「並列を保ったまま、競合そのものを起こさなくする」に置き直す。ロックを全呼び出し箇所に撒くのでなく、競合の源にだけ最小限のロックを置く。

## 要件

- UI に触れるテストが `t.Parallel()` のまま `-race -shuffle=on` で安定して通る。
- 並列度を犠牲にしない。直列化するのは共有状態への読み書きという極小区間だけにする。
- 競合をテスト層でなく源で消す。`WithUILock` と ebitenui 由来の `//nolint:paralleltest` を全廃できること。
- 機能を失わない。保守コストを最小にする。

## 調査結果

### 競合源は4つのグローバルに集中している

ebitenui v0.7.3 のパッケージレベル可変状態のうち、実行時に mutate されて競合するのは次の4箇所に限られる。`ContainerOpts` などの `*Opts` 群は init で一度設定され以降 read-only なので競合しない。

```go
// image/nineslice.go — 同期無しの map。並行書き込みは Go では即クラッシュする
var colorImages    map[color.Color]*ebiten.Image = map[color.Color]*ebiten.Image{}
var colorNineSlices map[color.Color]*NineSlice    = map[color.Color]*NineSlice{}

// internal/event/deferred.go — 遅延アクションキュー。AddChild 等が append する
var deferredActions []DeferredAction

// widget/widget.go — 遅延描画キュー
var deferredRenders []RenderFunc

// input/input.go — カーソル・ホバー・ウィンドウサイズ等の入力グローバル
var currentCursor string
var windowSize    image.Point
```

テストで実際に競合するのは、ウィジェット構築時の nineslice キャッシュへの並行 map 書き込みと、キューへの並行 append である。entityspec 系テストは `ui.Update()` や `Draw()` を呼ばずウィジェットを組んでラベルを読むだけなので、キューは append されるが drain されない。入力グローバルは `Update` ループでしか mutate されず、フレームを回さないテストでは触れない。つまり競合面はさらに狭く、キャッシュとキューの追記だけである。

### 上流にアップグレードの余地は無い

- v0.7.3 が最新である。リリースは 2026-03-16。master は4コミット先行するのみで、いずれもグローバル状態に触れていない。
- 上記4グローバルは master でも v0.7.3 と同一で、スレッドセーフ化も脱グローバル化もされていない。
- 状態をリセットする公式フックは存在しない。`AddDeferred`/`ExecuteDeferred` は `internal/` パッケージにあり consumer から import できず、テスト境界でキューを掃除する逃げ道も無い。
- thread-safety・data race・複数UI・並列テストに触れた issue/PR/discussion は1件も無い。上流の設計方針は暗黙に「1プロセス1UI・単一フレームループ前提」であり、複数インスタンスや並行利用は想定されていない。

### 代替ライブラリで競合を回避できるものは無い

Ebitengine 向けの retained-mode UI ライブラリを調べたが、実行時に mutate されるパッケージグローバルを持たないものは存在しなかった。詳細は「採用しなかった方法」に置く。

## 設計

ebitenui をフォークし、上記4グローバルの読み書きだけをライブラリ内部で直列化する。ロックを共有状態そのものに寄せることで、呼び出し側はロックを意識しなくなり、テストは `t.Parallel()` だけで書ける。ウィジェット構築やレイアウト計算はロック外に残るので並列度を失わない。

### nineslice キャッシュ

読み多寡のメモ化なので、意味を変えずに保護できる。競合はほぼ生じない。

```go
// フォーク後: 同期を持つ形にする。sync.Map か RWMutex いずれか
var colorNineSlices sync.Map // color.Color -> *NineSlice
var colorImages     sync.Map // color.Color -> *ebiten.Image
```

### 遅延キュー

append と drain のスライス操作だけをロックする。`a.Do()` は `AddDeferred` を再入し得るため、ロックの外で呼ぶ。ここが唯一の設計上の地雷である。

```go
// internal/event/deferred.go — フォーク後
var (
	deferredMu      sync.Mutex
	deferredActions []DeferredAction
)

func AddDeferred(d DeferredAction) {
	deferredMu.Lock()
	deferredActions = append(deferredActions, d)
	deferredMu.Unlock()
}

func ExecuteDeferred() {
	for {
		deferredMu.Lock()
		if len(deferredActions) == 0 {
			deferredMu.Unlock()
			return
		}
		a := deferredActions[0]
		deferredActions = deferredActions[1:]
		deferredMu.Unlock()

		a.Do() // ロック外で実行する。Do() が AddDeferred を再入しても安全
	}
}
```

`widget/widget.go` の `deferredRenders` も同じ形にする。`input` グローバルはフレームを回すテストが将来出たときに備え、同様に保護する。

### フォークの持ち方と上流還元

- go.mod に `replace` を置き、フォークを指す。パッチは最小に保ち、上流のタグに追従してリベースする。

```
// go.mod
replace github.com/ebitenui/ebitenui => github.com/kijimaD/ebitenui <fork-tag>
```

- 同じ変更を上流へ PR する。スレッドセーフ化は非破壊の追加であり、取り込まれればフォークを畳んで `replace` を外せる。上流に前例が無いので、競合の再現と `-race` のログを添えて提案する。

### 競合が消えたことの検証

フォークを差し込んだうえで、UI に触れるテストをすべて `t.Parallel()` 化し、`make test RACE=-race` を `-shuffle=on` で回す。競合検出ゼロを確認できたら `WithUILock` と ebitenui 由来の `//nolint:paralleltest` を削除する。ロックはライブラリ内部の共有状態へ移り、テストコードから消える。

## 採用しなかった方法

- **`WithUILock` で全体を直列化し続ける**: 競合は止まるが並列度を失い、テスト増加で実行時間が悪化する。要件の「並列を保つ」に反する。ユーザーの意図も源での解決にある。却下。
- **フォークで状態を `*UI` インスタンスへ完全に移す**: 複数UIを真に隔離できるが、遅延キューはウィジェットツリーの深部から `*UI` 参照無しに append される。所有者コンテキストを widget パッケージ全体に通す必要があり改修が大きく、上流との乖離も広がる。ruins の用途は1プロセス1UIで、テストもキューを drain しないため、この隔離までは要らない。YAGNI として却下。内部同期のフォークで足りる。
- **上流の修正を待つ**: v0.7.3 が最新で該当修正は無く、issue も前例も無い。待つ根拠が無い。上流 PR は出すが、待ちを前提にはしない。却下。
- **別のUIライブラリへ移行する**: 調べた候補はいずれも実行時に mutate されるパッケージグローバルを持ち、競合を回避できない。furex は同期無しの touch map とグローバル入力ソースを持ち、かつ widget・テーマ・list・window・scroll・nineslice が無く移行は事実上フルスクラッチになる。etk はUI全体を唯一のグローバル game として設計しており競合はむしろ悪化する。imgui 系は immediate mode で単一の C コンテキストを共有し並列に最も不利。移行しても機能を作り直したうえで結局グローバルを自前で潰すことになり、得が薄い。却下。
- **自前のUI抽象で ebitenui を包み差し替え可能にする**: 将来の乗り換えは楽になるが、それ自体は競合を消さない。import 面は widget・root・image に集中しており、いま抽象層を挟む必要は薄い。競合解決とは別課題として切り離す。却下。

## コメント

ロックを全呼び出し箇所に撒くのは、共有状態の同期責務が本来ライブラリの内側にあることの裏返しだった。フォークでその責務を源に戻せば、呼び出し側は素直な並列テストに戻り、`WithUILock` という足場を外せる。フォークは重い判断だが、競合面が4グローバルに局所化していること、代替も上流も手が無いこと、機能を失わないことから、最も割の合う道と判断する。
