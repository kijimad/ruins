# 並列テストの UI 競合を源で断つ: 状態をインスタンス所有にする

## 背景

ruins のテストは `make test` で `-shuffle=on` を効かせ並列化を進めている。しかし UI に触れるテストを `t.Parallel()` で並列にすると、ebitenui がウィジェットツリーの外にプロセス全体で1つ持つ可変状態が競合し、間欠的に失敗する。

現状の対処 `vrt.WithUILock` は、共有状態に触れる区間をミューテックスで直列化するものだ。競合は止まるが、直列化した区間ぶんの並列度を失う。これは競合を避ける対症療法であって、競合そのものを消してはいない。

目標を「並列を保ったまま、競合そのものを起こさなくする」に置き直す。

## 要件

- UI に触れるテストが `t.Parallel()` のまま `-race -shuffle=on` で安定して通る。
- 並列度を犠牲にしない。共有状態を直列化するのでなく、共有そのものを無くす。
- 競合をテスト層でなく源で消す。`WithUILock` と ebitenui 由来の `//nolint:paralleltest` を全廃できること。
- 機能を失わない。保守コストを最小にする。

## 調査結果

### 競合の全体像を race detector で実測した

`WithUILock` をロックしない no-op に置き換え、UI に触れるテスト4パッケージ、overlay・menuframe・states・menuloop を `-race -shuffle=on` で実行した。結果は次のとおり。

- **データ競合 1521 件。競合フレームは 3938 個すべて `github.com/ebitenui/ebitenui` 内部**だった。
- **ebiten 本体、hajimehoshi/ebiten の描画コアは競合 0 件。text/v2 も 0 件**。
- 競合サイトは ebitenui の遅延イベントキュー `AddDeferred`/`ExecuteDeferred`、入力グローバル `input.Update`/`CursorPosition`/`Wheel`/`KeyPressed`、フォーカスとウィンドウ、ウィジェット初期化時のハンドラ登録に集中していた。

これで「隠れた第二の原因」が無いことが確定した。ebiten 自身は同時ウィジェット構築に耐えている。競合の源は ebitenui のグローバル可変状態に閉じており、それを全て消せばフレーキーは残らない。

### ミューテックスでは撤去できない。テストが2種類あるため

競合するテストは2種類に分かれ、後者はロックでは意味が壊れる。

| テスト種別 | 競合の中身 | ミューテックスで足りるか |
| --- | --- | --- |
| 構築のみ。entityspec 等 | `AddChild` から遅延キューへの追記。drain しない | 足りる。追記を守れば安全 |
| フレーム駆動。states・menuloop の VRT リプレイ | `UI.Update()` を並行実行。共有キューを drain し、入力・カーソル・フォーカスの共有状態を書き換える | 足りない |

フレーム駆動テストでは、2つの UI が同時に `UI.Update()` を回すと、片方の Update がもう片方のキューに積まれたアクションを食い、共有カーソルやフォーカスを踏み合う。ミューテックスはクラッシュを止めるが意味は壊れたままだ。正しくするには `UI.Update()` 全体をロックで囲むしかなく、それは今の `WithUILock` と同じものになる。つまりライブラリ内部のミューテックス化は「WithUILock をライブラリへ移設」であって撤去ではない。

`WithUILock` が本当に不要になるのは、状態を UI インスタンスが所有したときだけだ。各 UI が自分のキュー・入力・フォーカスを持てば、並行 `Update()` は互いに素な状態に触れる。競合せず、ロックも要らず、意味も正しく、オーバーヘッドも無い。

### 上流にも代替ライブラリにも手が無い

- ebitenui v0.7.3 が最新で、該当グローバルは master でも未修正、外部からのリセット手段も無い。thread-safety を扱った issue も前例も無い。本番は単一UI単一スレッドで保護が不要なため、毎フレームのロックを上流が受け入れる見込みは薄い。
- Ebitengine 向けの代替 UI ライブラリを調べたが、furex・etk・imgui 系いずれも実行時に mutate されるパッケージグローバルを持ち、競合を回避できない。詳細は「採用しなかった方法」に置く。

### ruins が UI に使う面は小さい

現行コードが ebitenui から使うのは Container、Row・Grid・Anchor の3レイアウト、Text、Window、Graphic、TextInput 1箇所、NineSlice のテーマ、`ebitenui.UI` ルートに限られる。List・ComboButton・Slider・Checkbox・TabBook・ScrollContainer・ToolTip・DragAndDrop は使っていない。再実装が難しい重い部品を使っていないため、インスタンス所有の小さな UI を自前で持つことが現実的な選択肢になる。

### 他の Ebitengine 製ゲームの実践

生態系の定石を調べた。裏付けとして参照する。

- 実装は2つの陣営に割れる。作り込んだ商用タイトルと hajimehoshi 自身のコードは、生の Ebitengine に直接描く自前 immediate-mode が多い。aaaaxy、Odencat の全作、ebiten 公式 examples、新作 guigui がそれ。UI がアート主導のとき、テキストとスプライトを毎フレーム直に描く。
- ツールキットを使う層では ebitenui が事実上の標準。ただし旗艦採用の roboden ですら ebitenui を fork し、さらにパッド・キーボードのフォーカス移動は手書きしている。ライブラリのマウス前提が完全には合わない。フォークしても入力の作り込みは残る。
- ebitenui のグローバル状態はアーキテクチャ由来だと第三者検証でも一致した。`deferredActions` と `InputHandler` はプロセス共有で、2つの `*ebitenui.UI` はこれを共有する。上流を変えない限り並列テスト安全にできない。本設計の -race 実測と符合する。
- etk は UI 全体をパッケージグローバルにしており ebitenui より状態問題が重い。furex はレイアウト補助で、グローバル問題を解かない。
- UI の自動テストは生態系ではほぼ行われていない。ruins の VRT は先進的で、その規律ゆえに ebitenui のグローバル状態が顕在化した。競合はテストを厳密にやっている裏返しでもある。

含意は明確だ。シンプルさ・テスト容易性・並列安全を最優先する ruins には、グローバルを持たない自前の小さな UI が、生態系の成功例とも符合する。

## 設計

原則は「状態をインスタンスが所有する」だ。共有が無ければロックも要らず、並行しても競合しない。これを満たす実装として、ruins の実使用面に絞った小さな UI を自前で持つ。パッケージグローバルの可変状態をゼロにし、全状態を `UI` インスタンスへぶら下げる。

```go
// 全状態を UI インスタンスが所有する。パッケージグローバルの可変状態を持たない
type UI struct {
	root  Widget
	focus Widget
	input InputState // カーソル・ホバー・キー。UI ごとに独立
	// 遅延キューは持たない。イベントは構築時にツリーへ直接結ぶ
}

func (u *UI) Update(in InputSnapshot) { /* u.input を更新する。グローバルに触れない */ }
func (u *UI) Draw(cv Canvas)          { u.root.Draw(cv) }

// Canvas は描画先を抽象化する seam。テストは fake を渡し ebiten 無しで
// レイアウトとテキストを検証できる。本番は ebiten 実装を渡す
type Canvas interface {
	FillRect(r image.Rectangle, c color.Color)
	DrawNineSlice(r image.Rectangle, ns NineSlice)
	DrawText(pos image.Point, s string, face text.Face, c color.Color)
}

type Widget interface {
	Layout(bounds image.Rectangle) // 自身と子の矩形を確定する
	Draw(cv Canvas)
	Children() []Widget
}
```

`Canvas` を挟むことで、UI ツリーは ebiten から独立してテストできる。ロジックとレイアウトは fake Canvas で並列に検証し、実描画は ebiten 実装のアダプタに閉じる。実描画そのものは実測で並行安全と分かっているので、ここは薄いアダプタで足りる。

### 様式は保持型で宣言的に書く

様式は保持型に決めた。ruins の現行 ebitenui 利用の心的モデルに近く画面移行が小さいこと、試作で -race 競合ゼロを実証済みであることが理由。即時型はフォーカスを整数で持ち毎フレーム全描画する生態系主流の形だが、ruins の宣言的な画面記述を書き換える移行になるため採らない。

画面はツリーを式として組む宣言的な書き方にする。状態が変わったら画面を組み直す。コンストラクタは可変グローバルに触れないので、宣言的にしてもインスタンス所有と並列安全は保たれる。

```go
// 宣言的にツリーを式として組む。命令的な Add の列にしない
func specPanel(rows []SpecRow) Widget {
	items := make([]Widget, 0, len(rows))
	for _, r := range rows {
		items = append(items, Row(Label(r.Label), Label(r.Value)))
	}
	return Panel("panel_bg", 16, items...)
}
```

この宣言的コンストラクタ Row・Panel・Label を持つ試作で、32 ゴルーチンの並行 Update・Draw を含めて -race 競合ゼロ・ロック無しを確認した。

### 実現性の裏取り

確定の前に、薄い試作でインスタンス所有の実現性を検証する。UI インターフェースと1画面ぶんの試作を作り、多数の `t.Parallel()` テストを `-race` で回して競合ゼロを、ロック無しで達成できることを確かめる。裏が取れてから本実装へ進む。

### 移行のかたち

`Canvas` seam を先に用意し、画面を1つずつ ebitenui から自前 UI へ載せ替える。全画面を一度に置き換えない。UI 系 golden は描画差分ぶん再生成し、画面ごとに目視で確認する。全画面が移ったら ebitenui 依存と `WithUILock` を落とす。

## 採用しなかった方法

- **`WithUILock` で全体を直列化し続ける**: 競合は止まるが並列度を失い、テスト増加で実行時間が悪化する。源での解決でない。却下。
- **ebitenui をフォークしてグローバルをミューテックスで保護する**: 構築のみのテストは救えるが、フレーム駆動の VRT リプレイでは共有キューの消費が意味的に壊れる。`UI.Update()` 全体を囲むしかなく `WithUILock` の移設にしかならない。本番に無用なロック税も乗る。上流受理も見込み薄。却下。
- **ebitenui をフォークして状態を `*UI` へ完全に移す**: 正しい形だが、UI 所有権を widget ツリー・入力・フォーカス全体に通す巨大改修で、他人のコードに対して行うには重すぎる。上流との乖離も広がる。自前で最初からインスタンス所有にするほうが小さい。却下。
- **上流の修正を待つ**: 最新版に該当修正が無く、本番不要のロックを上流が入れる動機も薄い。待つ根拠が無い。却下。
- **別のUIライブラリへ移行する**: furex は同期無しの touch map とグローバル入力ソースを持ち widget・テーマ・window が無い。etk はUI全体を唯一のグローバル game として設計しており競合が悪化する。imgui 系は単一の C コンテキストを共有し並列に最も不利。いずれも競合を回避できず機能も作り直しになる。却下。

## コメント

実測が方針を決めた。競合は ebitenui のグローバル状態に閉じており、ebiten 本体は並行に耐える。そしてフレーム駆動テストがある以上、ロックでは `WithUILock` を落とせない。落とせるのは状態をインスタンス所有にしたときだけだ。ruins の UI 使用面が小さいことも実測できているので、インスタンス所有の小さな UI を自前で持つのが、本番無税・並列維持・意味正当を同時に満たす唯一の道になる。生態系調査でも、作り込んだ商用タイトルと hajimehoshi 自身のコードが自前 UI を採る一方、ツールキット利用層はフォークやフォーカス自作を強いられており、自前方針を裏付けた。

様式は保持型で宣言的に書くことに決めた。ruins の現行の心的モデルに近く移行が小さいこと、試作で実証済みであることによる。

entityspec のカバレッジ増強はこの決着後に再開する。退避先は `auto/test-entityspec-20260825`。

## 抽象度の検証と、そこで見つかった宿題

自前 UI が一通り動いたのち、レイアウトと描画の抽象がどこまで届いているかをブラウザのレンダリングパイプラインを物差しに照合した。段階ごとの詳細は図解版にまとめてある: https://claude.ai/code/artifact/f77cde9d-05c3-4ba4-b62a-20d785773cb0

達している軸と、届いていない軸がはっきり分かれた。

**達している**: 配置と描画の2フェーズ分離、描画バックエンドの `Canvas` seam、UAX#14 準拠の行分割、そして層の機械的強制。コアが非テスト661行に収まっているのは、配置を furex へ、行分割を go-text へ委譲した判断による。

**届いていない**: 内容から寸法が決まる仕組みが無い。`Widget` に希望サイズを申告するメソッドが無く、寸法は常に親が外から与える。結果として「内容から寸法を決めたい」箇所はすべて上位層の手計算になり、`text.Measure` の呼び出しが13箇所8ファイルへ散った。丸め方針も四捨五入と切り捨てで割れている。

構造で言えば、**描画には seam があるのに測定には seam が無い**。`Canvas` は `DrawText` を持つが `MeasureText` を持たない。この非対称が散在の源になっている。

もう1つ、`Widget.Layout(image.Rectangle)` がファサード経由で画面層に露出している。depguard は furex の import を封じたが、絶対座標を書く経路は型に開いたままで、職業選択・名前入力・メインメニューの3画面がそこから漏れている。このリポジトリが他所で徹底している「検出でなく構成で不可能にする」原則から外れる。

### 埋めないと決めたもの

クリップとスクロールは足さない。`ListCapacity` が入る行数を先に求めてページを切る設計で、はみ出しが構造的に発生しない。ゲームのメニューとしてはページングのほうが自然で、これは欠落でなく設計判断とする。合成レイヤ、z-index、ポインタ前提のイベント伝播も同じ理由で足さない。
