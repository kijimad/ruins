# overworld のアイテム配置を建物・部屋の意味論に沿ってスポーンする

## 背景

overworld にはまだ拾えるアイテムが一つも配置されていない。chunk 生成 `internal/overworld/chunkgen.go` の `NewChunkGen` は地形・NPC・prop・道・集落・散布物を置くが、item 系を一切呼ばない。overworld プランナー `PlannerTypeOverworldField` は `ItemTableName` が空で `ItemPlanner` が空振りし、`OverworldDefinition` は item テーブルのフィールドすら持たない。

一方で、この「建物や部屋に合わせた配置」を支える基盤はすでに揃っている。配置は「どこに置くか、すなわち部屋や家具の意味論」と「何を置くか、すなわち重みつきテーブル」の2軸に分けられる。この両輪が ruins にそれぞれ対応物を持つ。

| 必要な仕組み | ruins の対応 | 現状 |
|---|---|---|
| loot の重みつき抽選テーブル | `itemGroups` / `itemTables` + `raw.SelectByWeightFunc` | ある |
| 家具に紐づく loot | prop raw の `Storage.LootTableId` + `populateStorageLoot` | あり、overworld 建物でも稼働中 |
| 部屋の意味論に沿う床・什器上の loot 配置 | 計画層の `KindLoot` placement | レールとデータは投入済み、executor が捨てている |

決定的なのは3行目である。計画層 `internal/mapplanner/interior` はすでに部屋役割に沿った loot を emit している。`content_catalog.go` にキッチン役割の `snacks`/`drinks`/`bento`、薬局役割の `meds`/`bandage` が、重み・個数ダイス・配置意味論つきで定義済みである。ところが executor `internal/overworld/interior_furnish.go` は各 `Placed` を `interior.PropRawName(p.Ref)` で引き、写像できない Ref を `continue` で捨てる。`snacks` や `meds` は prop でないので黙って消える。`prop.go` と `urban.go` のコメントにも「raw の無い戦利品は置かない」「施設固有の戦利品はアイテム設計が固まってから足す」と明記があり、RNG ストリーム `0x4` も戦利品用に予約済みである。

つまり「どこに、どの loot グループを」は決定済みで純粋かつテスト可能な計画層にあり、欠けているのは「その抽象 loot グループを重み抽選して拾える実アイテムにする executor 経路」だけである。この設計はゼロから作るのでなく、作者が意図的に残した継ぎ目を閉じる。

## 要件

- 建物内のアイテムは部屋の役割に沿って出る。キッチンには食料、薬局には薬、店には商品。
- 屋外にも区画に応じた散布アイテムを出す。廃墟感を出す。
- 配置は決定的である。同一 seed で同一結果、再訪で一致する。VRT golden を割らない。
- 計画層 `interior` は純粋を保つ。raw に依存せず、抽象 Ref のみを emit する。抽選の実体化は executor が担う。
- アイテムは既存の `SpawnFieldItem` で `LocationOnField` 実体として出す。新規コンポーネントを足さない。

## 設計

### 全体像

2軸分離を踏襲する。「どこに、どの loot 語彙を」は計画層が抽象 Ref で決め、「その語彙を実アイテムへ重み抽選する」は executor が raw と決定的 RNG で行う。これは家具 loot が `Storage.LootTableId` を executor 側で解決するのと同じ構図で、床 loot と屋外 loot もこれに揃える。

`Placed` はデータモデルを変えない。`fill.go` の `selectTiles(room, placement, occupied, seed, sel.Count)` が個数ダイス由来の `Count` ぶんのタイルを返し、`KindLoot` placement は1つ1タイルの loot 山になる。executor は placement ごとに Ref を1回抽選して `SpawnFieldItem` すればよく、個数を `Placed` へ持ち回す必要がない。

```go
// Placed は変更不要。KindLoot 1件が床の1山に対応する
type Placed struct {
	Kind StuffKind
	Ref  string
	Pos  Vec
}
```

### A. 建物の床・什器上 loot を materialize する

executor `interior_furnish.go` の placed ループを Kind で分岐する。従来は prop 写像の可否だけで振り分けていたが、`KindLoot` を明示的に受ける。

```go
for _, p := range placed {
	pos := consts.Coord[consts.Tile]{X: g.offsetX + p.Pos.X, Y: g.offsetY + p.Pos.Y}
	switch p.Kind {
	case interior.KindLoot:
		// 抽象 loot Ref を item group へ写し、0x4 の決定的 RNG で1山を抽選して床へ置く
		groupID, ok := interior.LootGroupName(p.Ref)
		if !ok {
			continue // 写像の無い loot は置かない。lootRaw が単一のソース
		}
		if err := spawnFieldLoot(world, groupID, pos, lootRNG); err != nil {
			return nil, nil, err
		}
		occupied[pos] = true
	default:
		// 家具・装飾。従来経路。収納家具には populateStorageLoot が戦利品を格納する
		name, ok := interior.PropRawName(p.Ref)
		if !ok {
			continue
		}
		ent, err := lifecycle.SpawnProp(world, name, pos.X, pos.Y)
		if err != nil {
			return nil, nil, err
		}
		if err := populateStorageLoot(world, ent, name, lootRNG); err != nil {
			return nil, nil, err
		}
		occupied[pos] = true
	}
}
```

`spawnFieldLoot` は item group を1回引いて `SpawnFieldItem` する薄い関数である。group の distribution/collection 意味論と entry の `pack` ダイスは既存の抽選と共有する。

```go
// spawnFieldLoot は item group から1山を抽選し、床へアイテムを spawn する。distribution は重み比で1件、
// collection は各 entry を独立判定する。個数は entry の pack ダイスで振る。深度概念の無い地上なので
// item table の深度フィルタは通さず group を直接引く
func spawnFieldLoot(world w.World, groupID string, pos consts.Coord[consts.Tile], rng *rand.Rand) error {
	draws, err := raw.SelectFromItemGroup(world.Resources.RawMaster, groupID, rng)
	if err != nil {
		return err
	}
	for _, d := range draws {
		if _, err := lifecycle.SpawnFieldItem(world, d.Name, pos.X, pos.Y, d.Count); err != nil {
			return err
		}
	}
	return nil
}
```

`raw.SelectFromItemGroup` は既存の group 解決を executor から呼べる公開ヘルパとして切り出す。`item_planner.go` の `resolveItemSource` が持つ distribution/collection のロジックと重複させず、raw 層の一次ソースに寄せて両者が共有する。

### B. Ref から item group への写像 lootRaw

`prop.go` の `propRaw` と対称に、interior に loot 語彙の写像を新設する。抽象 Ref を raw の item group id へ写す単一のソースとし、executor と VRT が同じ表を引く。抽象語彙と raw の id を分離することで、raw 側の id 変更が interior の語彙へ波及しない。

```go
// internal/mapplanner/interior/loot.go
// loot の写像。interior の抽象 loot Ref をゲームの raw item group へ写す単一のソース。executor がこの表で
// アイテムを抽選し、VRT がこの表で loot の有無を描く。表に無い Ref は spawn されず描かれない
var lootRaw = map[string]string{
	"snacks":  "food",         // 当面は既存 group を再利用。後で snacks 専用 group へ細分化できる
	"drinks":  "food",
	"bento":   "food",
	"meds":    "healing_item",
	"bandage": "healing_item",
}

// LootGroupName は Ref に対応する raw item group 名と、spawn されるかを返す。executor と VRT が共有する
func LootGroupName(ref string) (string, bool) {
	id, ok := lootRaw[ref]
	return id, ok
}
```

既存 itemGroups には `food` と `healing_item` があるため、5つの Ref はすべて既存 group へ写せる。phase 1 は新規 group の authoring 無しで動く。flavor を上げたければ後から `snacks` 等の専用 group を raw に足し、写像先を差し替える。

### C. 施設別テーブルの拡充

施設種別 `FacilityKind` ごとに loot 語彙と家具中身を厚くする。store は商品、office は書類と貴重品、depot は資材、clinic/lab は薬と器材。手段は2つで、どちらも既存機構に乗る。

- 床・什器上 loot は `content_catalog.go` の役割別 content に `KindLoot` を足し、必要な語彙を `lootRaw` に写して raw に group を用意する。
- 家具中身は該当 prop raw の `Storage.LootTableId` を施設に合うテーブルへ向ける。`store_shelf`・`pantry`・`medicine_shelf`・`storage_box` は既にあり、`populateStorageLoot` が overworld 建物でも稼働済みなので、テーブル定義の拡充だけで効く。

新規に要る group は store 商品や office 貴重品など。英語ソースで定義し ja.po で訳す。既存アイテムを束ねるだけなら新規アイテムは不要。

### D. 屋外・区画の散布 loot

建物内に加え、屋外へも区画に応じた散布 loot を出す。これは既存レールが無いので新設する。overworld の chunk 生成に loot 散布 pass を足し、地区や biome に応じた item table を低密度で歩行可能・非占有な屋外タイルへ置く。

- テーブルは既存の `ruins_area`・`forest`・`cave` を biome ごとに使い分ける。urban の街路・庭は廃墟寄り、wilderness は森・洞窟寄り。
- 抽選は `raw.SelectItemByWeight` を深度0で通し、`SpawnFieldItem` する。
- 乱数は feature 群と同じ salt 方式に揃える。`ChunkSeed2D(runSeed, cx, cy)` から専用 salt で派生した RNG を使い、feature の当選 salt とも建物の `0x4` とも分離する。これで golden の `RunSeed: 42` を割らず、再訪で一致する。
- 密度は控えめにし、屋外を埋め尽くさない。歩行可能で未占有のタイルにだけ置く。

配置箇所は chunk 生成の後段で、地形・feature が確定し占有が分かってからにする。urban 建物内の loot は A の経路が担うので、屋外散布は建物 footprint を避ける。

### 決定論と VRT

- 建物 loot は既存の `0x4` ストリームを使う。屋外散布は `ChunkSeed2D` 由来の専用 salt。いずれもグローバル乱数を使わず建物・chunk ローカルで決定的にし、再訪一致と golden 安定を両立する。
- loot が ECS 実体になるとゲーム描画に乗る。states 系 golden は `RunSeed: 42` 固定なので、抽選結果も決定的に固定され golden は安定する。ただし全屋内・overworld golden の見た目が変わる。
- interior の `sprite_golden_test.go` は計画層の Placed を描く純粋テストで、loot の中身は executor の RNG に依存し計画層からは決められない。位置は決定的なので、`KindLoot` の座標には汎用の loot マーカーを描き、「そこに loot がある」ことだけを示す。中身の実アイテムは states 系 golden が担う。
- golden 差分はトレランスに隠れうる。該当 golden を削除して強制再生成し、差分を目視する。

### serde

loot は `LocationOnField` と `StageBound` を持つ通常の item 実体で、ダンジョンの床アイテムと同じ経路で永続化される。新規コンポーネントは足さない。serde の変更は無い。

## 採用しなかった方法

- **計画層 interior に rawMaster と RNG を渡し、具体アイテム名まで解決する**: ダンジョンの `ItemPlanner` とは揃うが、interior の「raw を持たない純粋な抽象 Ref 層」という設計を崩す。家具 loot が executor 側で解決する既存構図とも非対称になる。KindFurniture と KindLoot を同じ「抽象 Ref を executor が解決」で揃えるほうが一貫する。不採用。
- **content_catalog の Ref を raw の itemGroup id へ直結し、写像表を持たない**: 最もシンプルだが、interior の抽象語彙が raw の命名へ直接依存し、`propRaw` との非対称が生まれる。VRT と executor が共有する単一ソースも失う。`lootRaw` の間接参照は写像先の差し替えで語彙を細分化でき、既存 group への暫定写像で phase 1 を無 authoring で動かせる。不採用。
- **overworld 専用の item table を `ItemPlanner` に持たせ、部屋非依存でチャンクへ散布する**: 実装は軽いが「建物や部屋に合わせて」という要件を満たさない。屋外散布 D はこの方式に近いが、建物内は役割依存の A が担い、両者を分ける。区画非依存の散布だけでは不十分なので、単独では不採用。
- **loot 用の新規コンポーネントで置き場所を表す**: `LocationOnField` の既存 item 実体で足り、serde も既存経路に乗る。新規マーカーは冗長。不採用。

## コメント

- **開いた建物へ誰でも入って loot できる**。窓や扉の設計と併せ、建物は「入って漁る」対象になる。初期は控えめな密度から始め、バランスは後で調整する。
- **phase 1 は既存 group への暫定写像で無 authoring で動く**。`snacks`/`drinks`/`bento` を `food`、`meds`/`bandage` を `healing_item` に写すだけで、キッチンと薬局の床 loot が出る。flavor の細分化は phase を分ける。
- **VRT と in-game の乖離を作らない**という既存原則を守る。`lootRaw` を executor と VRT の単一ソースにし、片方だけが置く・描くを構造的に防ぐ。`propRaw` と同じ思想。
- **StuffKind の switch は網羅を意識する**。executor の Kind 分岐は `KindLoot` を明示し、他は既定の prop 経路へ落とす。`KindBeing`・`KindTrap` を interior_furnish で扱うかは別途整理する。
- **golden 再生成のトレランス隠れ**に注意する。loot で色が変わる golden はトレランスに埋もれうるので、該当を削除して強制再生成し目視する。
- **区画別 loot の考え方は他のローグライクを参考にした**。ただし設計は ruins の既存機構だけで自己完結する。用語や構造を外部に依存させない。
