# マクロ地図に道を方向つき線分で重ねる

## 背景

全画面の地形俯瞰図 `OverworldMapState` と HUD 右上の `MacroMap` は、1チャンク=1記号で場所の種別だけを描いている。プレイヤーは種別の点在は読めるが、集落どうしがどう繋がっているか、街道がどこを走るかを地図から読めない。道を地図に出したい。

道はタイル粒度で実在するが、地図はチャンク粒度なので「道がチャンクレベルにない」ことが素朴な障害に見える。しかし道の幾何は生成を伴わない純関数から完全に復元できる。

- 道は隣接リージョンの当選集落どうしを結ぶ L 字の舗装路。集落中心は `settlementPlacement.WinnerOf` で算出でき、経路は「始点の行に沿った水平辺 → 終点の列に沿った垂直辺」に分解される。角は `(bx, ay)`。
- 集落中心は当選チャンクのど真ん中 `chunkW/2` に置かれ、`roadWidth=4 << chunkW=24` なので、チャンク解像度では「道が通るチャンク＝チャンク空間の L 字上のチャンク」に一致する。
- 既に `scatter.go` の `onScatterRoute` と `outdoorZoneAt` が、同じ `WinnerOf`＋L 字をタイル生成なしで使う前例を持つ。

つまり種別体系 `chunkType`/`placeType` に道を足す必要はない。マクロ地図のモデルへ「そのチャンクを道がどの方角へ抜けるか」という副次情報を重ねればよい。着想は Cataclysm: DDA の俯瞰図の道だが、あちらは都市配置→接続探索を保存するステートフル生成で道セルを実体化する。ruins は道の幾何が seed の純関数なので、保存も接続グラフ構築も要らず、表示のたびに算出できる。

## 要件

- マクロ地図の各チャンクセルに、そのチャンクを通る道の接続方角を出す。全画面図と HUD の両方で見える。
- 未探索チャンクは道もフォグで伏せる。探索で開いたチャンクだけ道が見える。既存のフォグと同じ扱い。
- 生成側の種別分類 `chunkType`/`placeType` は変えない。道は純関数で算出する副次レイヤに留める。
- `overworld` パッケージは theme に依存しない。道の色はレンダラ側 theme が決める。

## 設計

### モデル: 方角ビット集合を MacroCell に足す

罫線素片グリフ（─│┌┐┼…）で道を描く案は破棄する。主フォント `KH-Dot-Dougenzaka-16` はドット絵フォントで U+2500 系罫線素片を1字も持たず、フォールバックの Nerd もシンボル専用でこれらを持たないため、罫線グリフは文字化けする。代わりにセル中央から接続辺へ実際の線分を引く。方向表現は同じで、フォント非依存になる。

そのためモデルは1文字でなく「接続方角のビット集合」を持つ。

```go
// RoadDir はチャンクを通る道が接続する方角のビット集合。線分描画で、セル中央から
// どの辺の中点へ線を引くかを表す。0 は道なし。
type RoadDir uint8

const (
	RoadN RoadDir = 1 << iota // 上、Y-1 の隣へ
	RoadS                     // 下、Y+1 の隣へ
	RoadE                     // 右、X+1 の隣へ
	RoadW                     // 左、X-1 の隣へ
)

// MacroCell は表示範囲内1チャンクの表示情報。種別文字と探索フラグに、道の接続方角を足す。
type MacroCell struct {
	Glyph      rune
	Discovered bool
	Road       RoadDir // このチャンクを通る道の接続方角。0 なら道なし
}
```

### 道の重ね合わせ: L 字を歩いて両端のビットを立てる

`road.go` と同じ結線を、チャンク空間で純関数として算出する。表示範囲に重なるリージョン対を走査し、当選集落 a→b の L 字上のチャンクへ方角ビットを積む。角は水平ビットと垂直ビットが同一チャンクに積まれて L 字の折れになり、交差はビットが 3・4 本立って T・十字になる。CDDA の接続方角メタデータと同じ効果を、生成なしで得る。

```go
// buildRoadOverlay は表示範囲に重なる範囲の道の接続方角を、絶対チャンク座標をキーに算出する。
// road.go と同じく隣接リージョンの当選集落どうしを L 字で結ぶ。生成は伴わない純関数。
func buildRoadOverlay(runSeed uint64, area MacroRange, rows consts.Chunk) map[consts.Coord[consts.Chunk]]RoadDir
```

分解は `road.go` の `drawRoadSegments` と厳密に合わせる。水平辺は始点 a の行 `a.Y`、垂直辺は終点 b の列 `b.X`、角は `(b.X, a.Y)`。地図の折れと実世界の道の折れが同じチャンクに来る。

### レンダラ: 線分を引く

全画面図 `renderMap` と HUD `MacroMap.Draw` は、地形色セルを敷いた後、`cell.Road != 0` なら道の線分を描く。どちらも既に矩形描画基盤を持つので、方角ごとにセル中央から辺の中点へ、太さ数 px の細い矩形を引く。色は新設の `theme.OverworldMapRoad`。未探索セルは既存のフォグ分岐の内側なので道も伏せる。

種別記号は道セルでもそのまま描く。荒れ地の `.` は道の交点の節に見え、集落の `T` は道の端点に街道が届く形になり、どちらも情報として自然。

## 採用しなかった方法

- **罫線素片グリフで道を描く**。1セル1文字のまま `Glyph` を罫線素片に差し替える案。レンダラ改修はほぼ不要で魅力的だが、主フォントもフォールバックも U+2500 系を持たず文字化けする。実測で全滅を確認。
- **ASCII の `-` `|` `+` で描く**。フォントは持つが、角・T・十字がすべて `+` に潰れて方向が読めない。「方向つき」の要件を満たさない。
- **`chunkType`/`placeType` に道種別を足す**。分類の中枢を汚し、道の「接続」という本質が1チャンク独立の種別に馴染まない。道は副次レイヤに留める方が素直。
- **道タイルを実際に生成して読む**。生成は重く、地図表示のためだけに帯を実体化するのは本末転倒。純関数で算出する既存方針に反する。
- **CDDA 式のステートフルな道保存**。ruins は道が seed の純関数なので保存が要らない。保存レイヤは無駄。
