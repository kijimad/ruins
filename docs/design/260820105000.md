# キー入力を3チャンネルに統一し束縛表からヒントを導出する

## 背景

メニュー操作の入力は 260817032634 の再生基盤と、その後の束縛表 `menuinput.Binding` への集約で、
「供給源 → 束縛表 → 共通キー」の1本に統一された。キー→Action 変換は `menuinput` の1点にあり、
モックキーボードで単体テストでき、`world.Resources.MenuInput` に Action 列を差せば本番フローのまま再生できる。

ただしこの統一はメニュー文脈に閉じている。ゲーム全体では入力がまだ3系統に割れている。

- **メニュー系**: `menuinput` 経由。再生可能、テスト可能
- **フィールド系**: `dungeon_input.HandleInput` がキーの if 連打で Action を返す。shooting・look_around・
  overworld_map・cube_panel も各自のミニ変換器を持つ。構造は `menuinput` と同型なのに供給源を見ないため、
  再生ドライバから駆動できずテストも届かない
- **テキスト系**: character_naming が IME 込みでキーを直読みする

さらに widgets/messagewindow が widget 内部でキーを直読みしており、変換の1点化から漏れている。

キー操作のヒント表示にも二重管理がある。`menuNavHint` とその extras は手書きの文字列で、
束縛の実体と独立に書かれる。設定メニューの言語切替を左右キーから Enter へ変えた際、
ヒント文字列の手動撤去が別途必要だった。挙動と表示が別の場所にあると、この種のずれは構造的に再発する。

VRT を全てリプレイ形式へ寄せる方針を進めるには、ダンジョン歩行・射撃・拾得が Action 列で
駆動できる必要があり、供給源の seam をメニュー外へ広げることが前提になる。

## 要件

- 全文脈のキー→Action 変換が1つの変換器を通る。state はキーを読まず、束縛表を宣言するだけにする
- 再生供給源が全文脈に効く。メニューでもダンジョンでも同じ注入点で駆動できる
- キー操作のヒント表示を束縛表から導出する。表を変えれば表示が追随し、二重管理をなくす
- キーバインドの単体テストを文脈横断で書ける。モックキーボードで表の1行ずつを検証できる
- テキスト入力は Action に還元しない。IME・編集状態は別チャンネルとして明示する

## 設計

### 3チャンネルモデル

入力を性質の異なる3チャンネルに分け、統一するのは Action チャンネルだけにする。

1. **Action チャンネル**: 押したキーが離散的な操作1つに対応するもの全て。メニュー操作・移動・射撃・
   モーダル開閉。本設計の対象
2. **テキストチャンネル**: character_naming の名前入力。IME の変換途中状態や編集操作は Action の語彙に
   還元できないため、キー直読みのまま例外として明文化する。再生が必要になれば文字列を別口で注入する
3. **ポインタチャンネル**: ebitenui が widget 内で完結して処理する。本設計の対象外

### 供給源の一般化

`world.Resources.MenuInput` はメニュー限定の名を返上し `InputSource` にする。
供給源が差されていれば全文脈がそこから読む。再生ドライバはこの1点だけでゲーム全体を駆動する。

```go
// resources.Resources
// 変更前
MenuInput inputmapper.Source
// 変更後
// InputSource は Action の入力供給源。nil なら本番どおりキーボードから変換する。
// メニューもフィールドも同じ供給源から読み、再生ドライバはここに Action 列を差す
InputSource inputmapper.Source
```

### 束縛表の拡張とパッケージ改名

変換器パッケージ `menuinput` はメニュー限定でなくなるため `keybind` に改名する。
Binding は押下モードと表示名を持つ。

```go
// keybind
// 変更前
type Binding struct {
	Key    ebiten.Key
	Shift  ShiftMode
	Action inputmapper.ActionID
}

// 変更後
// PressMode はキーの押下判定の種類
type PressMode int

const (
	// PressJust は押した瞬間の1フレームだけ発火する
	PressJust PressMode = iota
	// PressRepeat は押しっぱなしでリピート発火する。移動やカーソル送りに使う
	PressRepeat
)

// Binding は1つのキー操作と Action の対応。表の順で評価する
type Binding struct {
	Key    ebiten.Key
	Shift  ShiftMode
	Press  PressMode
	Action inputmapper.ActionID
	Label  string // ヒント表示の msgid。空なら隠しキーとしてヒントに出さない
}
```

メニューの共通キーはハードコードをやめ「メニュー共通の束縛表」になる。文脈差は全て表が持つ。
画面固有の断片と共通表は実行時に重ねず、構築時に `MustMerge` で1枚へ合成する。
条件が重なる行の組は合成時に拒否されるため、断片が別の断片のキーを黙って影で食う
継承的な事故は構造的に起きない。全行の条件が互いに素なので行順にも意味が無い。

```go
// keybind
// menuCommonBindings はメニュー共通のキー束縛。各メニューの固有表の後に評価する
var menuCommonBindings = []Binding{
	{Key: ebiten.KeyEscape, Press: PressJust, Action: inputmapper.ActionMenuCancel, Label: "Back"},
	{Key: ebiten.KeyArrowUp, Press: PressRepeat, Action: inputmapper.ActionMenuUp, Label: "Select"},
	// ... 左右・Tab・Enter
}

// ReadInput は1フレームぶんの入力を Action として読む。world が供給源を持つならそこから読み、
// 持たない本番では合成済みの表からキーボードで変換する
func ReadInput(world w.World, table []Binding) (inputmapper.ActionID, bool)

// MustMerge は断片を1枚に合成し、条件が重なる行の組を構築時に拒否する
func MustMerge(fragments ...[]Binding) []Binding
```

Enter は押下押上のワンセット検出という癖をデバイス層 `input.KeyboardInput` が持つ。
変換器は `KeyEnter` の判定にだけ `IsEnterJustPressedOnce` を使う。この癖は表では表現せず、
デバイス層の責務として変換器内に閉じる。

### ヒントの導出

ヒント行は束縛表から組む。手書きの `menuNavHint` 文字列を置き換える。
キー一覧ヘルプが全キーの正となった後は、常設フッターを `HelpHint` のヘルプ入口1項目に絞り、
画面を静かに保つ。`NavHint` は導出の本体としてヘルプ画面のフッターが使う。

```go
// keybind
// NavHint は束縛表からキー操作ヒントの1行を組む。Label が空の行は出さない。
// キーの表記は keyLabel が導出し、Shift 併用は大文字で表す
func NavHint(world w.World, tables ...[]Binding) string

// keyLabel は Binding のキー表記を返す。ebiten.KeyX と ShiftForbidden なら "x"、
// ShiftRequired なら "X"、Escape や Enter は既存のアイコン定数へ対応づける
func keyLabel(b Binding) string
```

item_action の verbList は既に「1行が Key・Action・表示を持ち、タブ見出しを導出する」形に
到達している。この設計はその形の全文脈への一般化で、Label の翻訳は既存どおり msgid を
`query.T` へ渡す。

表が全文脈に揃うと、表を列挙するだけのキー一覧ヘルプ画面が作れる。`menuloop.KeyHelpState` が
現在の文脈の表と共通表から一覧を導出して表示し、? すなわち Shift+Slash でどの画面からも開ける。
メニューでは Screen の入力ゲートが `ActionOpenKeyHelp` を吸って push し、ダンジョンは自分の
DoAction から push する。state を menuloop に置くのは、Screen が push するため states に置くと
import が循環するから。

### フィールド系の表化

`dungeon_input.HandleInput` の if 連打を dungeon 文脈の束縛表にする。

```go
// states
// dungeonBindings はダンジョン移動と各モーダル開閉の束縛表
var dungeonBindings = []keybind.Binding{
	{Key: ebiten.KeyM, Press: keybind.PressJust, Action: inputmapper.ActionOpenDungeonMenu, Label: "Menu"},
	{Key: ebiten.KeySpace, Press: keybind.PressJust, Action: inputmapper.ActionOpenInteractionMenu, Label: "Interact"},
	{Key: ebiten.KeyArrowUp, Shift: keybind.ShiftForbidden, Press: keybind.PressRepeat, Action: inputmapper.ActionMoveNorth},
	// ... 全キー
}
```

デバッグ専用キーは表に条件を持たせず、デバッグ専用の表を分けて readAction が設定を見て先頭へ足す。移動は4方向のみで、斜めへは Z/C の視点回転 Action で向きを変えてから直進する。2キー同時押しの表現は持たない。
shooting・look_around・overworld_map・cube_panel も同じ手順で各自の表へ畳む。
messagewindow は world を保持しているので、widget 自身が束縛表と `ReadInput` で読む形にする。呼び出し側の API を変えずに直読みが消え、供給源からの駆動も効く。

### 移行順序

各段が独立に出荷できる。①改名と Source コメント更新 ②Binding 拡張と共通キーの表化
③dungeon_input の表化。ここでダンジョンが再生可能になり最大の果実 ④残る state を1つずつ
⑤messagewindow ⑥ヒント導出への置き換え ⑦キー一覧ヘルプ。

## 採用しなかった方法

- **キー対応の外部データファイル化とゲーム内リバインド**。キーを変えたい要件が現状無い。表を Go 値で
  持てば型検査と単体テストで守れ、ホットリロードも要らない。リバインドが要件になったら表を serde
  する拡張で足り、いま外部化する理由がない
- **イベントバスによる入力配送**。フレームごとに pull で読む現行の同期モデルが崩れ、発火順序の推論が
  難しくなる。入力ゲートの排他、overlay 専有といった既存の制御構造は pull 型を前提に成立している
- **キーボードシングルトンの差し替えで再生する**。260817032634 で却下済み。キーリピートや Enter
  セッションの時間状態を再現する手間に対し、テストしたいのは Action から先のロジックで、
  キー対応は表の単体テストで別に守れる
- **ActionID の文脈別型分割**。どの文脈で来うるかは束縛表がスコープする。型を分けると変換と網羅
  義務が増えるだけで、フラットな ID と文脈表の組で十分に安全
- **テキスト入力の Action 化**。IME の変換途中状態・カーソル編集は離散 Action の語彙に還元できない。
  無理に押し込むと Action チャンネル全体の単純さが失われる
