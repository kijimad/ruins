# メニュー操作をコマンド列で再生し本番フローで動作確認する

## 背景

メニュー画面のランタイム `menuloop.Screen` は、入力を `inputmapper.ActionID` へ変換し `Model.DoAction(world, action)` へ渡す構造で、すでにコマンドパターンになっている。コマンドが `ActionID`、ハンドラが `DoAction`、供給源が `Screen.readAction` で、`readAction` は state が任意に実装する `ExtraInput` を先に試し、無ければ共通の `HandleMenuInput` へフォールバックする。

問題は、コマンドの**供給源が実キーボードだけ**で、スクリプトで与える経路が無いこと。そのためメニューの選択遷移を確認したいとき、選択肢が下記に限られる。

- 確認用の使い捨て state を新規に用意する。本番の state 構築や props とはずれた別物になりやすい。
- VRT の `AssertStateGolden` で state を構築して描く。ただし初期選択位置の1枚しか撮れず、カーソルを動かした後の状態を本番フローで再現できない。

やりたいのは、**本番と同じ `Screen.Update` フローに、あらかじめ決めたコマンド列を流し込んで**、使い捨て state を作らずに選択遷移や描画を確認できるようにすること。既存の `ExtraInput` seam があるので、供給源を1つ足すだけで本番ループを一切書き換えずに実現できる。

補足として `internal/input` には `MockKeyboardInput` があるが、`GetSharedKeyboardInput` はシングルトンで差し替え口が無く、`HandleMenuInput` の経路には刺さらない。よって現状のモックはキーボード実装の単体テスト専用で、メニュー操作の再生には使えていない。

## 要件

- 本番の `Screen.Update` を通してコマンド列を再生できる。`DoAction` から先のメニュー挙動を実物のまま検証する。
- 確認用の使い捨て state を作らず、実在メニュー state をそのまま駆動できる。
- ヘッドレスで各ステップの描画を撮れる。VRT のゴールデン資産と組み合わせられる。
- 本番挙動に影響しない。コマンド供給源を設定しないフレームは従来どおり実キーボードで動く。
- コマンド供給源はキー割り当てから独立させる。テストしたいのはメニューロジックであってキーバインドではない。キーとアクションの対応 `HandleMenuInput` は別に単体テストする。

## 設計

### コマンドとシナリオ

再生の単位は本番の `ActionID` そのものにする。別語彙を作らず、本番が扱うコマンドを再生単位に流用する。

```go
// Command はメニュー1操作。本番の ActionID をそのまま再生単位にする
type Command = inputmapper.ActionID

// Scenario は再生するコマンド列。1要素を1フレームで供給する。
// 空要素を挟みたいときは供給しないフレームとして表現する
type Scenario struct {
	Commands []Command
}
```

### 供給源を Screen に足す

`Screen` に任意のコマンド供給源を持たせ、`readAction` の最優先で試す。本番は未設定で従来経路のまま。

```go
// Screen に追加するフィールド
type Screen[P any] struct {
	// ...既存...
	// commands は任意のコマンド供給源。nil なら本番のキーボード経路。
	// 設定時はキーボードより優先し、決めた順にコマンドを1フレーム1件で返す
	commands func() (inputmapper.ActionID, bool)
}

// SetCommandSource は再生用の供給源を差す。テストや再生ドライバから使う
func (s *Screen[P]) SetCommandSource(src func() (inputmapper.ActionID, bool)) {
	s.commands = src
}
```

`readAction` の優先順位を「commands → ExtraInput → HandleMenuInput」に変える。commands が未設定なら現状と同一。

```go
func (s *Screen[P]) readAction() (inputmapper.ActionID, bool) {
	if s.commands != nil {
		if action, ok := s.commands(); ok {
			return action, true
		}
	}
	if h, ok := s.model.(ExtraInput); ok {
		if action, ok := h.ExtraInput(); ok {
			return action, true
		}
	}
	return HandleMenuInput()
}
```

供給源の実体はキューを1件ずつ吐くだけ。テスト専用に置く。

```go
// scenarioSource は Scenario を先頭から1フレーム1件で供給する
type scenarioSource struct{ rest []inputmapper.ActionID }

func (s *scenarioSource) next() (inputmapper.ActionID, bool) {
	if len(s.rest) == 0 {
		return "", false
	}
	a := s.rest[0]
	s.rest = s.rest[1:]
	return a, true
}
```

### 再生ドライバ

VRT の `renderStates` に相当する、コマンドを1歩ずつ進めるドライバを用意する。実 state を構築し、シナリオを供給しながら `Screen.Update` を回し、任意で各ステップを描く。使い捨て state を作らずに本番フローを再現する核がここ。

```go
// PlayScenario は実 state をコマンド列で駆動する。各ステップ後に capture が呼ばれ、
// 呼び出し側が描画を撮るか状態を検査する。capture が nil なら駆動のみ。
// state と Screen の結線方法は実装時に確定する。state が Screen を露出する口が要る
func PlayScenario(
	t *testing.T,
	buildState func(w.World) es.State[w.World],
	scenario Scenario,
	capture func(step int, world w.World, screen *ebiten.Image),
) {
	// 1. InitVRTWorld で world を作る
	// 2. state を構築し Screen へ scenarioSource を差す
	// 3. scenario.Commands を1件ずつ供給し Screen.Update を回す
	// 4. 各ステップ後に capture を呼ぶ。ebitenui グローバルは WithUILock で直列化する
}
```

### 使いどころの例

在庫メニューを開いて2つ下・1つ上へ動かし、確定する流れを本番経路で再生し、途中のゴールデンを撮る。

```go
PlayScenario(t, buildInventoryState, Scenario{Commands: []inputmapper.ActionID{
	inputmapper.ActionMenuDown,
	inputmapper.ActionMenuDown,
	inputmapper.ActionMenuUp,
	inputmapper.ActionMenuSelect,
}}, captureEachStepGolden)
```

## 採用しなかった方法

- **キーボードのシングルトンを差し替える**。`GetSharedKeyboardInput` に setter を足し、スクリプト化したキーを報告する `MockKeyboardInput` を差して `HandleMenuInput` ごと通す案。キー割り当ての層まで含めて本番に忠実になる利点はある。だがグローバル可変状態が増え、キーリピートや Enter セッションの時間状態を再現する手間がかかる。テストしたいのは `DoAction` から先のメニューロジックで、キー対応は別に単体テストできる。よってコマンドは `ActionID` 層で供給する。
- **各 state に `ExtraInput` で再生源を実装させる**。state 側にキューを持たせる案。再生のためだけに全 state が再生コードを抱えることになり本番コードが汚れる。供給源は Screen 側の任意フィールドに寄せ、state は無改造で駆動する。
- **確認用の使い捨て state を新規に作る**。本番の state 構築や props からずれた別物を作り込むことになり、確認したい本番フローと乖離する。本要件の目的そのものに反する。
- **本番 `play` バイナリに `--scenario` 再生を組み込む**。人が目視で確認できる利点はあるが、実キー入力しか無い今の本番ループへ供給源の切替とライフサイクル管理を持ち込む投資が重い。まずヘッドレス駆動を用意し、目視再生が要ると分かった時点で `SetCommandSource` を本番側から呼ぶ形へ広げられる。将来拡張として残す。

## コメント

- `PlayScenario` が state から `Screen` を取り出す結線口は実装時に確定する。state が `*Screen` を露出する最小の口を足すか、ドライバが state 経由で `SetCommandSource` を呼べる形にするかを見極める。
- 点滅アニメ（別 doc）とは独立。本ドライバは選択遷移の挙動確認が主眼で、点滅の脈動そのものは対象にしない。脈動を撮るなら本ドライバの capture を複数フレームに広げてアルファ列をサンプルする使い方はできる。

## 波及: VRT を単一 ebiten インスタンスで回す

現状の VRT はケースごとに `InitVRTWorld` で world を作り `renderStates` で描く。ebitenui のグローバル状態に触れるため `WithUILock` で直列化しており、`t.Parallel` で並べても実際はロック上で待ち合う。並列は名目で、非再入ロックの取り回しとケースごとの構築コストが残る。

`PlayScenario` は本番ループの中でコマンド列を再生し、各ステップを撮れる。これを推し進めると、複数ケースのスクショを1つの ebiten インスタンス上で順番に撮れる。メニューを開き、遷移し、撮り、次へ進む、を1本の再生で回す。並列で走らせないので `WithUILock` による直列化を意識する必要がそもそも無くなり、ケースごとの world 構築や ebitenui ツリーの組み直しを減らせるぶん速くなりうる。

本 doc の主眼は選択遷移の挙動確認で、この単一インスタンス化は `PlayScenario` が開く展望として記す。どこまで1インスタンスへ寄せるか、ケース間の後片付けを決定的に保つ方法は、実在 state の駆動が安定してから別途設計する。

実装で判明した点:

- **import 循環**。`menuloop` のテストが `vrt.WithUILock` を使うため、`vrt` 本体へ `menuloop` 依存を入れると `menuloop テスト → vrt → menuloop` で循環する。`PlayScenario` は `vrt/replay` サブパッケージへ分け、`vrt` 本体を無改造にして避けた。`WithUILock` を低層へ移す案は別ブランチと競合するため採らない。
- **遷移の1フレーム遅延**。`StateMachine.Update` は state が返した遷移を次フレーム冒頭で適用する。最後のコマンドが返した Push/Pop を反映させるため、供給源が尽きた状態で終端にもう1フレーム回して確定させる。
