# メニュー操作をコマンド列で再生し本番フローで動作確認する

## 背景

メニュー画面のランタイム `menuloop.Screen` は、入力を `inputmapper.ActionID` へ変換し `Model.DoAction(world, action)` へ渡す構造で、すでにコマンドパターンになっている。コマンドが `ActionID`、ハンドラが `DoAction`、供給源が `Screen.readAction` で、`readAction` は state が任意に実装する `ExtraInput` を先に試し、無ければ共通の `HandleMenuInput` へフォールバックする。

問題は、コマンドの**供給源が実キーボードだけ**で、スクリプトで与える経路が無いこと。そのためメニューの選択遷移を確認したいとき、選択肢が下記に限られる。

- 確認用の使い捨て state を新規に用意する。本番の state 構築や props とはずれた別物になりやすい。
- VRT の `AssertStateGolden` で state を構築して描く。ただし初期選択位置の1枚しか撮れず、カーソルを動かした後の状態を本番フローで再現できない。

やりたいのは、**本番と同じ `Screen.Update` フローに、あらかじめ決めたコマンド列を流し込んで**、使い捨て state を作らずに選択遷移や描画を確認できるようにすること。既存の `ExtraInput` seam があるので、供給源を1つ足すだけで本番ループを一切書き換えずに実現できる。

補足として `internal/input` には `MockKeyboardInput` があるが、`GetSharedKeyboardInput` はシングルトンで差し替え口が無く、`HandleMenuInput` の経路には刺さらない。よって現状のモックはキーボード実装の単体テスト専用で、メニュー操作の再生には使えていない。

## 要件

- 本番の `Screen.Update` を通してコマンド列を再生できる。`DoAction` から先のメニュー挙動を実物のまま検証する。
- 確認用の使い捨て state を作らず、実在メニュー state をそのまま駆動できる。
- ヘッドレスで各ステップの描画を撮れる。VRT のゴールデン資産と組み合わせられる。
- 本番挙動に影響しない。コマンド供給源を設定しないフレームは従来どおり実キーボードで動く。
- コマンド供給源はキー割り当てから独立させる。テストしたいのはメニューロジックであってキーバインドではない。キーとアクションの対応は `menuloop` 内の非公開関数として残し、別に単体テストする。

## 設計

### 再生の単位

再生の単位は本番の `ActionID` そのものにする。別語彙を作らず、本番が扱うアクションを再生単位に流用する。列は `[]inputmapper.ActionID` で足り、包む型は作らない。

入力の無いフレームは空の `ActionID` で表す。本番はキーを押していないフレームが大半なので、待ちが要る場面で並べる。state を push した直後のフレームは新しい `Screen` のタブ登録がまだ済んでいないため、続けて操作するならここに1つ挟む。

### 差し替え点は「キー → Action」の1点だけ

本番と再生で違うのは入力の出どころだけにする。差し替え点を `world` が持ち、`Screen` はそこから読む。

```go
// inputmapper
// Source は1フレームぶんの入力を Action として返す供給源
type Source func() (ActionID, bool)

// resources.Resources に足すフィールド
// MenuInput はメニュー操作の入力供給源。nil なら本番どおりキーボードから変換する
MenuInput inputmapper.Source

// menuloop
// ReadMenuInput は本番と再生で唯一分岐する点。後段の DoAction 以降は完全に同じ経路を通る
func ReadMenuInput(world w.World) (inputmapper.ActionID, bool) {
	if src := world.Resources.MenuInput; src != nil {
		return src()
	}
	return handleMenuInput()
}
```

`readAction` は本番と同じ「ExtraInput → 入力供給源」の順のままにする。`ExtraInput` はキーを直接読むのでヘッドレスでは必ず偽になり、供給源へ落ちる。順序を再生のために組み替える必要は無い。

```go
func (s *Screen[P]) readAction(world w.World) (inputmapper.ActionID, bool) {
	if h, ok := s.model.(ExtraInput); ok {
		if action, ok := h.ExtraInput(); ok {
			return action, true
		}
	}
	return ReadMenuInput(world)
}
```

供給源を `world` が持つ効き目は3つある。

- **本番 state に再生用の口が要らない**。`Screen` へ供給源を差す `SetCommandSource` も、それを state から呼ぶための `CommandDriven` interface も不要になる。
- **push した先の state にも効く**。特定の state に差す方式だと、シナリオ途中で積まれた state はキーボード経路に落ちて駆動が止まる。`world` 単位なら同じ列でメニューを開いて閉じるところまで回せる。
- **グローバル可変状態を作らない**。`world` 単位なので並列テストで競合しない。

### 再生ドライバ

VRT の `renderStates` に相当する、フレームを1つずつ進めるドライバを用意する。実 state を構築し、供給源を差してから本番の `MainGame.Update`・`MainGame.Draw` を回す。使い捨て state を作らずに本番フローを再現する核がここ。

```go
// PlayScenario は実 state を本番の MainGame ループで actions から駆動し、駆動し終えた
// MainGame を返す。遷移結果は game.StateMachine から検査できる。
// capture は各フレームの描画後に0起点のフレーム番号で呼ぶ。nil なら駆動のみ
func PlayScenario(
	t *testing.T,
	buildStates func(w.World) []es.State[w.World],
	actions []inputmapper.ActionID,
	capture func(frame int, world w.World, screen *ebiten.Image),
) *maingame.MainGame {
	// 1. InitVRTWorld で world を作る
	// 2. SetupStateMachine でレイアウトを確定させる。供給源を差す前なので Action を消費しない
	// 3. MainGame を組み、world へ供給源を差す
	// 4. len(actions)+1 フレームぶん game.Update を回し、各フレーム後に capture を呼ぶ
}
```

`StateMachine` は値型で `MainGame` がコピーを持つ。だから駆動も検査も `MainGame` 側に寄せる。呼び出し側へ別の `StateMachine` を返すと、`game.Update` の結果が反映されず遷移を観測できない。

### 使いどころの例

在庫メニューを開いて2つ下・1つ上へ動かし、確定する流れを本番経路で再生し、途中のゴールデンを撮る。

```go
PlayScenario(t, buildInventoryStates, []inputmapper.ActionID{
	inputmapper.ActionMenuDown,
	inputmapper.ActionMenuDown,
	inputmapper.ActionMenuUp,
	inputmapper.ActionMenuSelect,
}, captureEachFrameGolden)
```

## 採用しなかった方法

- **キーボードのシングルトンを差し替える**。`GetSharedKeyboardInput` に setter を足し、スクリプト化したキーを報告する `MockKeyboardInput` を差して `HandleMenuInput` ごと通す案。キー割り当ての層まで含めて本番に忠実になる利点はある。だがグローバル可変状態が増え、キーリピートや Enter セッションの時間状態を再現する手間がかかる。テストしたいのは `DoAction` から先のメニューロジックで、キー対応は別に単体テストできる。よってコマンドは `ActionID` 層で供給する。
- **各 state に `ExtraInput` で再生源を実装させる**。state 側にキューを持たせる案。再生のためだけに全 state が再生コードを抱えることになり本番コードが汚れる。供給源は world に寄せ、state は無改造で駆動する。
- **`Screen` に供給源を差す `SetCommandSource` を足す**。state が `CommandDriven` を実装して `Screen` へ委譲し、ドライバが最上段 state を型アサートして差す案。一度実装したが2つの難がある。1つは本番 state にテスト専用メソッドが生えること。もう1つは供給源が最上段 state に閉じるため、シナリオ途中で push された state はキーボード経路に落ちて駆動が止まること。差し替え点を world へ上げると両方消える。
- **`menuloop` にパッケージ変数として供給源を置く**。改修は最小だがグローバル可変状態が増え、テストの並列実行で競合する。キーボードのシングルトン差し替えを却下したのと同じ理由で採らない。
- **確認用の使い捨て state を新規に作る**。本番の state 構築や props からずれた別物を作り込むことになり、確認したい本番フローと乖離する。本要件の目的そのものに反する。
- **本番 `play` バイナリに `--scenario` 再生を組み込む**。人が目視で確認できる利点はあるが、実キー入力しか無い今の本番ループへ供給源の切替とライフサイクル管理を持ち込む投資が重い。まずヘッドレス駆動を用意し、目視再生が要ると分かった時点で `world.Resources.MenuInput` を本番側から差す形へ広げられる。将来拡張として残す。

## コメント

- 点滅アニメ（別 doc）とは独立。本ドライバは選択遷移の挙動確認が主眼で、点滅の脈動そのものは対象にしない。脈動を撮るなら本ドライバの capture を複数フレームに広げてアルファ列をサンプルする使い方はできる。

## 波及: VRT を単一 ebiten インスタンスで回す

現状の VRT はケースごとに `InitVRTWorld` で world を作り `renderStates` で描く。ebitenui のグローバル状態に触れるため `WithUILock` で直列化しており、`t.Parallel` で並べても実際はロック上で待ち合う。並列は名目で、非再入ロックの取り回しとケースごとの構築コストが残る。

`PlayScenario` は本番ループの中でコマンド列を再生し、各ステップを撮れる。これを推し進めると、複数ケースのスクショを1つの ebiten インスタンス上で順番に撮れる。メニューを開き、遷移し、撮り、次へ進む、を1本の再生で回す。並列で走らせないので `WithUILock` による直列化を意識する必要がそもそも無くなり、ケースごとの world 構築や ebitenui ツリーの組み直しを減らせるぶん速くなりうる。

本 doc の主眼は選択遷移の挙動確認で、この単一インスタンス化は `PlayScenario` が開く展望として記す。どこまで1インスタンスへ寄せるか、ケース間の後片付けを決定的に保つ方法は、実在 state の駆動が安定してから別途設計する。

実装で判明した点:

- **import 循環**。`menuloop` のテストが `vrt.WithUILock` を使うため、`vrt` 本体へ `menuloop` 依存を入れると `menuloop テスト → vrt → menuloop` で循環する。`PlayScenario` は `vrt/replay` サブパッケージへ分け、`vrt` 本体を無改造にして避けた。`WithUILock` を低層へ移す案は別ブランチと競合するため採らない。
- **`StateMachine` は値型**。`maingame.NewMainGame(world, sm)` は `StateMachine` のコピーを持つ。ドライバが自前の `StateMachine` を返すと `game.Update` の結果が反映されず遷移を観測できない。駆動も検査も `MainGame` 側へ寄せ、`*MainGame` を返す形にした。
- **遷移の1フレーム遅延**。`StateMachine.Update` は state が返した遷移を次フレーム冒頭で適用する。最後の Action が返した Push/Pop を反映させるため、フレーム数を `len(actions)+1` にする。終端を特別扱いせず一様に回すだけで済み、最後の capture が遷移確定後の画になる。
- **push 直後は1フレーム待つ**。積まれたばかりの `Screen` は `UseTabMenu` の登録が済んでいないため、同じフレームのカーソル移動が効かない。続けて操作するなら `replay.NoInput` を1つ挟む。
