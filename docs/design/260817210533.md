# アイテムのスタックを1つの同一性キーで統一する

## 背景

現状のスタックは品目ごとの真偽フラグに依存する。raw で `Stackable: true` を振ったアイテムだけ `Stackable{Count}` を持ち、個数を数値で保存する。積める品と積めない品の線引きは、実装者が品目ごとに手で決めた恣意的な分類であり、統一的な根拠がない。

同一スタック判定は `query.CanStackWith` が担い、RawID 一致に加えて腐敗品は鮮度段階の一致まで見る。併合時は累積劣化量 `RotAccrued` を個数で加重平均して1つに畳む。これは個体差を消して束を減らす割り切りで、新鮮な品と傷みかけの品が同じ段階なら混ざって鮮度が平均化される。

今後は耐久値や攻撃力のブレなど、個体ごとに異なる状態を足したい。個体差が増えるほど「数値でまとめて保存する」現状の方式は破綻する。加重平均で個体性を消すと、耐久や攻撃力の個体差そのものが失われるためである。現実の物体は本来スタックしない。個数はデータとして保存すべき実体ではなく、同一とみなせる個体を数えた結果にすぎない。

## 要件

- スタック可否と個数を、品目ごとのフラグでなく1つの統一ロジックで判定する。
- 個数はデータとして保存しない。同一とみなせるエンティティを数えた導出値にする。
- 個体差を足すとき、判定ロジックへの追加は最小で済む。耐久や攻撃力のブレは1項の追加で載る。
- 表示は従来どおり「個数 名前」で束ねて見せる。内部が個体でも一覧は煩雑にしない。
- 挙動の土台は現行の同一判定に合わせる。当面は RawID と鮮度段階で束ね、golden 表示は現状に揃える。

## 設計

同一スタック判定を、2要素を比較する述語でなく、アイテム1つから比較可能なキーを返す関数 `stackKey` に一本化する。キーが等しいアイテムだけが同一スタックに属する。スタック数はこのキーで束ねた同値クラスの大きさとして導出し、保存しない。

```go
// stackKey はアイテムのスタック同一性キーを返す唯一の権威。
// キーが等しいアイテムどうしだけが同一スタックに束ねられる。スタック数はこのキーで
// 束ねた同値クラスの大きさとして数え、保存しない。
// 個体差を足すときはキーに1項を加える。鮮度のような連続量は段階へ量子化して束ね、
// 生値のまま持てば1個ずつ個体化する。どちらにするかは項ごとに選ぶ。
type stackKey struct {
	RawID          string // 生成元の同定キー。まず品種が一致すること
	FreshnessStage int    // 腐敗品の鮮度段階。非腐敗品は 0 固定
	// 将来の個体差はここに項を足す。例:
	// DurabilityStage int // 耐久を段階へ量子化して束ねる
	// AttackRoll      int // 攻撃力のブレを生値で持てば1個ずつ個体化する
}

// SameStack は2つのアイテムが同一スタックかを返す。stackKey の等価そのもの。
func SameStack(world w.World, a, b ecs.Entity) bool {
	return StackKeyOf(world, a) == StackKeyOf(world, b)
}
```

個数の保存をやめる。`Stackable` コンポーネントと raw の `Stackable` フラグを廃止し、全アイテムを1個1エンティティで持つ。

```go
// 変更前
type Stackable struct {
	Count int // 所持数
}

// 変更後
// Stackable は廃止する。個数という状態を持つアイテムは存在しない。
// 「5個持つ」は stackKey が等しい5エンティティを持つことで表す。
```

数量を扱う経路は、保存された `Count` の増減から、エンティティ集合の操作へ移す。

- 生成: N 個の生成は、`Count=N` の1エンティティでなく N エンティティを作る。
- 個数取得: `GetEntityCount(entity)` は廃止。代わりに、指定範囲の中で対象と `stackKey` が一致するエンティティ数を返す `StackCountOf` を置く。範囲は呼び出し文脈で変わるので引数で渡す。リロードやクラフトの材料確認はバックパック内だけを数え、総重量は装備と収納も含む所有全体を数える。範囲を固定せず、数える場所を明示的に受け取る形にする。
- 表示: 一覧構築で在庫を `stackKey` ごとに束ね、代表1個と個数で「個数 名前」を出す。束は毎回この場で `stackKey` から作り直し、束の同一性を保存しない。ある個体が次のターンに鮮度段階を跨げば、次の再計算で別の束へ自然に分かれる。分裂を扱う特別な処理は要らない。
- 移動と分割: 「5個移す」は同一スタックから5エンティティを選んで移す。`ChangeItemCount` と `TransferUnits` の数値分割は、エンティティ集合からの選択と移送へ置き換える。
- 併合: `mergeStackableItems` と `RotAccrued` の加重平均は廃止する。個体はそれぞれ独立に劣化し、束ねるのは表示のときだけなので、劣化量を混ぜる処理自体が要らなくなる。
- 重量: `GetEntityWeight` の `Weight × Count` を廃止し、1エンティティは自身の重量そのものにする。総重量は所有エンティティの単純合算になる。

鮮度は各エンティティが独立に進む。同じ品でも拾った順に個別に腐り、平均化されない。攻撃力のブレは、生成時に引いた値を per-item コンポーネントで持ち、`stackKey` に生値で載せれば個体ごとに分かれる。耐久は段階へ量子化してキーに載せれば、同段階どうしは束ね、段階が変われば別スタックへ分かれる。いずれも `stackKey` に項を足す一手で表せる。

弾薬の口径タグ `AmmoTag` はキーに含めない。これは RawID から定まる定数で、同じ RawID なら必ず同じ口径になるため、キーに載せても RawID と重複するだけである。銃に合う弾を探す `FindAmmoInInventory` は、在庫のスタック同一判定とは別物の互換検索である。こちらは口径タグで引く用途を保ち、`Stackable` フィルタだけを外して残す。

## 採用しなかった方法

- **現状維持。`Stackable{Count}` に数を保存する。** 品目ごとに真偽を手で振る恣意的分類が残り、統一ロジックにならない。個体差を足すたび加重平均で個体性が消え、耐久や攻撃力のブレを表現できない。
- **CDDA 型ハイブリッド。個体品と charges で数える量品に2分類する。** 弾薬や液体を charges の数で持ち、それ以外を個体化する。エンティティ数は抑えられるが、品を2分類する手振りが残り「1つの統一ロジックで判定する」要件に反する。統一性を優先して採らない。
- **pairwise な `same(a, b)` を権威にする。** 2要素比較のままでは束ねが O(n^2) になり、拡張時も比較関数の分岐が増える。1つのキー関数に集約すれば O(n) で束ね、拡張はキーへの項の追加で済む。

## コメント

- 着想は CDDA の「均質な量は数でまとめ、個体差のある物は1つずつ持つ」という区別にある。本設計はその区別を品目分類でなく `stackKey` の等価へ写し、ruins の同一判定へ一本化する。
- 唯一の代償はエンティティ数が数量に比例することである。弾薬を多数持つ場面や大量出品でクエリ反復とセーブサイズが膨らむ。想定する数量は、弾薬でマガジン1本あたり数十発、通信販売の同時出品で数百品の桁である。この規模なら ECS の反復コストは許容範囲と見て、当面は導出される数として受け入れる。問題が実測で顕在化したら、スタック単位のキャッシュや量品だけの数値保持を後から足す余地を残す。使わないうちからは足さない。
- `stackKey` は連続量の扱いを項ごとに選べる。鮮度と耐久は段階へ量子化して束ね、攻撃力のブレは生値で個体化する。量子化するほど束が減り、生値にするほど個体に近づく。段階の粗さはゲーム体験に合わせて調整する。
