# ゴールデン画素比較のトレランスを実測に基づき緩和する

## 背景

vrt のゴールデンテストは描画 PNG をピクセル・トレランス比較でゴールデンと突き合わせるが、この比較がフレーキーだった。CI では #545 で8本、#549 の flaky-check でも同型の失敗が出て、main の `-race -count=10` では `TestGolden_Status` が10回中5回、トレランス 0.96% 超過で失敗した。

原因を計測して切り分けた。

- グリフのラスタライズは ebiten text/v2 の純 Go 実装で、同一入力なら環境によらずビット同一になる。ここは犯人でない
- **フレークの正体は GPU 合成の GL 実装差**である。ゴールデン生成マシンとテスト実行環境で Mesa や llvmpipe の版が違うと、アルファブレンドの丸めと AA エッジの補間が系統的にずれる。実測では、コミット済みゴールデンに対するローカル描画の厳密差分が10回連続で**ぴったり 1.322%** だった。ランダムノイズなら値が散る。定数なら系統差である
- 同一環境内でも並列実行でテクスチャアトラスやバッチ順が変わり、差分が境界を挟んでわずかに揺れる。系統差が旧トレランス 0.96% の境界すれすれに座っていたため、この揺れで落ちたり通ったりする境界フレークになっていた

## 設計

`noiseScale` を 8.0 から 17.0 にし、960×720 の全画面ステートでトレランスを約 0.96% から約 2% にする。実測の系統差 1.3% に対して余裕を持たせ、実行順の揺れが乗っても境界に近づかないようにする。

- 変更は係数1つで、コード・CI・運用の形は何も変えない
- 1画素あたり16階調の振幅フィルタは据え置く。差分の「数」の許容だけを広げ、「大きさ」の判定は変えない
- 代償として、全画面ゴールデンは約1.4万ピクセルまでの変化に沈黙する。メニュー1行規模の退行は検出できず、大きな崩れの検出と目視レビュー用に役割が寄る。小さいウィジェット単体のゴールデンは面積が小さいぶん比率が緩くても実害が出にくい

## 採用しなかった方法

- **描画環境のコンテナ固定** — golden の生成と検証を llvmpipe 版固定のコンテナに閉じ込め、系統差を根絶する案。検出力を保てる根治策で、Dockerfile の vrt ステージ・scripts のラッパー・Makefile のコンテナ実行化・CI のイメージ事前ロードまで実装したが、CI の test / flaky-check の実行形が大きく変わり、変更の割に得るものが小さいと判断して破棄した。フレークが再発したら第一の再検討先になる
- **画素 assert の除去** — フレークは消えるが画素退行の検出が全損し、目視だけに頼ることになる。トレランス緩和なら大きな崩れの検出は残せる
- **失敗時のリトライ** — フレークを隠蔽するだけで、境界上にある限りたまたま2回続けて超過すれば結局落ちる
- **ピクセルフォント等の AA レス描画への転換** — AA 勾配が消えれば環境差は振幅トレランスの下に沈む見込みだが、ゲームの見た目を変えるアートディレクション判断をテスト都合で下すことになる。ピクセルフォントを美術として採るなら別途検討する
- **論理内容のテキスト/JSON ゴールデンへの移行** — PR #556 で GoldenText メソッド・型スイッチ・ビューモデルの JSON 直列化の3形態を実装まで試した。いずれも State ごとのコードが残り、維持コストが検出実績に見合わないと判断してクローズした

## コメント

- 診断の決め手は「同一環境では差分が毎回ぴったり 1.322%」という計測だった。フレークは乱数でなく、2つの決定的な環境の間の固定オフセットとトレランス境界の組み合わせだった
- 検討の全経緯とテキストゴールデンの実装はクローズした PR #556 に残っている
