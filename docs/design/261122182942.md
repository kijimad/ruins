# ゲームのコードが名指ししない列挙を raw の表で定義し、列挙と表の一致を CUE で確かめる

## 背景

raw の CUE スキーマには、2種類の行が同じ値で引き合う列挙がある。道具の分類は、道具の行と置物の分解の定義が同じ分類で引き合う。弾の口径は、銃の行と弾の行が同じ口径で引き合う。

道具の分類は、列挙 `#ToolCategory` と表 `toolCategories` の両方で定義している。列挙の値ごとに表の行がちょうど1つあることを、Go の `validateEnumRows` が確かめている。同じ集合を2か所に書き、その一致を Go で検査している。

弾の口径は列挙 `#AmmoTag` だけで定義している。口径を足すにはスキーマを書き換えて生成し直す必要があり、raw の行だけでは足せない。

燃料の種別は、灯りの補充の PR で、raw の表 `fuelKinds` として定義する形にした。灯りが受ける種別と燃料の種別を、どちらもこの表の id から普通の参照で引く。種別を足すのは raw の行1つで済み、列挙と表の二重の定義も無い。道具の分類と弾の口径も、同じ形にできる。

列挙のままにすべき物もある。Go のコードが値ごとに振る舞いを分ける列挙は、Go の定数が要る。鮮度の段階は食べる処理が新鮮を名指しし、時間帯と季節は Go の定数へ写して振る舞いを分け、地図の点の種類は配置の処理が種類ごとに呼び分ける。道具の分類と弾の口径は、Go が値を名指しせず、引き合わせるための鍵として持つだけなので、表にしてよい。

この線引きを、すべての列挙に例外なく当てはめる。ゲームの振る舞いのコードが値を名指ししない列挙は、すべて表にする。開発用の道具 `internal/balance` での名指しは、文字列の id に書き換える。生成される定数を使わなくても、Go が自前の型の定数で同じ値を名指しするなら、名指ししている側に数える。調べた結果、名指ししない列挙は次の7つ。そのうち使える場面は、どこからも読まれていないので、表にせず欄ごと消す。表にするのは残りの6つ。

| 列挙 | 値の数 | 表 |
|---|---|---|
| `#ToolCategory` | 5 | 今の `toolCategories` |
| `#AmmoTag` | 4 | 新しい `ammoKinds` |
| `#Material` | 16 | 今の `materials`。報告表 `internal/balance/baseline.go` の `OIL`・`WOOD` は文字列の id に書き換える |
| `#SkillId` | 25 | 今の `skills`。`internal/balance/growth.go` の `SkillIdFist` は文字列の id に書き換える |
| `#Zone` | 13 | 新しい `zones` |
| `#UsableScene` | 3 | 表にしない。`#Consumable` の `usableScene` の欄ごと消す |
| `#Foliage` | 2 | 今の `foliageEffects` |

## 要件

- ゲームの振る舞いのコードが値を名指ししない列挙は、すべて raw の表の行で定義する。値を足すのは raw の行1つで済む。
- 引き合う両側の行は、どちらも表の id を参照で引く。表に無い id は CUE の検査で落ちる。
- 列挙と表の二重の定義と、その一致を確かめる Go の検査を無くす。
- 列挙の値ごとに行や欄の値をちょうど1つ持つことの検査は、すべて CUE で確かめる。Go の `validateEnumRows` と、その呼び出しをすべて無くす。
- Go の振る舞いは変えない。道具で置物を壊すときの倍率と産出、銃に弾を込める処理は今のまま働く。

## 設計

### 道具の分類

変更前。

```cue
// 道具の分類
#ToolCategory: "prying" | "precision" | "cutting" | "chopping" | "mining"

// 道具の分類の表。合う道具で壊したときに伸ばす技能を持つ
#ToolCategoryDef: {
	id!:    #ToolCategory
	skill?: #SkillId
}

#Tool: {
	categories!: [...#ToolCategory]
	grade!:      #ToolGrade
}

#Disassembly: {
	toolCategory?: #ToolCategory
	// 既存の欄は省略
}
```

変更後。

```cue
// 道具の分類の表。合う道具で壊したときに伸ばす技能を持つ。分類を足すときは raw にこの表の行を1つ足す
#ToolCategory: {
	id!:    #ToolCategoryId
	skill?: #SkillId
}

// 表の id の共通の書式
#TableId: string & strings.MinRunes(1) & strings.MaxRunes(50) & =~"^[a-z0-9][a-z0-9_]*$"

// 道具の分類の id
#ToolCategoryId: #TableId

#Tool: {
	categories!: [...#ToolCategoryId]
	categories_ref: [for x in categories {_toolCategoryIDs[x]}] @rawgen(-)
	grade!: #ToolGrade
}

#Disassembly: {
	toolCategory?: #ToolCategoryId
	if toolCategory != _|_ {
		toolCategory_ref: _toolCategoryIDs[toolCategory] @rawgen(-)
	}
	// 既存の欄は省略
}
```

- `refs.cue` に索引 `_toolCategoryIDs` を置く。索引は `{(x.id): true}` の形で、表に無い id を引くと、その `*_ref` の位置で `_|_` になって落ちる。表 `toolCategories` の行の id の重複は、`#Raws` に新しく足す `toolCategoryIds_unique` で落とす。
- 表の型の名前は、列挙の名前だった `#ToolCategory` を引き継ぐ。行の型の `Def` の接尾辞は、燃料の種別の表 `#FuelKind` にそろえて付けない。
- Go の型は列挙の `rawschema.ToolCategory` から、文字列の id の `rawschema.ToolCategoryId` になる。本番のコードは値を名指ししていないので、型を置き換えるだけで済む。`internal/components/skill_defs.go` の `ToolSkills` の map のキーと、`internal/activity/salvage.go` の比較がこれを使う。`ToolSkills` はリソースで保存されないことを、実装のときに確かめる。
- テストは、生成される定数 `rawschema.Prying`・`Chopping`・`Mining`・`Cutting` を使っている。列挙を消すと定数が無くなるので、文字列の id に書き換える。`ToolCategoryValues()` を使うテストも、表の行から作る形に書き換える。
- `internal/raw/validate.go` の `enumRows` から道具の分類の行を消す。

### 弾の口径

変更前。

```cue
// 弾の口径。銃と弾をこの口径で引き合わせる
#AmmoTag: "9mm" | "rifle" | "shell" | "energy_cell" @rawgen(prefix)

#Fire: {
	ammoTag?: #AmmoTag
	// 既存の欄は省略
}

#Ammo: {
	ammoTag?: #AmmoTag
	// 既存の欄は省略
}
```

変更後。

```cue
// 弾の口径の表。銃が撃てる口径と弾の口径を、この表の id で引き合わせる。口径を足すときは raw にこの表の行を1つ足す
#AmmoKind: {
	id!: #AmmoKindId
}

// 弾の口径の id
#AmmoKindId: #TableId

#Fire: {
	ammoTag?: #AmmoKindId
	if ammoTag != _|_ {
		ammoTag_ref: _ammoKindIDs[ammoTag] @rawgen(-)
	}
	// 既存の欄は省略
}

#Ammo: {
	ammoTag?: #AmmoKindId
	if ammoTag != _|_ {
		ammoTag_ref: _ammoKindIDs[ammoTag] @rawgen(-)
	}
	// 既存の欄は省略
}
```

```toml
[[ammoKinds]]
  id = "9mm"

[[ammoKinds]]
  id = "rifle"

[[ammoKinds]]
  id = "shell"

[[ammoKinds]]
  id = "energy_cell"
```

- 口径の id は `9mm` のように数字で始まる。表の id の書式は、すべての表で共通の型 `#TableId` に1つにまとめ、先頭の数字を許す。
- 欄の名前 `ammoTag` は変えない。銃の側も弾の側も同じ「口径」という性質を表すので、両側で同じ名前が正しい。燃料の種別で灯りの欄を `acceptedFuel`、燃料の欄を `kind` に分けたのは、受ける種別と自分の種別で役割が違ったためで、口径には当たらない。
- テストは、生成される定数 `rawschema.AmmoTagN9mm`・`AmmoTagRifle`・`AmmoTagShell` を使っている。文字列の id に書き換える。
- Go の型は `rawschema.AmmoTag` から `rawschema.AmmoKindId` になる。`internal/components/components.go` の `Fire.AmmoTag`・`Ammo.AmmoTag`、`internal/world/query/inventory.go` の `FindAmmoInInventory`、`internal/raw/raw.go` の写しがこれを使う。
- 表に表示名は持たせない。口径の名前を画面に出すときに足す。

### ほかの列挙

道具の分類と同じ形で、表の型と id の型に分け、参照する欄から索引で引く。

| 列挙 | 表の型と id の型 | 参照する欄 |
|---|---|---|
| `#Material` | `#Material`・`#MaterialId`。今の `#MaterialDef` を引き継ぐ | `#Item` の `material` |
| `#SkillId` | `#Skill` の `id` を `#SkillId` の書式の id にする | `#AttackType` の `skill`、`#ProfessionSkill` の `id`、`#SkillBook` の `targetSkill`、`#ToolCategory` の `skill` |
| `#Zone` | `#Zone`・`#ZoneId` を足す | `#DistrictLayer` の `zones`、`#FacilityZone` の `zone` |
| `#Foliage` | 今の `#FoliageEffect` を表の型に引き継ぐ | `#Tile` の `foliage` |

- `#SkillId` の熟練度 `#ProficiencyId` は、Go が値を名指しするので列挙のまま残す。
- `#UsableScene` は表にせず、列挙と、`#Consumable` の `usableScene` の欄と、`internal/components/components.go` の `UsableScene` の欄を消す。テストの中の TOML の文字列 `UsableScene = "ANY"` はコンパイルで捕まらないので、grep で探して消す。Go は `internal/raw/raw.go` でコンポーネントに写すだけで、どこからも読んでいない。読まない値のために表を足すより、消すほうが単純になる。使う場面を分ける仕組みが要るときに、そのとき要る形で足す。
- 型の名前を引き継ぐときは、道具の分類と同じく、表の型を素の名前にし、`Def` の接尾辞を付けない。
- 表の id の書式は、すべての表で `#TableId` の小文字のスネークケースにそろえる。6つの id の型は `#TableId` を使うだけにする。列挙のまま残す値、たとえば `#Element` の `NONE` は変えない。材質の `WOOD`・`OIL` などは大文字なので、小文字に改める。raw の行と、定数から書き換えるテストの文字列も小文字にする。表ごとに書式を変えるより、id の書式を1つにそろえることを優先する。保存データの値も変わるが、セーブの後方互換は考慮しない。
- 植生の欄のゼロ値 `""` は「植生なし」の意味のまま使う。`""` は表の id にならないので、意味は変わらない。
- id の型にすると、Go に書いた文字列の綴りの誤りはコンパイルで捕まらなくなる。対象は開発用の道具の `oil`・`wood`・`fist` と、テストで定数から書き換える文字列。ゲームの振る舞いのコードは値を名指ししないので、この代償を受け入れる。`material.go` の「enum で比較のタイプミスを型が弾く」というコメントも書き換える。
- 表の行の id の重複を落とす `_unique` の検査を、`#Raws` に足す。今は材質と植生の表の id の重複を `validateEnumRows` が落としていて、`validateEnumRows` を消すと検査がどこにも残らないため。足すのは `toolCategoryIds_unique`・`ammoKindIds_unique`・`materialIds_unique`・`foliageEffectIds_unique`・`zoneIds_unique`。名前は、既存の `attackTypeIds_unique` と同じく、型の名前でなく表の名前から付ける。技能は `skillIds_unique` が既にある。
- 型が変わるコンポーネントの欄が保存の対象になるかを、実装のときに確かめる。対象は `internal/components/skills.go` の `Skills.Data` の map のキー、`book.go` の `TargetSkill`、`material.go` の `Material.Kind`、`tile_environment.go` の `TileEnvironment.Foliage`、`components.go` の `Fire.AmmoTag`・`Ammo.AmmoTag`、欄ごと消す `Consumable.UsableScene`、リソースの `ToolSkills`。下の型は文字列のままで、保存の形は変わらないはず。`SkillIdValues()` は一致の検査だけが使い、表示の順には使っていない。
- 区域の型は、`internal/overworld/urban.go` の `zoneCatalog` と `zoneAt`・`rollFacilityInZone`、`internal/overworld/building.go`、`internal/raw/validate.go` の `DistrictZones`・`validateZoneBaseFacilities` が使う。名指しは無いので型を置き換えるだけで済む。

### 列挙のまま残すもの

| 列挙 | 残す理由 |
|---|---|
| `#FreshnessStageId` | 食べる処理が新鮮の段階を名指しする |
| `#TimeOfDayId`・`#SeasonId` | raw の値を Go の時間帯と季節の定数へ写し、振る舞いを分ける |
| `#PointFeatureKind` | 地図の配置の処理が集落と目印を呼び分ける |
| `#ConditionDeathCause` | 生成される定数は使わないが、raw の値を Go の `DeathCause` へ写し、その定数で名指しする |
| `#Element`・`#ProficiencyId` ほか | Go のコードが値ごとに振る舞いを分ける |

### 列挙と表の一致を CUE で確かめる

列挙のまま残す物は、値の集合を閉じておくためのもので、表にするのではない。値の集合は Go のコードとの約束で、振る舞いを持つ側の Go がコンパイルで確かめられる形にしておく。表を raw の行で開くと、Go が名指しする値を raw から消しても、コンパイルが通ったまま実行時に壊れる。

列挙の値ごとに行や欄の値がちょうど1つあることを、今は Go の `internal/raw/validate.go` の `validateEnumRows` で確かめている。対象は次のとおりで、すべて CUE に移す。

| 列挙 | 値を集める所 | 検査を置く所 |
|---|---|---|
| `#FreshnessStageId` | 表 `freshnessStages` の行の id | `#Complete` |
| `#TimeOfDayId` | 表 `timesOfDay` の行の id | `#Complete` |
| `#SeasonId` | 表 `seasons` の行の id | `#Complete` |
| `#PointFeatureKind` | 表 `pointFeatures` の行の id | `#Complete` |
| `#WeatherId` | 表 `weathers` の行の id | `#Complete` |
| `#SeasonId` | 天気の行ごとの季節の重みの id | `#Complete`。天気の行の添字ごとにループで置く |
| `#Shelter`・`#WaterExposure` | 表 `shelterEffects`・`waterEffects` の行の id | `#Complete` |
| `#HungerStageId`・`#FatigueStageId` | 表 `hungerStages`・`fatigueStages` の行の id | `#Complete` |
| `#ProficiencyId` | 技能の行の中の熟練度の id を全ての技能から集めた物 | `#Complete` |
| `#AttackCategory` | 表 `attackTypes` の行の id | `#Complete` |
| `#ConditionOnset` | 不調の行の発症の欄から集めた値 | `#Complete` |
| `#GlyphChunk` | 地図の記号の行のチャンクの欄から集めた値 | `#Complete` |
| `#Element` | 熟練度の耐性の欄から集めた値と `NONE` | `#Complete` |

表にする6つの列挙は、値の集合を表そのものが決めるので、この検査から外れる。欄ごと消す使える場面も外れる。

行の並びの形はそのままにし、行の id から作った struct と、列挙の値を必須のキーに持つ struct を重ねる検査を置く。検査は `#Raws` でなく、検査だけを持つ別の定義 `#Complete` に置く。`#Raws` は型と参照だけを求め、`#Complete` は表が揃っていることを求める。

```cue
#Complete: {
	// 鮮度の段階の表は、列挙の値ごとに行をちょうど1つ持つ。欠けた値は必須のキーで、
	// 列挙に無い id は閉じた struct で、重なった id は値の衝突で落ちる
	freshnessStages_complete: close({
		fresh!:  _
		stale!:  _
		rotten!: _
	}) & {if freshnessStages != _|_ for i, x in freshnessStages {(x.id): i}}
} @rawgen(-)
```

- 上の表のすべてに同じ形の検査を置き、`validateEnumRows` と、その呼び出しをすべて消す。行の欄や入れ子の表から値を集めるものも、集めた値で struct を作って同じ形で重ねる。
- 2重のループで集める `#ProficiencyId`・`#Element` は、struct の値を既存の `proficiencyIds_unique` と同じ `"skills.\(i).proficiencies.\(j)"` の形にする。値が raw のパスとして読めるので、重なりの報告からどの行かを追える。片方の添字だけだと、別の技能の同じ添字どうしで値が一致し、`#Element` の重なりが衝突として報告されないことがある。
- 行の id を集める検査のうち、`_unique` の検査もある熟練度・攻撃の種類・地図の点では、id の重なりが `#Raws` の `_unique` と `#Complete` の両方から報告される。報告が2つ出るだけで結果は正しいので、受け入れる。`_unique` の無い鮮度・時間帯・季節・天気・囲い・水・空腹・疲労の表と、行の id でなく欄の値を集める `#Element`・`#ConditionOnset`・`#GlyphChunk` では、`#Complete` だけが重なりを落とす。地図の記号の `mapGlyphIds_unique` は行の `id` を見るので、`chunk` の欄の重なりには関わらない。
- 天気の行ごとの季節の検査は、外側のキーを天気の id でなく行の添字にする。`{for i, w in weathers {"\(i)": close({…}) & {…}}}` の形。天気の id で束ねると、天気の id が重なったときに2つの行の季節が1つに合わさり、天気の重なりの報告に季節の重なりの報告が混ざる。
- 欄が無い行がある `#ConditionOnset` は、`if x.onset != _|_` で欄の無い不調を飛ばして集める。
- `validateResists` の「`NONE` で耐性を持つ熟練度は誤り」という検査も CUE に移す。熟練度の `resists` の欄に直に `#Element & !="NONE"` と書く。生成器の `andType` は `a & b` の型の側を使うので、Go の型は `*Element` のままで、`raw.go` の写しも変わらない。`#ResistElement` のような新しい定義にすると、生成器が別の Go の型を作り、型の変換が広がるので採らない。`"NONE"` を一致の検査の struct に最初から入れて衝突で落とす形は、エラーが重なりとして報告され意図とずれるので採らない。`validateResists` と `errResistNone` を消し、`internal/raw/condition_test.go` の該当する行を `rawcheck` のテストへ移す。
- 地図の点の種類のように `@rawgen(prefix)` を持つ列挙も、必須のキーは列挙の値そのもので書く。たとえば `settlement!: _`。
- 列挙の値を、列挙と検査の必須のキーの2か所に書く。CUE の `or()` を使えば値の並びから選言を作れるが、生成器 `internal/rawschema/gen` は列挙を選言の式として読むので、`or()` で書いた列挙を読めない。値を足すときは2か所を直す。どちらかを忘れると CUE が落とすので、食い違いは残らない。
- 検査は表の外の `#Complete` に置く。表の行の定義の中で表自身から作った索引を引くと評価が循環する。
- `#Complete` は `#Raws` を重ねず、検査だけを持つ。`#Raws & {…}` の形は、右辺から `freshnessStages` を名前で引けずにコンパイルできず、欄を宣言し直すと閉じた定義どうしの `&` で拒まれる。検査はパッケージの最上位の表を引く。`refs.cue` の索引と同じく、検査が引く表を最上位に宣言する。今の `refs.cue` に無い `freshnessStages`・`timesOfDay`・`seasons`・`pointFeatures`・`weathers`・`shelterEffects`・`waterEffects`・`hungerStages`・`fatigueStages`・`attackTypes`・`mapGlyphs` を足す。
- `rawcheck` に `ValidateComplete` を足す。今の `Validate` と同じく、パッケージの最上位に `raws` を重ねて検証し、続けて同じ値の `#Complete` の部分を検証する。`#Complete` だけを引いて `raws` を重ねると、最上位の表が空のままになり、索引が空になって正しいデータでも `*_ref` がすべて落ちるので、そうしない。違反の位置は `#Complete.<名前>_complete.<値>` になり、`rawcheck` のテストで `Paths()` を比べるときの期待値になる。
- 今の `Validate` は変えない。部分の fixture を使う `rawcheck` のテスト、たとえば空の `Raws{}` が通ることを主張する `internal/raw/validate_test.go` の `TestSchema_空のRawsは通る` や、`refs_test.go` の `makeRefRaws` で作る1行ずつの表は、`Validate` だけを通るので巻き込まれない。実データを検証する `TestValidate_実データが通る` は `ValidateComplete` に替える。`ValidateComplete` は `Validate` の検査を含むので、`Validate` を別に呼ばない。
- 生成器 `internal/rawschema/gen` は、最上位の `#` で始まる定義をすべて Go の型にし、`@rawgen(-)` は欄の単位でしか読まない。定義の単位の `@rawgen(-)` も読んで飛ばすようにし、`#Complete` を Go の型にしない。`writeDecl` は最上位の宣言の `rawgenAttrs` を既に読んでいるので、そこで `-` を見て戻るだけで済む。隠し定義 `_#Complete` にすると生成器からは外れるが、Go から引くのに `cue.Hid` とパッケージのパスが要り、`ValidateComplete` が複雑になるので採らない。
- 閉じた struct と必須のキーの重ね合わせで、欠けは `field is required but not present`、余りは `field not allowed`、重なりは `conflicting values` として、それぞれ `#Complete.<名前>_complete.<値>` の位置に別々に報告される。レビューで `cuelang.org/go v0.17.1` で評価して確かめた。重なりの報告には行の添字が値として出るので、どの行か追える。報告の位置は raw.toml の行でなくスキーマの位置なので、実データのテストが落ちたときの手がかりはパスと添字になる。
- `#Complete` の検査は表の有無に関わらず常に効かせる。表は `#Raws` の任意の欄のまま残し、表が無いことは検査の必須のキーで落とす。表が無いときは `if … != _|_` の分岐で検査の内側が空の struct になり、必須のキーが欠けて落ちる。表を必須の欄にすると、生成器が任意の欄だけを `*[]T` にするので Go の型が `[]T` に変わり、`PtrSlice(raws.X)` などの約80か所を書き換えることになるので、そうしない。Go の `internal/raw/validate.go` の `required` の一覧から、一致の検査が表の欠けを落とす `weathers`・`shelterEffects`・`waterEffects`・`hungerStages`・`fatigueStages` を消す。`foliageEffects` は表にするので一致の検査から外れ、`dungeons` と `settlements` は一致の検査に関わらないので、この3つは `required` に残す。
- 一致の検査と表の欠けの検査は、起動のときの Go から、CI で走る CUE に移る。`LoadFromFile` は起動のたびに `validateEnumRows` と `required` を走らせているが、`rawcheck` は本番のコードから呼ばれない。`internal/rawschema/doc.go` に書いたとおり、ゲームの本体に CUE を持ち込まない方針なので、起動のときには検査しない。`raw.toml` は `assets.FS` に埋め込まれ、CI の `TestValidate_実データが通る` が同じ物を検査するので、検査の漏れは起きない。

タイルの生成の仕様が同じ表のタイルを指す `tileSpawns_ref` は、表が自分自身を参照する形で、種別を別の表に分けても解消しない。今の `#Raws` に置いた形のままにする。

## 採用しなかった方法

- 材質を例外として列挙に残す: アイテムの行の多くとテストが定数を使い、置き換えが大きい。ただ、例外を作ると線引きが1つでなくなる。工数より一貫性を優先する。
- 道具の分類を列挙のまま残し、一致の検査だけ CUE に移す: Go が値を名指ししないのに、二重の定義と、足すたびにスキーマと raw の両方を直す手間が残る。一致の検査を CUE に移すのは、Go が値を名指しする列挙に限る。
- 弾の口径の欄を両側で別の名前にする: 燃料の種別とそろえて見えるが、口径は銃と弾で同じ性質なので、同じ名前が正しい。
- 列挙のまま残す物の表を、列挙の値をキーにした対応表の形にする: `[freshnessStages.fresh]` のように書き、キーを必須にすれば行の欠けを CUE が落とす。ただ、raw の TOML の書き方と、表を読む Go の処理が変わる。鮮度の段階は並びの順に意味があり、対応表にすると順が失われる。並びの形のまま確かめる案で足りる。
- 生成器を `or()` で書いた列挙に対応させ、値を1か所に書く: 列挙の値を並びに書き、そこから列挙と検査の両方を導ける。ただ、生成器が CUE の評価の結果から列挙を読むように作り直す必要があり、この設計の目的に対して大きい。2か所に書いても、片方を忘れれば CUE が落とすので食い違いは残らない。
- `#SkillId` を例外として列挙に残す: 型として広く使われ置き換えが大きいが、例外を作ると「なぜ外したか」を別に持つことになり、線引きが1つでなくなる。
- 一致の検査に関わる表を `#Raws` の必須の欄にする: 表が無いことを欄の必須で落とせるが、生成器が任意の欄だけを `*[]T` にするので Go の型が `[]T` に変わり、`PtrSlice` などの約80か所を書き換えることになる。検査の必須のキーで同じことを落とせるので、表は任意のまま残す。
- 一致の検査を `#Raws` に置く: 空の `Raws{}` が通ることを主張するテストや、1行ずつの表で作る fixture のテストが、表の欠けで落ちる。型と参照の検査と、表が揃っていることの検査は役割が違うので、定義を分ける。
- fixture をすべて、全部の列挙を満たす形に太らせる: fixture が実データとほぼ同じ大きさになり、列挙に値を足すたびに fixture も直すことになる。
- 表ごとに id の書式を変え、口径だけ先頭の数字を許す: 書式が表の数だけ散る。共通の型1つにまとめれば、そろえる方針がスキーマの上でも1か所になる。
- 一致の検査を、設計に挙げた4つの表だけ CUE に移す: 差分は小さいが、Go と CUE の2つの検査が並んで残り、次に列挙を足す人がどちらに合わせるか迷う。すべてを CUE に移して検査の仕組みを1つにする。
- 列挙と表の型の名前を `Def` の接尾辞で区別したままにする: 列挙を消すと区別する相手が無くなる。燃料の種別の表 `#FuelKind` にそろえ、表の型を素の名前にする。
