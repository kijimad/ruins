# ゲームの識別子と調整値を raw へ移す

## 背景

ゲームの設定の多くが Go に直接書かれている。数値の調整はコードの変更になり、raw から参照している識別子の実在も確かめられない。

| 設定 | 場所 |
|---|---|
| 不調の値。痛み、機能低下、回復の仕方と速さ、出血、死因、表示名と説明 | `conditionDefs`。参考 codebase: `internal/components/health_status.go:119` |
| 怪我が起こりうる部位 | `conditionDefs.parts` と `ConditionCanAffect` |
| 部位の表示名、身体機能、命中の重み | `bodyPartMetas`。参考 codebase: `health_status.go:255` |
| 攻撃の種類が負わせる怪我 | `injuryTypeFor` の switch。参考 codebase: `internal/activity/injury.go:25` |
| スキルの名前、説明、能力値、カテゴリ、熟練の係数 | `internal/components/skills.go`、`proficiency.go` |
| 内装の Ref から raw の prop と item group への対応、置き方の既定 | `internal/mapplanner/interior/prop.go`、`loot.go`、`archetype.go` |
| 天候の効果と期間、季節ごとの出やすさ | `internal/components/weather.go`、`internal/world/query/weather.go:19` |

raw はすでにこれらの識別子を文字列で参照しているが、検証が足りない。

- アイテムの `treats` は不調を、本と職業はスキルを指すが、実在を確かめていない。参考 codebase: `internal/raw/raw.go:223`、`:292`
- 部位は表示名がそのまま識別子を兼ね、表示名は翻訳の msgid でもある。表示を直すと参照が壊れる
- 攻撃の種類の値 `CANON` とスキル `cannon` は綴りが違う

## 要件

1. ゲームの識別子を raw の正式な id にそろえ、表示名と分ける。raw からの参照はすべて読み込み時に実在を検証する。
2. 調整値と、片側が持てば足りる参照は raw の行のフィールドに書く。多対多の参照は、持ち主の行に型の付いた id の配列で書く。
3. 関係を表す汎用の仕組み、たとえば `object#relation@subject` 型のタプルは作らない。
4. 段ごとに挙動を変えない。今の値と関係をそのまま移す。

## 設計

### 方針

- **値と参照は持ち主の行に書く。** 1つの関係は持ち主の行の1か所だけに書く。tsp の型と editor-ui の型の検査がそのまま効く。
- **識別子と表示名を分ける。** 行は `id` と `name` を別に持つ。`name` は翻訳の msgid、`id` は参照のためだけに使う。
- **コードが名前で分岐する識別子は Go の定数を残す。** 定数すべてに raw の行があることを読み込み時に検証し、両者のずれを止める。
- **コードの構造に結びついたものは Go に残す。** 部位の集合は身体機能の計算の配列の添字、空腹と疲労の段階の種類は分岐の名前、間取りのプランナーは関数なので移さない。
- **表の書き方は設計 doc 261109230757 にそろえる。** 選ばれる物を指すフィールドは `id`、重みは浮動小数の `weight`、何も出ないことは `nothing` で表す。重みで引く処理は `consts.Pick` を使い、raw から読んだ重みをそのまま渡す。

タプルを採らない理由は、移したい関係の大半が重み・個数・座標・順序のような属性を持つか、片側が持てば足りる1対1の参照だから。属性を持たない多対多は30〜40件ほどで、専用の仕組みに見合わない。

### 段

| 段 | 移すもの | 識別子 |
|---|---|---|
| 1 | 不調の値、怪我の部位、部位の命中の重み | 不調、部位 |
| 2 | スキルの名前・説明・能力値・カテゴリ・熟練の係数、攻撃の種類が負わせる怪我 | スキル、攻撃の種類 |
| 3 | 内装の Ref の対応と置き方の既定、生活感・荒廃・変種・目玉の置物の重みの表 | 内装の Ref |
| 4 | 天候の効果と期間、季節ごとの出やすさ、空腹と疲労の段階の境目 | 天候 |

3段目の重みの表は、#948 で `choice` の一覧として Go に書かれた。参考 codebase: `internal/mapplanner/interior/profile.go:82`、`hero.go:25`。境界値の switch でなく重みの並びになったので、そのまま raw の行へ移せる。4段目の天候の遷移も `consts.Pick` で引くようになり、季節ごとの重みを raw から渡すだけで済む。

表の書き方の変更は #949 で tsp と raw に入り、261109230757 は完了した。同じ raw.toml と tsp を同時に書き換える衝突の心配は無くなったので、1段目から着手できる。

以下は段ごとの設計。

### 1段目: 不調と部位

```toml
[[conditions]]
id = "fracture"
name = "Fracture"
description = "A broken bone. It will not heal until treated."
painPerSeverity = 18
bodyFuncDropPerSeverity = 20
recovery = "recover_after_tend"
recoverPer = 1
parts = ["arm", "hand", "leg", "foot"]

[[bodyParts]]
id = "arm"
name = "Arm"
hitWeight = 3.0
```

- `parts` を省いた不調は全部位に起こりうる。今の `ConditionCanAffect` の規則と同じ。
- `recovery` を省いた不調は ConditionSystem の管轄外になる。低体温と、量から導く過労と栄養失調が当たる。
- 部位の集合と身体機能との対応は Go の `bodyPartMetas` に残し、`id` を足す。raw の `bodyParts` は命中の重みと表示名だけを持ち、Go の部位すべてに行があることを検証する。命中の重みは `consts.Pick` に渡すので、表の重みと同じスカラー `EntryWeight` で型を付ける。参考 codebase: `oas/typespec/types.tsp:85`
- アイテムの `treats` はすでにスカラー `ConditionTypeName` の配列で型が付いている。参考 codebase: `oas/typespec/req.tsp:21`。値を新しい不調の id にそろえ、実在の検証を足す。
- 怪我の命中部位は、今の `hitPart` が `ConditionCanAffect` と `BodyPartHitWeight` で重みを作って `consts.Pick` で引いている。参考 codebase: `internal/activity/injury.go`。この重みの出どころを、不調の行の `parts` と raw の部位の `hitWeight` に替える。
- 不調には Go の名前の定数を置かない。コードが知るのは不調の名前でなく、不調を起こす仕組みとする。仕組みを Go の enum `ConditionOnset` にし、どの不調がどの仕組みで起こるかを不調の行の `onset` に書く。コードは `ByOnset` で仕組みから不調を引く。
- 攻撃で負う怪我は攻撃の種類の `injury` から引くので `onset` を持たない。きっかけの無い肝疾患も持たない。
- 量から導出する不調かどうかは、`onset` が疲労か空腹かで決まる。

```toml
[[conditions]]
id = "hypothermia"
onset = "cold"
```

```go
// 変更前
const ConditionHypothermia ConditionType = "Hypothermia"

// 変更後
type ConditionOnset string

const (
	OnsetCold       ConditionOnset = "cold"        // 体温が下がると TemperatureSystem が進める
	OnsetRottenFood ConditionOnset = "rotten_food" // 腐敗食を食べると確率で発症する
	OnsetFatigue    ConditionOnset = "fatigue"     // 疲労の量から読み取り時に導出する
	OnsetHunger     ConditionOnset = "hunger"      // 空腹の量から読み取り時に導出する
)

func (d ConditionDefs) ByOnset(o ConditionOnset) ConditionType
func (d ConditionDefs) IsDerived(ct ConditionType) bool
func (d ConditionDefs) Types() []ConditionType
```

- デバッグメニューの不調の付与も表から組み立てる。寒さによる不調は全身に、ほかは起こりうる最初の部位に、部位を限らない不調は胴に付ける。

### 不調の値の読み方

`components` の関数は `world` を受け取らずに `conditionDefs` を読んでいる。`raw` は `components` を import しているので、`components` から raw を読むと import が循環する。

そこで、不調の値の表 `ConditionDefs` を読み込み時に1度だけ組み立てて `world.Resources` に持ち、定義を読む `HealthStatus` のメソッドへ引数で渡す。対象は `BodyFuncs`、`ConsciousnessDrops`、`LocalDrop`、`BloodLossHPDrain`、`IsHPDraining` と、その内部の関数。本番の呼び出し元はどれも `world` を持つ。`components` のテストは、必要な不調だけを書いた表をテストの中で組み立てて渡す。

```go
// components
type ConditionDefs struct{ /* 不調ごとの ConditionDef と部位ごとの命中の重み */ }
func NewConditionDefs(conds map[ConditionType]ConditionDef, hitWeights [BodyPartCount]float64) ConditionDefs
func (d ConditionDefs) Def(ct ConditionType) (ConditionDef, bool)
func (d ConditionDefs) CanAffect(ct ConditionType, part BodyPart) bool
func (d ConditionDefs) HitWeight(part BodyPart) float64
func (d ConditionDefs) BodyFuncImpact(cond *HealthCondition, part BodyPart) (pain int, bodyFunc BodyFuncKind, drop int)
func (d ConditionDefs) BloodDrop(cond *HealthCondition) int
func (hs *HealthStatus) BodyFuncs(defs ConditionDefs, needConds ...HealthCondition) BodyFuncs

// raw
func NewConditionDefs(raws oapi.Raws) (gc.ConditionDefs, error)

// query
func ConditionName(world w.World, ct gc.ConditionType) string
func ConditionDescription(world w.World, ct gc.ConditionType) string
```

不調1件を読む関数は表のメソッドにし、`HealthStatus` 全体を畳むメソッドは表を引数で受け取る。表示名と説明は訳を通すので query が引く。

仕組みごとの不調と、部位すべてに行があることの検証は、部分的な raw を組み立てるテストを妨げないよう、参照の検証 `ValidateReferences` と分けて `LoadFromFile` だけが行う。

### 検証

読み込み時に次を確かめる。

- `conditions` と `bodyParts` の id が一意で、部位すべてに行がある。
- `onset` の値それぞれを、ちょうど1つの不調が持つ。
- 不調の `parts` が実在する部位を指し、全身を含まない。
- アイテムの `treats` が実在する不調を指す。
- 怪我の種類すべてに、起こりうる部位が1つ以上ある。抽選の対象が空になって panic するのを止める。

不調と部位の `name` と `description` は表示されるので、raw の訳の網羅テスト `TestRawTranslationCoverage` の対象に加える。

### 2段目: スキルと攻撃種別

```toml
[[skills]]
id = "sword"
name = "Swordsmanship"
summary = "Technique for handling swords"
gainedBy = "Raised by attacking with swords"
effect = "Increases sword damage and accuracy"
ability = "str"
category = "melee"
[[skills.proficiencies]]
id = "sword_damage"
perLevel = 5
[[skills.proficiencies]]
id = "sword_accuracy"
perLevel = 3

[[skillCategories]]
id = "melee"
name = "Melee"

[[attackTypes]]
id = "cannon"
injury = "fracture"
```

- スキルの表示名、概要、獲得条件、効果、能力値、カテゴリを `skills` の行に書く。カテゴリは `skillCategories` の行の順に、カテゴリ内のスキルは `skills` の行の順に表示する。
- 熟練の効果倍率は、倍率を左右するスキルの行の `proficiencies` に id とスキルLv1あたりの変化量 `perLevel` で書く。1つの倍率を持つスキルは1つなので、持ち主の行に書けば参照が1か所で済む。
- 攻撃種別の値を小文字の id にそろえ、`CANON` を `cannon` に直す。武器の攻撃種別は同じ名前の武器スキルで上達するので、`weaponSkillMap` を消して `WeaponSkillID` は id をそのままスキルにする。`AttackCanon` も `AttackCannon` に改名する。
- 攻撃種別が負わせる怪我を `attackTypes` の行の `injury` に書き、`injuryTypeFor` の switch を消す。怪我の表なので `ConditionDefs.Injury` が引く。

```go
// components
type SkillDefs struct {
	Skills        map[SkillID]SkillDef
	Categories    []SkillCategory // 表示順
	Proficiencies map[ProficiencyKey]ProficiencyDef
}
func (d SkillDefs) Name(id SkillID) string
func (d SkillDefs) Ability(id SkillID) AbilityID
func (d SkillDefs) ProficiencyValue(skills *Skills, abils *Abilities, bodyFuncs BodyFuncs, key ProficiencyKey) consts.Percent
func (d SkillDefs) ProficiencySources(skills *Skills, abils *Abilities, bodyFuncs BodyFuncs, key ProficiencyKey) []ProficiencySource
func (d ConditionDefs) Injury(at AttackType) (ConditionType, bool)

// raw
func NewSkillDefs(raws oapi.Raws) (gc.SkillDefs, error)

// query
func SkillName(world w.World, id gc.SkillID) string
```

Go に残すもの。

- `SkillID` と `ProficiencyKey` の定数。値の集合は tsp の enum `SkillId` と `ProficiencyId` が持ち、Go の定数は生成された enum の定数から定義する。enum に無い値はコンパイルで弾かれ、enum の値それぞれに raw の行がちょうど1つあることを読み込み時に確かめる。Go に全スキルの一覧は置かず、`Skills` はスキルを初めて読んだときに値0で作る。

```go
const SkillSword = SkillID(oapi.SkillIdSword)
const ProfSwordDamage = ProficiencyKey(oapi.ProficiencyIdSwordDamage)
```
- `WeaponSkillIDs`、`WeaponDamageKey`、`WeaponAccuracyKey`、元素の耐性キー。武器スキルとダメージ・命中のキーの対応は計算の構造で、名前から導ける。武器の効果倍率を同じ名前の武器スキルが持つことを検証する。
- 攻撃種別の射程、近接と遠隔の区分、表示ラベル。命中と射程の計算の構造なので移さない。

検証。

- スキル、カテゴリ、攻撃種別の id と、スキルをまたいだ効果倍率の id が一意。
- スキルのカテゴリ、本の `targetSkill`、職業のスキル、攻撃種別の `injury` が実在する。
- Go のスキル、効果キー、攻撃種別すべてに行があり、Go に無いスキルと効果キーの行が無い。

| ファイル | 変更内容 |
|---|---|
| `oas/typespec/` + 生成物 | `Skill`、`SkillProficiency`、`SkillCategory`、`AttackType`、`AbilityId`。`AttackCategory` を小文字に |
| `assets/metadata/entities/raw/raw.toml` | `[[skills]]` 24行、`[[skillCategories]]` 6行、`[[attackTypes]]` 7行。アイテムの `attackCategory` を小文字に |
| `internal/components/skills.go`、`proficiency.go`、`skill_defs.go` | 名前、説明、能力値、カテゴリ、係数の表を消し、`SkillDefs` にする |
| `internal/activity/injury.go` | `injuryTypeFor` を消し `ConditionDefs.Injury` を引く |
| `internal/balance/` | 熟練の倍率を raw から組み立てた `SkillDefs` で求める |

採用しなかった方法。

- **効果倍率を `[[proficiencies]]` の独立した行にしてスキルを参照する**: 持ち主のスキルの行に書けば参照が1か所で済み、スキルの実在の検証も要らない。
- **攻撃種別の行にスキルの参照を持たせる**: 武器の攻撃種別と武器スキルは同じ名前で1対1になったので、参照を書くと同じことを2か所で言うことになる。
- **武器のダメージと命中の行を Go で生成し係数だけ raw に置く**: 係数の置き場所が他の効果倍率と分かれる。14行を明示して書くほうが1行を見て値が分かる。
- **ログのスキル名を訳す**: 読書と分解でスキルが上がったときのログはスキル名を訳さずに出しているが、挙動を変えない方針なのでこの段では直さない。

### 3段目: 内装の Ref

```toml
[[interiorRefs]]
id = "register"
prop = "register"
placement = "near_door"
[[interiorRefs]]
id = "snacks"
itemGroup = "food"
placement = "center"
[[interiorRefs]]
id = "litter"
placement = "full_area"

[[interiorProfile.damages]]
id = "intact"
weight = 2.0
[[interiorProfile.densities]]
factor = 6
weight = 1.0
[[interiorProfile.heroes]]
id = "atmosphere"
weight = 25.0
refs = ["torii", "phonograph", "komainu", "pillar"]
```

- 内装レシピの Ref ごとに、置く prop、床 loot の item group、既定の置き方を `interiorRefs` の1行に書く。`propRaw`、`lootRaw`、`defaultArchetypes` の3つの表は同じ Ref を鍵にしていたので1つの行にまとまる。
- 既定の置き方は raw のレシピを `Content` へ変換する `toContent` で埋める。`Content.Resolve` は置き方の無い Stuff を全域へ倒すだけになり、表を引かない。
- 建物の生活感の損傷、散らかり、変種、家具量と、hero 部屋の目玉の重みを `interiorProfile` に書く。hero は種類ごとに重みと Ref の一覧を持ち、選んだ種類の一覧から1つを一様に引く。`heroKind` の switch は消える。
- `consts.PickUniform` は重み1の `consts.Pick` なので、家具量と目玉の Ref を重みの表へ移しても同じ seed で同じ値を引く。

```go
// interior
func PropRawName(raws oapi.Raws, ref string) (string, bool)
func LootGroupName(raws oapi.Raws, ref string) (string, bool)
func toContent(raws oapi.Raws, ic oapi.InteriorContent) (Content, error)
func newProfileTable(raws oapi.Raws) (profileTable, error)
func rollProfile(t profileTable, seed uint64) buildingProfile
func heroCenterpiece(t profileTable, seed uint64) (string, bool)
```

interior はもとから `oapi.Raws` を受け取って内装を作るので、1段目と2段目のような `world.Resources` の表は作らず、raw を直接引く。

Go に残すもの。

- 損傷、散らかり、変種の段階の定数。経年、外皮、塀の処理がこの名前で分岐する。raw の行は enum の値で書き、Go は enum から定数へ写す。
- variant が他の軸を上書きする規則、散らかりの小物の割合と役割ごとの小物、12棟に1棟という hero の頻度、経年・外皮・塀の値。どれも処理の分岐に埋まった値で、重みの表ではない。

検証。

- Ref の id が一意で、`prop` が props に、`itemGroup` が itemGroups か itemCollections にある。
- 損傷、散らかり、変種の行が OpenAPI スキーマの enum の値をちょうど1回ずつ持つ。enum の値の一覧はスキーマから読む。
- hero の Ref が prop を持つ Ref である。

| ファイル | 変更内容 |
|---|---|
| `oas/typespec/` + 生成物 | `InteriorRef`、`InteriorProfile` と各軸の choice、`BuildingDamage`、`BuildingClutter`、`BuildingVariant` |
| `assets/metadata/entities/raw/raw.toml` | `[[interiorRefs]]` 59行、`interiorProfile` |
| `internal/mapplanner/interior/prop.go`、`loot.go`、`archetype.go` | 3つの表を消し、raw の `interiorRefs` を引く |
| `internal/mapplanner/interior/profile.go`、`hero.go` | 重みの一覧を raw の `interiorProfile` から組む |
| `internal/overworld/`、`internal/balance/` | `PropRawName` と `LootGroupName` に raw を渡す |

採用しなかった方法。

- **既定の置き方を props の行に持たせる**: Ref は prop と1対1でない。`waitchair` と `chair` は同じ prop で置き方が違い、`snacks` や `litter` は prop を持たない。
- **interiorContents の各 Stuff に置き方を必ず書く**: 同じ家具型の置き方がレシピごとに散り、食い違いを防げない。
- **損傷などの重みを段階ごとの固定フィールド `intact = 2.0` で書く**: スキーマだけで欠けを止められるが、表の書き方 `id` と `weight` から外れる。enum の値の一覧はスキーマから読めるので、行の形のまま欠けを検証できる。
- **`profileTable` を `world.Resources` に持つ**: 内装の生成は `oapi.Raws` を受け取る純関数で、world を持たない。建物ごとに組んでも数十行で軽い。

### 4段目: 天候、空腹と疲労の段階

```toml
[[weathers]]
id = "blizzard"
tempModifier = -8
visionDelta = -28
severity = 2
spellTurnsMin = 450
spellTurnsMax = 900
[[weathers.seasons]]
id = "winter"
weight = 1.2

[[hungerStages]]
id = "hungry"
from = 0.33
severity = "minor"

[[fatigueStages]]
id = "exhausted"
from = 0.8
severity = "medium"
```

- 天候の効果、寒さの厳しさ、スペルの基準長を `weathers` の行に書く。季節ごとの出やすさの行列 `seasonAffinity` は、列である天候の行が持つ `seasons` の重みに分ける。
- 空腹と疲労の段階は、割合が `from` 以上の段階のうち `from` が最大のものになる。空腹は満腹度の割合、疲労は疲労の割合を見る。この1つの規則で今の空腹の `>=` と疲労の `<` の境目をどちらも表せる。段階で立つ栄養失調と過労の重症度を `severity` に書き、省くと立たない。
- 天候の種類と季節は Go の順序数 enum のままで、行の並びに依らず id から写す。遷移の粘りの距離は `WeatherKind` の並びに依るので、並びは Go に残す。

## 採用しなかった方法

- **関係を Zanzibar 型のタプル `object#relation@subject` で書く**: 移したい関係の大半は重み・個数・座標・順序を持つか、片側が持てば足りる1対1の参照で、素のタプルに載らない。属性を持たない多対多は30〜40件ほどしかない。文字列のタプルは tsp と editor-ui の型の検査も失う。
- **raw 全体をトリプルの書式に書き換える**: 表現は1つになるが、tsp による型の検証を失い、2万行の作り直しになる。
- **継承で重複を減らす**: 1行を見ても値が分からず、わかりにくい。
- **起動時に不調の表をパッケージ変数へ登録する**: グローバルな可変状態になり、登録を忘れたテストが空の表で黙って動く。
- **不調の名前の定数を Go に残し、すべてに行があることを検証する**: 怪我と攻撃の対応を raw へ移すと、骨折と切り傷はデバッグメニューからしか名指しされなくなる。低体温や食中毒も、コードが知る必要があるのは名前でなく起こる仕組みで、名前の定数は仕組みと不調の対応をコードに埋め込むことになる。
- **Go に全スキルと全効果キーの一覧を手で書き、raw の行と照らす**: Go には定数ブロックを列挙する手段が無く、定数を足すたびに一覧へも足す二重管理になる。値の集合を tsp の enum に置けば、生成された定数とスキーマから取れる。
- **仕組みの名前を `trigger`、`origin`、`cause` にする**: `trigger` はワープの仕掛け、`origin` は座標の原点、`cause` は死因 `DeathCause` とすでに意味が衝突する。病気の発症に使う `onset` にそろえた。
- **部位の集合と身体機能も raw へ移す**: 部位は `HealthStatus.Parts` の配列の添字で、身体機能の計算の構造になっている。
