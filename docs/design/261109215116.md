# 不調の値を raw の行へ、怪我の関係を Zanzibar 型のタプルへ移す

## 背景

不調の設定はすべて Go に直接書かれている。

| 設定 | 場所 |
|---|---|
| 不調の種類 | `ConditionType` の定数。参考 codebase: `internal/components/health_status.go:80` |
| 痛み、機能低下、回復の仕方と速さ、出血、死因、表示名と説明 | `conditionDefs` |
| 怪我が起こりうる部位 | `conditionDefs.parts` と `ConditionCanAffect`。参考 codebase: `health_status.go:201` |
| 攻撃の種類が負わせる怪我 | `injuryTypeFor` の switch。参考 codebase: `internal/activity/injury.go:25` |
| アイテムが治す怪我 | raw の `treats` を `Remedy.Treats` へ写す。参考 codebase: `internal/raw/raw.go:292` |

数値はバランスの調整値で、データで扱いたい。関係は種類ごとに別々の仕組みで持っていて、switch、Go の表、raw のフィールドと散らばっている。`treats` が実在する不調を指すかの検証も無い。

raw の書き方は次の方針で分ける。各物だけが持つ値と、1つの物を指す参照は、今の raw.toml の行のフィールドに書く。物と物の多対多の関係と、組への所属は、Zanzibar 型のタプル `object#relation@subject` に書く。1つの関係はどちらか一方にだけ書く。

本 doc はこの方針を怪我の領域へ最初に当て、タプルの仕組みを作る。

## 要件

1. 不調ごとの値を raw の `[[conditions]]` の行に持つ。
2. 怪我の関係をタプルで書く。攻撃の種類が負わせる怪我、怪我が起こりうる部位、アイテムが治す怪我。
3. 部位をまとめる組を、組への所属のタプルで書ける。
4. 判定の入口は `Check` と `Expand` の2つだけにする。規則は組の構成員への展開1段だけにする。
5. 関係の型を宣言し、読み込み時にすべてのタプルの型と参照先の実在を検証する。
6. 挙動は変えない。今の値と関係をそのまま移す。

## 設計

### 行。不調の値

```toml
[[conditions]]
id = "Fracture"
name = "Fracture"
description = "A broken bone. It will not heal until treated."
painPerSeverity = 18
bodyFuncDropPerSeverity = 20
recovery = "recover_after_tend"
recoverPer = 1
```

- `recovery` を省いた不調は ConditionSystem の管轄外になる。低体温と、量から導く過労と栄養失調が当たる。
- 起こりうる部位は行に書かない。多対多の関係なのでタプルに書く。
- Go の `ConditionType` 定数は、コードが名前で参照する種類のために残す。いまの7種はすべてコードから参照されている。

### タプル。怪我の関係

```toml
relations = [
  "attackcat:FIST#causes@condition:Fracture",
  "attackcat:CANON#causes@condition:Fracture",
  "attackcat:SWORD#causes@condition:Laceration",
  "attackcat:SPEAR#causes@condition:Laceration",
  "attackcat:BOW#causes@condition:Laceration",
  "attackcat:HANDGUN#causes@condition:Laceration",
  "attackcat:RIFLE#causes@condition:Laceration",

  "partgroup:limbs#member@part:Arm",
  "partgroup:limbs#member@part:Hand",
  "partgroup:limbs#member@part:Leg",
  "partgroup:limbs#member@part:Foot",
  "partgroup:core#member@part:Head",
  "partgroup:core#member@part:Torso",

  "condition:Fracture#affects@partgroup:limbs#member",
  "condition:Laceration#affects@partgroup:limbs#member",
  "condition:Laceration#affects@partgroup:core#member",

  "item:splint#treats@condition:Fracture",
  "item:bandage#treats@condition:Laceration",
]
```

主体に `partgroup:limbs#member` と書くと、その組の構成員を指す。展開は1段だけで、組の中に組を入れることはしない。

### 関係の型

どの種類の物が、どの関係で、何を指せるかを宣言する。

```toml
[[relationTypes]]
object = "attackcat"
relation = "causes"
subjects = ["condition"]

[[relationTypes]]
object = "partgroup"
relation = "member"
subjects = ["part"]

[[relationTypes]]
object = "condition"
relation = "affects"
subjects = ["part", "partgroup#member"]

[[relationTypes]]
object = "item"
relation = "treats"
subjects = ["condition"]
```

物の種類ごとに、何をもって実在とするかを決める。

| 種類 | 実在の出どころ |
|---|---|
| `condition` | raw の `conditions` の行 |
| `item` | raw の `items` の行 |
| `attackcat` | Go の `AllAttackTypes` |
| `part` | Go の部位の名前。全身は命中の対象外なので含めない |
| `partgroup` | `member` のタプルに現れる名前 |

### 判定の入口

```go
// Relations は raw の relations を索引にしたもの。読み込み時に1度だけ組み立てる
type Relations struct { /* object#relation から主体の集合への索引 */ }

// Check は object が relation で subject に至るかを、組の展開1段まで含めて返す
func (r Relations) Check(object Ref, relation string, subject Ref) bool

// Expand は object の relation が指す主体を、組を構成員に展開して返す。並びは raw の記述順
func (r Relations) Expand(object Ref, relation string) []Ref
```

置き場所は `internal/raw` にする。関係は raw のデータで、型の検証も raw の検証に並べるため。新しいパッケージは作らない。

### 怪我の処理の置き換え

```go
// 変更前
injuryType := injuryTypeFor(attack.GetAttackCategory())
part := hitPartForRoll(rng.IntN(totalHitWeight(injuryType)), injuryType)

// 変更後
causes := rels.Expand(raw.AttackCat(attack.GetAttackCategory()), "causes")
injury := causes[rng.IntN(len(causes))]
parts := rels.Expand(injury, "affects")
part := pickByHitWeight(rng, parts)
```

- 攻撃の種類が負わせる怪我は、今はどれも1つなので、選び方は挙動に影響しない。複数になったときは一様に選ぶ。重みが要れば行のフィールドに持たせる。
- 命中の重みは部位の値なので、Go の `bodyPartMetas` に残す。
- `ConditionCanAffect` と `conditionDefs.parts` を消す。

### 治療の置き換え

`Remedy.Treats` を消し、`Remedy` は効き目 `Potency` だけを持つ。治せるかは `rels.Check(item, "treats", condition)` で判定し、治せる不調の一覧は `Expand` で引く。使う側の4か所を置き換える。参考 codebase: `internal/activity/use_item.go:151`、`internal/widgets/entityspec/spec.go:428`、`internal/states/character_state.go:423`、`internal/raw/raw.go:292`。

### 不調の値の読み方

`components` の関数は `world` を受け取らずに `conditionDefs` を読んでいる。`raw` は `components` を import しているので、`components` から raw を読むと import が循環する。

そこで、不調の値の表 `ConditionDefs` を読み込み時に1度だけ組み立てて `world.Resources` に持ち、定義を読む `HealthStatus` のメソッドへ引数で渡す。対象は `BodyFuncs`、`ConsciousnessDrops`、`LocalDrop`、`BloodLossHPDrain`、`IsHPDraining` と、その内部の関数。本番の呼び出し元は6か所で、どれも `world` を持つ。`components` のテストは、必要な不調だけを書いた表をテストの中で組み立てて渡す。

### 検証

読み込み時に次を確かめる。

- タプルの書式が `object#relation@subject` に従う。
- 各タプルの object と subject の種類が、関係の型の宣言に合う。
- タプルの参照先がすべて実在する。
- `conditions` の id が一意で、Go の `ConditionType` 定数すべてに行がある。
- 攻撃の種類すべてに `causes` が1つ以上あり、怪我の種類すべてに `affects` が1つ以上ある。抽選の対象が空になって panic するのを、読み込み時に止める。

## 採用しなかった方法

- **raw 全体を Zanzibar で書き直す**: 数値や順序のある構造を表せず、行とタプルの2つが混ざったまま全体を作り直すことになる。
- **raw 全体をトリプルの書式に書き換える**: 表現は1つになるが、tsp による型の検証を失い、2万行の作り直しになる。
- **継承で重複を減らす**: 1行を見ても値が分からず、わかりにくい。
- **関係から関係を導く規則を入れる**: 継承と同じく、たどらないと結果が分からなくなる。規則は組の展開1段にとどめる。
- **タプルに数値を載せる**: 同じ関係が複数の経路で導かれたときの合成の決まりが要る。数値は行のフィールドに持つ。
- **起動時に不調の表をパッケージ変数へ登録する**: グローバルな可変状態になり、登録を忘れたテストが空の表で黙って動く。
- **部位の種類と命中の重みも raw へ移す**: 部位は `HealthStatus.Parts` の配列の添字で、身体機能の計算の構造になっている。
