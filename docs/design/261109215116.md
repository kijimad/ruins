# 不調の調整値を raw へ移し、データで扱えるようにする

## 背景

不調の設定はすべて Go の表に直接書かれている。参考 codebase: `internal/components/health_status.go` の `conditionDefs`。

| 設定 | 場所 |
|---|---|
| 不調の種類 | `ConditionType` の定数 |
| 表示名・説明、痛み、機能低下、回復の仕方と速さ、出血、死因 | `conditionDefs` |
| 起こりうる部位 | `conditionDefs` の `parts`。PR #946 で足す |

痛みや回復の速さはバランスの調整値で、アイテムや敵と同じくデータで扱いたい。いまは調整のたびに Go を書き換えてビルドし直す必要があり、エディタからも触れない。

raw とつながっているのは、治療アイテムの `treats = ["Fracture"]` だけで、不調の種類を名前の文字列で参照している。参考 codebase: `internal/raw/raw.go:292`。この名前が実在する不調かを確かめる検証は無い。

## 要件

1. 不調ごとの調整値を raw の `[[conditions]]` に持つ。表示名、説明、痛み、機能低下、回復の仕方と速さ、出血、死因、起こりうる部位。
2. Go の `ConditionType` 定数は、コードが名前で参照する種類のために残す。いまの7種はすべてコードから参照されている。
3. Go の定数のすべてに raw の行があることを、raw の検証で保証する。
4. 治療アイテムの `treats` が raw の不調を指すことを、raw の検証で保証する。
5. 挙動は変えない。いまの値をそのまま raw へ移す。

## 設計

### データ

```tsp
/** 不調1種の調整値 */
model Condition {
  id: ConditionTypeName;
  name: string;
  description: string;
  painPerSeverity: ConditionPain;
  bodyFuncDropPerSeverity: ConditionBodyFuncDrop;
  recovery?: RecoveryMode;
  worsenPer?: ConditionTimerRate;
  recoverPer?: ConditionTimerRate;
  bloodDropPerSeverity?: ConditionBloodDrop;
  cause?: DeathCause;
  parts?: BodyPartName[];
}

enum RecoveryMode { recover_after_tend, progress_until_tend, recover_over_time }
```

- `recovery` を省略した不調は、ConditionSystem の管轄外になる。低体温と、量から導く過労・栄養失調がこれに当たる。いまの `Recovery == ""` と同じ意味。
- `parts` を省略した不調は全部位に起こる。部位名は `BodyPart` の名前の文字列で書き、読み込みで Go の値へ写す。
- 部位の種類そのものは Go に残す。部位は `HealthStatus.Parts` の配列の添字で、身体機能の計算の構造になっているため。

Go 側は、いまの `ConditionDef` を値として持つ表を作る。

```go
// ConditionDefs は不調の種類ごとの調整値の表。raw の conditions から組み立てる
type ConditionDefs map[ConditionType]ConditionDef
```

### 定義の読み方。引数で渡す

いまは `components` の関数が、`world` を受け取らずにパッケージの表 `conditionDefs` を読んでいる。raw は `world.Resources.RawMaster` にあり、`raw` パッケージは `components` を import しているので、`components` から raw を読むと import が循環する。

そこで、定義の表を引数で渡す。

- raw の読み込み時に `ConditionDefs` を1度だけ組み立て、`world.Resources` に持つ。
- 定義を読む `HealthStatus` のメソッドは、`ConditionDefs` を引数に取る。`BodyFuncs`、`ConsciousnessDrops`、`LocalDrop`、`BloodLossHPDrain`、`IsHPDraining` と、その内部の `conditionSeverityImpact`、`conditionBloodDrop`、`bloodLossCause`。
- 本番の呼び出し元は6か所で、どれも `world` を持つので `query.ConditionDefs(world)` で渡す。参考 codebase: `internal/world/query/body_funcs.go`、`internal/systems/condition.go`、`internal/systems/health_regen.go`、`internal/states/character_info.go`。
- 表示名と説明は `query.ConditionName(world, ct)` と `query.ConditionDescription(world, ct)` から引く。呼び出し元は7か所で、どれも `query.T` で訳しているので `world` を持つ。
- `components` のテストは、必要な不調だけを書いた `ConditionDefs` をテストの中で組み立てて渡す。raw を読まずに済み、テストが前提にする値が目に見える。

### 検証

`raw.ValidateRaws` に次を足す。

- `conditions` の id が一意である。
- Go の `ConditionType` 定数すべてに、同じ id の行がある。
- 治療アイテムの `treats` のすべてが、`conditions` の id を指す。
- `parts` のすべてが、実在する部位の名前である。

## 採用しなかった方法

- **起動時に `components` のパッケージ変数へ表を登録する**: 呼び出し元の変更が最も少ない。ただしグローバルな可変状態になり、登録を忘れたテストは空の表で黙って動く。
- **raw から Go の表をコード生成する**: 実行時の受け渡しが要らず、循環も起きない。ただし raw を実行時のデータとして読む既存の作りと二重になり、raw を変えるたびに生成し直す手順が増える。
- **不調の計算を `components` から `query` へ移す**: `HealthStatus` が純粋なデータになり、`world` から定義を読める。ただし移す範囲が広く、この変更の目的より大きくなる。
- **部位の種類も raw へ移す**: 部位は配列の添字で身体機能の計算の構造なので、データで足せても計算のコードを直す必要が残る。
- **命中の重みを raw へ移す**: 調整値ではあるが、部位の表 `bodyPartMetas` と一緒に扱うほうが自然で、部位を移さない以上この変更には入れない。
