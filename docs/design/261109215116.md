# ゲームの識別子と調整値を raw へ移す

## 背景

ゲームの設定の多くが Go に直接書かれている。数値の調整はコードの変更になり、raw から参照している識別子の実在も確かめられない。

| 設定 | 場所 |
|---|---|
| 不調の値。痛み、機能低下、回復の仕方と速さ、出血、死因、表示名と説明 | `conditionDefs`。参考 codebase: `internal/components/health_status.go:119` |
| 怪我が起こりうる部位 | `conditionDefs.parts` と `ConditionCanAffect` |
| 部位の表示名、身体機能、命中の重み | `bodyPartMetas`。参考 codebase: `health_status.go:255` |
| 攻撃の種類が負わせる怪我 | `injuryTypeFor` の switch。参考 codebase: `internal/activity/injury.go:25` |
| スキルの名前、説明、能力値、カテゴリ、熟練の係数 | `internal/components/skills.go`、`proficiency.go` |
| 内装の Ref から raw の prop と item group への対応、置き方の既定 | `internal/mapplanner/interior/prop.go`、`loot.go`、`archetype.go` |
| 天候の効果と期間、季節ごとの出やすさ | `internal/components/weather.go`、`internal/world/query/weather.go:19` |

raw はすでにこれらの識別子を文字列で参照しているが、検証が足りない。

- アイテムの `treats` は不調を、本と職業はスキルを指すが、実在を確かめていない。参考 codebase: `internal/raw/raw.go:223`、`:292`
- 部位は表示名がそのまま識別子を兼ね、表示名は翻訳の msgid でもある。表示を直すと参照が壊れる
- 攻撃の種類の値 `CANON` とスキル `cannon` は綴りが違う

## 要件

1. ゲームの識別子を raw の正式な id にそろえ、表示名と分ける。raw からの参照はすべて読み込み時に実在を検証する。
2. 調整値と、片側が持てば足りる参照は raw の行のフィールドに書く。多対多の参照は、持ち主の行に型の付いた id の配列で書く。
3. 関係を表す汎用の仕組み、たとえば `object#relation@subject` 型のタプルは作らない。
4. 段ごとに挙動を変えない。今の値と関係をそのまま移す。

## 設計

### 方針

- **値と参照は持ち主の行に書く。** 1つの関係は持ち主の行の1か所だけに書く。tsp の型と editor-ui の型の検査がそのまま効く。
- **識別子と表示名を分ける。** 行は `id` と `name` を別に持つ。`name` は翻訳の msgid、`id` は参照のためだけに使う。
- **コードが名前で分岐する識別子は Go の定数を残す。** 定数すべてに raw の行があることを読み込み時に検証し、両者のずれを止める。
- **コードの構造に結びついたものは Go に残す。** 部位の集合は身体機能の計算の配列の添字、空腹と疲労の段階の種類は分岐の名前、間取りのプランナーは関数なので移さない。
- **表の書き方は設計 doc 261109230757 にそろえる。** 選ばれる物を指すフィールドは `id`、重みは浮動小数の `weight`、何も出ないことは `nothing` で表す。重みで引く処理は `consts.Pick` を使い、raw から読んだ重みをそのまま渡す。

タプルを採らない理由は、移したい関係の大半が重み・個数・座標・順序のような属性を持つか、片側が持てば足りる1対1の参照だから。属性を持たない多対多は30〜40件ほどで、専用の仕組みに見合わない。

### 段

| 段 | 移すもの | 識別子 |
|---|---|---|
| 1 | 不調の値、怪我の部位、部位の命中の重み | 不調、部位 |
| 2 | スキルの名前・説明・能力値・カテゴリ・熟練の係数、攻撃の種類が負わせる怪我 | スキル、攻撃の種類 |
| 3 | 内装の Ref の対応と置き方の既定、生活感・荒廃・変種・目玉の置物の重みの表 | 内装の Ref |
| 4 | 天候の効果と期間、季節ごとの出やすさ、空腹と疲労の段階の境目 | 天候 |

3段目の重みの表は、#948 で `choice` の一覧として Go に書かれた。参考 codebase: `internal/mapplanner/interior/profile.go:82`、`hero.go:25`。境界値の switch でなく重みの並びになったので、そのまま raw の行へ移せる。4段目の天候の遷移も `consts.Pick` で引くようになり、季節ごとの重みを raw から渡すだけで済む。

表の書き方の変更は #949 で tsp と raw に入り、261109230757 は完了した。同じ raw.toml と tsp を同時に書き換える衝突の心配は無くなったので、1段目から着手できる。

以下は1段目の設計。2段目以降は着手時にこの doc へ書き足す。

### 1段目: 不調と部位

```toml
[[conditions]]
id = "fracture"
name = "Fracture"
description = "A broken bone. It will not heal until treated."
painPerSeverity = 18
bodyFuncDropPerSeverity = 20
recovery = "recover_after_tend"
recoverPer = 1
parts = ["arm", "hand", "leg", "foot"]

[[bodyParts]]
id = "arm"
name = "Arm"
hitWeight = 3.0
```

- `parts` を省いた不調は全部位に起こりうる。今の `ConditionCanAffect` の規則と同じ。
- `recovery` を省いた不調は ConditionSystem の管轄外になる。低体温と、量から導く過労と栄養失調が当たる。
- 部位の集合と身体機能との対応は Go の `bodyPartMetas` に残し、`id` を足す。raw の `bodyParts` は命中の重みと表示名だけを持ち、Go の部位すべてに行があることを検証する。命中の重みは `consts.Pick` に渡すので、表の重みと同じスカラー `EntryWeight` で型を付ける。参考 codebase: `oas/typespec/types.tsp:85`
- アイテムの `treats` はすでにスカラー `ConditionTypeName` の配列で型が付いている。参考 codebase: `oas/typespec/req.tsp:21`。値を新しい不調の id にそろえ、実在の検証を足す。
- 怪我の命中部位は、今の `hitPart` が `ConditionCanAffect` と `BodyPartHitWeight` で重みを作って `consts.Pick` で引いている。参考 codebase: `internal/activity/injury.go`。この重みの出どころを、不調の行の `parts` と raw の部位の `hitWeight` に替える。
- Go の `ConditionType` 定数は、コードが名前で参照する種類のために残す。値は raw の `id` と同じにする。

```go
// 変更前
type ConditionType string // 値は "Fracture" のような表示名寄りの文字列

// 変更後。値を raw の id にそろえる
const ConditionFracture ConditionType = "fracture"
```

### 不調の値の読み方

`components` の関数は `world` を受け取らずに `conditionDefs` を読んでいる。`raw` は `components` を import しているので、`components` から raw を読むと import が循環する。

そこで、不調の値の表 `ConditionDefs` を読み込み時に1度だけ組み立てて `world.Resources` に持ち、定義を読む `HealthStatus` のメソッドへ引数で渡す。対象は `BodyFuncs`、`ConsciousnessDrops`、`LocalDrop`、`BloodLossHPDrain`、`IsHPDraining` と、その内部の関数。本番の呼び出し元はどれも `world` を持つ。`components` のテストは、必要な不調だけを書いた表をテストの中で組み立てて渡す。

```go
// components
type ConditionDefs struct{ /* 不調ごとの ConditionDef と部位ごとの命中の重み */ }
func NewConditionDefs(conds map[ConditionType]ConditionDef, hitWeights [BodyPartCount]float64) ConditionDefs
func (d ConditionDefs) Def(ct ConditionType) (ConditionDef, bool)
func (d ConditionDefs) CanAffect(ct ConditionType, part BodyPart) bool
func (d ConditionDefs) HitWeight(part BodyPart) float64
func (d ConditionDefs) BodyFuncImpact(cond *HealthCondition, part BodyPart) (pain int, bodyFunc BodyFuncKind, drop int)
func (d ConditionDefs) BloodDrop(cond *HealthCondition) int
func (hs *HealthStatus) BodyFuncs(defs ConditionDefs, needConds ...HealthCondition) BodyFuncs

// raw
func NewConditionDefs(raws oapi.Raws) (gc.ConditionDefs, error)

// query
func ConditionName(world w.World, ct gc.ConditionType) string
func ConditionDescription(world w.World, ct gc.ConditionType) string
```

不調1件を読む関数は表のメソッドにし、`HealthStatus` 全体を畳むメソッドは表を引数で受け取る。表示名と説明は訳を通すので query が引く。

Go の定数と部位すべてに行があることの検証は、部分的な raw を組み立てるテストを妨げないよう、参照の検証 `ValidateReferences` と分けて `LoadFromFile` だけが行う。

### 検証

読み込み時に次を確かめる。

- `conditions` と `bodyParts` の id が一意で、Go の `ConditionType` 定数と部位すべてに行がある。
- 不調の `parts` が実在する部位を指し、全身を含まない。
- アイテムの `treats` が実在する不調を指す。
- 怪我の種類すべてに、起こりうる部位が1つ以上ある。抽選の対象が空になって panic するのを止める。

不調と部位の `name` と `description` は表示されるので、raw の訳の網羅テスト `TestRawTranslationCoverage` の対象に加える。

## 採用しなかった方法

- **関係を Zanzibar 型のタプル `object#relation@subject` で書く**: 移したい関係の大半は重み・個数・座標・順序を持つか、片側が持てば足りる1対1の参照で、素のタプルに載らない。属性を持たない多対多は30〜40件ほどしかない。文字列のタプルは tsp と editor-ui の型の検査も失う。
- **raw 全体をトリプルの書式に書き換える**: 表現は1つになるが、tsp による型の検証を失い、2万行の作り直しになる。
- **継承で重複を減らす**: 1行を見ても値が分からず、わかりにくい。
- **起動時に不調の表をパッケージ変数へ登録する**: グローバルな可変状態になり、登録を忘れたテストが空の表で黙って動く。
- **部位の集合と身体機能も raw へ移す**: 部位は `HealthStatus.Parts` の配列の添字で、身体機能の計算の構造になっている。
