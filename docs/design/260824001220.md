# コード監査: worldgen・Ark stale pointer・serde 2026-08-24

## 背景

golangci-lint による静的検査が手厚いリポジトリのため、forcetypeassert・errcheck・nilerr/nilnil・exhaustive 等の機械検知漏れを補う目的で、internal 配下を対象にコードの意図と振る舞いを読む監査を行った。lint がパターンとして捕まえられない、意味を理解しないと分からない誤りだけを対象にしている。

以下5件を、いずれも実コードを直接確認し失敗シナリオを具体化したうえで報告する。修正はこの doc の範囲外とし、着手は人が取捨選択する。

## 問題1: 遺跡入口・小集落の当選が `chunkTypeAt` の優先順位を守らず衝突する

**file:line**: `internal/overworld/dungeon_entrance.go:28-43`、`internal/overworld/settlement.go:52-62`、`internal/overworld/schematic.go:129-143`

**症状**: `chunkTypeAt`（`schematic.go:129`）はチャンク種別を「市街地 > 遺跡入口 > 小集落 > ランドマーク > 荒れ地」の優先順位で1つに決める唯一の分類源で、コメントでも「地図も生成もこの分類を唯一の源にする」と明言している。ところが実際の配置処理はこの優先順位を守っていない。

- `dungeonEntranceFeature.place`（dungeon_entrance.go:28）は `dungeonEntrancePlacement.At` の当選だけを見て `SpawnDungeonEntrance` を無条件実行する。市街地判定 `urbanRegionOf` にも小集落判定 `settlementPlacement` にも一切譲らない。
- `settlementFeature.place`（settlement.go:52）は市街地 `urbanRegionOf` にだけ譲り、遺跡入口 `dungeonEntrancePlacement` には譲らない。

各 `Placement` は `(runSeed, 座標)` の独立した純関数で、Spacing・Salt が異なるため異なる種別の当選チャンクが偶然一致しうる。

**根拠・失敗シナリオ**: `runSeed=12345, rows=20, x∈[-200,200)` の範囲で実際に探索したところ、settlement と dungeonEntrance の当選が2箇所、urban と dungeonEntrance の当選が4箇所で衝突した。

- **urban ∩ dungeonEntrance**: `chunkTypeAt` は市街地を優先するため俯瞰図には市街地の記号だけが出る。しかし `dungeonEntranceFeature.place` は市街地判定を無視して座標中心に遺跡入口 prop を無条件配置するため、実体としては市街地の建物・壁の中に遺跡入口が埋まる。`planUrbanLot`/`furnishBuilding` は敷地のほとんどを建物で埋めるため、壁タイル上に置かれれば遺跡入口は到達不能になり、かつ地図上には一切現れないので発見しようがない。
- **settlement ∩ dungeonEntrance**: `chunkTypeAt` は遺跡入口を優先するため地図には遺跡入口の記号だけが出る。しかし `settlementFeature.place` は遺跡入口の当選を見ないため、同じチャンクに集落も生成してしまう。地図に存在しない集落が実体としては存在し、かつ同じチャンク中心付近に遺跡入口と集落の生成物が重なる。

**修正方針案**: `settlementFeature`/`dungeonEntranceFeature` が独自に `Placement.At` を呼ぶのをやめ、`chunkTypeAt(runSeed, c, rows)` の戻り値が自分の担当種別と一致するかどうかだけで判定する。`wildernessLandmarkFeature` は既にこの形になっており、それに倣う。優先順位の定義を `chunkTypeAt` 一箇所に閉じることで、地図と実体の食い違いを構造的に防げる。

## 問題2: `gc.Rect.Width()/Height()` の排他的セマンティクスと部屋描画の包含セマンティクスが `mapplanner/lib.go` だけ取り違えられている

**file:line**: `internal/mapplanner/lib.go` の `selectRoom`（573-603）・`randomPositionInRoom`（607-621）・`randomPositionNear`（625-639）・`isInAnyRoom`（655付近）

**症状**: `gc.Rect.Width()/Height()` は `Max-Min`（`internal/components/field.go:46`、Min=2,Max=10 なら Width=8 とテストで明示された排他的な値）を返す。一方、部屋の生成・描画側は `Min〜Max` を両端含む半開でなく閉区間として扱う。`RectRoomPlanner.createRoom` は `Max.X = min(x+w, width) - 1` で「幅wタイルの最後のタイル添字」として Max を決め、`RoomDraw.rectangle`/`BigRoomDraw.drawBasicBigRoom` は `for x := room.Min.X; x <= room.Max.X` で両端を含めて描画する。同じパッケージ内の `ruins_planner.go:94-95`（`building.Width() + 1`）や `big_room_test.go:31-32`（`room.Width() + 1`）はこの食い違いを +1 で正しく補正しているが、`lib.go` の4関数だけ補正を欠く。

**根拠・失敗シナリオ**:
1. `randomPositionInRoom`/`randomPositionNear` は `tx` を `[Min.X, Min.X+Width())` すなわち `Max.X` 自身を除く範囲でしか生成しない。しかし実際には `Max.X` 列・`Max.Y` 行も床タイルとして描画されているため、部屋の最右列・最下行には NPC・アイテムが恒久的にスポーンしない。`isInAnyRoom` も同じ半開区間で判定するため、その列を「部屋外」と誤判定する。
2. より深刻なのは実幅1タイルの部屋（`Max.X == Min.X`）が生成された場合。`Width()==0` となるため `selectRoom` は `w>0 && h>0` の条件で重みゼロとして完全に除外し、`randomPositionInRoom` に直接渡しても `rw<=0` で即 false になる。実際には1タイル幅の有効な床がある部屋なのに、抽選対象・スポーン候補から完全に脱落する。
3. `selectRoom` のコメントは「配置可能タイル数に比例した自然な分布」と謳うが、実際の面積 `w*h` ではなく `(w-1)*(h-1)` で重み付けされるため、特に小部屋で選択確率が数分の1に歪む。

**修正方針案**: `Width()/Height()` の意味自体は変えず、`lib.go` 側の4箇所を他の呼び出し箇所（`ruins_planner.go`、`big_room_test.go`）に倣って `+1` した実タイル数で扱うよう統一する。あるいは `gc.Rect` に実タイル数を返すメソッドを新設し、全呼び出し元をそちらへ寄せて排他的セマンティクスとの取り違えの芽を断つ。

## 問題3: `StatsChangedSystem` が `CharModifiers` の `Upsert` で構造変更した後、無効化された `Abilities` ポインタを読み続ける

**file:line**: `internal/systems/stats_changed.go:37`,`120-131`,`133-138`

**症状**: `abils := world.Components.Abilities.Get(entity)`（37行目）で Ark のアーキタイプ領域への直接ポインタを取得したあと、121-131行目で `entity` が `Skills` を持つ場合に `gc.Upsert(world.ECS, world.Components.CharModifiers, entity, effects)` を呼ぶ。`Upsert`（`components.go:21`）は対象コンポーネントを未保持なら `comp.Add` する実装で、`Add` はエンティティを新しいアーキタイプ領域へコピー移動する構造変更である。ruins-review が明記するとおり、この構造変更は既存の `Get` ポインタを無効化する。ところが136行目の `hp.Max = maxHP(abils)` は、この構造変更より前に取得した `abils` を無反省に読み続けている。

**根拠・失敗シナリオ**: `internal/save/serde.go:121-128` はロード直後、`Abilities` を持つ全エンティティへ `StatsChanged` を一括付与する。ダンジョン内に同型の敵が複数体いる状態でセーブ・ロードすると、`StatsChangedSystem.Update` が同一アーキタイプの複数エンティティを連続して処理する。最初の1体で `CharModifiers.Add` が呼ばれると、Ark はその移動元アーキタイプ領域を swap-remove で詰めるため、同アーキタイプに残る別エンティティの `Abilities` データがその領域へ移動してくる可能性がある。結果として、後続で136行目が読む `abils` は移動前に取得した stale なポインタになり、別エンティティ由来の値、または未定義に近いデータを指したまま `hp.Max` の計算に使われる。HP上限が実際の能力値と無関係な値に化ける。

単体エンティティだけを扱う既存テスト `stats_changed_test.go` では同アーキタイプに他エンティティが存在しないため症状が顕在化せず、見逃されている。同種処理を行う `internal/world/gameaction/profession.go` は `CharModifiers` の `Upsert` を `abils` 使用の後に置いており、`stats_changed.go` だけ順序が逆転している。

**修正方針案**: `abils` を使う「HP/Pools を更新」ブロック（133-138行目）を `CharModifiers` の `Upsert`（120-131行目）より前に移動する。あるいは `Upsert` 呼び出し後に `abils = world.Components.Abilities.Get(entity)` で再取得してから `maxHP(abils)` を呼ぶ。

## 問題4: `ActionPickup` がターン/継続アクティビティのゲートを迂回する

**file:line**: `internal/states/dungeon_input.go:96-112`,`148-157`

**症状**: `DoAction`（96行目）は「UI系アクションはターンを消費しないので常に実行可能」というコメント（102行目）のもと、`ActionOpenDungeonMenu` 等の純粋な画面遷移アクションと同じバケツに `ActionPickup` を含めている。しかし `ActionPickup` の実処理（148-157行目）は `activity.Execute(activity.NewPickupTileActivity(...))` を直接呼ぶ、ターンを消費しうる実ゲームアクションであり、コメント自身の前提と矛盾している。

**根拠・失敗シナリオ**: プレイヤーが読書等の継続アクティビティを実行中（`HasActivity(world, playerEntity) == true`）に拾得キーを押すと、`ActionPickup` は default 節（103-111行目）の `CanPlayerAct`/`HasActivity` チェックを一切通らずに `activity.Execute` → `StartActivity` へ進む。`StartActivity`（`internal/activity/activity_manager.go:160-175`）は `Validate` より前に既存アクティビティを無条件で `InterruptActivity` する実装になっている。足元に何も拾う物が無く `PickupTileActivity` の `Validate` が失敗するケースでも、既存の継続アクティビティ（読書・押す・休息等）は `Validate` 失敗より先に既にキャンセルされてしまう。`internal/systems/turn_system.go:26-27` のコメントは「継続中の入力は DungeonState が `HasActivity` で塞ぐ」という不変条件を明言しており、他の全ゲームアクション（移動・攻撃・調べる等）は正しく `HasActivity` でブロックされるのに、`ActionPickup` だけがこの不変条件の抜け穴になっている。

**修正方針案**: `ActionPickup` を「常に実行可能」バケツ（96-101行目）から外し、他のゲームアクションと同様に default 節、すなわち `CanPlayerAct`/`HasActivity` チェックを通過した後で処理するようにする。

## 問題5: `stage.Purge` が `StageBound` エンティティを削除するとき、それが所有する在庫を巻き添えにしない

**file:line**: `internal/world/stage/stage.go:54-60`

**症状**: `Purge` はその階の `StageBound` を持つエンティティだけを `RemoveEntity` する。商人 NPC のように `LocationInStorage{Owner: merchant}` で在庫アイテムを所有するエンティティが対象に含まれる場合、在庫アイテム自体は `GridElement` を持たないため `stage.Bind` の対象外で `StageBound` が付かず、`Purge` の走査対象にならない。結果、商人本体だけが消え、在庫は死んだ `Owner` を指したまま world に残り続ける。

**根拠**: `SpawnNeutralNPC`（`internal/world/lifecycle/spawn.go:98-131`）は商人 NPC に `PopulateMerchantStock`（`merchant.go:29`）で在庫アイテムを付与する。`enterDebugPlannerFloor`（`internal/states/dungeon_floor.go:398,414`）は実際に `stage.Purge` を呼ぶ経路として存在する。同種の孤児化問題は `internal/worldstream/worldstream.go` の `RemoveEntitiesInXRange` で既に発見・修正済みで、`removeOwnedStorage`（61-83行目）がコメントで「所有者を消すときに一緒に消さないと死んだ所有者を指す孤児になり、serde で保存され蓄積する」と明記している。`stage.Purge` は同種の除去処理でありながらこの対策を欠く。`stage.go:185` 相当の `OnStop` は将来的な完全離脱にも `stage.Purge` の使用を想定したコメントがあり、影響範囲はデバッグ経路に限らない。

**失敗シナリオ**: `stage.Purge` を経由してステージを離脱するたびに、孤児化した在庫アイテムが world に蓄積する。これらは死んだ `Owner` を参照したまま serde の保存対象になり、セーブファイルが肥大化するほか、`Owner` を前提にした在庫関連のクエリ・UI がこの孤児エンティティを誤って拾うと未定義の挙動になりうる。

**修正方針案**: `worldstream.removeOwnedStorage` 相当の「所有物も道連れに削除する」処理を共有ヘルパーとして `lifecycle` 側に切り出し、`stage.Purge` と `worldstream.RemoveEntitiesInXRange` の両方から呼ぶようにする。
