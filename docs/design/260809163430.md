# activity パッケージのわかりやすさ改善

## 背景

Validate を単一 error + UserError 型の契約へ整理し、UI 上できない前提崩れを system
エラーへ再分類した。この作業中に見つかった実バグ、reload の致命化・push の gamelog
漏れ・read の英語漏れ、は3つとも同じ弱点から来ていた。**検証や分類が Validate の
外に漏れている**ことだ。構築関数や状態層の事前チェックが Validate を迂回し、握りつぶし
や致命化を生む。

活動系の入口も混在している。`Execute(NewX())` の直呼び、`ExecuteXAction` ラッパ、
`ExecuteInteraction`→`executeX`、が並存し、どれが正規経路か読み取りづらい。

これらは挙動バグの温床であると同時に、初見の読み手が「できる/できないの判定はどこか」
「実行の入口はどれか」を掴みにくくしている。ここでは大きな作り替えでなく、activity 内の
責務整理として改善候補を TODO に残す。ECS システムへの作り替えは対象外とする。

## 設計

改善候補を効果と手間で並べる。着手順の推奨は 1 → 3 → 2。

### 1. 構築関数を無誤化し、Validate を唯一のゲートにする（最有力）

`NewReloadActivity` は無誤化済み。残る `NewPushActivity`・`NewPullActivity`・
`NewDisassembleActivity`・`NewReadActivity` は `(*gc.Activity, error)` で検証して生 error
を返す。さらに `executeDisassemble`・`executePullCube`・`ExecuteMoveAction` は Execute の
前に事前チェックして分岐する。この二重・三重化が push の無言バグの温床だった。

- 規約: 構築関数は組むだけ。可否判定は Validate だけが行う。
- 全 `NewXActivity` を `*gc.Activity` のみ返す形へ。事前チェックを撤去し Execute→Validate に一本化。
- 効果: 「できる/できない」を読むとき Validate 1箇所で済む。分類・ログ・翻訳の二重管理が消え、同種バグが構造的に起きない。

### 2. Params の型アサートを消す

全 Behavior が冒頭で `p, ok := comp.Params.(*gc.XParams); if !ok { return system err }`
を繰り返す。ジェネリックな取り出し、例 `paramsOf[gc.MoveParams](comp)`、か型パラメータ化
した `Behavior[P]` にすれば、この定型と「target is not set」系の枝を17実装から一掃できる。

### 3. Behavior の自明メソッドを埋め込みで省く

`Start`・`Finish`・`Canceled` の多くは `log.Debug` だけ。デフォルト実装を埋め込めるように
すると、各 Behavior は意味のある `Validate`・`DoTurn` だけを書けばよくなる。

### 4. Execute とインテントラッパの層を明確にする

`Execute(comp, actor, world) (*ActionResult, error)` は任意の活動を回す唯一のエンジン。
`ExecuteReloadAction`・`ExecuteShootAction`・`ExecuteMoveAction`・`ExecuteWaitAction` は
その上の「組む＋Execute＋戻り簡約」を束ねたインテント層のラッパ。名前が兄弟に見えて層が
違ううえ、次のちぐはぐで関係が読みにくい。

- カバレッジが不揃い。ラッパがあるのは一部だけで、drop・use_item・read・pickup は状態が
  `Execute(NewX())` を直呼びしている。
- 戻り型が違う。Execute は `(*ActionResult, error)`、ラッパは `error`。
- 一部だけラッパな根拠が歴史的経緯で、設計上の必然でない。

方針: 薄いラッパは置かない。build と Execute だけの `ExecuteShootAction`・`ExecuteReloadAction`
は削除し、状態は `Execute(NewX())` を直呼びする。押し処理やプレイヤー解決などロジックを持つ
`ExecuteMoveAction`・`ExecuteWaitAction` だけラッパとして残す。`Execute` は aiinput の planner
が任意 comp を汎用実行するため汎用入口として公開のまま。doc.go に層関係を明記する。

### 5. attack アクティビティを近接として明確にリネームする

近接攻撃は `AttackBehavior`・`gc.BehaviorAttack`・`gc.AttackParams`・`NewAttackActivity` と
「attack」で名付くが、射撃 `ShootBehavior` も攻撃であり、相互作用は `InteractionMelee`。
「attack」が近接と総称の両義で紛らわしい。近接であることを名前で示し shoot と対にする。
gc.Activity は skipComponents なので命名変更は保存へ影響しない。

## 採用しなかった方法

- **`Execute` を完全に private 化する**: aiinput の planner が任意 comp を汎用実行するため、
  汎用入口としての公開は残す。状態からの直呼びを無くすのは候補 4 で扱う。
- **即時アクションを継続アクションと別インターフェースへ完全分離**: 現状の「全部継続、即時は
  1ステップで完了」は DRY で正しい。型を分けると経路が二重になり、統一の利点を失う。見送る。

## コメント

- 1 は今セッションの実バグ3件の真因を潰す最小の規約化。着手優先度が最も高い。
- どれも activity 内の整理であり、挙動を変えない。着手時は `make check` で担保する。
