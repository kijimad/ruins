# コード監査: VRT専用ステートのクエリ内削除・セーブ書き込み非原子性・raw表の検証漏れ 2026-11-23

## 背景

自律コード監査エージェントによる定期監査タスク。golangci-lint は forcetypeassert・errcheck・nilerr/nilnil・exhaustive・makezero 等が既に有効で機械的な問題は既に捕捉しているため、今回は internal 配下、oapi・editor-ui を除く、を対象に lint が捕まえられない意味論的な誤りを横断的に読み込んだ。

internal/activity・internal/aiinput・internal/systems・internal/states・internal/formula・internal/world・internal/save・internal/worldstream・internal/dungeon・internal/mapplanner・internal/mapspawner・internal/maptemplate・internal/overworld・internal/components・internal/raw・internal/rawschema・internal/loader を4系統に分けて並列で精読した。過去の監査doc、`260711000833.md` から `261026002202.md` までは事前に通読し、既出の問題、ダンジョン生成・リロード・セーブの基本整合性、ステージ共存下の座標検索漏れ、手続き生成ドアの破壊不能化等、は対象から除外した。

activity・aiinput・skill 系は継続アクティビティの規約、生存ガード・資源再解決・StatsChangedのHasガード等、に沿って精読したが、確信を持てる新規の問題は無かった。以下4件は、いずれも敵対的な自己検証、実際の失敗シナリオの構成、既存コードとの非対称性の確認、ark ライブラリ本体のソース確認、実データの走査、を経て報告する。

## 検出した問題

### 1. VRT専用ステートの `clearEntities` がクエリ反復中に `RemoveEntity` を呼び、呼ばれれば確実に panic する

**file:line**: `internal/states/mapgen_visualizer.go:211-230`（`clearEntities`、212-220行目の `spriteRenderQuery` ループ内218行目、221-227行目の `gridElementQuery` ループ内225行目）

```go
func (st *MapGenVisualizerState) clearEntities(world w.World) {
	spriteRenderQuery := ecs.NewFilter1[gc.SpriteRender](world.ECS).Query()
	for spriteRenderQuery.Next() {
		entity := spriteRenderQuery.Entity()
		if !world.Components.Player.Has(entity) &&
			!world.Components.LocationInBackpack.Has(entity) &&
			!world.Components.LocationEquipped.Has(entity) {
			world.ECS.RemoveEntity(entity) // クエリロック中に構造変更
		}
	}
	gridElementQuery := ecs.NewFilter1[gc.GridElement](world.ECS).Query()
	for gridElementQuery.Next() {
		entity := gridElementQuery.Entity()
		if !world.Components.Player.Has(entity) {
			world.ECS.RemoveEntity(entity) // 同様
		}
	}
	query.InvalidateSpatialIndex(world)
}
```

**症状**: `ecs.NewFilter1[...].Query()` はクエリ生成時にワールドをロックし、`Next()` が false を返すまでロックが外れない。ロック中に `World.RemoveEntity` を呼ぶと必ず panic する。

**根拠・失敗シナリオ**:
1. `github.com/mlange-42/ark@v0.8.3/ecs/filter_gen.go` の `Query()` は `lock: f.world.lockSafe()` でロックを取得する。
2. `ecs/world.go:117` の `World.RemoveEntity` は本体の前に `w.checkLocked()` を呼び、`ecs/world_internal.go:518-522` の `checkLocked` は `w.IsLocked()` が真なら `panic("cannot modify a locked world: collect entities into a slice and apply changes after query iteration has completed")` を投げる。この panic メッセージ自体が「クエリ中に集めてループ外で変更しろ」という Ark の設計契約を明示している。
3. `MapGenVisualizerState.OnStop`（`mapgen_visualizer.go:80-83`）は `clearEntities` を呼ぶ。`OnStart`（`mapgen_visualizer.go:47-77`）は毎回 `mapspawner.Spawn` でタイル・NPC・アイテム・propをスポーンするため、このステートを一度 Start した後に Stop すれば、`SpriteRender` または `GridElement` を持つプレイヤー以外のエンティティが必ず1体以上存在する。
4. 現在このステートを使う唯一の経路は `internal/states/golden_test.go` の `vrt.RenderPNG(t, vrt.States(&gs.MapGenVisualizerState{...}))` で、`internal/vrt/state.go` の `SetupStateMachine` は `es.Init` と `PushState` だけを呼び、`PopState`、つまり `OnStop`、を一度も呼ばない。そのため現行の `make test`/`make lint` ではこの panic 経路を一度も通らず、埋もれている。同ファイル内の他の削除処理、`internal/systems/dead_cleanup.go`・`internal/systems/visual_effect.go` 等、は全て「クエリで集めてからループ外で削除する」collect-then-mutate を徹底しているのに対し、この関数だけが唯一クエリ内で直接 `RemoveEntity` している。

**なぜ lint で捕まらないか**: `ecs.NewFilter1[...]` は型として正当なクエリ構築であり、forcetypeassert・errcheck・exhaustive 等の静的解析はこの呼び出しを問題として検出しない。「クエリ反復中は構造変更禁止」は Ark のランタイム不変条件であり、golangci-lint にこれを検出するカスタムルールは入っていない。

**反証の検討**: 「このステートはVRT専用で実際には Pop されないので無害」という反論を検討した。しかし `OnStop` は `es.State[w.World]` インターフェースの一部として明示的に実装されており、「エンティティを削除する」という doc コメントも付いている。呼ばれないことを前提にした実装はこのメソッドの存在自体と矛盾する。複数スナップショットを順番に見せる・デバッグメニューから対話的に開閉するなど自然な拡張をした瞬間、あるいは単に `OnStop` を呼ぶテストを足した瞬間にこの panic が顕在化する。既報告の「ステージ共存下の座標検索問題」とは別種の Ark 不変条件違反、クエリロック中の構造変更、であり重複ではない。

**修正方針案**: `dead_cleanup.go`/`visual_effect.go` と同じ collect-then-mutate パターンに直す。両方のクエリで削除対象エンティティをまず `[]ecs.Entity` に集め、両クエリの `Next()` ループが終わった後にまとめて `world.ECS.RemoveEntity` を呼ぶ。`GridElement` を持つエンティティは大抵 `SpriteRender` も持つため2つのクエリの結果が重複しうるので、削除前に `world.ECS.Alive(entity)` を再チェックするか、集合を `map[ecs.Entity]struct{}` でユニーク化してから削除する。

### 2. 手動セーブの書き込みが非原子的で、書き込み中の異常終了が既存スロットのデータを破壊する

**file:line**: `internal/save/desktop.go:28-37`（`saveDataImpl`、31行目の `os.WriteFile(fileName, data, 0644)`）、呼び出し元 `internal/states/factories.go:142-168`（`NewSaveMenuState`、158行目の `saveManager.SaveWorld(world, slotName)`）

```go
// internal/save/desktop.go
func (sm *SerializationManager) saveDataImpl(slotName string, data []byte) error {
	fileName := filepath.Join(sm.saveDirectory, slotName+saveFileExt)
	err := os.WriteFile(fileName, data, 0644)
	if err != nil {
		return fmt.Errorf("failed to write save file: %w", err)
	}
	return nil
}
```

**症状**: `os.WriteFile` は対象ファイルを `O_TRUNC` で開いてから書き込むため、既存の同名スロットファイルを一旦空にしてから新データを書く。書き込み中に異常終了すると、ファイルは空または中途半端な内容のまま残る。

**失敗シナリオ**: `NewSaveMenuState`（`internal/states/factories.go:144-168`）は固定4スロット `slot1`〜`slot4` に対し、既存セーブへ直接 `saveManager.SaveWorld(world, slotName)` で上書き保存する。保存処理中にプロセスが強制終了・クラッシュ・電源断・ディスク満杯などで中断すると、まだ良好だった直前のセーブデータが壊れたファイル、空または不完全な gzip、に置き換わり、そのスロットのセーブを完全に失う。`AutoSave`（`internal/save/manager.go:262-271`）はタイムスタンプ付きの新規ファイル名、`auto_<UnixNano>`、を使うため同じファイルを上書きせず影響は小さいが、手動4スロットは常に同名ファイルへの直接上書きになるため影響が大きい。

**なぜ lint で捕まらないか**: 型アサーションやエラー握り潰しではなく、ファイルI/Oの原子性という実行時のクラッシュ耐性の問題。`os.WriteFile` の戻り値エラーは正しく `fmt.Errorf` で返されており `errcheck` を通過する。

**反証の検討**: 「`RestoreWorldFromJSON` のチェックサム検証・probe ワールドでの二重検証があるから壊れたセーブも安全に扱える」という反論を検討したが、それらはあくまで読み込み時に壊れたデータをエラーとして検出し本番ワールドを無事に保つ話であり、書き込み自体が既存の良好なファイルを破壊すること自体を防ぐものではない。壊れたセーブはロードが失敗するだけで復元できず、そのスロットのデータはプレイヤーから見て失われる。既存の「ダンジョン生成・リロード・セーブの基本整合性」監査はエンティティ・座標整合性を指しており、本件のファイルI/O原子性は別種の問題で重複しない。

**修正方針案**: 一時ファイルへ書き込んでから `os.Rename` で目的のファイル名へ原子的に差し替える。`os.CreateTemp(sm.saveDirectory, ...)` に書き込み、`Sync`・`Close` の後に `os.Rename(tmp, fileName)` する。WASM側、`internal/save/wasm.go`、は `localStorage.setItem` がブラウザ側で単一キーの置き換えとして扱われるため対象外でよい。

### 3. Items・Members・CommandTables・DropTables・ItemTables・EnemyTables の id 重複が検証されない

**file:line**: `internal/rawschema/refs.cue:53,62-66`（`_itemIDs`・`_memberIDs`・`_commandTableIDs`・`_dropTableIDs`・`_itemTableIDs`・`_enemyTableIDs`）、`internal/rawschema/schema.cue:1462-1488`（`xxxIds_unique` の一覧、items/members/commandTables/dropTables/itemTables/enemyTables が無い）、`internal/raw/reference_test.go:161-186,199-241`（`TestRawDuplicateNames`、items/members/commandTables/dropTables/itemTables/enemyTables は `Name` フィールドの重複だけを見る）、`internal/raw/raw.go:37-45,96-102,114-120,602-656`（`FindByKey`・`FindItem`・`FindMember`・`GetCommandTable`・`GetDropTable`・`GetItemTable`・`GetEnemyTable`、いずれも `Id` をキーに線形検索し最初の一致を返す）

**症状**: `raws.Items`/`Members`/`CommandTables`/`DropTables`/`ItemTables`/`EnemyTables` に同じ `id` を持つ行が2つ以上あっても、CUE 検証・Go テストのどの段階でも検知されない。

**根拠**: `refs.cue` の参照索引は `{(x.id): true}` という形で id をキーに常に定数 `true` を割り当てる。CUE のユニフィケーションは `true & true = true` で矛盾しないため同じ id の行が複数あっても衝突しない。一方、`schema.cue:1462` 以降に実在する `bodyAttackIds_unique`/`facilityIds_unique`/`materialIds_unique`/`conditionIds_unique` 等は `{(x.id): i}` とループの添字 `i` を値にしており、重複行があると異なる `i` が同じキーに衝突して CUE がエラーを出す。この `_unique` の列に items/members/commandTables/dropTables/itemTables/enemyTables は存在しない。Go 側の `TestRawDuplicateNames` も `Id` ではなく `Name` のみを見ている。`FindByKey`（`raw.go:37-45`）は線形探索で最初の一致を返すだけで重複検知はしない。

**失敗シナリオ**: 既存の `id = "healing_potion"` を持つアイテムをコピペしてバランス調整版を作る際、`name` だけ変えて `id` を変え忘れると、`make check`/`make lint`/`make test` が全て通る。実行時は `FindItem` が最初の行を返すため新しい行のステータス変更は完全に無効化され、誰かがレシピ・ドロップテーブル・初期装備でこの id を参照しても常に古い定義の効果になる。エラーも警告も出ないため、手動プレイでバランスの変化が反映されないことに気づくまで発覚しない。CommandTables/DropTables/ItemTables/EnemyTables も同様で、`GetCommandTable` 等が最初の一致を返すためテーブルの差し替えが無視される。

**なぜ lint で捕まらないか**: TOMLデータの中身の整合性であり、forcetypeassert/exhaustive等のGoコード向けlintは関与しない。

**反証の検討**: 現在の `assets/metadata/entities/raw/raw.toml` を Python の `tomllib` で実際に走査し、items、587件、members、79件、commandTables、74件、dropTables、55件、itemTables、26件、enemyTables、17件、のいずれにも `id` 重複は無いことを確認済み。つまり現状ではこの欠陥は発火していない。「意図的に name だけで十分」という可能性も検討したが、`FindByKey` 系の参照キーは一貫して `Id` であり、`Name` の重複が無くても `Id` が重複すれば実害が出る構造なので意図的な仕様とは考えにくい。`Tile`/`Prop` だけは既に `Id` ベースの重複テストがあり、コメントで「表示名は重複しうるので id で検証する」と明記されていることからも、items/members 等は単純な対応漏れと判断した。

**修正方針案**: `schema.cue` の `_unique` ブロックに `itemIds_unique`/`memberIds_unique`/`commandTableIds_unique`/`dropTableIds_unique`/`itemTableIds_unique`/`enemyTableIds_unique` を他の表と同じパターン、`{(x.id): i}`、で追加し `make generate` で反映する。

### 4. EnemyTableEntry・ItemTableEntry の `minDanger > maxDanger` という範囲逆転が検証されない

**file:line**: `internal/rawschema/schema.cue:697-698`（`#EnemyTableEntry.minDanger!`/`maxDanger!`）、`:1108-1109`（`#ItemTableEntry` 同様、いずれも `#DangerLevel` のみで2フィールド間の大小関係の制約が無い）、`internal/raw/validate.go:404-411`（`validateWeathers` が `SpellTurnsMin > SpellTurnsMax` を `errSpellTurnsReversed` で明示的に検証している一方、敵/アイテムテーブルの `minDanger`/`maxDanger` に同種のvalidatorが無い）、`internal/raw/raw.go:1055-1072`（`EnemyEntriesAt`/`ItemEntriesAt`/`inDanger`、`lo <= danger && danger <= hi` で判定）

**症状**: `EnemyTableEntry`/`ItemTableEntry` の `minDanger`/`maxDanger` を入れ替えて書いても、CUEスキーマも Go 側の `validateRules` も検知しない。

**根拠**: `inDanger`（`raw.go:1065-1072`）の `lo <= danger && danger <= hi` は `lo > hi` のとき、どんな `danger`、1以上、に対しても絶対に真にならない。そのエントリは `EnemyEntriesAt`/`ItemEntriesAt` で常に除外され、`SelectEnemyByWeight`/`DrawFromItemTable` の抽選対象に一切載らなくなる。エラーも例外も発生しない。

**失敗シナリオ**: 新しい敵/アイテムを危険度5〜10で出すつもりで `minDanger = 10`/`maxDanger = 5` と書き間違える、あるいは既存行をコピペして danger帯だけ変えるときに上下を書き違えると、そのテーブル行は未来永劫どの階層でも絶対に抽選されない。`make check` 等は通り、他のエントリの重みだけで正常に抽選が回るためゲームは普通に動き続け、「この敵/アイテムが出ない」とプレイで気づかれるまで発覚しない。

**なぜ lint で捕まらないか**: TOMLデータの整合性であり、Goコード向けの静的解析は関与しない。

**反証の検討**: 実データ、enemyTables 17件・itemTables 26件の全エントリ、を Python で走査し、現状は `minDanger <= maxDanger` が全て守られていることを確認済み。したがって現時点でアクティブに発火している不具合ではない。ただし `validateWeathers` という同形の既存チェックが存在する以上、意図的に敵/アイテムテーブルだけ対象外にした形跡はなく、単純な抜けと判断した。

**修正方針案**: `internal/raw/validate.go` に `validateWeathers` と同じ形の `validateDangerRanges` を追加し、`EnemyTableEntry`/`ItemTableEntry` の `MinDanger > MaxDanger` を `validateRules` のバリデータ一覧、`validate.go:45-57` 付近、に足す。

## 採用しなかった代替

- **1件目を「どうせ呼ばれないので無視」とする**: `OnStop` インターフェースの契約と doc コメントに反し、将来の拡張やテスト追加で即座に顕在化するため採らない。
- **2件目を「セーブ失敗時にユーザーへ警告するだけ」で済ませる**: 警告ではファイル破壊そのものを防げない。原子的差し替えはコスト小で確実に防げるため、警告だけで済ませる案は採らない。
- **3・4件目を「実データに違反が無いなら今は不要」として見送る**: 機械検知可能な欠陥を人手の注意力だけに委ねるのは、CLAUDE.md の「機械検知可能 → golangci-lint のルール有効化 / カスタム linter 化する」方針、ここでは CUE 制約・Go validator、に反するため、放置ではなく検証追加を推す。
