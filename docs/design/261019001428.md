# コード監査: 施設間取り分割とアクティビティ中断処理 2026-10-19

## 背景

自律コード監査エージェントが internal 配下を横断的に精読した。golangci-lint は forcetypeassert・errcheck・nilerr/nilnil・exhaustive・makezero 等を既に有効にしており、型アサーション未チェックやエラー握り潰しのような機械的に捕まる問題は対象外とし、コードの意図と振る舞いを理解しないと分からない誤りだけを探した。領域ごとに4系統、ECS・serde・world層、ゲームロジック・AI層、マップ生成・幾何層、UI・入力・その他層で並行調査し、候補を自分で再現・敵対的に検証したうえで、確度の高い2件に絞った。本 doc はこの2件の報告であり、修正は行っていない。採否はレビューで判断してほしい。

## 検出した問題

### 問題1: `splitSpan` の最小サイズ clamp が親矩形の固定境界まで押し出す

- file:line: `internal/mapplanner/interior/split.go:99-109`

```go
// 各室 >= minRoomSideSplit を保つ。まず左から前室に押され、次に右から末尾室に押し戻す
for i := 1; i <= n; i++ {
    if bounds[i]-bounds[i-1]+1 < minRoomSideSplit {
        bounds[i] = bounds[i-1] + minRoomSideSplit - 1
    }
}
for i := n - 1; i >= 0; i-- {
    if bounds[i+1]-bounds[i]+1 < minRoomSideSplit {
        bounds[i] = bounds[i+1] - minRoomSideSplit + 1
    }
}
```

`bounds` は長さ `n+1` で、`bounds[0]` と `bounds[n]` は呼び出し元の `strip` が渡した帯の外側境界 `lo`・`hi` に固定されるべき値。ところが1本目のループは `i <= n` で `bounds[n]` まで、2本目のループは `i >= 0` で `bounds[0]` まで書き換え範囲に含んでいる。コメント「まず左から前室に押され、次に右から末尾室に押し戻す」が意図する動きは内部境界 `bounds[1..n-1]` の調整のはずで、外側境界まで動かす意図はコメントとも矛盾する。

- 根拠（失敗シナリオ）: 実際に `lo=0, hi=3`（帯の幅4タイル）、`n=3`（3室に分割）、`minRoomSideSplit=3` で `bounds=[0,1,2,3]`（等分割後の初期値）を与えて1本目のループを手計算すると、`bounds[1]=2 → bounds[2]=4 → bounds[3]=6` と伝播し、最終的に `bounds=[0,2,4,6]` になる。固定されるべき `bounds[3]`（元の `hi=3`）が `6` まで押し出され、2本目のループもこの壊れた値を基準に判定するため訂正されない。実際に Go で再現し確認済み。`internal/mapplanner/interior/facility_plan.go` の `storeBackSide`（店舗のバックヤードを柱状に3分割する型）は `n := 2 + childSeed(seed, 6_000_000)%2` で約半数の seed が `n=3` を選び、分割する帯の幅は `backCol` の `H`（店舗の全高）または `storeBackBottom` 側では footprint の全幅で、建物が小さいテンプレでは `minRoomSideSplit*n-(n-1)=7` 未満になりうる。このとき最後の室の矩形が建物の footprint の外へ突き出し、後続の家具配置・到達性チェック・壁描画が「室は footprint 内に収まる」という前提の上で、実際には footprint 外の座標へ書き込む、または隣接施設・市街地の区画と重なる間取りを生成しうる。
- なぜ lint で捕まえられないか: `bounds` はスライスの範囲内インデックスなので境界外アクセスにはならず、型・nilチェックにも抵触しない。「`bounds[0]`/`bounds[n]` は常に `lo`/`hi` に固定される」という不変条件をループの範囲指定が静かに破る、純粋な算術ロジックの誤りで、forcetypeassert/errcheck/exhaustive/makezero のいずれの対象でもない。
- 修正方針案: 1本目のループを `for i := 1; i < n; i++`、2本目を `for i := n - 1; i > 0; i--` とし、`bounds[0]`・`bounds[n]` を対象から外す。ただしそれだけだと内部境界だけでは最後の室の最小サイズを `hi` 基準で保証できない場合が残るため、2本目のループが `bounds[n-1]` を `bounds[n](=hi)` 基準で正しく押し戻せているかを別途、`minRoomSideSplit*n > hi-lo+1` のような縮退ケースを含めたユニットテストで固定する。

### 問題2: `RestBehavior.DoTurn` が敵接近時にキャンセル理由を2重に上書きし、未訳の破損メッセージを表示する

- file:line: `internal/activity/rest.go:66-69`、`internal/activity/activity_manager.go:115-119`,`247-264`

```go
// rest.go DoTurn
if !query.IsAreaSafe(world, actor) {
    Cancel(comp, "rest interrupted because enemies are nearby")
    return ErrRestEnemiesNearby
}
```

```go
// activity_manager.go stepActivity
if err := behavior.DoTurn(stored, entity, world); err != nil {
    log.Error("activity turn processing error", ...)
    CancelActivity(entity, fmt.Sprintf("error: %s", err.Error()), world)
    return
}
```

```go
// activity_manager.go CancelActivity
Cancel(comp, reason) // reason = "error: cannot rest because enemies are nearby" で上書き
if err := behavior.Canceled(comp, entity, world); err != nil { ... }
```

- 根拠（失敗シナリオ）: `DoTurn` は `Cancel` で `comp.CancelReason` を `"rest interrupted because enemies are nearby"` に設定した直後、非nilの `ErrRestEnemiesNearby` を返す。`stepActivity` は `DoTurn` のエラーを「システムエラー」経路として扱い、`CancelActivity(entity, "error: "+err.Error(), world)` を呼ぶ。`CancelActivity` は無条件に `Cancel(comp, reason)` を再実行し、`comp.CancelReason` を `"error: cannot rest because enemies are nearby"` へ上書きしたうえで `RestBehavior.Canceled` を呼ぶ。`Canceled` はプレイヤーの場合 `query.T(world, comp.CancelReason)` で理由を翻訳して `"Rest interrupted: %s"` に埋め込み表示するが、上書き後の文字列は `.po` に登録された msgid ではないため `i18n.Catalog.Translate` は原文へフォールバックする。結果、日本語設定でも `"Rest interrupted: error: cannot rest because enemies are nearby"` という英語の生文字列混じりの破損メッセージがそのままゲームログに表示される。休息中に敵が接近するたびに必ず発生する。

  同じ「周囲の敵接近で中断」を扱う `sleep.go:74`・`disassemble.go:122`・`read.go:124`・`wait.go:65`・`reload.go:92` はいずれも `Cancel(comp, ...)` の直後に `return nil` しており、`stepActivity` の `IsCanceled` 分岐を正しく通って `CancelActivity` の再実行を経由しない。`rest.go` だけがこの系列から外れて `return err` にしており、横並び比較でも他との不整合が確認できる。`.claude/skills/ruins-review/SKILL.md` の「対象消滅など transient な中断は Cancel + return nil のままにし、両者を種類で区別する」という既存の明文規約にも反する。
- なぜ lint で捕まえられないか: `err` は正しく非nilで呼び出し元が検査しているため errcheck には抵触しない。`Cancel` が2度呼ばれる経路自体は構造変更やパニックを伴わないため Ark の strict semantics にも抵触しない。「DoTurn内で自らキャンセルした場合は nil を返すべき」という契約は skill の文書にのみ存在し、型やインターフェースでは強制されていない意味論的な誤りで、静的解析の射程外。
- 修正方針案: `rest.go:68` の `return ErrRestEnemiesNearby` を他の Behavior と揃えて `return nil` に直す。合わせて、`stepActivity` が `DoTurn` 内で既に `Cancel` 済みの `comp` を「システムエラー」として再度 `CancelActivity` に渡さないよう、`IsCanceled(stored)` を `DoTurn` のエラー検査より先に見るか、`CancelActivity` 側で既にキャンセル済みの `comp.CancelReason` を上書きしないガードを入れることも検討する。根本原因は「DoTurn内キャンセル後の return err」という表面化しやすいパターンが各 Behavior に委ねられている点なので、単体テストで `RestBehavior.DoTurn` が敵接近時に `nil` を返すことを固定するだけでなく、将来似た実装ミスを防ぐため共通ヘルパー経由にする案も比較検討に値する。

## 採用しなかった方法

- 2件とも実装修正まで行う案は見送った。CLAUDE.md の運用上、監査エージェントは発見のみを行い、取捨選択と実装はレビューを経て人が行う。
- UI/入力層の監査では束縛表の不整合は検出されず、`ActionMenuLeft`/`ActionMenuRight` が本番の `menuloop.Screen` 経由では到達しない死んだ経路であるという低確信度の所見のみだったため、本 doc には積まなかった。クラッシュや誤表示を伴わない設計上の瑕疵であり、確度が足りないと判断した。
- ECS/serde/world層の監査では、`BuyStock`/`SellStock` のロールバックが `MoveMembersToBackpack` の部分成功を想定していない点が指摘されたが、現状 `MoveToBackpack` は常に `nil` を返す実装のため今は発火しない死んだ防御コードであり、「具体的な失敗シナリオ」の基準を満たさないため見送った。

## コメント

このリポジトリは golangci-lint が非常に手厚く、かつレビュー観点が skill として明文化されているため、lint で機械的に捕まる問題や既知の落とし穴は既にほぼ潰れている。4系統の並行監査でも大半のパッケージは「精読したが問題なし」という結果だった。今回残った2件は、いずれも「隣接する似たコードと比較しないと気づけない非対称性」が共通する。問題1は分割アルゴリズムの境界固定という不変条件がループの範囲指定1文字で破れている例、問題2は同系列の Behavior 群の中で1箇所だけ契約から外れている例で、どちらも静的解析ではなく横断比較と手計算による再現で確度を上げた。
