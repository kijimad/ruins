# コード監査: 手続き生成ドアの破壊不能化 2026-09-21

## 背景

自律コード監査エージェントによる定期監査タスク。golangci-lint は forcetypeassert・errcheck・nilerr/nilnil・exhaustive・makezero 等が有効で機械的な問題は既に捕捉しているため、今回は internal 配下を対象に lint が捕まえられない意味論的な誤りを横断的に読み込んだ。

直近のコミット群、全 prop に hp を必須化し殴って壊せるようにする、死体再攻撃クラッシュと撤去遅延の2フォローアップに対象を絞り、prop 破壊・分解回収、Item/Prop 正マーカーへの置き換えリファクタ、キューブ収納/展開状態、PlayTime のセーブ/ロード整合の4系統に分けて並列で精読した。過去の監査doc、`260803144226.md` から `260914001354.md` までは事前に通読し、既出の問題は対象から除外した。

キューブ収納/展開の状態機構は設計doc `260920004814.md` が accepted のまま未実装であることを確認し、対象コードが存在しないため監査を見送った。Item/Prop マーカー置き換えリファクタと PlayTime まわりは、各々のコミット・関連ファイルを実際に読み、境界ケースを検討したが、確信を持って報告できる新規の問題は無かった。

以下1件は、prop 破壊可能化のコミットが明言した不変条件「全 prop は殴って壊せる、頑丈さは hp で決まる」が、実際には手続き生成ドアで成立していないことを実コードで確認できたため報告する。

## 検出した問題

### 1. 手続き生成ダンジョンのドアだけ「殴って壊せる」対象から漏れている

**file:line**: `internal/world/lifecycle/spawn_prop.go:129-156`（`SpawnDoor`）、`internal/mapspawner/spawner.go:199-207`（`spawnDoors`）、`internal/mapplanner/door_planner.go`・`internal/mapplanner/lib.go:281`（`DoorPlanner`）、`assets/metadata/entities/raw/raw.toml:16616-16628`（raw の `door` prop 定義）

**症状**: `SpawnDoor` は raw を経由せず `gc.EntitySpec` を直接組み立てており、`HP` を持たず `Interactable.Interactions` も `InteractionDoor` だけで `InteractionMelee` を含まない。`internal/states/action_handlers.go:225` の `getInteractionActions` はエンティティ自身の `Interactable.Interactions` だけを走査してアクション一覧を作るため、`InteractionMelee` を持たないこのドアには「攻撃」の選択肢自体が現れない。

**根拠・失敗シナリオ**: ダンジョン生成の標準プランナーチェーンは `internal/mapplanner/lib.go:281` で `chain.With(DoorPlanner{DoorChance: 0.8})` を組み込んでおり、部屋の入口の8割にドアを配置する。`DoorPlanner.PlanMeta`（`door_planner.go:15`）はこれを `MetaPlan.Doors`（`DoorSpec` のスライス）へ積み、`mapspawner.spawnDoors`（`spawner.go:200`）が `metaPlan.Doors` を走査して `lifecycle.SpawnDoor` を直接呼ぶ。この経路は raw を一切参照しないため、ほぼ全てのダンジョンで大量に生成される通常のドアは HP も近接攻撃の相互作用も持たない。

一方、`raw.toml` には `hp = 50` を持つ `door` prop 定義があり `NewPropSpec`（`raw.go:689`）を通せば他 prop と同様に HP と `InteractionMelee` が無条件で付与される。しかしこの raw エントリを名前 `"door"` で参照する箇所は `internal/maptemplate/palette_test.go` のテストコード以外に存在しない。`grep -rn '"door"'` で確認した限り、`mapplanner`・`mapspawner`・`maptemplate` の非テストコードは一切この raw prop を使わない。つまり `door` prop の hp=50 は実プレイでは到達しない死んだ設定であり、実際にプレイヤーが遭遇するドアは全て `SpawnDoor` の hard-coded 経路を通る。

コミット `78a1925` は「全 prop は殴って壊せる、頑丈さは hp で決まる」を明言し、扉についても「扉も壊せるようになる」とリスク節に書いている。しかしこの不変条件はドアの主経路には反映されておらず、プレイヤーはどれだけ攻撃してもダンジョンの通常ドアを破壊できない。crash はしないが、直近で確立したばかりの設計意図とコードが食い違ったまま気づかれない状態。

**なぜ lint で捕まらないか**: 型アサーションや nil 化、二重 Add のような機械的パターンではなく、「ドア生成に raw 経由と非 raw 経由の2つの実装が並存し、hp 必須化のときに片方だけ更新された」という設計レベルの不整合。`SpawnDoor` は文法的に正当な `EntitySpec` 構築であり、静的解析・exhaustive チェックの対象にならない。

**反証の検討**: `metaPlan.Props` に `Door != nil` の raw prop を混ぜて配置する経路自体は `mapspawner.spawnProps`（`spawner.go:166`)に実装があり機能する。したがって「ドアは仕組み上壊せない」わけではなく、実際に使われている生成経路がその機構を使っていないだけだと確認した。また `SpawnCube` も同様に HP を持たないが、プレイヤーの乗り物であり「壊せるべき」という意図はコミットメッセージにも raw にも存在しないため対象外とした。ドアだけがコミットで明示的に「壊せるようになる」と言及されており、対象として扱う。

**修正方針案**:
- `spawnDoors`/`SpawnDoor` を `raw.NewPropSpec(raws, "door")` ベースに作り直し、`Orientation`・`IsOpen` 等ドア固有フィールドだけ後付けする形にして、他 prop と同様に HP・`InteractionMelee` を付与する。
- あるいは「手続き生成ドアは意図的に破壊不可のままにする」という設計判断であれば、raw の `door` prop の hp=50 エントリとコミットメッセージの記述を実態に合わせて訂正し、意図を明文化する。
