# 施設内装の生成 —— Zorbus の content モデルの翻案

## 背景

`20260724_69` のリアルさ改善で、タイル級の内装がランダム散布で「店に見えない」と測定・指摘された。
役割ベースの家具配置でごま塩をやめる方針は立てたが、その配置規則をどんな器で書くかは未確定だった。

Zorbus のビルド解説 `building.zorbus.net` を読み、内装への応用を検討した。Zorbus は2つの独立した仕組みを持つ。
一方は部屋レイアウトの生成アルゴリズム、他方は部屋へ中身を流し込む content システム。**施設内装に効くのは後者の
content システム**である。前者は本 doc の関心ではない。理由は後述する。

Zorbus の content システムの要点は、中身の宣言を**幾何から切り離す**ことにある。content は「どの prefab か」でなく
「どういう area が要るか」を要件で宣言し、要件を満たす任意の area に流し込まれる。60を超える待ち伏せ prefab の
いずれにも同じ待ち伏せ content が入る。中身は placement 意味論を持つ stuff の重み付きリストで、家具・戦利品・敵・
装飾を**意味のある位置**に置く。これがランダム散布と決別して「設計されたもの」に見せる核心である。

## 要件

- **決定的な純関数**。内装は建物という有界インスタンス内で `buildingSeed = hash(runSeed, footprint)` から一括生成し、
  再訪で一致し serde 安全であること。建物という有界インスタンス内に置く。`20260724_69` の生成
  パイプラインでは Feature 層が建物を配置し、その内側の内装を本 doc が担う。
- **幾何と中身の分離**。content は area 要件で宣言し、特定の部屋形状や prefab に固定しない。器を1つ足すだけで施設種を
  増やせること。
- **placement 意味論**。家具・戦利品を中央・壁際・全域・名前付きゾーンなど意味のある位置へ置き、散布をやめる。
- **データ化可能**。最初は Go 定義、器が固まったら TOML/raw へ。`20260724_69` の Content 語彙 TOML 化の指針と揃える。
- **グローバル状態を持たない**。Zorbus は per-level の可変キャップとグローバル乱数で content を撒くが、これは
  `20260724_69` が却下したステートフル配置である。有界インスタンス内の seed 固定選択に置き換える。
- **非循環の pass DAG**。各 pass は前段出力と `childSeed = hash(parentSeed, index)` のみに依存する。反復手法は
  固定K回＋決定的フォールバックへ還元してから載せる。
- **抽選は slice+sort+seed**。Go の map を抽選に使わない。同 seed 2回生成の完全一致を CI で強制する。
- **抽選の単位は束**。anchor 付きグループを第一級にし、机だけあって椅子が無い抽選事故を構造で防ぐ。
- **意図の可読性**。説明のつかない配置を出さない。塞ぐなら瓦礫で理由を添える。believability の敵は乱数でなく
  意図の不在である。

## 設計

### 生成パイプライン

生成は固定段数の非循環 pass 列で、各 pass は前段の出力と childSeed のみに依存する。追記その2〜その6の
収穫を統合した現行の全体像。

```text
footprint(doc 69 の Feature 層)
 → lot 外構       敷地・塀・門・外構。建物を裸で置かない。追記その4
 → 分割文法       決定的 BSP を既定、面積要件が強い施設は squarified treemap
 → 隣接グラフ化   Room 列と接続。廊下は spine-first / repair / none を類型で選ぶ
 → ゾーン分類     entrance 根の BFS 距離ラベリング
 → FacadePass     正面判定・入口・窓・看板・シャッター
 → content 抽選   ThemeTags と RoomReq 照合で部屋ごとに当選
 → placement      密度場と決定的間引きで束を配置
 → usage_wear     生活痕。行動遷移表から固定 n 手
 → 廃墟化         場3枚 → 固定K世代 CA → しきい値写像
 → 検証           到達性・classifyRoom・Lynch 検収
```

### layout↔content 契約

content は部屋の形を知らず、分割文法が確定した契約だけを読む。

```go
// Room は分割文法の出力。content システムはこの契約のみに依存する
type Room struct {
	Rect     Rect
	Doorways []Doorway
	Zone     ZoneTag // Entrance / Display / Service / Storage / Corridor ...
}
```

- ゾーン印は独立のラベリング pass が付与する。entrance の部屋を根に隣接グラフを BFS し、根からの距離で帯を切る
- 廊下は検出せず生成時に `ZoneCorridor` を宣言する。幾何検出・位相検出は誤分類ゆえ不採用。詳細は追記その6
  - 生成は spine-first / repair / none を施設類型で選ぶ。廊下幅 W は追記その3の実基準、民家1・診療所2・
    学校2〜3タイル、を類型から引く
  - repair の挿入経路は placement より前の段で確定し、通ったタイルを ZoneCorridor と aisle_skeleton
    予約の両方に登録する。以降の content pass は予約を density=0 として避けるので、廊下と棚間通路が
    衝突しない
- 多層は必須でない。廃ビルなど限定類型のみ BuildingPlan の3規則、footprint 包含・階段室固定・分割線継承で
  「同じ建物の2階」を導出する。詳細は追記その4

### content モデル

occurrence と placement の2段分離。何を置くかは文脈条件付き重みリスト、どこへ置くかは placement 意味論が
担う。抽選の単位は単品でなくアンカー付きの束。根拠は SAG・Scene Grammar・activity バンドルの三重収束で、
詳細は追記その3とその5。

```go
// Content は「どういう部屋に・何を・どこへ」の宣言。Requirements を満たす任意の部屋へ流し込む
type Content struct {
	ID           string
	ThemeTags    []string     // 施設種のグルーピング。biome や規模から重み付き抽選する
	Requirements RoomReq      // どういう部屋が要るか。MinSize / MinExits / MaxExits / Zones
	Props        ContentProps // 照明・床材テーマ・施錠率など部屋全体の性質
	Groups       []Group      // 抽選単位の束の列
}

// Group は保証セットとランダム充填を分ける。散布を殺す芯
type Group struct {
	Style GroupStyle // PickEach=必ず全部 / PickOne=重みで1つ / PickN=N個
	Items []Stuff
}

// Stuff は1つの配置指示。Satellites があれば anchor と衛星の束を1回で置く
type Stuff struct {
	Kind       StuffKind // Furniture / Loot / Being / Decor / Trap
	Ref        string
	Placement  Placement
	Zone       string
	Chance     int
	Amount     Dice
	Satellites []AnchoredStuff // anchor 相対の固定オフセット候補列。尽きたら諦める
}

// Archetype は家具型が自分の配置作法を知る。レシピは「レジ1・棚3〜5」と言うだけでよい
type Archetype struct {
	Footprint Size
	UseArea   Clearance // 方向つき利用域。footprint 空き + use_area 歩行可能の二重判定
	Default   Placement
	NeedsWall bool
	RW        int      // 部屋別必須度 0..3。3 はほぼ必須。ProcTHOR の実証済み注釈
	Tags      []string
}

// 補助型。実装の起点として最小の形だけ確定し、詳細は実装時に詰める
type Dice struct{ Base, Sides, Bonus int } // 1d3+1 相当。定数個数は Sides=0 で表す
type Clearance struct{ Up, Right, Down, Left int } // 4方向の必要空マス。等方値は4辺同値で表す
type AnchoredStuff struct {
	Ref     string
	Offsets []Vec2 // anchor 相対の候補列。前から試し、置ければ確定、尽きたら衛星を諦める
}
```

`PickEach` の Group 内に置けなかった保証 stuff があれば、その stuff の `Ref` を差し替えた縮退版を
`alternative` として同じ Group に並べる。旧案の `IfPrevFailed` は「直前1つの失敗を後続が拾う」暗黙の
連鎖で順序依存だったが、Group と alternative なら「この保証枠を満たす候補列」を宣言的に書けて順序に
依存しない。fillRoom は Group ごとに候補を上から試し、Style の要求個数を満たしたら打ち切る。

### placement 意味論 —— 密度場で統一する

散布をやめる要は、各 stuff が置き場所を持つことである。各 placement は「タイル → スカラ density」の純関数で
統一実装する。density は 0..1 に正規化した値、0 が置かない・1 が必ず置く、と規約する。間引きは
`hash(seed, x, y, placementSalt)` を 0..1 へ正規化した閾値 t と比べ、`density >= t` のタイルを候補にする。
正規化は `hash 出力の uint64 / 2^64` で行う。候補は slice に積み sort してから Amount 個を上から取る。
幾何が予約した通路・戸口は density=0 で「塞がない」を構造的に保証する。

| モード | 内容 |
|---|---|
| `center` / `wall` / `corner` / `full_area` / `zone` | 基本。zone は矩形に加えディスクも許す |
| `row` | 平行列。axis と通路幅を幾何に焼き込む。ゴンドラ・ラック・オフィス島 |
| `attached` | anchor 相対の beside / on_top / flanking |
| `near_origin` / `far_from_origin` / `in_view_of_origin` | 入口からの距離帯と可視。レジは入口近く、薬品は奥 |
| `sequence` / `mirror_pair` | 軸上の順序配置と軸対称ペア。神社の参道と狛犬 |
| `exclusion_zone` | 負の placement。デケレーション帯・参道・廊下は「置かない帯」。空白が設計を作る |

補助属性は orientation・personal_space・instance_count・alternative・symmetry。実装は
`SelectCenter / SelectWallMidpoints / SelectCorners / SelectDoorFront` の地点セレクタ純関数の合成で行う。

散布の質を上げる規則。全域・中央の候補はパリティ格子 `(x+y)%2==0` に限定して通行を保証する。格子整列は
空間相関ジッタ ±0.25〜0.35 タイルで崩す。全域配置は隣接同型伝播で塊を作る。向きは zone 単位で1回抽選して
揃える。一様乱数の散布は clustering illusion により不自然に見えるため、散らしはブルーノイズに置換する。
StuffKind は原案どおり Furniture / Loot / Being / Decor / Trap を同じ器で扱う。

### 施設の例 —— コンビニ

「店に見える」は実在の店の定石を知っているかの問題で、PCG 論文には載っていない。冷蔵ケースは最奥壁、
レジは入口脇、雑誌は窓沿い、動線は外周 racetrack。定石の出典と施設別の翻訳は追記その3。

```text
Content{ID: "conv_store", ThemeTags: ["shop_basic"],
  Requirements: {MinSize: 20, MinExits: 1, MaxExits: 2},
  Props: {Light: 100, FloorTheme: "linoleum"},
  Groups: [
    {PickEach, [ {Furniture, "walkin_cooler", far_from_origin+wall, Amount: 6},
                 {Furniture, "register",      near_origin,          Amount: 1},
                 {Furniture, "gondola",       row,                  Amount: 3} ]},
    {PickN(2), [ {Loot, "lo_snacks", zone: "gondola", Amount: 2d4},
                 {Loot, "lo_drinks", zone: "cooler",  Amount: 1d4},
                 {Loot, "lo_bento",  wall,            Amount: 1d3} ]},
    {PickOne,  [ {Decor, "sp_litter", full_area, Amount: 1d3+1},
                 {Being, "be_looter", far_from_origin, Chance: 30} ]},
  ]}
```

数値は実基準に根拠を持たせる。小売通路1〜2タイル、倉庫メイン通路3タイル、診察室9.9㎡以上・待合3.3㎡以上は
医療法、コンビニは13×15タイル前後、入口デケレーション半径2タイルは exclusion_zone。神社は参道→鳥居→手水舎→
拝殿→本殿の sequence と狛犬・灯籠の mirror_pair、すなわち日本の「奥」の直列層で最深部に報酬と物語を置く。
民家は水回りの隣接集約と築年変数で「かつて生きていた街」の形態を作る。

### ルート分配 —— 3段間接化と略奪3ノブ

戦利品は部屋タイプ→コンテナ種別→テーブルIDの3段で引く。幾何は部屋に名前を付けるだけで中身を知らず、
バランス調整は該当テーブル1箇所で済む。zone volume の AABB オーバーレイで「カウンター裏だけレジ系」の
細粒度も書ける。大域には保証スポーンと品目クォータの2段を前置してからコンテナ単位の局所抽選に入る。
略奪済み感はコンテナ空振り率・junk 混入率・テーブル変種選択の3ノブで独立に調整する。詳細は追記その3。

### 時間の層 —— 生活痕と廃墟化

配置だけでは新品の店しか出ない。content 確定後に2つの post-pass が時間を刻む。

- usage_wear。部屋の行動遷移表から seed で固定 n 手を引き、小物追加・作業域外への退避堆積・持ち去り欠損を
  適用する。散乱が乱数でなく最後の行動の因果になる
- 廃墟化。exposure・moisture・accessibility のスカラ場3枚 → condition で決まる固定K世代の CA 崩壊伝播 →
  しきい値写像で錆・カビ・植生・瓦礫へ書き換える
- 直交乗算軸。変種・散らかり・損傷を独立抽選し、少量データを数千通りに見せる。CDDA 実測の比率、
  変種 97/0.6/1/0.9/0.5・散らかり 6:3:1・損傷 2:3:1 を初期値にする
- 略奪は anchor 温存・衛星欠損で表す。構造を保ったまま中身を欠くと部屋の可読性が残る。パリンプセストの
  二段 theme、基底時代+転用時代の上書きで時間差分を見せる。詳細は追記その3〜その5

### 世界への据え付け

内装の外側は doc 69 と接続する。lot pass が敷地・塀・門・外構を与え、建物を裸で置かない。FacadePass が
正面判定・窓・看板・シャッターを与える。稀少セットピースは FeatureSpec と Extra 層の2層で分配し、静的 pity
で下限を保証する。歴史は chronicle を一次データに、同名三面刻印と未解決参照の意図的残置で奥行きを出す。
詳細は追記その4とその5。

### 流し込みの決定性

Zorbus のグローバル乱数と per-level 可変キャップは採らない。決定化は3操作に還元する。

- 深さ・試行回数は固定K上限で打ち切り、決定的フォールバックへ落とす
- 候補は slice に集め安定 sort してから seed で引く。Go の map を抽選に使わない
- seed は `childSeed = hash(parentSeed, index)` の引数導出で分岐する。可変な seed スタックや乱数器の
  持ち回りをしない。pass の追加が他 pass の結果を変えない

roomSeed は `(buildingSeed, 部屋index)` から導き、Content を ThemeTags と Requirements で候補化して
roomSeed の重み付き抽選で当てる。施設種の希少度は per-level キャップでなく ThemeTags の重みと Requirements
の厳しさで表す。「研究施設は大都市の大部屋だけ」は `MinSize` と biome 制約で表現でき、可変状態を持たずに
希少化できる。同 seed 2回生成の完全一致テストを CI の必須検査にする。

### 検証

- 到達性のハード制約。ドアから全 stuff の use_area まで BFS 到達可能を配置成立条件にする
- classifyRoom の逆検証。contents から role を推定し、店のはずが店に見えない部屋を reject する。廊下タグの
  幾何検査も同じ枠に入る
- Lynch 検収。生成された街のミニマップで district と landmark が言えるかを自然さのテストにする
- ERA 指標6種と TPKLD 二距離を固定 seed 列の golden 分布で CI 比較する。eyeball の受け入れ基準は
  「2枚並べて違いを言葉にできるか」「この配置から誰が何をしたか読めるか」。詳細は追記その3とその5

### Zorbus からの採用と不採用

| Zorbus の機構 | 採否 | ruins での扱い |
|---|---|---|
| content を幾何から切り離し要件で宣言 | 採用 | `RoomReq` で要件だけ結合。器の芯 |
| placement 意味論 center/wall/full_area/zone | 採用 | `Placement` enum。散布をやめる主装置 |
| 名前付きゾーン zone=vz_... | 採用 | 分割文法が印を付けた区画へ role 配置 |
| ThemeTags でグルーピングし重み抽選 | 採用 | biome・規模から施設種を選ぶ |
| selection グループから1つ選ぶ | 採用 | Stuff の変種を1つ抽選 |
| chance / amount ダイス / if_previous_failed | 採用 | 確率・個数・フォールバック |
| プレハブ Vault と marks の手描き併用 | 部分採用 | 少数の authored 断片は将来。まずは規則生成 |
| room レイアウト生成アルゴリズム | 不採用 | 分割文法(建物→部屋)を使う。理由は下記 |
| per-level 可変キャップ・グローバル乱数配置 | 不採用 | 有界インスタンス内の seed 固定選択に置換 |
| scramble_areas でエリア順を乱す | 不採用 | 決定的選択と相反する |

## 採用しなかった方法

- **Zorbus の room レイアウト生成アルゴリズム(Mike Anderson 方式)** —— area を marks から成長させ post-processing で
  つなぐ方式。優れた汎用ダンジョン生成だが、建物レイアウトは分割文法(建物→部屋)を採る方針であり、
  分割文法のほうが「事務所・コンビニのグリッド区画」という現代日本の建物に素直で、決定的・有界・純関数に自然に乗る。
  Zorbus 方式は将来の自然洞窟や不定形ダンジョンの候補として温存する。本 doc の関心は
  レイアウトでなく内装なので採らない。
- **分割文法だけで内装まで書く** —— 文法規則の中に家具配置を直書きすると、施設種ごとに規則が分岐して肥大する。
  content を別レイヤに切り出し要件で結ぶ Zorbus 方式のほうが、施設追加をインスタンス追加に還元でき拡張性が高い。
- **CDDA の mapgen をそのまま写す** —— 完成マップの手描き前提で工数が合わない。`20260724_69` の結論どおり、真似るのは
  技術であって完成品でない。Zorbus の content モデルはまさにその「少数の再利用可能な規則」に当たる。
- **WFC で内装を敷く** —— 意味的構造を出せない。WFC は隣接ルールしか理解せず「店にはレジがあり入口を向く」を
  出せないため、内装の肌理に用途を限定し、骨格と役割配置は content システムが担う。
- **手描きプレハブだけで内装を作る** —— 量産の工数が無い。少数の authored 断片は Zorbus の Vault 同様に将来の上乗せに
  留め、まずは規則生成でライブラリを埋める。

追記調査で加わった主な不採用。理由の詳細は各追記の一覧表にある。

- **実行時の MCMC・焼きなまし・生 WFC・ソルバ** —— 収束待ちが非有界で純関数と両立しない。Fisher 2015 の
  実測棄却が裏書き
- **廊下の幾何検出・位相検出** —— 誤分類が構造的。生成時宣言 `ZoneCorridor` で置換
- **真 z-level の多層** —— CDDA の自然さは単層平面の性質が大半。外皮 FacadePass と屋根合成で代替
- **動的経済・動的 pity・開封時抽選** —— プレイヤー状態依存は再訪一致を壊す。静的クォータと生成時確定で代替
- **組合せ数の KPI 化** —— 知覚される多様性を保証しない。部屋アーキタイプ数と密度プロファイル数を KPI にする
- **歴史の実シミュレーション** —— 年表レコードの軽量生成と三面刻印で「歴史があったように見せる」

## 追記(2026-07-25): 家具付け手法の横断調査と content モデルの拡張

`r/roguelikedev` の「Furnishing procedurally generated rooms」を起点に、家具付け手法を5ファミリで横断調査した。
Brogue の machines、Caves of Qud の builders/population/zone-template、DF/RimWorld/Unangband の機能先行、制約配置の
学術、vault DSL とデコレータ/スタンプ。5本は強く収束し、本 doc の Zorbus content モデルを拡張する骨格を与えた。Reddit
本体は取得できなかったので、主題を各手法の原典から調べた。

### 貫く原理 —— 「設計された」を生む4条件と決定化の還元

散布を「設計されたもの」に変えるのは、どのゲームでも同じ4条件だった。

1. **保証セット＋ランダム充填**。部屋を部屋たらしめる物を必ず置き、風味だけを抽選する。DF はアンカー家具が部屋を
   定義し、Qud は pickeach＋pickone、Brogue は minimumInstanceCount がこれにあたる。
2. **関係を持つ配置**。壁付け・向き・隣接・整列・対称・「Aの近く/視界内」。散布が原理的に出せない空間の意図。
3. **役割ゾーンの間接化**。空間の意味・埋める内容・座標を三分離する。レイアウトは領域を役割タグ付けし、宣言テーブルが
   タグ→内容を張る。
4. **順序付き決定パイプライン＋到達性ガード**。粗→細で置き、歩行可能性を幾何に焼き込むか flood-fill で保証する。

決定性は還元で担保する。焼きなまし・WFC・candidate-and-score のような反復パスも、seed・反復回数・乱数列・tie-break を
固定し、収束待ちを固定K回＋決定的フォールバックに置換すれば純関数になる。各パスは `roomSeed = hash(buildingSeed,
roomID, passName)` から独立ストリームを引く。**Go の map を配置抽選に使わない**。候補は slice に集め sort してから seed で
引く。この一点を外すと再訪ごとに家具が入れ替わる。

### content モデルの拡張

Zorbus モデルの `Stuff{placement, chance, amount}` を、意味論とより豊かな placement 語彙へ拡張する。

**(1) アーキタイプに配置作法を持たせる。** 各家具型が自分の合法配置を知る。レシピは「レジ1・棚3〜5」と言うだけでよい。

```go
type Archetype struct {
	Footprint Size      // 占有。移動を阻む
	Clearance Clearance // 手前に空けるべき利用・接近マス。塞ぐと使えない
	Default   Placement // 既定の置き方
	Supports  []string  // 上に載せられる物のタグ
	NeedsWall bool
	Tags      []string // sleeping/service/storage/ornate 等。役割で参照する
}
```

**(2) placement 語彙。** center/wall/full_area/zone を、関係と距離・視界の語彙へ広げる。Brogue の MF_* が既存 enum の
上位集合なので増分で足せる。

| モード | 内容 | 出所 |
|---|---|---|
| `wall` | 壁付け。anchor 側＋壁背向きで正面を室内へ | 制約配置 |
| `corner` | 二壁の角。wall より先に走らせる | 制約配置 |
| `row` | 平行列。axis/row_spacing/item_spacing/aisle_width。通路を幾何に焼き込む | 制約配置 |
| `attached` | anchor＋relation: beside/tucked/on_top/flanking/around | 制約配置 |
| `near_origin`/`far_from_origin` | 起点からの距離帯。レジは入口近く、薬は奥 | Brogue |
| `in_view_of_origin` | 起点から見える所。商品はレジから見える | Brogue |
| `not_in_hallway` | 通路を塞がない | Brogue |
| `along_inside_wall`/`outside_door`/`interior` | Qud の hint 語彙 | Qud |

補助フィールド: `orientation`(face_entrance/center/zone/away_from_wall)、`personal_space`(散らして山積みを防ぐ)、
`instance_count`(3〜6)、`alternative`(一群から1つ、intact/looted 等)、`symmetry`(mirror_axis＋flanking)。

**(3) 保証セット＋ランダム充填。** group style を持たせる。散布を殺す芯。

```go
type Group struct {
	Style Style // PickEach=必ず全部 / PickOne=重み1つ / PickN=N個
	Items []Stuff
}
```

`PickEach` で店を店たらしめる物、すなわちレジ・棚を必ず置き、`PickOne/PickN` で風味を抽選する。major/minor の階層と
等価。前段の「アンカー先行」も PickEach の1形。

**(4) 役割ゾーンの間接化。** 分割文法がサブ領域を役割タグ付け(entrance/service/storage/display/social)し、per-role
テーブルが「タグ→重み付き内容」を張る。Brogue の choke 成長を使えば「一扉の奥」を幾何から back-room ゾーンとして
導出できる。

### 決定パイプラインと到達性ガード

家具付けは固定順の pass 列にする。Qud の builders 粗→細、Brogue の順序付き feature list に対応する。地形塗りと物体
配置は別 pass 型にする。

```text
FurnishRoom(roomSeed, room, zoneTags):
  1. door_apron ＋ aisle_skeleton を予約（keep-out）
  2. zone 解決
  3. zone ごと: corner → wall → row → center の major → attached 従属 → minor 装飾
  4. 到達性 assert
```

到達性・修復ガードは有界インスタンスでは必須。塞がった部屋はその seed で永久に塞がる。flood-fill で全ドア連結・全
interactive 家具の到達・店の通路走査を検査する。失敗は blocker を固定順で撤回・移動、最終フォールバックはアンカー
骨格。aisle_skeleton を先に予約すれば歩行可能性が構造的に保証され、事後検査は安全網になる。

### 戦利品パズル = 依存グラフ machine（Brogue）

戦利品は「payload＋それを守る guard machine」にする。鍵は同じ seed 生成が発行し、グラフ全体を1建物 seed に閉じる。
少数の guard カタログ×payload カタログで、内的整合な setpiece が組合せ的に増える。

- 例は施錠された薬局奥。payload=薬を奥ゾーンに far_from_origin、locked shutter で封鎖。鍵=キーカードを前カウンター裏に
  near_origin、この machine 番号を付与。任意で dormant な略奪者を shutter の視界内に。鍵と錠を同一 seed 生成が出すので
  必ず解け、再訪で一致する。
- 一般化してオフィスの金庫＋所長机の鍵、倉庫の檻＋ウインチ。
- `machineNumber` は建物ローカルの連番。グラフは建物を跨がない。
- atomic build-with-rollback。scratch grid に適用し、奥が狭すぎたら巻き戻して非施錠棚 variant へ。elaborate→simple→bare
  の順序付きフォールスルーは seed 決定的。

### theme レコードと authoring 層

seed 由来 theme は Qud のグローバル史をルックアップ化したもの。`hash(worldSeed, footprint)→{era, faction, condition,
motifs}` を静的カタログ引きし、テーブル・占有者・prop mixin を選び、建物ごとに1つ署名オブジェクト、略奪されたレジの
日付付きレシート等を置く。粗いハッシュにすれば地域一貫性も出る。放棄・略奪 theme には「何が起きたか」の手掛かり prop、
バリケード・血痕・避難通知を置く。

authoring 層は Cogmind 風テンプレート。施設のシルエットを reference-char テンプレートで描き、内容は seed で roll、隣接
同一 char は同一物に解決して棚の列を作り、回転・鏡像で4〜8倍、door 数要件を fingerprint にする。vault DSL の
`SUBST`/`NSUBST` ノックアウトで在庫を欠けさせ variant を出す。数十枚で足り、数千枚は要らない。スタンプ、ベッド＋
ナイトスタンド等と対称は最安の「意図」倍率器。再帰アンカー、desk→{on_top: 書類, beside: 椅子} で1指定が furnished
corner を生む。

### 検証と flavor

role-detector を QA に使う。RimWorld の逆で、純関数 `classifyRoom(contents)→role`。店のはずが店に分類されない部屋を
reject・repair する。seed 横断でテストでき、chance ベース配置にも DF の保証を与える。

flavor machine カタログは Brogue 由来。戦利品の無い9割の部屋に、施設別の flavor machine、荒れた棚・倒れたストレッチャー・
蝋燭の輪を置く。戦利品を増やさず character を与え、空き箱部屋を無くす。

### 効き目ランクと段階導入

1. **保証セット＋ランダム充填**(PickEach＋PickOne/PickN)。既存 stuff-list への最小増分で最大効果。まず着手する。
2. **placement 語彙の拡張＋アーキタイプ意味論**。wall(anchor/向き)・corner・row(通路)・attached が「設計された」の主装置。
3. **決定パイプライン＋到達性ガード**。塞がり防止は必須。
4. **役割ゾーン間接化と Cogmind テンプレート**。シルエットを authored、在庫を手続き。
5. **依存グラフ machine と flavor machine**。戦利品パズルと無戦利品部屋の character。
6. **theme レコードと role-detector 検証**。物語的一貫性と QA。

### 採らない・後回し（この追記の範囲）

- **焼きなまし/MCMC の実行時反復**(Merrell 2011, Yu 2011) —— グローバル反復。決定パスへ還元して term だけ採り、sampler は
  捨てる。
- **オーバーワールドタイル場への生 WFC** —— グローバル制約伝播が無限依存連鎖になり純関数性と両立しない。家具の部屋内マイクロ配置には有界 WFC を将来候補に
  するが、固定崩壊順＋リスタート上限→散布フォールバック必須で、まずは順序付き reject パスの方が単純で失敗しない。
- **完全 authored な vault の大量手描き** —— 工数が無い。数十枚のスケルトン＋共有テーブル・スタンプで組合せ変化を出す。
- **candidate-and-score の10〜15案生成**(Archmage) —— 後で品質レバーに。まずは順序パスで足りる。
- **Qud/CDDA のグローバル史・逐次 RNG** —— seed 由来 theme のルックアップと建物ローカル生成に置換する。

## 追記(2026-07-25) その2: 分割文法・決定的組立・密度場の横断調査

前追記が家具付けの5ファミリを整理したのに続き、既存整理と重複しない5つの新規軸を横断調査した。建物の分割文法、決定的モジュール組立、他ゲーム/OSS の特殊部屋実装、宣言的・事例ベースの配置学術、実務家の一次情報。5軸は互いに盲目に走らせたが、いくつかの設計判断へ独立に収束した。収束は裏取りとして本 doc の骨格を補強し、非重複な新知見は content モデルを一段厚くした。

### 5軸を貫く収束 —— 独立経路が同じ設計に着地した

- **幾何と中身の分離は普遍**。CGA shape grammar の scope/split、Shattered Pixel Dungeon の builder/painter 二相、CDDA の palette、Fisher 2012 の occurrence/placement 分離、UE5/Houdini の density 場が、5つの独立分野から同じ「割る責務と詰める責務を分ける」に着地した。本 doc の要件2は業界普遍の原則であると確認できた。
- **ゾーンは entrance からの距離で導ける**。squarified treemap の connectivity tree、cyclic 生成の entrance→goal 距離、space syntax の depth/integration が、独立に「根からの距離でゾーン帯を切る」へ収束した。名前付きゾーンの導出はこの距離ラベリングで具体化する。
- **決定化は3操作へ還元される**。すなわち深さと試行回数の固定K上限、候補を slice に集め安定 sort してから seed 抽選、可変状態を `childSeed = hash(parentSeed, index)` の引数導出へ置換。Minecraft jigsaw の max_depth、arc consistency の伝播と崩壊の分離、grammar の深さ cap が同じ骨に至る。SPD の pushGenerator が可変グローバルで本 doc の要件1に反する点は反面教師。
- **業界的傍証**。ruins のゾーン語彙 entrance/service/storage/display/social は、Marson & Musse が住宅生成で独立に到達した service/private/social とほぼ同型。役割をグラフで先に決め後段で空間へ落とす順序は業界で妥当と裏付けられた。

### 収穫1: 分割文法の実体と layout↔content 契約

本 doc が関心外と棚上げした分割文法に、実装可能な既定案が得られた。content は分割文法の出力に依存するため、供給側の実体と両者の契約だけは本 doc で固定する。

- **分割は決定的 BSP を既定、面積要件が強い施設は squarified treemap**。treemap は目標面積へ aspect ratio を1に寄せて詰める貪欲法で、入力面積 slice の順序のみに依存する。sort→seed で並べれば Go の map を使わず決定的。CGA の scope/split/repeat の概念は、相対分割で形状非依存、repeat で棚を幅いっぱいに可変数、を状態なしで表す裏付けになる。文法エンジンの全実装は YAGNI、概念と面列挙だけ翻案する。
- **契約を型で閉じる**。分割 pass の出力を `Room{ rect Rect; doorways []Doorway; zone ZoneTag }` とする。`zone` は独立ラベリング pass が付与し、entrance 矩形を根に隣接グラフを BFS して根からの距離でゾーン帯を切る。placement 意味論の中央・壁際・全域は rect と doorways から幾何導出し、壁際は CGA 流に壁面を列挙して doorway 隣接面を除外することで、ドアを塞がない棚置きを文脈依存で保証する。
- **生成は非循環パス DAG**。footprint → 分割 → 隣接graph化 → ゾーン分類 → RoomReq 解決 → placement 適用 → 装飾層。各 pass は前段出力のみに依存し、buildingSeed からの一括純関数生成に自然に乗る。Ludomotion の層状パイプラインと Dormans の mission/space 二段分離が同じ形を示す。cyclic 生成の鍵錠ループ機構は施設内装の静的性ゆえ不採用、段階解決の思想のみ採る。

### 収穫2: placement 意味論の統一表現 —— 密度場 + 決定的間引き

UE5/Houdini の attractor-density を翻案すると、center/wall/full_area/zone を個別ロジックでなく1つの「タイル→スカラ density」純関数の族として統一できる。

- 各候補タイルに placement が density を与える。中央は部屋中心を attractor に `density = ramp(1 - dist/max)`、壁際は壁距離の逆、全域は一定、ゾーンは中心ディスクを attractor に。
- 間引きは `density >= hash(seed, x, y) の 0..1 値` で決める。候補は slice に `(density, threshold, stuff)` を積み sort してから走る。map 不使用・再訪一致・グローバル可変なしを同時に満たす。
- 幾何が予約したタイルは density=0 とすることで、UE の exclusion volume に相当する「幾何が先に予約した通路・戸口を塞がない」を自然に取り込む。
- ゾーン契約は矩形に加えディスク `(中心, 半径, stuff)` も許すと表現力が上がる。Reddit の MMalficia の第二パス円が先例。

### 収穫3: 決定化の学術的裏付け —— 伝播と崩壊の分離

本 doc の「有界K回＋決定的フォールバック」に学術的な骨が付いた。

- **arc consistency の伝播と崩壊の分離**。placement 制約で候補 domain から unsupported を除く決定的・有界な伝播 pass と、seed 固定の1回崩壊選択に分ける。WFC の無制限 backtrack はKで打ち切り決定的フォールバックへ還元する。AC-3 の worklist・support・domain の語彙をそのまま使える。
- **Wang tiles の座標ハッシュ決定選択**。辺整合候補から `hash(位置)` で1枚選ぶ。再訪一致・状態なし・並び順非依存が本質的に備わり、slice+sort+seed と完全整合する。
- **occurrence/placement の2段分離**。Fisher 2012 の「何を置くか＝文脈条件付き重みリスト」「どこへ置くか＝placement 意味論」の分離は、本 doc content モデルの直接の学術的裏付け。連続 GMM とベイズ sampler は捨て、重みは学習でなく設計データで与える。
- **space syntax の位相指標**。部屋グラフの depth・integration や可視性を決定的解析 pass で先に算出し、幾何側の位相指標が中身側の重み関数を条件づける。奥の部屋ほど宝箱重み増、統合度が高い部屋ほど通路家具、など。
- **宣言的制約層は仕様・検証に限定**。ASP は placement 妥当性の宣言と golden 検証の語彙として、factor graph は候補スコア合成として採るが、CDCL 探索・RJMCMC の収束待ち sampler は決定性・非有界性ゆえ実行時不採用。

### 収穫4: content モデルの細部拡張

前追記の Archetype/Group/placement 語彙に、非重複な部品を足す。

- **socket 命名でゾーン契約を一般化**。Minecraft jigsaw の name/target のように、部屋の戸口や anchor を socket 名で宣言し、content が同名 socket を要求して意味的に接続する。未接続 socket には既定封鎖 stuff を置く契約を明示する。SnapGridFlow の「未接続辺は Wall で封鎖」が先例。
- **palette の二相解決**。CDDA の char→stuff 対応表を部屋形状から切り離し再利用する。重み付き候補は型で解決規則を切り替える。terrain/furniture は1つ抽選、すなわち sort→累積重み→seed、items/fields は全部適用、すなわち安定順。place_nested の neighbors 近傍条件は footprint 内で閉じる範囲のみ将来採る。
- **地点セレクタ API**。Reddit nesguru の知見。部屋を受け `SelectCenter/SelectWallMidpoints/SelectCorners/SelectDoorFront` の純関数プリミティブを整え、placement 意味論をその合成で表す。テスト容易で決定的。
- **連続 trait の近似一致と対称サブセット**。Reddit fractalpixel の知見。stuff に fancy 等の連続 trait、部屋に目標 trait を持たせ `重み = f(|trait - target|)` を抽選前に確定する。松明・鏡など対称配置されやすい壁家具は対称サブセットとして placement に持たせる。
- **パリティ格子で通行保証**。Reddit GameDesignerMan の知見。全域・中央の候補を `(x+y)%2==0` に限定すれば抽選結果によらず通路が残る。決定的で検証不要、本 doc の aisle_skeleton 予約を安価に補完する。
- **決定的ジッタと隣接同型伝播**。Cogmind の décor 機序。候補点へ seed 由来の小オフセットで整列の単調さを崩す。全域配置で隣接タイルが同じ stuff を引き継ぐと床材・草むらが塊で出て自然。走査順を固定すれば決定的。テンプレート本体は前追記と重複ゆえ見送る。
- **部屋テンプレの重み付き選択＋適用ガード述語**。NetHack の frequency と eligible/mindiff。stuff の重みリストを一段上げ、部屋テンプレ自体の重み選択と階層ガードを contents から分離する。
- **幾何を先に作り役割を後付け割当**。Diablo1 の floodfill re-purpose。生成済み部屋を決定的スコアで役割づけしてから役割別 stuff を流す。RimWorld の逆 classifyRoom と接続し QA にも効く。DCSS の ORIENT enum は placement 意味論の型化の先例、DF の連続矩形面積実測は area 要件の充足判定側の設計を示す。

## 追記(2026-07-25) その3: ドメイン定石・活動駆動・略奪表現・評価の横断調査

前2追記が「どう置くか」の技術を固めたのに対し、本追記は技術の外側を埋める5軸を調査した。実世界の店舗・建築の定石、人間の活動・アフォーダンスから配置を導く学術、サバイバル系の部屋定義とルート分配、ニューラル室内合成と ProcTHOR、荒廃表現と生成器の品質評価。ruins は「略奪された日本の店」を出したいゲームであり、配置技術だけでは新品のコンビニしか出ない。本追記が「らしさ」の残り半分を埋める。

### 5軸を貫く収束 —— 配置の単位は束、決定化は一次文献が裏書きした

- **アンカー付きの束への三重収束**。ProcTHOR の Semantic Asset Group、すなわち親アセットに子をアンカーで結んだ複合エントリ。認知心理学 Scene Grammar の実証、すなわちシーンは anchor object と衛星オブジェクトのフレーズ集合で組織され人は anchor を頼りに理解する。Fu 2017 の activity バンドル、すなわち活動が成立するカテゴリ集合を単位に補完する。3つの独立分野が「配置の抽選単位は単品でなくアンカー付きの束」に到達した。前追記の attached・再帰アンカーはこの束の一形であり、束を第一級の抽選単位に昇格させる。机だけあって椅子が無い抽選事故を構造的に防ぐ。
- **決定化方針の一次文献による裏書き**。Fisher 2015 は MCMC を「提案コストが高く連鎖の混合が遅すぎる」と実測で棄却し greedy 逐次挿入を採用したと明記する。Qi 2018 の MCMC は1部屋20〜40分を要する。キッチン三角形の現代的定式化は0-1整数計画で確率もサンプラも登場しない。本 doc の「反復は固定K回＋決定的フォールバック」は学術の実務でも同じ結論に達している。
- **略奪表現の三面一致**。Scene Grammar の「anchor 温存・衛星欠損」という文法の故意の違反、サバイバル系のコンテナ空振り率・junk 混入率、Ma 2016 由来の持ち去り欠損が、いずれも「構造を保ったまま中身を欠く」に収束する。部屋の可読性を壊さず略奪済みを表現する原則になる。

### 収穫1: 実世界定石を content 定義へ —— 施設文法

「店に見える」は突き詰めると実在の店の定石を知っているかの問題で、PCG 論文には載っていない。業界資料から施設別の定石を placement 語彙へ翻訳した。1タイル約1m。

- **コンビニの文法**。ウォークイン冷蔵ケースは最奥壁に連続配置し裏1タイルをバックヤードにする。目的買いの飲料を最奥に置き往復で全棚の前を通らせるのが実在の設計意図。レジは入口脇 near_origin、雑誌ラックは窓沿いか入口側の壁で賑わいを演出、ゴンドラは中央 row で通路1〜2タイル、動線は外周 racetrack。標準は50〜60坪、13×15タイル前後。
- **負の placement を第一級に**。小売のデケレーションゾーン、すなわち入口から2〜4タイルは何も置かない余白、参道、廊下はいずれも「置かない帯」である。`exclusion_zone` を content 定義の第一級要素にする。密度でなく空白が設計された印象を作る。door_apron・aisle_skeleton の予約と同じ機構で表せる。
- **sequence と mirror_pair の意味論**。神社は参道→鳥居→手水舎→拝殿→本殿が一軸に直列し、狛犬・灯籠は軸対称の対。origin からの順序付き配置 `sequence` と軸対称ペア `mirror_pair` の2語彙が要る。対は軸からの符号反転オフセットで決定的に生成できる。
- **向きの整列は zone 単位で1回抽選**。オフィス島・ゴンドラ・ベンチは同一 zone 内で回転を揃えるだけで人工感が跳ね上がる。stuff 単位でなく zone 単位で向きを1回引く。
- **数値は実基準に根拠を持たせる**。診察室9.9㎡以上・待合3.3㎡以上は医療法の実基準。小売通路1〜2タイル、倉庫メイン通路3タイル、廊下2タイル。診療所は受付が待合と診察の境界で双方を見通せる位置、待合の椅子は対面を避ける。民家は水回りの隣接集約が間取りらしさの核、伝統民家は田の字型。倉庫は U字動線で入口近くに検品台、最奥に高価値保管。

### 収穫2: use_area と活動駆動の生活痕

- **use_area 方向付きクリアランス**。Archetype に「使用側オフセット領域」を追加し、配置成立条件を footprint の空きと use_area の歩行可能の二重判定にする。Qi 2018 の affordance map、Fisher 2015 の interaction maps と activity free space、Kán 2017 の4方向 clearance が全て同一のデータ形式に還元される。前追記の Clearance をこれで方向付きに具体化する。gaze・touch の相互作用語彙はタイル世界では「use_area から遮蔽なしで見える」「use_area に隣接」の2語彙に簡約してよい。
- **functional_triangle 制約**。厨房系は貯蔵・水場・火元の3 role 間のタイル距離に min/max 帯を課す。NKBA の実数値、各辺1.2〜2.7m・周長4〜8m をタイル換算で持つ。帯判定は純関数、満たせなければ距離最小へフォールバック。
- **usage_wear pass**。content 確定後に走る生活痕の pass を新設する。Ma 2016 の行動駆動進化の還元で、部屋の行動遷移表から seed で固定 n 手を引き、各手が key stuff の use_area 側へ小物を追加し、既存 stuff を working zone 外へ最小距離退避させ、一部を持ち去り済みとして削除する。廃墟の散乱を乱数散布でなく「最後に行われた行動の帰結」として決定的に出す。椅子は机から引き出された向きで止まり、退避物は作業域の縁に堆積する。終端を略奪・逃走に偏らせるだけで廃墟性が出る。
- **circulation のハード制約化**。Kán 2017 の到達不能率を翻案し「ドアから全 stuff の use_area まで BFS 到達可能」を配置成立条件にする。到達性ガードの具体形。

### 収穫3: ルート分配の3段間接化と略奪の3ノブ

サバイバル系4作が共通して「アイテム→コンテナ、コンテナ→部屋タイプ」の間接化を採る。

- **部屋タイプ→コンテナ種別→テーブルIDの3段**を content モデルの正式構造にする。Project Zomboid の procList 形式、すなわち重み付きテーブル参照の slice に min/max と採用確率を添える形を Go の定義型で写す。幾何は部屋に名前を付けるだけで中身を知らない。バランス調整は該当テーブル1箇所で済み局所的。
- **zone volume オーバーレイ**。7 Days to Die の sleeper/loot volume の静的翻案。幾何の部屋矩形とは別に content 層が AABB で loot zone・脅威 zone を宣言する。カウンター裏だけレジ系テーブル、のような部屋より細かい粒度も書ける。開封時抽選は不採用とし、seed とコンテナ座標から生成時に確定させる。
- **大域パスの2段構え**。抽選前に The Long Dark 型の保証スポーン制約を敷き、DayZ 型の品目クォータを seed 付きシャッフルで施設群へ分配してから、コンテナ単位の局所抽選に入る。DayZ の教訓は経済ループとタグ照合語彙が分離できることで、動的なのは補充ループだけ、タグ照合は静的移植できる。
- **略奪済み感の3ノブ**。コンテナ空振り率、junk 混入率、テーブル変種選択。いずれも seed 純関数のまま独立に調整できる。世界単位やチャンク単位で変種を1つ引けば再訪一致と探索の変化が両立する。

### 収穫4: ProcTHOR 参照アーキテクチャと開発時 LLM 下書き

- **ProcTHOR は本 doc と同じ問題を静的注釈＋段階サンプリングだけで解いた大規模実証**。ニューラルでなく純手続き。room spec の木→再帰分割→部屋タイプ組ごとの接続確率→家具→小物の段構成は本 doc の pass 設計と同型で、16 spec から10^11 超の間取りを出した。持ち帰るのは4点。部屋別必須度 rw 0〜3 のスケール、edge/corner/middle と standalone 禁止の placement 注釈、Semantic Asset Group という anchor 付き複合エントリ、receptacle 対応表による小物の二段 pass。18 SAG で約2000万通りという「少数の束で組合せ爆発を得る」実績値も参考になる。
- **配置 pass の副段階分解**。ATISS の属性分解に倣い、種類→位置→向きを独立の決定的ステップに分け、向きの定石は facing 属性の静的表で持つ。学習分布そのものはドメイン不一致で数値が移植できず、形式のみ採る。
- **開発時 LLM 下書きワークフロー**。Holodeck が示すとおり LLM は記号的制約の生成では安定し、数値座標を書かせると破綻する。LayoutGPT の実測で類似例なしの座標生成は範囲外率43%が86%へ跳ねる。そこで施設別 content 定義を「座標なし・記号のみ」で LLM に下書きさせ、スキーマ検証と人手レビューを経て静的データへ焼き込む。実行時バイナリには LLM も検索も残さない。Holodeck の5分類制約語彙 global/distance/position/alignment/rotation は placement enum の網羅性チェックリストに使う。

### 収穫5: 廃墟化 post-pass とシーン文法

- **廃墟化 post-pass の3層設計**。清潔な内装グリッドと theme と seed を受け取る純関数。第1層は決定的スカラー場3枚、破口・窓からの BFS による exposure、水源からの減衰 BFS による moisture、開放近傍数による accessibility。第2層は固定K世代のセルオートマトンによる崩壊伝播で、K は condition から決める。severe は K=6、light は K=2。γ-ton tracing の「壊れた所ほど壊れやすい」フィードバックは CA の遷移規則が自然に表現する。第3層は場のしきい値写像で錆・カビ・植生・瓦礫へ書き換える。植生は moisture と exposure の積が高い所、汚れは accessibility が低い隅。TLOU の因果規則、根は水源沿い・植物は割れ窓の光へ、がそのまま場の式になる。
- **Scene Grammar のフレーズ配置と略奪の文法違反**。配置を部屋 role→フレーズ集合の抽選→anchor を placement で置き衛星を anchor 相対の固定オフセット候補列で置く、の2段にする。略奪は anchor 温存・衛星欠損として表現する。anchor ごと消すと部屋の可読性が壊れるため避ける。Võ らの「anchor がシーン理解を支える」実証に基づく。
- **ヴィネット演算子**。バリケード、ドア隣接タイルへ家具を移動し向きを揃える。脱出跡、出口へ向かう散乱列。生活痕、一角だけ清掃済みと寝床と火気。各ヴィネットは幾何述語と theme 述語の前提条件と有界の書き換えを持つ純関数スタンプにする。Worch & Smith の矛盾回避則、ゲーム内で起きない事象を痕跡にしない、は前提条件の静的検査として機械化する。
- **Fallout 4 の教訓**。幾何キットの組み立てと clutter による語りの層を分離して大規模生産を成立させた。幾何と中身の分離が AAA の実運用でも同じ形になる傍証。

### 収穫6: 設計されたもの度の定量化

進捗の「設計されたもの度をメトリクスで測る」を具体化する。

- **内装向け ERA 指標**。全てグリッドの純関数。密度 = 家具タイル/床タイル。壁際率 = 壁隣接家具/家具総数。到達率 = 入口 BFS 到達床/全床。対称度 = 1 − 左右反転との不一致率。anchor 被覆率 = anchor 半径2以内の家具/家具総数。迂回度 = 入口→奥の最短路長/マンハッタン距離。condition ごとに期待帯を持たせる。新品店舗は対称度が高く、略奪後は落ちるのが正しい。
- **運用は golden 分布の CI 比較**。固定 seed 列 0..N-1 で N 個生成し、指標ペアの2Dヒストグラムを golden として commit、CI で再計算し差分検知する。決定的なので flaky にならない。ペアは密度×対称度と到達率×迂回度から始める。
- **Tile Pattern KL-Divergence の二距離**。手置きの模範内装を参照分布に、生成集合との距離を品質、生成集合内ペアの平均距離を多様性とする。設計されたもの度は「一様ランダム配置との距離」として定義でき、ランダムから遠く模範に近いほど設計的。廃墟化 pass の前後で両距離を追えば「設計性を適度に壊しランダムには落としていない」を回帰テストで担保できる。
- **Danesh の概念のみ**。対話ツールは不要で、ヘッドレスの固定 seed メトリクス計算、golden 差分検知、オフラインのパラメータ探索スクリプトの3点を CI へ移す。探索は非決定でよく、見つかったプリセットだけを commit すればゲームの決定性は保たれる。

## 追記(2026-07-25) その4: CDDA ベンチマーク解剖と到達可能性の判定

ゴールを「CDDA レベルのマップの自然さ」に固定し、ベンチマークとの差分を測る5軸を調査した。CDDA そのものの実測解剖、敷地・都市肌理レイヤ、知覚多様性の理論、立体と建物外皮、稀少セットピースの分布。CDDA リポジトリは 2026-07-24 時点 master を実際にスパースクローンして計測した。

### CDDA の自然さの分解 —— 実測

| 対象 | 実数 |
|---|---|
| mapgen JSON | 897 ファイル、262,214 行、エントリ 6,760 個 |
| 1画面マップ | 2,865 枚。うち住宅の手描き地上階レイアウト 115 種 |
| palette | 513 本。item_group 5,457 本、うち家具別収納 SUS_* 251 本 |
| 都市生成の機構 | C++ 約600行。中心距離1変数＋正規分布1本＋重み表 houses177/shops223/parks51 |
| 生活感の直交軸 | 変種 97/0.6/1/0.9/0.5、散らかり 6:3:1、損傷 2:3:1、警報 1:3 を palette が独立抽選 |
| 稀少シーン | specials 212 件＋map_extra 77 種。道路 1/100、屋内 1/90 発火、テーブル内重み比 3500:1 |
| snippet | graffiti 68・survivor_notes 380 ほか53ファイル。タグ展開 `<city>` で文脈増幅 |
| 屋根 | 自動生成なし。全建物の屋根 om_terrain 495 種が手描き |

分解の結論。**CDDA の自然さ = 高密度の手描きデータ × 薄いが的確な直交抽選機構**。タイル単位の見た目の説得力は7〜8割がデータ由来で、部屋の形・家具の並び・動線は全て人が描いている。一方「同じ家を二度見ない」感覚の5割以上は機構由来で、palette 直交合成が115レイアウトを数千通りに乗算する。都市スケールの自然さはほぼ機構由来で必要データは重み表450行程度。

### 総合判定 —— 条件付きで到達可能

| 自然さの成分 | CDDA の実現手段 | ruins での充足 | 判定 |
|---|---|---|---|
| 都市の文法。都心商店・郊外住宅・町外れ | 距離＋正規分布＋重み表の薄い機構 | 機構移植のみ。チャンク類型構想と整合 | **機構で届く** |
| 敷地への埋まり。庭・塀・私道 | テンプレートへの焼き込み | lot pass の新設。本追記収穫1 | **機構で届く** |
| 建物の外形。窓・入口・看板・屋根 | 手描き。屋根は495種人手 | FacadePass＋屋根合成。機構化で CDDA を超えうる | **機構で届く** |
| 散らかり・損傷・変種の乗算 | palette 直交合成 | 廃墟化 post-pass を損傷軸と位置づけ、散らかり軸・変種軸を追加 | **機構で届く** |
| 稀少シーンの分布 | specials＋map_extra の2層 | FeatureSpec＋Extra 層の2層。静的 pity | **機構で届く＋少量データ** |

| コンテンツの絶対量 | 15年分26万行 | 不要。直交乗算軸の移植で少量データを数千通りに見せる | **数週間規模の authoring で閾値超え** |

**結論: 条件付きで到達可能**。CDDA がデータで賄う成分の大半は機構で代替でき、その機構の多くは本 doc の前3追記で設計済み。残る条件は2つ。第一に「部屋単位の説得力」の機構代替が実際に効くかで、これは本 doc の placement 意味論・束抽選・施設文法の実装と eyeball 検証で確かめるしかない。第二に少量の authoring 投資で、見積りは部屋テンプレ30〜60種、日本の家具収納グループ40〜80本、物語バリアント10〜20種、セットピース15〜25種、テキスト断片150〜300本。合計数週間規模で、26万行の正面戦は不要。

### 収穫1: 敷地レイヤ —— 建物を裸で置かない

CDDA の house01.json 検証で判明した重要事実。**CDDA は parcel 分割をしていない**。敷地は塀・門・芝・パティオ・5%確率の事故車両チャンクごと 24x24 テンプレートに焼き込まれている。CDDA 級の見た目に区画分割アルゴリズムは必須でなく、本質は「建物が裸で地面に置かれない」こと。

- **lot pass の挿入**。チャンク→道路→街区抽出→敷地短冊分割→敷地分類→footprint→外構→内装。街区の道路沿い長辺を間口幅で刻む1パスで、Vanegas 系の再帰やリジェクトは不要。チャンク境界の道路端点は境界座標のハッシュで両側チャンクが独立に同じ答えを出し、縫合不要。
- **日本の敷地5類型**。戸建短冊は間口4〜6タイルで塀囲い・前庭なし。旗竿地は短冊分割の剰余に幅1タイル通路を通す救済で、接道義務の帰結がそのまま日本らしさの演出になる。商店街は間口2〜3タイルの店舗兼住宅連続。団地は lot 分割せず1街区に南面平行配棟を関数で敷く。ロードサイドは footprint を後方へ寄せ前面を駐車場で埋め道路際に看板。
- **外構の語彙**はアンカー別テーブルで持つ。境界上に塀・生垣・門、前面帯に駐車・アプローチ、外壁沿いに室外機・給湯器、南側に物干し・菜園、道路側に電柱30m間隔・自販機・ゴミ集積所。ポスアポのオーバーレイとして放置車両・バリケード・雑草・崩れ塀を確率つきチャンクで重ねる。

### 収穫2: 外皮と屋根 —— 多層は必須ではない

CDDA の自然さを分解すると、窓が通りに並ぶ・入口が正面・店がガラス張り・建物が道路に向く、という**単層平面で完結する性質**が大半を占める。CDDA 自身 z-level 凍結時代から自然と評価されていた。足りないのは立体でなく外皮。

- **FacadePass を最優先で新設**。分割文法の後、content の前に挟む。正面判定は道路に最も近い外周辺、入口は front 辺に1個、窓は背後の部屋役割で決まる。居室は3〜4タイルごとに窓1、水回りは小窓、階段室・収納は無し、角1タイル以内は開口禁止。店舗は front 壁をガラス帯＋看板に置換し、腐朽度からシャッター閉鎖率を導く。**シャッター商店街はポスアポ日本で最も安い説得力の源泉**。
- **屋根は描画側の合成1パス**。footprint の縦横比から棟線と勾配面を導出、ビルはパラペット＋屋上設備。CDDA は495種を手描きしており、ここを機構化できれば CDDA を超える部分になる。
- **「同じ建物の2階」は BuildingPlan の純関数**で解く。footprint 包含・階段室固定・分割線継承の3規則。CDDA が手書きペアテンプレで保証していたものの機械化。廃ビル・2階建て住宅の類型に限定導入し、全建物に義務付けない。真 z-level は不採用。CDDA ですら10年がかりの大改修で、ステージ遷移方針と衝突する。

### 収穫3: 知覚多様性 —— 組合せ数を KPI にしない

Rabii & Cook の定理が理論的に確定させた。部品のランダム結合は可能性空間を指数的に膨らませるが知識を何も加えず、知覚的に平凡な oatmeal を量産する。ProcTHOR の2000万通りという数字は知覚される作り込みを保証しない。

- **変種投資の優先順位**。部屋アーキタイプ数 > フロアレイアウトパターン数 > 密度プロファイル数 > 家具プール数 > 小物数。家具スワップの掛け算より構造軸。No Man's Sky の失敗と Origins での改善が同じ順序を実証した。
- **二層構造**。大多数の背景の部屋は perceptual differentiation 水準でよく、プールスワップと密度揺らぎで足りる。uniqueness 投資は全部屋の1〜2割の hero 部屋に集中する。
- **believability の敵は乱数でなく意図の不在**。CHI 2026 の実験でプレイヤーは人間製と機械製をほぼ判別できないが、機械っぽさの記号を見つけた瞬間に評価が下がる。説明のつかない生成結果には瓦礫・崩落など視覚的理由付けを必ず添える。The Swindle の教訓。
- **rare は孤立させる**。von Restorff 効果により、異質な項目は孤立しているほど記憶される。landmark 級は1フロア1個を目安に、複数置くなら種類と場所を離す。Cogmind の性格配分、報酬46%・雰囲気25%・リスクリワード15%・危険14%を部屋予算表の初期値にする。
- **密度と緊張のカーブ**。均一密度が最悪の単調さを生む。L4D の intensity 管理を静的翻案し、密集と空白・危険と安全を空間軸上で交互配置する。

### 収穫4: 直交乗算軸 —— CDDA の実比率を初期値に

CDDA の生活感の正体は palette の直交合成で、実測した比率がそのまま ruins の初期値に使える。

- **変種軸**。標準97%・放棄0.6%・建築中1%・サバイバリスト0.9%・ためこみ症0.5%。数十軒に1軒だけ事情のある家が出る。
- **散らかり軸**。整頓6:乱雑3:汚部屋1。乱雑は「あるべきでない場所の物」の上書きで、食卓に食器50%、床に洗濯物、机に郵便物20%。
- **損傷軸**。無傷2:小破3:大破1。3分の2の家に何らかの損傷。ドア破損3/20、窓破壊2/11、家具全壊1/80。本 doc の廃墟化 post-pass はこの軸に相当する。
- 家具の中身は家具1種に1テーブルの収納グループで持つ。CDDA の SUS_* 方式。日本なら押入れ・仏壇・下駄箱・神棚など40〜80本で生活感の閾値を超えると推定。

### 収穫5: 稀少セットピース —— 2層分配と静的 pity

- **2層分離**。地図に残る FeatureSpec セットピース層と、チャンク独立抽選の Extra 層を別機構で持つ。CDDA の specials / map_extras の分業と同型。Extra は `hash(seed, "extra", chunkID)` で 1/N 発火し重みテーブルを引く。null 重みを必ず置き、追加しても総発火率が動かない安全弁にする。
- **頻度は桁で分ける**。common 1/50〜500、rare 1/5千〜5万、legendary は保証のみ。CDDA の1テーブル内 3500:1 が示すとおり、中途半端な頻度ばかりだと全部が「たまに見るやつ」に均されて記憶に残らない。
- **静的 pity**。Minecraft の salt 独立リージョン配置に、スーパーリージョン内 argmin のリージョンへ必ず1つ置く保証を重ねる。動的 pity timer は純関数の背骨を壊すので不採用、空間クォータで完全代替できる。triangular 寄せ、乱数2つの平均、で間隔分散も締まる。
- **テキスト増幅**。タグ展開つき snippet プール。`<地名>` の差し込みは最寄り Settlement 名を doc 69 の「生成せず算出」で引く。落書き・避難所の伝言・張り紙・レシートは2026日本の世界観と相性が良い。類型×場所述語で、車両事故は道路上・生活痕は建物内のみ発火。
- **発見の記録**。セットピース発見時にオーバーマップへ印と名前を残す。記憶は「見た」でなく「記録された」ときに定着する。CDDA の autonote 方式。

### 必須条件チェックリスト —— 5軸統合版

1. 全建物が lot を持ち道路に間口を持つ。門→玄関の経路が接続し、塀が境界を可視化する
2. FacadePass。入口は道路側、窓は部屋役割、店はガラス帯と看板、腐朽度でシャッター
3. footprint からの決定的屋根合成で外形の輪郭を作る
4. 敷地5類型が地区タイプで出し分けられる
5. 散らかり・損傷・変種の直交軸を独立抽選し、少量データを数千通りに乗算する
6. 部屋アーキタイプ数を多様性 KPI にし、hero 部屋1〜2割に uniqueness を集中する
7. 説明のつかない生成結果に視覚的理由付けを添える。意図の不在が唯一のバレ筋
8. FeatureSpec/Extra の2層分配、頻度の桁分離、静的 pity、タグ展開 snippet、発見の記録
9. authoring 投資。部屋テンプレ30〜60種・収納グループ40〜80本・物語バリアント10〜20種・セットピース15〜25種・テキスト150〜300本

## 追記(2026-07-25) その5: 自然さ・現実感・奥深さの知覚機序

問いを一段掘り下げ、「何が人に、生成された感のない自然さ・現実感・奥深さを知覚させるか」を5軸で調査した。都市・建築理論、視覚統計と計算美学、歴史と内的整合、アポフェニアと物語投影、実ゲーム世評の解剖。前提の仮説は「自然さの知覚は生成側でなく受容側の性質」であり、5軸すべてがこれを裏付けた。

### 5軸を貫く答え —— 自然さを知覚させる5機序

1. **相互応答の痕跡**。要素が互いを入力に持つこと。Alexander の not-separateness、Antonov の「インフラから外へ。一貫性は気づかれずに感じられるべき」、URR の相関の網、制約適応としての roughness が同じ結論。oatmeal の正体はローカル独立抽選がこれを破壊すること。粗さはノイズで汚すのでなく、川で歪む街路・斜面で欠ける区画のように**制約充足の副産物**として生む。
2. **統計的中間帯**。機械っぽさは白色ノイズ極と過剰規則極の2つに寄る。自然と手作りは中間、1/f 型スペクトルと中程度の複雑性に集まる。数値目標が立つ。下地フィールドのスペクトル勾配 β≈2.0、輪郭のフラクタル次元 D=1.3〜1.5、タイル遷移エッジ密度 0.25〜0.40。一様乱数は塊を生み「乱数を撒くほど不自然」になるためブルーノイズへ置換する。
3. **読める構造と場所の個性**。Lynch の5要素が揃うとメンタルマップが作れ「理解できた」感覚が現実感として返る。個性は量でなく署名で、1ロケーションに決定的に1つの際立つ特徴を保証する方がバリエーション増より効く。echoes、街ごとのモチーフパラメータ束を配下の全生成が参照する仕組みが genius loci の実装体。
4. **時間の層**。奥行きの正体は時間差分の知覚。廃墟のリアリティは「かつて生きていた街の形態」が前提で、生きていた形が滅びているから哀感が出る。宮崎英高の Elden Ring 論、かつて街や村だった場所がいま敵の徘徊する廃墟である、は ruins のコンセプトの直接の裏付け。
5. **補完労働の誘発**。人は3要素と関係だけから物語を構築し、しかも解釈は収束する。Heider & Simmel の実測で97%が同じ人格を読んだ。説明はこの補完労働を奪い世界を浅くする。プレイヤーの脳が最後の生成器であり、生成側の仕事は関係の配置と整合の保証まで。

### 収穫1: 生きた構造の文法 —— Alexander 15特性の生成規則化

The Nature of Order の15特性を1つずつタイル生成規則へ翻訳した。15特性を手続き生成の規則系として体系適用した先行研究は確認できず、先行例の薄い領域である。

- 全面採用: levels of scale は分割比 1:2〜1:3 の制約。strong centers は中心先決の生成順序で anchor 研究と合流。alternating repetition は A B A B の周期関数。good shape は矩形合成と凹凸上限。local symmetries は「全体対称は死に、局所対称は生きる」で対称スケールに上限。contrast は隣接地区のパラメータ距離に最小閾値。gradients は街内部の中心距離勾配。echoes はモチーフ束。the void は街に1つの装飾密度ゼロ領域。simplicity は密度上限と「置かない」への明示的重み。not-separateness は独立抽選の全廃という原則そのもの。
- 翻案: boundaries は 2〜4 タイルの遷移帯。positive space は残余空間の凸性検証。deep interlock は軒下・縁側・店先という半屋外の第3タイル種。
- Lynch の5要素は検収条件にする。道の3階層、チャンク横断の edge、入った瞬間に分かる district、交差点 node、街ごとに一意の landmark 1〜2個。「ミニマップを見て地区と目印が言えるか」がそのまま自然さのテスト。
- prospect-refuge は可視性の検証規則に還元。入口から全タイルが見える部屋を禁止し遮蔽を1つ保証、広場の縁に物陰の帯。
- Jacobs の翻訳は**築年変数**。街区内で昭和木造・文化住宅・平成マンションを分散させ「かつて生きていた街」の形態を作る。echoes が場所の共通性、築年が時間の多様性で、両方あって実在の街になる。
- 日本の「奥」。中心に象徴を置く西洋型でなく、門→前庭→主屋→奥の直列層で最深部に報酬と物語を置く。神社・旧家・施設の敷地テンプレートに使う。

### 収穫2: 統計的シグネチャの数値目標

- **下地フィールドの 1/f 化**。高度・密度・劣化の連続フィールドを spectral synthesis か diamond-square で生成し、2D FFT の径方向スペクトル勾配を β≈2.0、許容 1.8〜2.4 に制御。D=(5−β)/2 の関係で輪郭次元と連動するため、単一の 1/f 下地から両目標を同時制御できる。
- **輪郭のフラクタル次元 D=1.3〜1.5**。街外形・道路網・瓦礫帯・水際を box-counting で測り逸脱を補正。D=1.4 で皮膚コンダクタンスのストレス最小、D=1.3 で前頭α波最大という生理実験の裏づけを持つ唯一の明確な選好帯。直線直角だけの街区は D≈1.0 で人工的。
- **配置は一様乱数を捨てる**。clustering illusion により人はランダムの塊を不自然と感じる。ポアソンディスクで最小間隔を保ち、格子整列には ±0.25〜0.35 タイルのジッタを空間相関ノイズで与える。近接物が似た向きにずれると手作業の癖に近づく。
- **複雑性のガードレール**。タイル遷移エッジ密度 0.25〜0.40、種別エントロピーを最大の 0.5〜0.7 倍、圧縮率を中域に。局所に対称ランドマークを1〜2割混ぜ処理流暢性を確保する。
- **不気味さは双方向ダイヤル**。不安の源は曖昧さでなく非典型特徴。通常ゾーンは妥当性検証と人の痕跡で下げ、恐怖ゾーンだけ非典型を1〜2個局所挿入する。wabi-sabi は独立規則でなくこれらの美学的裏づけとして統合。非対称・奇数・むらのある風化。

### 収穫3: 奥行き = 歴史の知覚

- **二重帳簿の原理**。世界内の痕跡と参照可能な記録が同一の決定的年表を指すとき、奥行きは検証可能性から生まれる。DF の Legends はプレイヤーの大半が読まないのに、読めるという事実だけで信頼が成立する。軽量な年表レコードを一次データとし、地名・snippet・署名オブジェクトを全てそこからの導出にする。
- **同名三面刻印**。歴史エントリは最低3つの表現面に同じ固有名詞で現れて初めて「歴史」と知覚される。Qud の教え。因果整合の検証器は不要で、同名反復だけを保証する決定的参照解決で足りる。神話的曖昧さはコスト削減と両立する。
- **未解決参照は資産**。言及されるだけで生成されない地名・人名が「地図の端の向こう」を作る。Tolkien の未踏の遠景。全参照解決はむしろ世界を小さく見せる。生成しない場所こそ最も安価なコンテンツ。封鎖入口の署名オブジェクトは必ず「その先」の地名参照とペアで出す。
- **矛盾の設計**。同一事件を faction 別に食い違う語りで出す。実在の史料も矛盾し、全知の一貫性はむしろ作り物臭い。整合検証は事実レイヤーのみに掛け、語りレイヤーの矛盾は推奨とする。
- **パリンプセストの二段 theme**。基底時代と転用時代の2レコードを重ね、窓を塞いだ煉瓦・教室の避難所間仕切りのような用途変更の痕跡を上書き配置する。ポスアポ日本は崩壊前・避難期・崩壊後の三層が自然に取れる。
- **faction スタイルシート**。URR の相関の網。各勢力に色・記号・梱包様式を決定的に割り当て、プレイヤーが「この青いテープはあの派閥だ」と未知の廃墟で推論できるようにする。推論可能性が内的整合性の知覚そのもの。

### 収穫4: アポフェニア設計 —— プレイヤーの脳が最後の生成器

- **chronicle / sift / narrativize の3層分離**。Ryan のアーキテクチャを設計語彙として輸入する。世界生成時に「実際に起きたこと」の内部 chronicle を決定的に生成し、プレイヤーに見せるのは narrativize された断片だけ。整合の保証は chronicle 側の責務、曖昧さは表出側の権利。手書きフレーバーは生成された事実に矛盾しない範囲で意味を上乗せする。これが apophenia hacking のコンテンツ制作規約になる。
- **最小物語ユニットは3要素＋関係**。二体の白骨の距離と向き、内側からバリケードされた扉、開いた金庫と散った紙幣。関係トリプルを決定的に配置するだけで説明文は不要。要素が孤立するとただの瓦礫に落ちる。受け入れ基準は「この配置から誰が何をしたか読めるか」。
- **1ロケーション1個性、1断片1事実**。オートミール対策はバリエーション増でなく署名的特徴の保証。テキスト断片は chronicle の事実を1つ露出し、動機・因果は空ける。生成テキストに世界観の総括や解説を語らせない。
- **Ship Log 型の知識記録**。発見した断片を関係網で自動記録する外部記憶。Outer Wilds の知識ベース進行と Kreminski の retelling 支援を同時に満たす最小実装。確定判定は Obra Dinn 式に控えめで、複数断片の整合が揃った時だけ静かに裏書きする。
- **決定性を物語資産として売る**。リロール不能な世界は「実際に起きた事実」になり、undo 不能性が結果の物語化を強制する。シードを世界の固有名として UI で前面に出せば、同一世界の目撃談共有という Boatmurdered 型のコミュニティ語りが構造的に可能になる。GM 型の動的介入は narrative paradox を再導入するので入れない。

### 収穫5: 世評から逆算した投資優先ランキング

批評・レビュー・開発者証言から「生きた世界」の根拠を抽出し、投資順に並べた。

1. **機能的一貫性**。空間が「何のためにあったか」から導出されていること。称賛される全ての世界の最下層にこれがある
2. **意味連鎖の clutter**。小物単体でなく2〜5個の組で出来事を語らせる。Bethesda の実測、プレイヤーは建築の反復より小物の反復に先に気づく
3. **骨格と固有性の分離**。kit は建築的同一性、固有性は clutter・照明・敵の別レイヤで与える。反復管理の核
4. **密度が広さに勝る**。神室町の雑居ビル論、壁一枚で別世界。日本らしさは建物の形より自販機・電柱・貼り紙という生活インフラの記号
5. **歴史の二層重ね**。Disco Elysium の2つの70年代、弾痕の壁
6. **遠望とループ**。見えた場所へ行ける、通った場所へ抜けられる。構造理解の報酬化
7. **プレイヤーに無関心な無駄**。報酬にならない失せ物掲示。世界がプレイヤーの都合で存在しないことの証明
8. **システム文法の隠蔽**。マーカー・規定数タスクの露出がテーマパーク批判の引き金
9. **反応性・事後シミュレーション**。風化・浸水・植生の後処理が作為の指紋を消す
10. **手作り断片の縫合比率**。Valheim の受容が示す、生成の自然さの相当部分は埋め込まれた手作り局所が担う

## 追記(2026-07-26) その6: 廊下の定義

layout↔content 契約の未決だった「廊下」を定義する。要点は概念分離と、検出でなく生成時宣言。

### 概念分離 —— 廊下は2層ある

| 層 | 実体 | 例 | 扱い |
|---|---|---|---|
| 部屋間廊下 corridor | 部屋と部屋を繋ぐ建築要素 | 診療所の患者動線、中廊下型民家 | 本追記で定義。`Room` の一種 |
| 部屋内通路 aisle | 部屋の中の歩行帯 | ゴンドラ間、フォークリフト路 | 定義済み。aisle_skeleton 予約と exclusion_zone、密度場 density=0 |

コンビニに廊下は無く aisle だけがあり、診療所の動線は部屋になっていない corridor である。未定義だったのは corridor 側だけ。

### 定義方式 —— 検出でなく生成時宣言

- 幾何検出、幅≤2 かつ縦横比≥3 を廊下とみなす、は不採用。細長い納戸を誤検出し、広いロビーの廊下的機能を取りこぼす。
- 位相検出、部屋グラフの関節点を廊下とみなす、も不採用。田の字民家では居室が通路を兼ねて関節点になり誤分類する。
- **採用は生成時宣言**。ruins は決定的生成であり、分割文法は「接続のために作った」ことを知っているから、生成時に `zone = ZoneCorridor` をタグ付けする。検出は QA 側に回し、classifyRoom の逆演算「廊下タグの部屋が幾何的にも廊下らしいか」を回帰テストにする。role-detector 方針と対になる。Brogue の not_in_hallway は掘削の副産物としての廊下を事後検出するための語彙で、宣言方式の ruins は同じ語彙をより安く持てる。

### 生成パターン3種 —— 施設類型で選ぶ

```
1. spine-first  廊下を先に引く。entrance から軸方向に幅Wの帯を予約し、
                残りを両側へ BSP 分割する。診療所・オフィス・学校。
                日本の中廊下型住宅そのもの
2. repair       BSP 後の到達性修復。ドアだけで到達できない部屋があれば
                最短路で廊下を挿入する。Marson & Musse の方式。旗竿地の
                竿と同型の「救済が演出になる」パターン
3. none         廊下なし。コンビニ・倉庫は単室で aisle のみ、
                田の字民家は襖で居室が直結し縁側が半屋外通路を担う
```

診療所の患者動線とスタッフ動線の分離は spine-first を2本引く拡張で表す。これが施設らしさの決め手になる。

### corridor 部屋の性質 —— 既存機構への接続

- **content**: RoomReq 照合から除外し、廊下専用の軽い content のみ許す。消火器・掲示・傘立て・スリッパ棚を wall 配置、stuff 密度ほぼ0。追記その3の負の placement「廊下は置かない帯」と一致する。
- **ゾーン分類**: BFS 距離ラベリングは廊下を通過して数える。廊下自体も depth を持つが content 重みには使わない。
- **幅の実基準**: 民家1タイル、診療所2タイル、車椅子すれ違い、学校2〜3タイル。追記その3の数値表に加える。
- **知覚面**: 廊下は Alexander の thick boundary、部屋を直結させず間に挟む帯、と「奥」の直列層、門→廊下→奥の間、の実装体。prospect-refuge 検証では廊下の見通しが prospect、脇の部屋口が refuge になる。

## 追記(2026-07-26) その7: 非民家の room 定義拡張

VRT の montage で非民家の部屋割りと中身が単調だった原因を分解すると、資産でなく room 定義の不足に行き着いた。民家は役割→content の表 `houseRoomContents` で9種の部屋を作り分けるのに対し、店と診療所は役割が実質 main/back の2種に潰れ、奥室が全部同じ倉庫・全部同じ診察室になる。CDDA のコンビニ・食料品店・診療所を基準に、足りない room 型を洗い出す。

### 根本原因 —— 役割カタログが民家にしか無い

- `roleContent`(multiroom.go) は非民家を main / back / corridor の3役割にしか写さない。`houseRoomContents` 相当の「役割→content 表」が店・診療所に無く、`back` は `backRoomContent` の施設1種へ収束する。
- `clinicContent` は単室診療所の名残で、待合の主室に `exam_bed`×3 + `medcabinet`×3 を積む。多部屋化した今、待合にも診察台が出て待合に見えない。scope 過大。
- 薬局奥の施錠戦利品は `guardedLoot` をテストで後付けするだけで、部屋型になっていない。

### 足りない room 型（CDDA 基準）

不足の芯は資産でなく定義。トイレ・オフィス・薬局を作る什器(便器・流し・机・薬棚)は in-game raw も揃っている。

| 施設 | 不足している room 型 | 定義する既存什器 |
|---|---|---|
| 店 | レジ帯・バックオフィス・従業員トイレ・冷蔵庫室・休憩室 | register / desk・chair / toilet・sink / walkin_cooler / table・chair |
| 診療所 | 受付(待合と分化)・薬局(施錠)・トイレ・医師室・供給室 | reception / medcabinet・meds / toilet・sink / desk・chair / medcabinet・bandage |

唯一の資産欠落は `desk` に VRT スプライトが無い点。オフィス・受付室を VRT で見せるには single/ に desk スプライトを起こす。他の room は新規資産ゼロで定義できる。

### 設計 —— `houseRoomContents` を全施設へ横展開する

役割→content の表を施設ごとに持ち、`roleContent` はまず施設カタログを引く。テンプレ(PlanStore/PlanClinic)は奥室へ多様な役割名を割り当てる。

```go
// facilityRoomContents は施設種別ごとの「役割名→content」表を返す。houseRoomContents を民家以外へ
// 横展開したもの。テンプレが付けた役割名で各室の内装を引く。表に無い役割は backRoomContent へ落とす。
func facilityRoomContents(facility string) map[string]Content

// roleContent は施設カタログ優先で content を引く。main は施設の顔、それ以外は施設カタログ、無ければ奥室既定。
func roleContent(facility, role string, seed uint64) Content {
	if role == "main" {
		return facilityContent(facility, seed)
	}
	if c, ok := facilityRoomContents(facility)[role]; ok {
		return c
	}
	return backRoomContent(facility)
}
```

役割名の割り当て(テンプレ側):

```
店 PlanStore:   sales=main / 奥室を storeroom・office・restroom・coldroom へ抽選で振り分け
診療所 PlanClinic: waiting=待合専用content / 診察室=exam / 奥に pharmacy(施錠)・restroom・office を混ぜる
```

`clinicContent` は待合専用へ切り出し `exam_bed` を抜く。診察台は `examRoomContent` にだけ置く。薬局は部屋型 `pharmacy` にして、`guardedLoot` の施錠戦利品を待合でなく薬局部屋へ紐付ける。

### 検証

段別・変種ゴールデンで、店の奥室がオフィス・トイレ・倉庫に分かれ、診療所の奥室が診察室・薬局・トイレに分かれることを目視する。`classifyRoom` の署名表に restroom(toilet+sink)・office(desk)・pharmacy(medcabinet+meds) を足し、役割どおりに分類できることを回帰テストにする。

## 追記(2026-07-26) その8: 外形の articulation と庭 —— 矩形を埋め尽くさない

建物が全て clean な矩形で、外周と内壁のパターンが少ない。玄関の凹み・張り出し・L字が無い。さらに footprint が広く、各部屋が広がりすぎて余る。CDDA の家屋は overmap タイルを矩形で埋めず、前庭の芝・玄関ポーチの凹み・張り出したガレージ・L字/コの字の平面・中庭を持つ。ruins は逆に footprint 矩形を全部屋で埋めるので単調で余る。

### 根本原因 —— footprint = 建物になっている

- overworld の `drawUrbanBuilding` が footprint 矩形の外周を壁・内側を床に描き、interior はその矩形を全部屋で埋める。建物は必ず footprint と同じ clean な矩形になる。
- 「部屋が広すぎる」は footprint が広いのに引き算が無いから。日本家屋の部屋は狭く、余剰は庭・土間・縁側が吸う。

### 設計 —— 建物を footprint より小さく取り、差分を庭にする

余剰空間を*引き算*で消す。3つの独立軸で articulation と庭を足す。

```go
// Site は footprint 内の敷地計画。建物輪郭・庭・部屋・入口を分ける。overworld と VRT が同じ Site を描く。
// footprint をそのまま埋めず、建物を内側へ取り、差分を庭(dirt+観葉)にする。
type Site struct {
	Footprint Rect         // overworld が渡す区画。この中で敷地計画する
	Building  Rect         // 建物の外周矩形。入口側に前庭を空け footprint より内側へ寄る
	Garden    map[Vec]bool // footprint 内の建物外タイル。前庭・玄関の凹み・坪庭。dirt で描き観葉を点在
	Door      Vec          // 建物壁上の入口。footprint 辺でなく建物辺に寄る。前庭が街路との間に挟まる
	Rooms     []HouseRoom
}
```

- **軸A 坪庭(部屋を庭に)**: テンプレの1室を役割 `garden` にする。その室の内側を garden タイル(dirt+観葉)にし家具を置かない。壁は残るので囲われた坪庭・光庭になる。テンプレ非依存で「部屋が広すぎる」を最も安く解く。広い1室を庭に引くと余剰が消える。
- **軸B セットバック前庭**: 入口側に前庭を空け、建物を footprint より内側へ取る。入口を建物辺へ寄せ、街路との間に前庭(dirt+観葉)を挟む。CDDA の lawn setback の最小版。
- **軸C 玄関ポーチの凹み**: 入口の壁を1マス凹ませてポーチにする。外形が clean な矩形でなくなり、玄関が読める。張り出しは屋根整合が要るので凹みを先に入れる。

### 検証

VRT の montage で、坪庭・前庭・玄関の凹みが出て外形と部屋の広さが変わることを目視する。overworld は Site の garden を dirt、building 輪郭を壁として描き、VRT と一致させる。garden タイルは既存の dirt を使い、観葉 prop を点在させる。芝タイルは資産が要るので今後。中庭・L字/コの字・張り出し・縁側は articulation の拡張として今後。

## 追記(2026-07-27) その9: VRT=in-game の徹底 —— 本番サイズと単一 prop フィルタ

コードレビューで、施設テンプレ(PlanStore/PlanClinic/PlanHouse)が in-game で一度も発火しないことが判明した。本番の市街地チャンクは 20x20 で、街路 4 を引き setback で縮めた建物区画は最大でも 14x12 程度。テンプレ下限 22/24 に満たず、planRooms は常に BSP(SubdivideBuilding)へ落ちる。だが建物ゴールデンは 26x18/28x20 という本番より大きい footprint を使い、テンプレの間取り・焼き込み玄関・戦利品を描いていた。VRT が「in-game を写す」前提が、footprint と prop の両方で崩れていた。

### 判断 —— 現状のチャンクサイズを正とし、テンプレを本番サイズで発火させる

当初は「BSP を正とし VRT を BSP に合わせる」方向で書いたが、それだと in-game の建物が「言われないと何の施設か分からない」main/back のままで、本 doc の目的(施設と分かる平面)を満たさない。チャンク拡大は影響が広く採らない。よって**現状のサイズ(20x20 チャンク → footprint 13〜16)を正とし、その狭さでテンプレが発火するようテンプレ側を直す**。VRT はその本番サイズをそのまま写す。

- **テンプレ下限を本番サイズへ下げる**: `facilityPlanner` の下限を 22/24 から 12x9 まで下げる。setback 後の建物 14x12 程度でも店・診療所・民家テンプレが発火する。footprint 13(建物 11x10)だけは分割不能で BSP の1室に落ちるが、これは最小の一部にとどまる。
- **狭さ向けのコンパクト民家を足す**: 10室廊下型は 24x16 が要るので本番に入らない。`PlanHouseCompact` を追加し、24x16 未満は living/bedroom/kitchen/bath の田の字4室へ切り替える。`PlanHouseAny` がサイズで両者を振り分ける。
- **前庭を浅くする**: `frontYard` を 3 から 2 へ。前庭を深く取りすぎると建物がテンプレ下限を割るので、庭とテンプレ発火を両立させる。
- **footprint を本番サイズに揃える**: 建物・段別ゴールデンを `prodFootprint`(16)で回す。テンプレが発火した施設の間取りに、setback 前庭・玄関ポーチ・確率的坪庭・経年が乗る実態を写す。
- **prop フィルタを単一ソースにする**: `interiorPropRaw` を overworld から interior の `PropRawName` へ移す。overworld の spawn と VRT の描画が同じ関数を引くので、片方だけが戦利品を描く/置くという乖離が構造的に起きない。VRT は in-game に出る prop(家具＋raw のある装飾)だけを描く。
- **集合一致をテストで固定**: `TestSpriteFiles_描画対象とingameのspawnが一致する` が spriteFiles と PropRawName の Ref 集合が完全一致することを守る。片方に Ref を足し忘れると落ちる。
- **発火と非退化を回帰テストで固定**: `TestFurnishBuilding_施設テンプレが本番サイズで奥室を役割へ分化する` がテンプレが BSP の back を出さず施設固有役割を出すことを、`TestFurnishBuilding_部屋が退化しない` が全室が内側床を持つことを、本番 footprint 範囲の多 seed で守る。閾値・比率割りの退行をゴールデン目視より前に止める。footprint の範囲はその10で 24 チャンク基準へ更新した。

## 追記(2026-07-27) その10: CDDA サイズ感 —— チャンク24・一辺開放の前庭・坪庭の見送り

その9でテンプレを本番サイズで発火させた後、VRT を見ると建物・部屋が CDDA より一回り小さく、前庭が建物を全周で囲む細い帯になって「壁に囲まれた土」に見えた。原因は縮尺と前庭の取り方の2点。

### 判断 —— 縮尺をチャンク24へ上げ、前庭を道路側の一辺だけ開放する

CDDA の縮尺は1建物=1OMT=24タイルで、建物本体が18〜22を占め部屋は5〜10マス角。現行は20チャンク→建物~14で部屋内側~5×4と、CDDA の寝室1室に家1軒を詰めていた。VRT の評価基準を CDDA のサイズ感に置き、器そのものを CDDA へ寄せる。

- **チャンクを 20→24 に上げる**: `NewOverworldDefinition` の chunk を 24x24 に。CDDA の1OMTと同縮尺。span20→footprint 17〜20→建物~18×17→部屋内側~7×6 で、CDDA の寝室〜居間サイズになる。1チャンク=1建物の縮尺は保つ。
- **前庭を一辺開放にする**: `insetBuilding` を入口側の一辺だけ内寄せに変える。他の3辺は footprint の縁まで建物で埋め、庭を道路側の一辺の全幅に集める。全周の細い帯が消え、堀に見えなくなる。CDDA の前庭も道路側に広く取るもの。
- **坪庭を一旦やめる**: `pickGardenRoom` と `roleGarden` の室機能を削る。建物内の土の中庭は四方が壁で「囲まれた土」の一因だった。`Site.Garden` の仕組みは前庭で使い続ける。和風町家など固有施設に絞って再導入できる余地は残す。

### 積み残し

- 部屋が広くなったぶん、什器の密度が薄く床が余る。部屋面積に応じた什器量のスケールは今後。
- 前庭は土だけで殺風景。芝・生垣・観葉の散布は資産を見て今後。
- 民家は建物~18幅で 24x16 の10室廊下型が入らず、コンパクト4室のまま。廊下型を出すにはチャンク28相当が要る。今後の判断。
