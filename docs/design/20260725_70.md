# 施設内装の生成 —— Zorbus の content モデルの翻案

## 背景

`20260724_69` のリアルさ改善で、タイル級の内装がランダム散布で「店に見えない」と測定・指摘された。
役割ベースの家具配置でごま塩をやめる方針は立てたが、その配置規則をどんな器で書くかは未確定だった。

Zorbus のビルド解説 `building.zorbus.net` を読み、内装への応用を検討した。Zorbus は2つの独立した仕組みを持つ。
一方は部屋レイアウトの生成アルゴリズム、他方は部屋へ中身を流し込む content システム。**施設内装に効くのは後者の
content システム**である。前者は本 doc の関心ではない。理由は後述する。

Zorbus の content システムの要点は、中身の宣言を**幾何から切り離す**ことにある。content は「どの prefab か」でなく
「どういう area が要るか」を要件で宣言し、要件を満たす任意の area に流し込まれる。60を超える待ち伏せ prefab の
いずれにも同じ待ち伏せ content が入る。中身は placement 意味論を持つ stuff の重み付きリストで、家具・戦利品・敵・
装飾を**意味のある位置**に置く。これがランダム散布と決別して「設計されたもの」に見せる核心である。

## 要件

- **決定的な純関数**。内装は建物という有界インスタンス内で `buildingSeed = hash(runSeed, footprint)` から一括生成し、
  再訪で一致し serde 安全であること。建物という有界インスタンス内に置く。`20260724_69` の生成
  パイプラインでは Feature 層が建物を配置し、その内側の内装を本 doc が担う。
- **幾何と中身の分離**。content は area 要件で宣言し、特定の部屋形状や prefab に固定しない。器を1つ足すだけで施設種を
  増やせること。
- **placement 意味論**。家具・戦利品を中央・壁際・全域・名前付きゾーンなど意味のある位置へ置き、散布をやめる。
- **データ化可能**。最初は Go 定義、器が固まったら TOML/raw へ。`20260724_69` の Content 語彙 TOML 化の指針と揃える。
- **グローバル状態を持たない**。Zorbus は per-level の可変キャップとグローバル乱数で content を撒くが、これは
  `20260724_69` が却下したステートフル配置である。有界インスタンス内の seed 固定選択に置き換える。

## 設計

### 器の全体像

内装生成は「content 定義」と「room への流し込み」に分ける。room レイアウトは建物を再帰分割して部屋にする
分割文法が供給する。その分割文法は本 doc の関心外で別途設計する。分割文法が部屋矩形と出入口・ゾーンを
確定し、本 doc の content システムがその部屋へ中身を流す。

```go
// Content は1種類の内装の「どういう部屋に・何を・どこへ」を1つにまとめた宣言。
// 特定の部屋形状に縛られず、Requirements を満たす任意の部屋へ流し込まれる。
type Content struct {
	ID           string
	ThemeTags    []string   // 施設種のグルーピング。biome や規模から重み付き抽選する
	Requirements RoomReq    // どういう部屋が要るか
	Props        ContentProps // 部屋全体に効く性質
	Stuff        []Stuff    // 置く中身の並び。上から順に評価する
}

// RoomReq は content が要求する部屋の条件。幾何との結合を要件だけに留める。
type RoomReq struct {
	MinSize  int      // 最小床面積
	MinExits int      // 最小出入口数
	MaxExits int      // 最大出入口数。0 は「行き止まり限定」を表せる
	Zones    []string // 必要な名前付きゾーン。無い部屋は候補から外す
}

// ContentProps は部屋全体の性質。照明・施錠・音などランタイム表現に効く。
type ContentProps struct {
	Light      int    // 明るさ
	FloorTheme string // 床材テーマ
	ChestLock  int    // 宝箱の施錠確率
}
```

### stuff —— placement 意味論を持つ中身

散布をやめる要は、各 stuff が置き場所を持つことである。Zorbus の placement=center / top_wall / full_area /
zone を翻案する。

```go
// Placement は stuff の置き場所。ゼロ値の暗黙でなく明示の enum にする。
type Placement int

const (
	PlaceRandom   Placement = iota // 空きマスへランダム。最後の手段
	PlaceCenter                    // 部屋中央。レジ・祭壇など主役
	PlaceWall                      // 壁際。棚・ベッド・什器
	PlaceFullArea                  // 全域へ散らす。血痕・瓦礫・落ち葉など装飾
	PlaceZone                      // 名前付きゾーン。分割文法が印を付けた区画
)

// StuffKind は中身の種類。家具・戦利品・敵・装飾・トラップを同じ器で扱う。
type StuffKind int

const (
	StuffFurniture StuffKind = iota // 什器・設備
	StuffLoot                       // 戦利品。ロールタグから抽選
	StuffBeing                      // 敵・NPC
	StuffDecor                      // 装飾。血・litter・crushed 床
	StuffTrap                       // トラップ
)

// Stuff は1つの配置指示。chance で確率、amount でダイス個数、zone で区画を指定する。
type Stuff struct {
	Kind      StuffKind
	Ref       string    // 家具ID・ロールタグ・敵ID など Kind に応じた参照
	Placement Placement
	Zone      string    // Placement==PlaceZone のときの区画名
	Chance    int       // 0..100。省略は必ず置く
	Amount    Dice      // 個数。1 固定や 1d3+1 など
	IfPrevFailed bool   // 直前の stuff が置けなかったときだけ試すフォールバック
}
```

### 施設の例 —— コンビニ

「店に見える」を placement で表す。レジは中央、棚は壁際、商品は棚ゾーン、床の汚れは全域。

```text
Content{ID: "conv_store", ThemeTags: ["shop_basic"],
  Requirements: {MinSize: 20, MinExits: 1, MaxExits: 2},
  Props: {Light: 100, FloorTheme: "tile"},
  Stuff: [
    {Furniture, "register",   PlaceCenter, Chance: 100, Amount: 1},
    {Furniture, "shelf",      PlaceWall,   Chance: 100, Amount: 3d2},
    {Loot,      "lo_snacks",  PlaceZone,   Zone: "shelf", Amount: 2d4},
    {Loot,      "lo_drinks",  PlaceZone,   Zone: "shelf", Amount: 1d4},
    {Decor,     "sp_litter",  PlaceFullArea, Amount: 1d3+1},
    {Being,     "be_looter",  PlaceRandom, Chance: 30, Amount: 1d2},
  ]}
```

### 流し込みの決定性

Zorbus のグローバル乱数と per-level 可変キャップは採らない。代わりに有界インスタンス内で seed 固定の選択にする。

- 建物内の各部屋に、分割文法が確定した `(buildingSeed, 部屋index)` から `roomSeed` を導く。
- その biome・規模・部屋位置に合う Content を、ThemeTags と Requirements で候補化し、`roomSeed` から重み付き抽選する。
- Content 内の Stuff を上から評価し、`chance`・`amount`・placement を `roomSeed` 由来の PRNG で解決する。順序と
  乱数列が seed だけに依存するので、再訪で完全一致し serde 不要になる。
- 施設種の希少度は per-level キャップでなく、ThemeTags の重みと Requirements の厳しさで表す。「研究施設は大都市の
  大部屋だけ」は `MinSize` と biome 制約で表現でき、可変状態を持たずに希少化できる。

### Zorbus からの採用と不採用

| Zorbus の機構 | 採否 | ruins での扱い |
|---|---|---|
| content を幾何から切り離し要件で宣言 | 採用 | `RoomReq` で要件だけ結合。器の芯 |
| placement 意味論 center/wall/full_area/zone | 採用 | `Placement` enum。散布をやめる主装置 |
| 名前付きゾーン zone=vz_... | 採用 | 分割文法が印を付けた区画へ role 配置 |
| ThemeTags でグルーピングし重み抽選 | 採用 | biome・規模から施設種を選ぶ |
| selection グループから1つ選ぶ | 採用 | Stuff の変種を1つ抽選 |
| chance / amount ダイス / if_previous_failed | 採用 | 確率・個数・フォールバック |
| プレハブ Vault と marks の手描き併用 | 部分採用 | 少数の authored 断片は将来。まずは規則生成 |
| room レイアウト生成アルゴリズム | 不採用 | 分割文法(建物→部屋)を使う。理由は下記 |
| per-level 可変キャップ・グローバル乱数配置 | 不採用 | 有界インスタンス内の seed 固定選択に置換 |
| scramble_areas でエリア順を乱す | 不採用 | 決定的選択と相反する |

## 採用しなかった方法

- **Zorbus の room レイアウト生成アルゴリズム(Mike Anderson 方式)** —— area を marks から成長させ post-processing で
  つなぐ方式。優れた汎用ダンジョン生成だが、建物レイアウトは分割文法(建物→部屋)を採る方針であり、
  分割文法のほうが「事務所・コンビニのグリッド区画」という現代日本の建物に素直で、決定的・有界・純関数に自然に乗る。
  Zorbus 方式は将来の自然洞窟や不定形ダンジョンの候補として温存する。本 doc の関心は
  レイアウトでなく内装なので採らない。
- **分割文法だけで内装まで書く** —— 文法規則の中に家具配置を直書きすると、施設種ごとに規則が分岐して肥大する。
  content を別レイヤに切り出し要件で結ぶ Zorbus 方式のほうが、施設追加をインスタンス追加に還元でき拡張性が高い。
- **CDDA の mapgen をそのまま写す** —— 完成マップの手描き前提で工数が合わない。`20260724_69` の結論どおり、真似るのは
  技術であって完成品でない。Zorbus の content モデルはまさにその「少数の再利用可能な規則」に当たる。
- **WFC で内装を敷く** —— 意味的構造を出せない。WFC は隣接ルールしか理解せず「店にはレジがあり入口を向く」を
  出せないため、内装の肌理に用途を限定し、骨格と役割配置は content システムが担う。
- **手描きプレハブだけで内装を作る** —— 量産の工数が無い。少数の authored 断片は Zorbus の Vault 同様に将来の上乗せに
  留め、まずは規則生成でライブラリを埋める。

## 追記(2026-07-25): 家具付け手法の横断調査と content モデルの拡張

`r/roguelikedev` の「Furnishing procedurally generated rooms」を起点に、家具付け手法を5ファミリで横断調査した。
Brogue の machines、Caves of Qud の builders/population/zone-template、DF/RimWorld/Unangband の機能先行、制約配置の
学術、vault DSL とデコレータ/スタンプ。5本は強く収束し、本 doc の Zorbus content モデルを拡張する骨格を与えた。Reddit
本体は取得できなかったので、主題を各手法の原典から調べた。

### 貫く原理 —— 「設計された」を生む4条件と決定化の還元

散布を「設計されたもの」に変えるのは、どのゲームでも同じ4条件だった。

1. **保証セット＋ランダム充填**。部屋を部屋たらしめる物を必ず置き、風味だけを抽選する。DF はアンカー家具が部屋を
   定義し、Qud は pickeach＋pickone、Brogue は minimumInstanceCount がこれにあたる。
2. **関係を持つ配置**。壁付け・向き・隣接・整列・対称・「Aの近く/視界内」。散布が原理的に出せない空間の意図。
3. **役割ゾーンの間接化**。空間の意味・埋める内容・座標を三分離する。レイアウトは領域を役割タグ付けし、宣言テーブルが
   タグ→内容を張る。
4. **順序付き決定パイプライン＋到達性ガード**。粗→細で置き、歩行可能性を幾何に焼き込むか flood-fill で保証する。

決定性は還元で担保する。焼きなまし・WFC・candidate-and-score のような反復パスも、seed・反復回数・乱数列・tie-break を
固定し、収束待ちを固定K回＋決定的フォールバックに置換すれば純関数になる。各パスは `roomSeed = hash(buildingSeed,
roomID, passName)` から独立ストリームを引く。**Go の map を配置抽選に使わない**。候補は slice に集め sort してから seed で
引く。この一点を外すと再訪ごとに家具が入れ替わる。

### content モデルの拡張

Zorbus モデルの `Stuff{placement, chance, amount}` を、意味論とより豊かな placement 語彙へ拡張する。

**(1) アーキタイプに配置作法を持たせる。** 各家具型が自分の合法配置を知る。レシピは「レジ1・棚3〜5」と言うだけでよい。

```go
type Archetype struct {
	Footprint Size      // 占有。移動を阻む
	Clearance Clearance // 手前に空けるべき利用・接近マス。塞ぐと使えない
	Default   Placement // 既定の置き方
	Supports  []string  // 上に載せられる物のタグ
	NeedsWall bool
	Tags      []string // sleeping/service/storage/ornate 等。役割で参照する
}
```

**(2) placement 語彙。** center/wall/full_area/zone を、関係と距離・視界の語彙へ広げる。Brogue の MF_* が既存 enum の
上位集合なので増分で足せる。

| モード | 内容 | 出所 |
|---|---|---|
| `wall` | 壁付け。anchor 側＋壁背向きで正面を室内へ | 制約配置 |
| `corner` | 二壁の角。wall より先に走らせる | 制約配置 |
| `row` | 平行列。axis/row_spacing/item_spacing/aisle_width。通路を幾何に焼き込む | 制約配置 |
| `attached` | anchor＋relation: beside/tucked/on_top/flanking/around | 制約配置 |
| `near_origin`/`far_from_origin` | 起点からの距離帯。レジは入口近く、薬は奥 | Brogue |
| `in_view_of_origin` | 起点から見える所。商品はレジから見える | Brogue |
| `not_in_hallway` | 通路を塞がない | Brogue |
| `along_inside_wall`/`outside_door`/`interior` | Qud の hint 語彙 | Qud |

補助フィールド: `orientation`(face_entrance/center/zone/away_from_wall)、`personal_space`(散らして山積みを防ぐ)、
`instance_count`(3〜6)、`alternative`(一群から1つ、intact/looted 等)、`symmetry`(mirror_axis＋flanking)。

**(3) 保証セット＋ランダム充填。** group style を持たせる。散布を殺す芯。

```go
type Group struct {
	Style Style // PickEach=必ず全部 / PickOne=重み1つ / PickN=N個
	Items []Stuff
}
```

`PickEach` で店を店たらしめる物、すなわちレジ・棚を必ず置き、`PickOne/PickN` で風味を抽選する。major/minor の階層と
等価。前段の「アンカー先行」も PickEach の1形。

**(4) 役割ゾーンの間接化。** 分割文法がサブ領域を役割タグ付け(entrance/service/storage/display/social)し、per-role
テーブルが「タグ→重み付き内容」を張る。Brogue の choke 成長を使えば「一扉の奥」を幾何から back-room ゾーンとして
導出できる。

### 決定パイプラインと到達性ガード

家具付けは固定順の pass 列にする。Qud の builders 粗→細、Brogue の順序付き feature list に対応する。地形塗りと物体
配置は別 pass 型にする。

```text
FurnishRoom(roomSeed, room, zoneTags):
  1. door_apron ＋ aisle_skeleton を予約（keep-out）
  2. zone 解決
  3. zone ごと: corner → wall → row → center の major → attached 従属 → minor 装飾
  4. 到達性 assert
```

到達性・修復ガードは有界インスタンスでは必須。塞がった部屋はその seed で永久に塞がる。flood-fill で全ドア連結・全
interactive 家具の到達・店の通路走査を検査する。失敗は blocker を固定順で撤回・移動、最終フォールバックはアンカー
骨格。aisle_skeleton を先に予約すれば歩行可能性が構造的に保証され、事後検査は安全網になる。

### 戦利品パズル = 依存グラフ machine（Brogue）

戦利品は「payload＋それを守る guard machine」にする。鍵は同じ seed 生成が発行し、グラフ全体を1建物 seed に閉じる。
少数の guard カタログ×payload カタログで、内的整合な setpiece が組合せ的に増える。

- 例は施錠された薬局奥。payload=薬を奥ゾーンに far_from_origin、locked shutter で封鎖。鍵=キーカードを前カウンター裏に
  near_origin、この machine 番号を付与。任意で dormant な略奪者を shutter の視界内に。鍵と錠を同一 seed 生成が出すので
  必ず解け、再訪で一致する。
- 一般化してオフィスの金庫＋所長机の鍵、倉庫の檻＋ウインチ。
- `machineNumber` は建物ローカルの連番。グラフは建物を跨がない。
- atomic build-with-rollback。scratch grid に適用し、奥が狭すぎたら巻き戻して非施錠棚 variant へ。elaborate→simple→bare
  の順序付きフォールスルーは seed 決定的。

### theme レコードと authoring 層

seed 由来 theme は Qud のグローバル史をルックアップ化したもの。`hash(worldSeed, footprint)→{era, faction, condition,
motifs}` を静的カタログ引きし、テーブル・占有者・prop mixin を選び、建物ごとに1つ署名オブジェクト、略奪されたレジの
日付付きレシート等を置く。粗いハッシュにすれば地域一貫性も出る。放棄・略奪 theme には「何が起きたか」の手掛かり prop、
バリケード・血痕・避難通知を置く。

authoring 層は Cogmind 風テンプレート。施設のシルエットを reference-char テンプレートで描き、内容は seed で roll、隣接
同一 char は同一物に解決して棚の列を作り、回転・鏡像で4〜8倍、door 数要件を fingerprint にする。vault DSL の
`SUBST`/`NSUBST` ノックアウトで在庫を欠けさせ variant を出す。数十枚で足り、数千枚は要らない。スタンプ、ベッド＋
ナイトスタンド等と対称は最安の「意図」倍率器。再帰アンカー、desk→{on_top: 書類, beside: 椅子} で1指定が furnished
corner を生む。

### 検証と flavor

role-detector を QA に使う。RimWorld の逆で、純関数 `classifyRoom(contents)→role`。店のはずが店に分類されない部屋を
reject・repair する。seed 横断でテストでき、chance ベース配置にも DF の保証を与える。

flavor machine カタログは Brogue 由来。戦利品の無い9割の部屋に、施設別の flavor machine、荒れた棚・倒れたストレッチャー・
蝋燭の輪を置く。戦利品を増やさず character を与え、空き箱部屋を無くす。

### 効き目ランクと段階導入

1. **保証セット＋ランダム充填**(PickEach＋PickOne/PickN)。既存 stuff-list への最小増分で最大効果。まず着手する。
2. **placement 語彙の拡張＋アーキタイプ意味論**。wall(anchor/向き)・corner・row(通路)・attached が「設計された」の主装置。
3. **決定パイプライン＋到達性ガード**。塞がり防止は必須。
4. **役割ゾーン間接化と Cogmind テンプレート**。シルエットを authored、在庫を手続き。
5. **依存グラフ machine と flavor machine**。戦利品パズルと無戦利品部屋の character。
6. **theme レコードと role-detector 検証**。物語的一貫性と QA。

### 採らない・後回し（この追記の範囲）

- **焼きなまし/MCMC の実行時反復**(Merrell 2011, Yu 2011) —— グローバル反復。決定パスへ還元して term だけ採り、sampler は
  捨てる。
- **オーバーワールドタイル場への生 WFC** —— グローバル制約伝播が無限依存連鎖になり純関数性と両立しない。家具の部屋内マイクロ配置には有界 WFC を将来候補に
  するが、固定崩壊順＋リスタート上限→散布フォールバック必須で、まずは順序付き reject パスの方が単純で失敗しない。

## 追記(2026-07-25) その2: 分割文法・決定的組立・密度場の横断調査

前追記が家具付けの5ファミリを整理したのに続き、既存整理と重複しない5つの新規軸を横断調査した。建物の分割文法、決定的モジュール組立、他ゲーム/OSS の特殊部屋実装、宣言的・事例ベースの配置学術、実務家の一次情報。5軸は互いに盲目に走らせたが、いくつかの設計判断へ独立に収束した。収束は裏取りとして本 doc の骨格を補強し、非重複な新知見は content モデルを一段厚くした。

### 5軸を貫く収束 —— 独立経路が同じ設計に着地した

- **幾何と中身の分離は普遍**。CGA shape grammar の scope/split、Shattered Pixel Dungeon の builder/painter 二相、CDDA の palette、Fisher 2012 の occurrence/placement 分離、UE5/Houdini の density 場が、5つの独立分野から同じ「割る責務と詰める責務を分ける」に着地した。本 doc の要件2は業界普遍の原則であると確認できた。
- **ゾーンは entrance からの距離で導ける**。squarified treemap の connectivity tree、cyclic 生成の entrance→goal 距離、space syntax の depth/integration が、独立に「根からの距離でゾーン帯を切る」へ収束した。名前付きゾーンの導出はこの距離ラベリングで具体化する。
- **決定化は3操作へ還元される**。すなわち深さと試行回数の固定K上限、候補を slice に集め安定 sort してから seed 抽選、可変状態を `childSeed = hash(parentSeed, index)` の引数導出へ置換。Minecraft jigsaw の max_depth、arc consistency の伝播と崩壊の分離、grammar の深さ cap が同じ骨に至る。SPD の pushGenerator が可変グローバルで本 doc の要件1に反する点は反面教師。
- **業界的傍証**。ruins のゾーン語彙 entrance/service/storage/display/social は、Marson & Musse が住宅生成で独立に到達した service/private/social とほぼ同型。役割をグラフで先に決め後段で空間へ落とす順序は業界で妥当と裏付けられた。

### 収穫1: 分割文法の実体と layout↔content 契約

本 doc が関心外と棚上げした分割文法に、実装可能な既定案が得られた。content は分割文法の出力に依存するため、供給側の実体と両者の契約だけは本 doc で固定する。

- **分割は決定的 BSP を既定、面積要件が強い施設は squarified treemap**。treemap は目標面積へ aspect ratio を1に寄せて詰める貪欲法で、入力面積 slice の順序のみに依存する。sort→seed で並べれば Go の map を使わず決定的。CGA の scope/split/repeat の概念は、相対分割で形状非依存、repeat で棚を幅いっぱいに可変数、を状態なしで表す裏付けになる。文法エンジンの全実装は YAGNI、概念と面列挙だけ翻案する。
- **契約を型で閉じる**。分割 pass の出力を `Room{ rect Rect; doorways []Doorway; zone ZoneTag }` とする。`zone` は独立ラベリング pass が付与し、entrance 矩形を根に隣接グラフを BFS して根からの距離でゾーン帯を切る。placement 意味論の中央・壁際・全域は rect と doorways から幾何導出し、壁際は CGA 流に壁面を列挙して doorway 隣接面を除外することで、ドアを塞がない棚置きを文脈依存で保証する。
- **生成は非循環パス DAG**。footprint → 分割 → 隣接graph化 → ゾーン分類 → RoomReq 解決 → placement 適用 → 装飾層。各 pass は前段出力のみに依存し、buildingSeed からの一括純関数生成に自然に乗る。Ludomotion の層状パイプラインと Dormans の mission/space 二段分離が同じ形を示す。cyclic 生成の鍵錠ループ機構は施設内装の静的性ゆえ不採用、段階解決の思想のみ採る。

### 収穫2: placement 意味論の統一表現 —— 密度場 + 決定的間引き

UE5/Houdini の attractor-density を翻案すると、center/wall/full_area/zone を個別ロジックでなく1つの「タイル→スカラ density」純関数の族として統一できる。

- 各候補タイルに placement が density を与える。中央は部屋中心を attractor に `density = ramp(1 - dist/max)`、壁際は壁距離の逆、全域は一定、ゾーンは中心ディスクを attractor に。
- 間引きは `density >= hash(seed, x, y) の 0..1 値` で決める。候補は slice に `(density, threshold, stuff)` を積み sort してから走る。map 不使用・再訪一致・グローバル可変なしを同時に満たす。
- 幾何が予約したタイルは density=0 とすることで、UE の exclusion volume に相当する「幾何が先に予約した通路・戸口を塞がない」を自然に取り込む。
- ゾーン契約は矩形に加えディスク `(中心, 半径, stuff)` も許すと表現力が上がる。Reddit の MMalficia の第二パス円が先例。

### 収穫3: 決定化の学術的裏付け —— 伝播と崩壊の分離

本 doc の「有界K回＋決定的フォールバック」に学術的な骨が付いた。

- **arc consistency の伝播と崩壊の分離**。placement 制約で候補 domain から unsupported を除く決定的・有界な伝播 pass と、seed 固定の1回崩壊選択に分ける。WFC の無制限 backtrack はKで打ち切り決定的フォールバックへ還元する。AC-3 の worklist・support・domain の語彙をそのまま使える。
- **Wang tiles の座標ハッシュ決定選択**。辺整合候補から `hash(位置)` で1枚選ぶ。再訪一致・状態なし・並び順非依存が本質的に備わり、slice+sort+seed と完全整合する。
- **occurrence/placement の2段分離**。Fisher 2012 の「何を置くか＝文脈条件付き重みリスト」「どこへ置くか＝placement 意味論」の分離は、本 doc content モデルの直接の学術的裏付け。連続 GMM とベイズ sampler は捨て、重みは学習でなく設計データで与える。
- **space syntax の位相指標**。部屋グラフの depth・integration や可視性を決定的解析 pass で先に算出し、幾何側の位相指標が中身側の重み関数を条件づける。奥の部屋ほど宝箱重み増、統合度が高い部屋ほど通路家具、など。
- **宣言的制約層は仕様・検証に限定**。ASP は placement 妥当性の宣言と golden 検証の語彙として、factor graph は候補スコア合成として採るが、CDCL 探索・RJMCMC の収束待ち sampler は決定性・非有界性ゆえ実行時不採用。

### 収穫4: content モデルの細部拡張

前追記の Archetype/Group/placement 語彙に、非重複な部品を足す。

- **socket 命名でゾーン契約を一般化**。Minecraft jigsaw の name/target のように、部屋の戸口や anchor を socket 名で宣言し、content が同名 socket を要求して意味的に接続する。未接続 socket には既定封鎖 stuff を置く契約を明示する。SnapGridFlow の「未接続辺は Wall で封鎖」が先例。
- **palette の二相解決**。CDDA の char→stuff 対応表を部屋形状から切り離し再利用する。重み付き候補は型で解決規則を切り替える。terrain/furniture は1つ抽選、すなわち sort→累積重み→seed、items/fields は全部適用、すなわち安定順。place_nested の neighbors 近傍条件は footprint 内で閉じる範囲のみ将来採る。
- **地点セレクタ API**。Reddit nesguru の知見。部屋を受け `SelectCenter/SelectWallMidpoints/SelectCorners/SelectDoorFront` の純関数プリミティブを整え、placement 意味論をその合成で表す。テスト容易で決定的。
- **連続 trait の近似一致と対称サブセット**。Reddit fractalpixel の知見。stuff に fancy 等の連続 trait、部屋に目標 trait を持たせ `重み = f(|trait - target|)` を抽選前に確定する。松明・鏡など対称配置されやすい壁家具は対称サブセットとして placement に持たせる。
- **パリティ格子で通行保証**。Reddit GameDesignerMan の知見。全域・中央の候補を `(x+y)%2==0` に限定すれば抽選結果によらず通路が残る。決定的で検証不要、本 doc の aisle_skeleton 予約を安価に補完する。
- **決定的ジッタと隣接同型伝播**。Cogmind の décor 機序。候補点へ seed 由来の小オフセットで整列の単調さを崩す。全域配置で隣接タイルが同じ stuff を引き継ぐと床材・草むらが塊で出て自然。走査順を固定すれば決定的。テンプレート本体は前追記と重複ゆえ見送る。
- **部屋テンプレの重み付き選択＋適用ガード述語**。NetHack の frequency と eligible/mindiff。stuff の重みリストを一段上げ、部屋テンプレ自体の重み選択と階層ガードを contents から分離する。
- **幾何を先に作り役割を後付け割当**。Diablo1 の floodfill re-purpose。生成済み部屋を決定的スコアで役割づけしてから役割別 stuff を流す。RimWorld の逆 classifyRoom と接続し QA にも効く。DCSS の ORIENT enum は placement 意味論の型化の先例、DF の連続矩形面積実測は area 要件の充足判定側の設計を示す。

## 追記(2026-07-25) その3: ドメイン定石・活動駆動・略奪表現・評価の横断調査

前2追記が「どう置くか」の技術を固めたのに対し、本追記は技術の外側を埋める5軸を調査した。実世界の店舗・建築の定石、人間の活動・アフォーダンスから配置を導く学術、サバイバル系の部屋定義とルート分配、ニューラル室内合成と ProcTHOR、荒廃表現と生成器の品質評価。ruins は「略奪された日本の店」を出したいゲームであり、配置技術だけでは新品のコンビニしか出ない。本追記が「らしさ」の残り半分を埋める。

### 5軸を貫く収束 —— 配置の単位は束、決定化は一次文献が裏書きした

- **アンカー付きの束への三重収束**。ProcTHOR の Semantic Asset Group、すなわち親アセットに子をアンカーで結んだ複合エントリ。認知心理学 Scene Grammar の実証、すなわちシーンは anchor object と衛星オブジェクトのフレーズ集合で組織され人は anchor を頼りに理解する。Fu 2017 の activity バンドル、すなわち活動が成立するカテゴリ集合を単位に補完する。3つの独立分野が「配置の抽選単位は単品でなくアンカー付きの束」に到達した。前追記の attached・再帰アンカーはこの束の一形であり、束を第一級の抽選単位に昇格させる。机だけあって椅子が無い抽選事故を構造的に防ぐ。
- **決定化方針の一次文献による裏書き**。Fisher 2015 は MCMC を「提案コストが高く連鎖の混合が遅すぎる」と実測で棄却し greedy 逐次挿入を採用したと明記する。Qi 2018 の MCMC は1部屋20〜40分を要する。キッチン三角形の現代的定式化は0-1整数計画で確率もサンプラも登場しない。本 doc の「反復は固定K回＋決定的フォールバック」は学術の実務でも同じ結論に達している。
- **略奪表現の三面一致**。Scene Grammar の「anchor 温存・衛星欠損」という文法の故意の違反、サバイバル系のコンテナ空振り率・junk 混入率、Ma 2016 由来の持ち去り欠損が、いずれも「構造を保ったまま中身を欠く」に収束する。部屋の可読性を壊さず略奪済みを表現する原則になる。

### 収穫1: 実世界定石を content 定義へ —— 施設文法

「店に見える」は突き詰めると実在の店の定石を知っているかの問題で、PCG 論文には載っていない。業界資料から施設別の定石を placement 語彙へ翻訳した。1タイル約1m。

- **コンビニの文法**。ウォークイン冷蔵ケースは最奥壁に連続配置し裏1タイルをバックヤードにする。目的買いの飲料を最奥に置き往復で全棚の前を通らせるのが実在の設計意図。レジは入口脇 near_origin、雑誌ラックは窓沿いか入口側の壁で賑わいを演出、ゴンドラは中央 row で通路1〜2タイル、動線は外周 racetrack。標準は50〜60坪、13×15タイル前後。
- **負の placement を第一級に**。小売のデケレーションゾーン、すなわち入口から2〜4タイルは何も置かない余白、参道、廊下はいずれも「置かない帯」である。`exclusion_zone` を content 定義の第一級要素にする。密度でなく空白が設計された印象を作る。door_apron・aisle_skeleton の予約と同じ機構で表せる。
- **sequence と mirror_pair の意味論**。神社は参道→鳥居→手水舎→拝殿→本殿が一軸に直列し、狛犬・灯籠は軸対称の対。origin からの順序付き配置 `sequence` と軸対称ペア `mirror_pair` の2語彙が要る。対は軸からの符号反転オフセットで決定的に生成できる。
- **向きの整列は zone 単位で1回抽選**。オフィス島・ゴンドラ・ベンチは同一 zone 内で回転を揃えるだけで人工感が跳ね上がる。stuff 単位でなく zone 単位で向きを1回引く。
- **数値は実基準に根拠を持たせる**。診察室9.9㎡以上・待合3.3㎡以上は医療法の実基準。小売通路1〜2タイル、倉庫メイン通路3タイル、廊下2タイル。診療所は受付が待合と診察の境界で双方を見通せる位置、待合の椅子は対面を避ける。民家は水回りの隣接集約が間取りらしさの核、伝統民家は田の字型。倉庫は U字動線で入口近くに検品台、最奥に高価値保管。

### 収穫2: use_area と活動駆動の生活痕

- **use_area 方向付きクリアランス**。Archetype に「使用側オフセット領域」を追加し、配置成立条件を footprint の空きと use_area の歩行可能の二重判定にする。Qi 2018 の affordance map、Fisher 2015 の interaction maps と activity free space、Kán 2017 の4方向 clearance が全て同一のデータ形式に還元される。前追記の Clearance をこれで方向付きに具体化する。gaze・touch の相互作用語彙はタイル世界では「use_area から遮蔽なしで見える」「use_area に隣接」の2語彙に簡約してよい。
- **functional_triangle 制約**。厨房系は貯蔵・水場・火元の3 role 間のタイル距離に min/max 帯を課す。NKBA の実数値、各辺1.2〜2.7m・周長4〜8m をタイル換算で持つ。帯判定は純関数、満たせなければ距離最小へフォールバック。
- **usage_wear pass**。content 確定後に走る生活痕の pass を新設する。Ma 2016 の行動駆動進化の還元で、部屋の行動遷移表から seed で固定 n 手を引き、各手が key stuff の use_area 側へ小物を追加し、既存 stuff を working zone 外へ最小距離退避させ、一部を持ち去り済みとして削除する。廃墟の散乱を乱数散布でなく「最後に行われた行動の帰結」として決定的に出す。椅子は机から引き出された向きで止まり、退避物は作業域の縁に堆積する。終端を略奪・逃走に偏らせるだけで廃墟性が出る。
- **circulation のハード制約化**。Kán 2017 の到達不能率を翻案し「ドアから全 stuff の use_area まで BFS 到達可能」を配置成立条件にする。到達性ガードの具体形。

### 収穫3: ルート分配の3段間接化と略奪の3ノブ

サバイバル系4作が共通して「アイテム→コンテナ、コンテナ→部屋タイプ」の間接化を採る。

- **部屋タイプ→コンテナ種別→テーブルIDの3段**を content モデルの正式構造にする。Project Zomboid の procList 形式、すなわち重み付きテーブル参照の slice に min/max と採用確率を添える形を Go の定義型で写す。幾何は部屋に名前を付けるだけで中身を知らない。バランス調整は該当テーブル1箇所で済み局所的。
- **zone volume オーバーレイ**。7 Days to Die の sleeper/loot volume の静的翻案。幾何の部屋矩形とは別に content 層が AABB で loot zone・脅威 zone を宣言する。カウンター裏だけレジ系テーブル、のような部屋より細かい粒度も書ける。開封時抽選は不採用とし、seed とコンテナ座標から生成時に確定させる。
- **大域パスの2段構え**。抽選前に The Long Dark 型の保証スポーン制約を敷き、DayZ 型の品目クォータを seed 付きシャッフルで施設群へ分配してから、コンテナ単位の局所抽選に入る。DayZ の教訓は経済ループとタグ照合語彙が分離できることで、動的なのは補充ループだけ、タグ照合は静的移植できる。
- **略奪済み感の3ノブ**。コンテナ空振り率、junk 混入率、テーブル変種選択。いずれも seed 純関数のまま独立に調整できる。世界単位やチャンク単位で変種を1つ引けば再訪一致と探索の変化が両立する。

### 収穫4: ProcTHOR 参照アーキテクチャと開発時 LLM 下書き

- **ProcTHOR は本 doc と同じ問題を静的注釈＋段階サンプリングだけで解いた大規模実証**。ニューラルでなく純手続き。room spec の木→再帰分割→部屋タイプ組ごとの接続確率→家具→小物の段構成は本 doc の pass 設計と同型で、16 spec から10^11 超の間取りを出した。持ち帰るのは4点。部屋別必須度 rw 0〜3 のスケール、edge/corner/middle と standalone 禁止の placement 注釈、Semantic Asset Group という anchor 付き複合エントリ、receptacle 対応表による小物の二段 pass。18 SAG で約2000万通りという「少数の束で組合せ爆発を得る」実績値も参考になる。
- **配置 pass の副段階分解**。ATISS の属性分解に倣い、種類→位置→向きを独立の決定的ステップに分け、向きの定石は facing 属性の静的表で持つ。学習分布そのものはドメイン不一致で数値が移植できず、形式のみ採る。
- **開発時 LLM 下書きワークフロー**。Holodeck が示すとおり LLM は記号的制約の生成では安定し、数値座標を書かせると破綻する。LayoutGPT の実測で類似例なしの座標生成は範囲外率43%が86%へ跳ねる。そこで施設別 content 定義を「座標なし・記号のみ」で LLM に下書きさせ、スキーマ検証と人手レビューを経て静的データへ焼き込む。実行時バイナリには LLM も検索も残さない。Holodeck の5分類制約語彙 global/distance/position/alignment/rotation は placement enum の網羅性チェックリストに使う。

### 収穫5: 廃墟化 post-pass とシーン文法

- **廃墟化 post-pass の3層設計**。清潔な内装グリッドと theme と seed を受け取る純関数。第1層は決定的スカラー場3枚、破口・窓からの BFS による exposure、水源からの減衰 BFS による moisture、開放近傍数による accessibility。第2層は固定K世代のセルオートマトンによる崩壊伝播で、K は condition から決める。severe は K=6、light は K=2。γ-ton tracing の「壊れた所ほど壊れやすい」フィードバックは CA の遷移規則が自然に表現する。第3層は場のしきい値写像で錆・カビ・植生・瓦礫へ書き換える。植生は moisture と exposure の積が高い所、汚れは accessibility が低い隅。TLOU の因果規則、根は水源沿い・植物は割れ窓の光へ、がそのまま場の式になる。
- **Scene Grammar のフレーズ配置と略奪の文法違反**。配置を部屋 role→フレーズ集合の抽選→anchor を placement で置き衛星を anchor 相対の固定オフセット候補列で置く、の2段にする。略奪は anchor 温存・衛星欠損として表現する。anchor ごと消すと部屋の可読性が壊れるため避ける。Võ らの「anchor がシーン理解を支える」実証に基づく。
- **ヴィネット演算子**。バリケード、ドア隣接タイルへ家具を移動し向きを揃える。脱出跡、出口へ向かう散乱列。生活痕、一角だけ清掃済みと寝床と火気。各ヴィネットは幾何述語と theme 述語の前提条件と有界の書き換えを持つ純関数スタンプにする。Worch & Smith の矛盾回避則、ゲーム内で起きない事象を痕跡にしない、は前提条件の静的検査として機械化する。
- **Fallout 4 の教訓**。幾何キットの組み立てと clutter による語りの層を分離して大規模生産を成立させた。幾何と中身の分離が AAA の実運用でも同じ形になる傍証。

### 収穫6: 設計されたもの度の定量化

進捗の「設計されたもの度をメトリクスで測る」を具体化する。

- **内装向け ERA 指標**。全てグリッドの純関数。密度 = 家具タイル/床タイル。壁際率 = 壁隣接家具/家具総数。到達率 = 入口 BFS 到達床/全床。対称度 = 1 − 左右反転との不一致率。anchor 被覆率 = anchor 半径2以内の家具/家具総数。迂回度 = 入口→奥の最短路長/マンハッタン距離。condition ごとに期待帯を持たせる。新品店舗は対称度が高く、略奪後は落ちるのが正しい。
- **運用は golden 分布の CI 比較**。固定 seed 列 0..N-1 で N 個生成し、指標ペアの2Dヒストグラムを golden として commit、CI で再計算し差分検知する。決定的なので flaky にならない。ペアは密度×対称度と到達率×迂回度から始める。
- **Tile Pattern KL-Divergence の二距離**。手置きの模範内装を参照分布に、生成集合との距離を品質、生成集合内ペアの平均距離を多様性とする。設計されたもの度は「一様ランダム配置との距離」として定義でき、ランダムから遠く模範に近いほど設計的。廃墟化 pass の前後で両距離を追えば「設計性を適度に壊しランダムには落としていない」を回帰テストで担保できる。
- **Danesh の概念のみ**。対話ツールは不要で、ヘッドレスの固定 seed メトリクス計算、golden 差分検知、オフラインのパラメータ探索スクリプトの3点を CI へ移す。探索は非決定でよく、見つかったプリセットだけを commit すればゲームの決定性は保たれる。
