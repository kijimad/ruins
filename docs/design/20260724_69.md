# オーバーワールド生成の統合設計

旧 `20260723_66`(街生成)・`20260723_67`(縦チャンク任意数化)・`20260724_68`(生成アーキテクチャ)を1枚へ
統合する。本 doc が最新の結論で、反復の経緯 —— 批判レビュー、PR レビュー反映、Minecraft リージョン方式への
改良、世界観の全面刷新 —— は3枚分の git 履歴に残る。本文は結論だけを、決定理由と却下案を添えて示す。

## 背景と世界観

生成ロジックの豊かさはこのゲームの面白さのキモである。ゆえに拡張性と高い表現性に耐える横断設計が要る。
初稿は生成の seam を「街」という具体に置いており、種類を増やすたびに `IsXChunk` の分岐が増える天井があった。
本 doc は生成を層のパイプラインとデータ駆動可能な FeatureSpec レジストリに置き、街・市街地・遺跡・資源・
ハザードを同型のインスタンスにする。

世界観は現実寄り。2026年日本、未知災害後の世界。詳細は `docs/plan/lore.md`。コア体験は**ゆるやかな制約下の
オープン探索**である。

- 主軸はオープンな探索。明確な東ゴールへプレイヤーを追い立てる構造にはしない。
- 寒波前線は**西から東へ**進み、呑まれた土地は凍てつく。**寒いのは背後の西**である。プレイヤーは前線に
  背を押されるが、追い立てられはしない。前線は「いずれ確実に呑まれる」ゆるやかな制約として探索を方向づける。
  東へ進むほど厳しくなる難度は前線でなく**東進距離の軸**が担う。2軸を混同しない。前線ロジックの X 一軸は
  据え置く。
- 生成は `(seed, 座標)` の純関数を保つ。難易度もプレイヤー状態でなく座標由来にする。これが決定性・serde・
  再訪一致を守る背骨になる。動的生成は射程外。

参考は CDDA と Minecraft。CDDA から中身の重み・配置制約の語彙、Minecraft から決定的チャンク生成とリージョン
配置を採る。各々の強い部分だけ翻案し、CDDA のグローバル乱数依存は採らない。

## 最終目的地（射程）

- **バイオーム第一級**。region ごとに地形・敵・気候が変わる。境界は noise で連続。
- **地物5カテゴリ**。小集落、市街地・大都市、遺跡入口、資源、ハザード。すべて同型の FeatureSpec。
- **難易度勾配3軸**。うち生成が読むのは座標由来の2軸、東進(基礎難度・報酬)とレーン(南北 Y、リスク/リワード
  分岐)。前線(西からの寒冷)は時間依存なので生成には入れず、実行時オーバーレイが担う。
- **クロスチャンク構造**。街をつなぐ道、region をまたぐ大型構造。決定的に協調。
- **決定的・静的**。プレイヤー状態を入力にしない。
- **コード先行、データ化可能**。最初は Go 定義、器が固まったら TOML/raw へ。

## 場所の類型 —— いずれも特別扱いせず同型の地物にする

現実寄りの世界観に合わせ、街を一様な補給点とはしない。規模と危険で分ける。

- **小集落・一軒家**（`Settlement`）。生存者がいる交易・補給・改造・雇用・情報・休息の場。村・農家・峠の
  一軒家など。規模が小さく比較的安全。**無状態で stash なし**。開始拠点もこの類型。
- **市街地・大都市**（`UrbanRuin`）。地表の高リスク・高リターン地帯。**規模が大きいほどモンスターも戦利品も
  多い**。複数チャンクに及ぶ地表の攻略対象で、深さ y は持たない。補給の場ではない。自衛隊基地跡や研究施設も
  この危険帯に属する。
- **遺跡・ダンジョン**（`RuinEntrance`）。深さ y を持つ階層ステージ。入口から入り階を進む。**地下とは限らない**。
  廃ビルは上へ、地下室・地下墓・自然洞窟は下へ。y の向きは構造しだいで、y を足すだけの一類型。Phase 8
  (`20260720_65`)「遺跡は隣のステージにすぎない」統合方針の延長に置く。**y の有無と危険度は独立の軸**。
  ただの地下室やビルのような低危険の y 構造もあれば、基地のように y を持たない高リスク地帯もある。
  凍晶の濃いステージも y の有無を問わず存在する。

小集落と市街地・大都市を**別カテゴリ**にするのが要。「補給の安全な小集落」と「高リスク高報酬の大都市」を
分ける。市街地は地表の大型 POI なので Feature 層に spec を1つ足し、Connection 層が扱う複数チャンクの大型
構造として決定的に配置する。規模でリスクと報酬が変わる点を、その `Content` と `Placement` が表す。

## 設計

### 1. 生成パイプライン（層）

チャンク生成 `GenerateChunk(coord)` を層の列にする。`NewChunkGen` はこの閉包を構成するコンストラクタで、
座標を受けるのは生成関数のほう。各層は前層の出力に作用し、`(runSeed, 座標)` から決定的。乱数源は用途で
使い分ける。per-chunk の抽選は `ChunkSeed2D`、biome などの連続場は runSeed シードの noise(§3)。単層に全部を
詰めず、各層を差し替え・合成・単体テスト可能な段にする。

```text
GenerateChunk(coord):
  prog    := ProgressionAt(seed, coord)  // 1. 難易度場（東進・レーンの2軸。前線は実行時）
  biome   := BiomeAt(seed, coord)        // 2. バイオーム（連続 noise、Y にも依存）
  terrain := GenTerrain(coord, biome)    // 3. 地形（biome でパラメータ化）
  PlaceFeatures(coord, biome, prog)      // 4. 地物（FeatureSpec レジストリ）
  DrawConnections(coord)                 // 5. 道・大型構造（近傍を算出して結ぶ）
  Decorate(coord)                        // 6. 継ぎ目・小物
```

### 2. Progression 場（生成が読むのは2軸）

座標から静的に難易度を導く純関数。動的入力なし。**前線軸は生成に入れない**。前線位置は `TotalTurns` から
導出される時間の関数であり、生成入力に混ぜると同じチャンクの再生成結果が時刻で変わり、再訪一致が壊れる。
前線の寒冷・危険は既存の temperature / frost 系が**実行時オーバーレイ**として重ねる。「生成は座標純関数、
時間依存の効果はその上に実行時で乗る」という分離を不変条件にする。

レーン軸は南北 Rows>1 を空間的な広がりでなく**リスク/リワードの明確な分岐**にするために持たせる。あるレーンは
報酬が多いが危険、別は安全だが乏しい。**レーンのリスク配分は seed 依存**にし、ランごとに変える。固定配分の
「北は常に危険」は周回で読みが固定化し単調になるため採らない。可読性は biome の見た目と、集落の情報サービス
(§6)が担う。

```go
// Progression は座標由来の難易度。プレイヤー状態にも時間にも依存しないので決定的。
type Progression struct {
	East int // 開始からの東進距離。基礎難度・報酬 tier
	Lane int // 南北レーン。リスク/リワードの分岐。配分は seed 依存
}

func ProgressionAt(runSeed uint64, c ChunkCoord) Progression
```

Biome の敵スケール、Feature の距離帯 Constraints、報酬 tier がこれを読む。前線は X 一軸のまま全行を貫き、
レーン差は南北軸の Progression と Biome が担う。

### 3. Biome 層（第一級・連続 noise・Y 依存）

```go
// Biome は地形・敵・気候を束ねる第一級概念。どの地物を許すかは FeatureSpec 側の
// Constraints.Biomes だけが持ち、Biome 側には持たない。判定の二重管理を避け、TOML 化も阻害しない。
type Biome struct {
	Name       string
	Planner    mapplanner.PlannerType // 地形生成のプランナ
	EnemyTable string                 // 敵の湧き表
	TempOffset int                    // 気候。既存 temperature 系へ接続し二重管理を避ける
}

// BiomeAt は連続 noise で biome を決める。region 離散でなく境界が滲む。Y にも依存させ
// レーンごとに地形を差別化する。
//
// noise は runSeed だけでシードし、絶対座標で引く連続場にする。ChunkSeed2D は隣接チャンクで
// 無相関になるよう撹拌した per-chunk ハッシュなので、バイオーム場には使えない。使うと
// チャンク境界で biome が割れる。ChunkSeed2D は per-chunk の地物ロール専用。
func BiomeAt(runSeed uint64, c ChunkCoord) *Biome
```

粒度はハイブリッドにする。地形タイルのパレットは per-tile の連続場から引き、「滲む境界」を実際に作る。
Feature の Constraints 判定と敵テーブルは per-chunk の代表値、すなわちチャンク中心のサンプルで足りる。
チャンク単位の1値だけにするとチャンク一辺ごとの角張った境界になり、滲む境界にならない。

### 4. Feature 層（FeatureSpec レジストリ）

地物を種類ごとの述語でなく、統一 spec のインスタンスにする。ここが拡張性の芯。種類の追加は分岐でなく
インスタンスの追加に還元する。

```go
type FeatureKind int

const (
	FeatureSettlement   FeatureKind = iota // 小集落・一軒家。補給・安全
	FeatureUrbanRuin                        // 市街地・大都市。地表の高リスク高報酬・複数チャンク
	FeatureRuinEntrance                     // 遺跡入口。深さ y の階層へ
	FeatureResource                         // 資源・採集
	FeatureHazard                           // 危険地帯・POI・イベント
)

// FeatureSpec は1種類の地物の「どこに・どの条件で・何を」を1つにまとめた宣言。
type FeatureSpec struct {
	Kind        FeatureKind
	Placement   Placement    // どこに撒くか
	Constraints Constraints  // どの biome・距離帯で許すか
	Content     ContentGen   // 何を置くか
}

// PlacementMode は配置方式。ゼロ値の暗黙でなく明示の enum で区別する。
type PlacementMode int

const (
	PlaceRegion  PlacementMode = iota // リージョンに高々1つ。小集落・遺跡・市街地
	PlaceScatter                      // 密度散布。資源など
)

// Placement は配置ルール。疎な構造は Minecraft のリージョン方式、密な散布は Scatter。
type Placement struct {
	Mode       PlacementMode
	Spacing    consts.Chunk // Region: リージョンの一辺
	Separation consts.Chunk // Region: 最小間隔
	Salt       uint64       // 種類ごとに相関を切る
	Density    int          // Scatter: 散布密度
}

// Constraints は配置可否。CDDA の locations/city_distance/occurrences の翻案。
type Constraints struct {
	Biomes      []string // 許可 biome
	EastBand    [2]int   // 東進距離帯 [min,max]。難易度勾配で出現を絞る
	Occurrences [2]int   // 出現回数域
}

// ContentGen は確定した地物の中身を配置する。biome と prog を受け表現を変える。
type ContentGen func(world w.World, c ChunkCoord, seed uint64, b *Biome, p Progression) error
```

- **Settlement**(小集落)は最初の実装インスタンス。§5 で詳述。
- **UrbanRuin**(市街地・大都市)は複数チャンクの大型 POI。規模が大きいほどモンスターも戦利品も多い点を
  `Content` と `Placement` が表す。Connection 層がクロスチャンク配置を担う。
  - **RuinEntrance を内包できる**。lore の市街地は駅・地下街・ビル群を含み、これらは多層＝遺跡の素材である。
    市街地の中心部に階層への入口を置き、「地表の危険帯を突破して奥の入口に潜る」二段のリスク構造を作る。
    合成は Content が他 Feature の入口 prop を置けることで表現し、レジストリ機構は変えない。
  - **チャンク片の導出不変条件**。市街地の各チャンク片は `(citySeed, 相対offset)` の純関数で、**隣接チャンクを
    生成せずに**自分の断片を描けること。帯ストリーミングでは都市の一部だけが先に生成されるため、この不変条件を
    破ると生成順序依存が再発する。
- 遺跡入口・資源・ハザードは別 spec。当面はコード、将来は TOML で足すだけ。

### 5. 小集落の生成（Settlement の実装）

`Settlement` FeatureSpec の中身。旧 doc 66 の設計を最終形として据える。

- **配置は Minecraft のリージョン方式**。世界を `Spacing` チャンク四方のリージョンに分け、リージョンごとに
  `(seed, regionX, regionY, salt)` で seed した値が `[0, Spacing-Separation)` のオフセットを引き、そのチャンクを
  候補にする。「1リージョンに高々1つ」「最小 `Separation`」を O(1) で決定的に保証する。窓最大方式の帯端問題も
  消える。`townScore = ChunkSeed2D` の別名で、閾値と窓判定は不要になった。
  **実装確定**: Y は帯が [0, Rows) に有界なのでリージョンで割らず、リージョンごとに帯の全行から当選行を
  1つ引く。Y もリージョンで割ると行数より大きいオフセットの当選が帯の外へ落ち、行数の少ない帯に地物が
  ほぼ出なくなるため。判定は `Placement.At(runSeed, c, rows)` の純関数。
- **中身は規模で gate した重み付き施設テーブル**。CDDA の city_size と houses/shops の翻案。小さな集落は
  基本施設のみ、規模が大きいほど施設が多様になりレアも出る。中心からの距離で種別を切り替える。施設は現代
  日本の意匠(コンビニ・薬局・宿・骨董品店ほか)。武器・防具は骨董品店で扱う。
- **無状態・stash なし**（旧 doc 66 案B を確定）。街に永続状態を持たせず、フィールドにアイテムを残さない。
  serde すべき可変状態が無く、seed からの決定的再生成と完全に整合する。
- **開始チャンク特例**。新規ゲームの開始点は必ず小集落にし、店・雇用・合成の必須サービスを確定配置する。
- `ChunkSeed2D` を唯一のエントロピー源にし、グローバル乱数を使わない。
- **経済はスコープ外**。集落ごとの産物・不足プロファイル、価格差、在庫・枯渇の記憶は本設計では扱わない。
  本設計はマクロ地図の生成に集中する。交易の経済設計は別ドキュメントで行う。その際は「無状態の表層」と
  「在庫・枯渇の記憶」の緊張、design.md の逗留の有限性と低い床・高い天井、を正面から扱う必要がある。
- **雇用候補の実装注意**。無状態の集落は、雇用済みの候補を再訪時にそのまま再提示しうる。候補の identity を
  `(集落seed, スロット)` から決定的に導き、生成時に隊ロスターと照合して雇用済み候補をスキップすれば、
  追加の永続状態なしで二重化を防げる。

### 6. Connection 層（クロスチャンク）

`Placement` が純関数なので、あるチャンクは近傍リージョンの拠点位置を**生成せず算出**できる。道はその位置を
結び、市街地・大都市のような region 大型構造も決定的に配置する。Minecraft が構造物を生成せず座標算出するのと
同じ原理。

```go
// NearbyFeatures は生成を伴わず、近傍にある指定種の Feature 位置を決定的に算出する。
func NearbyFeatures(runSeed uint64, c ChunkCoord, kind FeatureKind, radius consts.Chunk) []ChunkCoord
```

`NearbyFeatures` は道の結線だけでなく、**集落サービス「情報」の実装基盤**を兼ねる。lore の小集落は交易・雇用と
並んで情報を商う。配置が純関数なので、集落で噂を買う＝`NearbyFeatures` を引いて未踏の地物をミニマップへ印す、
が**追加の永続状態ゼロ**で実装できる。seed 依存にしたレーンのリスク配分(§2)の可読化も、この情報サービスと
biome の見た目が担う。

### 7. 帯インフラ —— 縦チャンク数を任意数にする

生成が走る座標基盤。旧 doc 67。現状の帯は縦1行だが、南北レーンのため行数 `Rows` を任意数にする。東西は無限
ストリーミング、南北は `Rows` に有界で非ストリーミング。`Rows=1` は現状と挙動同値。

```go
type Band struct {
	chunkW    consts.Tile
	chunkH    consts.Tile  // 縦スロット配置に要る
	k         consts.Chunk // X方向のチャンク数
	rows      consts.Chunk // Y方向のチャンク数。1 で現状
	eastIndex consts.Chunk
}
func (b *Band) Rows() consts.Chunk  { return b.rows }
func (b *Band) Height() consts.Tile { return b.rows.Tiles(b.chunkH) } // = rows*chunkH

// ChunkGen は2次元。ChunkCoord は X 絶対(東西無限)、Y 有界[0,Rows)
type ChunkCoord struct{ X, Y consts.Chunk }
type ChunkGen func(c ChunkCoord, offsetX, offsetY consts.Tile) error

// ChunkSeed2D は runSeed と (cx,cy) から決定的シードを導く。cx,cy を独立に混ぜる。後方互換は保証しない
func ChunkSeed2D(runSeed uint64, cx, cy consts.Chunk) uint64
```

- `generateBandChunks` は `rows × k` の2重ループ。`Level.TileHeight = rows*chunkH`。
- **チャンク寸法はマスタ定数で可変**。目安は 100×100 タイル。現行コードの定数は 50×50 で、定数変更だけで
  移行できるよう寸法を直書きしない。
- **シフトは X のみ・列(全行)単位**。`RemoveEntitiesInXRange` で端列の全 Y を破棄、`TranslateAllEntities(±chunkW,0)`、
  新端列は `rows` 行を生成。南北移動は破棄・再生成を伴わない。
- **`AbsTileY` は追加しない**。Y は非ストリーミングの有界ローカル座標で足りる。
- **縦境界の継ぎ目** `RecalcSeamAutotileY(world, boundaryY)`。X 版と同じく境界両側のタイル実在プローブで
  帯端を自己スキップするため、全体高さの引数は不要。実装時に確定した簡素化。
- **serde に `Rows`**。`SeamlessBand.Rows` を追加。`startNewBand` で `sb.K` の隣に `sb.Rows = band.Rows()` を書く。
  `restoreFromSave` で読み `Rows=0→1` 正規化。旧セーブ互換。
- **前線は X 一軸のまま**。全行を貫く。行ごとに地形が違いレーン差が生まれる。

### 8. 決定性とコード→データ

- 全層は `(runSeed, 座標)` 由来の決定的関数。プレイヤー状態も時間も入力にしない。動的生成は射程外。
  乱数源は用途で使い分ける。per-chunk の抽選は `ChunkSeed2D`、biome などの連続場は runSeed シードの
  noise(§3)。`Progression` も座標純関数(§2)。
- `FeatureSpec`・`Biome` は Go の登録表で始める。フィールドは TOML スキーマへ一対一で写せる形にし、レジストリ
  interface を安定させる。器が固まったら `raw`/TOML へ移す。

## 採用しなかった方法

- **種類ごとの述語** `IsTownChunk`/`IsRuinChunk`…。分岐が増え合成しない。`FeatureSpec` の別インスタンスにする。
- **CDDA のグローバル乱数方式**。生成順序に依存し、帯シフト・再訪・reload で世界が変わる。`ChunkSeed2D` の
  決定的配置に徹する。Minecraft の実績ある王道。
- **窓最大の隣接抑制**。`O(MinGap²)` で帯端の片側窓問題を抱える。Minecraft のリージョン方式に置き換え O(1)。
- **region 離散の biome**。境界が四角く不自然。noise で連続に滲ませる。
- **バイオーム場を ChunkSeed2D から引く**。per-chunk 無相関ハッシュでは境界が割れる。連続 noise を runSeed で
  シードし絶対座標で引く。
- **前線軸を生成入力に入れる**。前線位置は時間の関数で、混ぜると同じチャンクの再生成が時刻で変わり再訪一致が
  壊れる。前線は実行時オーバーレイに限る。
- **`Biome.AllowFeature` による許可判定**。`Constraints.Biomes` と二重管理になり、func フィールドはデータ駆動化を
  阻害する。spec 側に一本化。
- **レーンリスクの固定配分**。周回で読みが固定化し単調。seed 依存にし、可読性は biome の見た目と情報サービスで
  担保する。
- **全域2次元ストリーミング(Y も無限)**。過剰。固定行数 `Rows` の帯で足りる。南北シフトも不要。
- **`AbsTileY` 追加**。Y は有界なので不要な抽象。X の絶対軸だけ持つ。
- **街に stash・永続状態**。帯シフトで破棄・再生成されるため保持できない。無状態(案B)に確定。
- **街を一様な補給点**。規模と危険で分け、小集落(補給・安全)と市街地・大都市(高リスク高報酬)を別カテゴリに。
- **前線が追い立てる構造**。オープン探索を主軸にし、前線は難易度勾配へフレーミングを寄せる。ロジックは不変。
- **最初からデータ駆動**。器が固まる前に TOML スキーマを凍結すると手戻り。コード先行→移行。
- **動的生成(プレイヤー反応)**。決定性・serde・再訪一致が崩れる。難易度は座標由来の Progression に限る。

## 実行計画

各段は単独で `make check` 緑を保つ。`Rows=1`・`cy=0` を現状同値に保つのが全段の退避路で、大改造を小さな緑の
積み重ねに分解する。

1. **共有前提**。`ChunkCoord`・`ChunkSeed2D` を入れる。転置・隣接で散ること、後方互換を保証しないことをテスト。
2. **帯インフラ**。`Band` に `chunkH`・`rows`。`ChunkGen` を2次元化。`generateBandChunks` 2重ループ。シフトを列
   単位に。縦継ぎ目・`serde Rows`・マスタ行数。`Rows=1` 同値、`Rows>1` の通し。
3. **パイプライン骨格**。層の順序と純関数境界を固定。`ProgressionAt`(東進・レーン2軸、配分 seed 依存)。
   `BiomeAt`(連続 noise・ハイブリッド粒度)。前線が生成入力に混ざらないことをテストで固定。
4. **FeatureSpec レジストリ**。Settlement を最初の1インスタンスに。仮 `spawnTown` をその `Content` へ再構成、
   収納撤去、無状態、開始チャンク特例。`ChunkTown` 判定をリージョン方式で。
5. **カテゴリを増やす**。市街地・大都市(`UrbanRuin`)、遺跡入口、資源、ハザードを FeatureSpec として順次。
6. **Connection 層**。道・大型構造の `NearbyFeatures`。市街地のクロスチャンク配置。
7. **レーン差別化**。`Progression`/`Biome` の Y 依存でレーンをリスク/リワードに分ける。
8. **データ化**。器が固まったら `FeatureSpec`・`Biome` を `raw`/TOML へ移す。

## 追記(2026-07-24): CDDA 徹底調査の反映

`./Cataclysm-DDA` を4視点 —— overmap special/connection/highway、JSON mapgen、地域差・散布・天候、
スポーン・ホード・z-levels —— で調査し、採るもの・翻案するもの・採らないものを確定する。

### 決定性の再確認 —— CDDA で「隣接を生成せず整合」するのは highway だけ

- 事実。special 配置と local road は共有 RNG と生成順に依存し、純関数でない。唯一 highway だけが
  (a) 座標決定的な交点グリッドと (b) **端点順をソートで固定した決定的ルーティング**で、隣接オーバーマップを
  生成せずに跨境整合を実現している。
- 反映。Connection 層の実装規則として「**経路導出の入力を正規化する**。両端点をソートしてからルーティング
  する」を定める。これが両側のチャンクが独立に同じ道を導ける条件になる。本設計のリージョン方式 Feature
  配置は、highway の交点グリッドの完全純関数版に相当し、方針の裏付けが取れた。

### UrbanRuin —— 全体一括導出とチャンク断片描画、規模比例式

- mutable special の phases/joins による有機的成長は生成順依存で、そのままは使えない。ただし**成長を
  citySeed だけから全体一括で走らせれば純関数になる**。市街地は「citySeed から街区レイアウト全体を導出し、
  各チャンクはその断片を描く」。導出結果はキャッシュしてよいが、キャッシュはただの高速化で正しさに関与しない。
- スポーン量は CDDA の都市式を翻案する。`敵総数 = 規模 × 係数`、拡散半径も規模比例、中心ほど濃い。
  「規模が大きいほどモンスターも戦利品も多い」をこの線形式で表す。

### Terrain 層の実装戦略 —— 抽象タイルと biome 解決

- CDDA の region_terrain_and_furniture、擬似地形ID→地域別の重み付き実地形へのタイル毎置換、を翻案する。
  **mapplanner は抽象タイルIDを出し、biome 解決層がタイル毎に実タイルへ置換する**ポストプロセスにする。
  プランナ全体を biome 対応へ書き換えるより侵襲が小さい。変更箇所表の `internal/mapplanner` 行はこの戦略で
  実装する。
- biome 境界は CDDA の森 biome フェザリング、隣接 biome を重みに混ぜる方式、を参考に滲ませる。

### Content の語彙 —— TOML 化の指針

- 重み付き値 `[[値, 重み]]` を語彙の基本にし、**null に大重みを与える疎な確率配置**のイディオムを使う。
- **スコープ付き一回抽選**。集落全体で一貫させたい値、配色・荒廃度などは settlementSeed から導出する。
  CDDA は parameter の scope 機構でこれを実現しているが、純関数モデルでは seed 導出だけで同じ性質が手に入る。
- 散布は sequence 順 + one_in の早い者勝ち、森 biome 方式。
- 施設は「本体 rows + 記号ごとの平行辞書 + 共有パレット + nested 部品」の三層を翻案モデルにする。
  既存 `maptemplate`/palette の延長に置ける。palette 合成規則は「末尾優先・外側優先・加算物は両適用」。
- predecessor 方式、下敷き地形を先に生成し差分だけ記述する、は本設計のパイプラインと同型。Content は
  「地形の上の差分」として書く。

### 敵表の語彙

- monster group の**重み予算方式**を翻案する。予算(既定1000)を使い切らない残りが既定エントリ、無スポーンなら
  null、に回る。密度を予算で、群れを pack_size で、時間帯・時期の条件を conditions で表す。
  `Biome.EnemyTable` と UrbanRuin の Content はこの語彙で書く。

### 前線=実行時オーバーレイの裏付け

- CDDA の天候は `(seed, 時刻, 座標)` の純関数オーバーレイで、生成物には一切焼かない。本設計の
  「前線は生成に混ぜず実行時系が重ねる」分離と完全同型で、実績ある構造だと確認できた。

### 採らないもの

- **mutable special の逐次成長そのまま**。生成順依存。citySeed 一括導出に転換して採る。
- **local road の greedy path + MST そのまま**。共有 RNG 依存で、スライディング窓上の MST は窓境界で辺が
  不安定になる。結線は近傍リージョンの決定的なペア規則と端点正規化ルーティングで行う。
- **update_mapgen**。既存タイルへの後付け差分。無状態方針では不要。
- **放浪ホード**。抽象個体群の動的レイヤは永続の動的状態を要する。「前線に押される群れ」の表現として将来
  検討の価値はあるが、本設計の射程外。
- **map extras の適用記録**。CDDA は生成時に1回抽選し適用済みを永続記録するが、純関数の再抽選は同じ結果を
  返すので記録自体が不要になる。
- **z スタック + 階段フラグの位置規約**。CDDA は「同じ x,y に階段を置く」暗黙規約で縦を繋ぐ。ruins は
  `PortalConnection` で行き先を明示結線しており、そちらのほうが曖昧さがない。据え置き。

## 追記(2026-07-25): リアルさ改善 —— ジェネレータ方式

### 背景と測定

プレイでの指摘。チャンク級では街・建物に連続性がなくランダムに見え、タイル級では prop が
ランダム散布で店に見えない。測定で裏取りした。隣接する建物チャンクの同一施設率は 0.231、
完全ランダムの期待値 0.228 とほぼ一致。**施設配置の空間相関はゼロ**、純粋なごま塩だと確定した。

根本原因は2階層で別。

- チャンク級 —— 各チャンクが座標ハッシュから独立に施設を抽選する。記憶を持たない per-cell
  関数は「セル間の相関」を表現できないが、リアルさはまさにその相関に宿る。1チャンク1建物で
  得た生成順非依存の代償が、この構造の貧しさだった。
- タイル級 —— ランダム散布は原理的に「設計されたもの」に見えない。「店に見える」は生成でなく
  authored な性質。

### 方針: インスタンスでなくジェネレータを作る

CDDA はお手本だが、**完成マップを真似ない**。CDDA が何千枚もの mapgen を持てるのはコミュニティの
人手ゆえで、各マップを良く見せている技術自体は少数の再利用可能な規則だ。真似るのはその技術、
すなわち **規則・小部品というジェネレータ**であって、完成品ではない。手描きマップを大量に作る工数は
無いという制約を、ジェネレータ化で回避する。決定性・無限ストリーミング・座標純関数はすべて維持し、
全レバーを `(citySeed, 座標)` の純関数として書く。

質は authoring の量でなく**制約と合成**から来る。制約を1つ足すごとに、出力が「尤もらしいノイズ」から
「設計されたもの」へ近づく。制約は少数の規則で書け、無限の出力に効く。

### レバーA: 構造化都市 cityPlan(チャンク級の相関)

per-chunk 独立をやめ、**都市 seed から街全体を一括導出する純関数** cityPlan を置く。各チャンクは
同じ plan を計算して自分の断片を描くので、決定性と生成順非依存は保たれる。50×50 時代にチャンク内で
やっていた一括導出を、都市リージョンの規模へ持ち上げる。

```go
// cityPlan は都市 seed から街全体の構造を一括導出する純関数。全チャンクが同一に計算する。
type cityPlan struct {
    w, h   consts.Chunk               // 都市の大きさ。チャンク単位
    center consts.Coord[consts.Chunk] // 都心。ゾーニングの基準点
    roads  roadGraph                  // 連結した道路網。全建物が到達可能であることを保証する
    lots   map[consts.Coord[consts.Chunk]]lot
}

type lot struct {
    hasBuilding bool         // 空き地・公園なら false
    facility    facilityKind // zone の重みで抽選する
    zone        zone         // 中心距離で決まる。downtown/commercial/residential/industrial
    frontage    edge         // 道路に面する辺。扉はこの辺に開ける
}

type zone uint8 // 中心からの距離帯。zone ごとに施設抽選の重みを変える
```

- **ゾーニング**: 中心距離で zone を決め、zone が施設の重みを変える。都心は商業・骨董・研究、外周は
  住宅、産業区は倉庫。これで隣接同種率が上がり「地区」が生まれる。
- **道路網**: 都心を通る目抜き通り＋グリッド、または中心からの成長。連結を保証し、建物は道路に
  面する lot にのみ置く。
- **扉は frontage の辺へ**: 現行の北/西固定より構造的に正しい。

### レバーB: 部屋分割の文法(建物→部屋)

建物の矩形を再帰的に壁で分割して部屋にする。BSP/split grammar。規則1つで無限の間取りが出る。
手描きマップは要らない。

```go
// splitBuilding は建物内寸を再帰的に2分割し、壁とドアで仕切った部屋一覧を返す純関数。
// minRoom を下回るまで分割し、各分割線に1つドアを開けて全部屋の連結を保つ。
func splitBuilding(rng *rand.Rand, rect rect, minRoom consts.Tile) []room

type room struct {
    rect rect
    role roomRole // 大きさ・入口からの距離で決まる。shopFloor/storeroom/bedroom/office...
}
```

### レバーC: 役割ベースの家具配置(散布をやめる)

今の最悪点への特効薬。prop をランダムな空きマスへ置くのをやめ、**部屋の役割と壁からの相対位置で
置く規則**にする。家具1種につき規則1つ。「レジは入口に面した壁沿い」という1規則が、ランダム散布と
「店に見える」の差を生む。

```go
// furnishRule は役割ごとの家具配置規則。壁沿い・入口付近・中央など位置の意味を持つ。
type furnishRule struct {
    role     roomRole
    place    []furnitureSpec // prop名 + 配置アンカー(壁沿い/入口沿い/中央/隅)
}

type placeAnchor uint8 // alongWall / nearEntrance / center / corner / rowAisle
```

| 役割 | 配置規則の例 |
|---|---|
| 店舗フロア | レジを入口沿いの壁、棚を通路状に平行、商品ケースを壁沿い |
| 寝室 | ベッドを壁に接して、クローゼットを隅、ランプをベッド脇 |
| 倉庫 | 木箱・樽を壁沿いに積む、中央は搬入通路 |

### レバーC2: 部屋の役割を単一概念にして家具と戦利品を束ねる

レバーB の部屋分割と C の役割家具を統合し、部屋・エリアに**具体的な役割**(トイレ・キッチン・厨房・
倉庫・売場・寝室・バックヤード・診察室…)を持たせる。役割は**家具規則とアイテムグループの両方**を
持つので、役割を1つ決めれば置く家具も湧く戦利品も同時に決まる。CDDA の mapgen が location に
furniture と item_group を結ぶのを翻案する。front/back の2値を、意味を持つ役割の enum へ広げる。

```go
// roomRole は部屋・エリアの意味。家具と戦利品を1つの概念で束ねる真実の源。
type roomRole uint8

// roleSpec は役割ごとの家具規則と戦利品。家具と戦利品を同じ役割から導くので不整合が出ない。
type roleSpec struct {
	furniture []furnishSpec // 何をどこに置くか。既存のアンカー規則を流用
	loot      string        // itemGroup 名。空なら戦利品なし
	lootMax   int           // 部屋に湧く最大数。密度
}

// facilityRooms は施設が持つべき部屋の役割を宣言する。入口の部屋に先頭の役割、残りは
// 大きさ順に続きを割り当てる。小部屋=トイレ、大部屋=居間/売場の size ヒューリスティック。
var facilityRooms map[facilityKind][]roomRole
```

戦利品が場所の意味と一致するのが核心。診療所の薬倉庫で回復アイテム、キッチンで食料、骨董品店で
武器、倉庫で素材。プレイヤーは「薬が欲しいから診療所を探す」という意味的な探索目標を持てる。既存の
`SpawnFieldItem`・`GetItemGroup`・`SelectItemByWeight` と itemGroups(回復アイテム・食料・素材類・各種
武器防具)を流用する。doc 冒頭で別ドキュメント送りにしたアイテム・経済設計への橋にもなる。roleSpec.loot が
「どの場所に何が出るか」を宣言的に持つので、経済はこの土台に乗せられる。

検証は「施設が期待する役割の部屋を持つ」「戦利品が場所と一致する」「家具と戦利品が同じ役割から出る」。

### レバーD: 生成＆選別パイプライン(ライブラリを人手でなく生成で埋める)

小部品を手描きで貯めるのでなく、**ジェネレータで大量に生成し、良いものだけを選別して TOML に
保存する**。PCG の generate-and-test の翻案。完全ランダムは品質を保証できず「厳しい」が、選別を
挟むと採用したものだけが実行時に届くので**品質の下限が保証される**。人間の役割は「描く人」から
「選ぶ人」に変わり、採否は authoring の数十分の1の労力で済む。手描きマップの大量作成という工数の
壁を、生成＋選別で回避する。

5段のパイプライン。

1. **生成** —— レバーB/C の規則(`drawCityBuilding`・`furnishRoom`)が候補を1棟出す。実装済み。
2. **自動選別** —— 構造メトリクス(レジが入口向き・通路がある・全部屋連結・被覆率)で機械的に
   不合格を弾き、人間が見る候補を良いものに絞る。メトリクスは検証と選別の二役を担う。
3. **人間の採否** —— 合格候補を PNG で並べ、採用/却下する。`GenerateSampleBuilding` の単独生成と
   フォグ無し描画(TestMapGenimages 方式)が、この選別 UI になる。
4. **TOML 保存** —— 採用した world 領域を ASCII マップ＋パレットの facility テンプレへ書き出す。
   新規のシリアライザ(world→TOML)が要る。
5. **実行時サンプル** —— `renderCityChunk` は候補を毎回生成せず、施設のテンプレ集から `chunkSeed` で
   1枚を決定的に選んで焼き込む。既存の `assets/levels/facilities/*.toml` と maptemplate の ASCII 機構を
   流用する。純関数のままで、検証済みテンプレなので悪い出力が出ない。生成コストも軽い。

```go
// facilityLibrary は施設種別ごとの採用済みテンプレ集。実行時に chunkSeed で1枚を引く。
type facilityLibrary map[facilityKind][]facilityTemplate

type facilityTemplate struct {
    id   string     // 由来の seed など。再現・差し替えのため
    w, h consts.Tile
    ascii []string  // maptemplate と同じ ASCII レイアウト。パレットは共有
}
```

トレードオフ。テンプレ数が少ないと反復が見える。生成を回して数十枚貯める、実行時にミラーや
パレット差し替えで小変化を足す、で緩和する。選別は人間の時間だが自動選別で軽くなる。読む側の
maptemplate は既存なので、新規は書く側(シリアライザ)と実行時サンプルに絞られる。

### 道具の使い分け: WFC は将来の地形に限定

WFC(波動関数崩壊)は1枚の例から無限の似た出力を作れるが、隣接ルールしか理解せず**意味を持たない**。
「店にはレジがあって入口を向く」という意味的構造は WFC には出せない。だから建物内装には役割ベースの
文法が勝る。WFC は原野の岩・植生・瓦礫のようなテクスチャ的な散らしに向くので、将来そこに限定して
検討する。決定性・チャンク局所性との整合も課題として残る。

### 検証メトリクス

チャンク級は数値で回して退行を止める。タイル級は「規則が生む出力」を検証する。authored な完成品は
回帰テストできないが、authored な規則が生む出力は検証できる。

| メトリクス | 合格条件 | レバー |
|---|---|---|
| ゾーニング相関 | 隣接同種率 ≫ ランダム期待(現状 0.231≈0.228 を大きく超える) | A |
| 道路連結性 | 全建物が道路網から BFS で到達可能 | A |
| 道路接面率 | 建物の 100% がいずれかの辺で道路に面する | A |
| 中心距離×商業度 | 正の相関(都心ほど商業) | A |
| 部屋の連結 | 全部屋が入口からドア経由で到達可能 | B |
| 家具の意味 | 例: レジが入口を向く率が高い | C |
| 孤立壁 | 0 | A/B |
| 選別合格率 | 生成候補のうち自動選別を通る割合。低ければ規則を改善する目安 | D |

### 段階的実装計画

1. **メトリクス基盤を先に**。ゾーニング相関・道路連結・接面率のテストヘルパーを作り、現状値を
   ベースラインで固定する。
2. **レバーC(役割ベース家具)から着手**。最短で「店に見えない」を改善できる。before/after を
   「レジが入口を向く率」などの数値と俯瞰図で見せる。 —— 実装済み。
3. **レバーD 段3の選別 UI**。`GenerateSampleBuilding` で施設ごとに候補を単独生成し、フォグ無しで
   PNG 化する golden を作る。何枚生成すれば足りるかの肌感をここで得る。
4. **レバーB(部屋分割)** を足し、大部屋を廊下と部屋に。全部屋連結をメトリクスで固定。候補の質が上がる。
5. **レバーD 段2・4・5**。自動選別のメトリクス化、採用テンプレの TOML シリアライザ、実行時サンプル。
6. **レバーA(cityPlan)** でゾーニング＋道路網。隣接同種率の上昇と接面 100% を確認。`ChunkPlace` は
   cityPlan 経由に統一し、地図と実物の一致を保つ。

### 採用しなかった方法(この追記の範囲)

- **per-chunk 独立の継続** —— 測定で相関ゼロと確定。却下。
- **純手続きのランダム散布内装(現状)** —— authored に見えない。却下。
- **完全ランダムを実行時にそのまま使う** —— 品質を保証できない。生成＆選別で採用済みだけを
  実行時に届け、品質の下限を担保する。
- **完成マップの大量手描き** —— 工数が無い。生成＆選別でライブラリを埋め、人手は採否に絞る。
- **WFC を内装へ** —— 意味的構造を出せない。地形の散らしに用途を限定して将来検討。
- **全部 authored な都市(CDDA そのまま)** —— コミュニティ規模の人手が前提。技術だけ翻案し、手続き
  配置＋規則ベース＋小部品のハイブリッドにする。

## 追記(2026-07-25): 生成手法の横断サーベイと層別採否

「CDDA のようにリアルな世界を、決定的な純関数 `(seed, 座標)` かつチャンク・ストリーミングのまま生成する手法」を
広く調査した。地形地形学・気候バイオーム・空間相関配置・制約文法合成・ゲーム事例の5ファミリを並列調査し、本 doc の
制約に照らして採否を決めた。結論は現行方針を裏付けつつ数点を鋭くする。

### 貫く原理 —— リアルさは層間の相関、純関数はそれをどう合法に得るか

賞賛される世界の一貫性はノイズ自体でなく、層と層の間の authored な相関から来る。Minecraft のスプライン、RimWorld の
緯度、DF の因果史がそれである。純関数制約が禁じるのはその相関を生む2機構だけだ。1つはグローバル緩和、すなわち DF の
全球侵食。もう1つは状態を持つ順序シミュレーション、すなわち DF/CDDA の履歴と逐次配置。ゆえに ruins はその見た目を
3つの合法手で再現する。

1. **共有の低周波構造をチャンクがサンプルする**。ごま塩の治療。各チャンクが自分の座標だけをハッシュするのをやめ、複数
   チャンクが同じ低周波場を読む。
2. **有限窓で近傍を再計算する**。固定半径のセルを再計算するのは合法。生成済みの隣接チャンクを読むのは禁止。この線引きが
   全手法の合否を決める。
3. **有限構造は全体導出→断片描画**。町・遺跡・建物を1ハッシュ seed の有界インスタンスに閉じ、全体を決定的に導出してから
   現チャンクの断片だけ描く。

WFC・グラフ文法・ASP のような本質的にグローバルな強力手法は、ストリームせず seed 固定の有界インスタンスかオフラインへ
追い出すことで制約と両立する。境界をどこに引くかがすべてである。

### 層別アーキテクチャ

技法は層で仕分ける。層0-2 は厳格な純関数チャンク、層3 は有界インスタンス、層C はランタイム外。

| 層 | 対象 | 純関数性 | 採る技法 |
|---|---|---|---|
| 0 連続場 | 標高・気候・ゾーニング | 点関数で成立 | レイヤ化ノイズ＋domain warp、Minecraft の気候パラメータ→スプライン、RimWorld の score-and-argmax |
| 1 領域 | バイオーム区・地質帯 | 有限窓で成立 | jittered-grid ハッシュ Voronoi、静的 Voronoi プレート |
| 2 地物配置 | 集落・都市・遺跡入口・資源 | 有限窓で成立 | クラスタ点過程 Matérn/Neyman-Scott の反転、Factorio spot-noise、Minecraft random_spread、距離場ダウンタウン勾配、Wang/コーナータイルの辺ハッシュ |
| 3 有界インスタンス | 建物内部・遺跡ダンジョン | seed 固定・入場時一括 | 分割文法 建物→部屋、グラフ文法 鍵/扉/サイクル、有界 WFC 内装の肌理 |
| C オフライン | 検証済みテンプレート | ランタイム外 | ASP/制約ソルバで攻略可能性を保証した型を製造し ID をハッシュ選択 |

河川は流域タイル partition＋drain-to-source で局所化する。各タイルの出口を境界の最低標高点に固定すれば、隣接1タイルの
共有だけで継ぎ目が繋がる。侵食は川に寄生する疑似 stream-power ポストプロセスに留め、集水域は川の次数で代理する。全球
flow-accumulation と本物の反復侵食は捨てる。

### ごま塩問題への効き目ランク

チャンク級の施設配置が空間相関ゼロという測定済みの問題への処方を、効果対工数で順位付けする。4つは1本のパイプラインに
合成でき、各層は独立に純関数なので合成しても純関数のままである。

1. **低周波ゾーニング場**。civ/wealth を共有サンプルし domain warp で有機化。施設抽選をこの場の重みから引く。アーキ変更
   ゼロで相関長は周波数で調整できる。まず着手する。
2. **クラスタ点過程**。親セルが町中心、その子建物リストをチャンクが再計算して自分に落ちる分だけ残す。純関数のまま集めて
   町にする決定版。
3. **リージョン配置＋距離場勾配**。粗リージョンに1つの町か遺跡入口をハッシュ配置し、中心からの距離でダウンタウンから郊外
   への falloff を作る。遺跡入口は overmap special に対応する。
4. **Wang 辺ハッシュ**。タイルでなく共有辺の座標をハッシュして色を決めれば、左右のチャンクが境界で同じ色を独立に算出し、
   道と川の連続が隣接読みなしで保証される。

### 本 doc との接続 —— 裏付けと新規

現行方針の多くを調査が裏付けた。マルチノイズ Biome 層、UrbanRuin の全体導出→断片描画、WFC を有界に限定、レバー B の
分割文法、レバー A の cityPlan 相関。いずれも独立の調査が同じ結論へ至った。

そのうえで数点を鋭くする。

- レバー A の相関を**クラスタ点過程**として厳密化する。親セル→子建物の有限窓再計算が、純関数のまま clump を作る形式的な
  型である。
- Connection 層の道・川に **Wang コーナータイルの辺ハッシュ**を採る。継ぎ目連続を隣接生成なしで保証する。
- 地形基盤を **hash Voronoi × レイヤ化ノイズ**、河川を **drain-to-source**、気候と地形の結合を **Minecraft スプライン**で
  与える。
- 歴史をシミュレーションでなくルックアップで表す。遺跡の荒廃度・支配勢力・災害期を座標の純関数にすれば、DF/URR 級の物語感を
  無シミュ・無状態で得られる。災害後日本の設定に直結する。
- 資源・POI に **Factorio spot-noise** を採る。コーン減衰と abundance 場で、パッチが設計どおりの場所に群れる。

### 採らない手法と理由(この追記の範囲)

- **全球 flow-accumulation・本物の反復侵食(DF)** —— 上流全域の積分と時間反復でグローバル。純関数化不能。川寄生の疑似侵食で
  代替する。
- **Lloyd 緩和・Fortune 法の Voronoi** —— 全点集合が要る。jittered-grid ハッシュ Voronoi で代替する。
- **CDDA の逐次 RNG 配置** —— 都市生成後に状態付き RNG で special を埋めるため順序依存。データスキーマ
  region_settings/overmap_special は採り、アルゴリズムは捨てる。
- **Minecraft concentric_rings** —— 世界原点と大域角度予算が要る。無限帯に不適。
- **ランタイムの真 Poisson-disk** —— セル間の衝突解決で順序依存。jittered-grid 近似で代替する。
- **オーバーワールドタイル場への生 WFC** —— グローバル制約伝播の無限依存連鎖と backtracking の非有界時間が、純関数性・
  再訪同一・save/load を壊す。用途は層3の有界内装に限定し、必ず既定タイルのフォールバックで有界化する。
- **ASP をランタイムに** —— 最悪指数時間で低レイテンシ供給に不適。オフラインの型製造に限定する。
